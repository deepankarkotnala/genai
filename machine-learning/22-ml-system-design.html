ML System Design, Deployment & Monitoring

A dedicated round for ML Engineer roles, and assumed knowledge for every other. The most common real failure is not model quality — it is training/serving skew.

3 · Core intuitions

The most common real failure is training/serving skew, not model quality

Skew arises when the features computed at training time differ from those computed at serving time — different code paths, different default values, different units, different timezone handling, a category vocabulary that has since grown, or an aggregation computed over a different window. The model is not wrong; it is being fed different data than it was trained on.

This is precisely the problem a feature store exists to solve: define each feature once, compute it through one code path, and serve it to both training and inference. Absent a feature store, the discipline is to serialize preprocessing inside the model pipeline and to log serving-time feature values so you can compare their distributions against training.

Distinguish the three kinds of drift, because they need different responses

DriftWhat changedDetectable fromTypical response
Data / covariateP(x) — the input distribution movedInputs alone, immediatelyRetrain on recent data, or reweight
ConceptP(y|x) — the relationship itself movedRequires labelsRetrain, and often new features
Label shiftP(y) — the base rate movedLabels, or outcome ratesRecalibrate and re-tune the threshold

Concept drift is the dangerous one, because it is only directly detectable after your label delay — meanwhile you monitor proxies. Label shift is the cheapest to fix, often needing only a threshold re-tune.

You often cannot measure model performance in real time

If a loan default takes 12 months to materialize, your accuracy metric is 12 months delayed. So the monitoring stack has to be layered: immediate signals (input distributions, prediction distribution, latency, error rates, null rates, unseen-category rates), near-term proxies (business KPIs, human review agreement, override rate), and delayed ground truth (the actual metric, when labels arrive). Saying this unprompted is one of the strongest production signals you can give.

Feedback loops are the subtle production killer

If your fraud model blocks a transaction, you never learn whether it was actually fraud. If your recommender only shows what it predicts you will like, you only collect labels for what it already recommended. The model’s decisions shape the data used to train its successor, which can entrench errors and progressively narrow the distribution the model sees.

Mitigations: hold out a small random control group that bypasses the model, use exploration (epsilon-greedy or bandit approaches) to collect counterfactual data, and explicitly model the selection — “trained on approved loans, scored on all applicants” is a classic instance and a great thing to raise.

Start with a baseline, and be willing to say “no ML”

A well-tuned rule can capture much of the value, is trivially explainable and deployable, and gives you the number your model must beat. In a design round, proposing the non-ML baseline first is a strong signal — it shows you optimize for business outcome rather than for using ML.

5 · Hands-on drill

  1. Write a full design document for one system — fraud detection, churn prediction, or demand forecasting — using the ten-step framework. Two pages. Include the latency budget, the label delay, the monitoring table and the rollback plan.
  2. Build a Pipeline that serializes all preprocessing with the model, save it, load it in a separate process, and score a single row. Confirm identical output — that exercise is the concrete version of the skew answer.
  3. Implement population stability index (PSI) from scratch and compute it between two time slices of a dataset. Establish for yourself what PSI value corresponds to a drift worth alerting on.
  4. Simulate concept drift: train on the first half of a time-ordered dataset, then evaluate on rolling windows of the second half and plot performance decay. That decay curve is what a retraining cadence is derived from.
  5. Wrap a model in a minimal FastAPI service, measure p50/p95 latency under load, then add batching or caching and measure again.
⚠️
Gotchas that fail candidates
  • Not asking clarifying questions before designing.
  • Jumping straight to the model and skipping data, labels and serving.
  • Not mentioning any baseline.
  • Not knowing what training/serving skew is.
  • Conflating data drift and concept drift.
  • Claiming you will monitor accuracy in real time when labels are delayed.
  • No rollback plan. Always mention shadow or canary deployment and a kill switch.
  • Ignoring cost. Cost per prediction is a real constraint, and asking about it is a strong signal.

6 · Interview questions

6 questions
01Design a fraud detection system for a payments company.designfraudfeature storelatency＋
Strong answer

I would clarify first, then follow the framework.

Clarify: transaction volume and peak TPS; the latency budget (real-time authorization implies tens of milliseconds, which drives every later choice); the relative cost of a missed fraud versus a false decline; whether there is a human review team and its capacity; how quickly chargeback labels arrive (typically weeks to months); and regulatory constraints.

Frame: binary classification per transaction producing a risk score, with the score driving a three-way decision — approve, challenge with step-up authentication, or decline — rather than a binary one, since a challenge tier dramatically reduces the cost of uncertainty.

Baseline: the existing rules engine, kept running alongside the model as both a safety net and a benchmark.

Data and features: transaction attributes plus aggregate features over card, merchant, device and IP across multiple time windows. Velocity features — count and amount in the last minute, hour and day — are typically the strongest signal. Critically, all aggregates must be computable within the latency budget, which means precomputing them in a feature store with streaming updates rather than querying at request time. And a leakage audit: exclude anything derived from the chargeback process.

Model: gradient-boosted trees as the primary — fast inference, strong on tabular, native missing-value handling — with unsupervised anomaly scores as additional features to catch novel patterns the labelled fraud does not cover.

Imbalance and evaluation: roughly 0.1% positive, so PR-AUC as the offline metric, scale_pos_weight, a threshold set by expected cost, and calibration since the score feeds a cost-based decision. Strictly time-based splits with an embargo matching the label delay, and metrics segmented by merchant category and geography.

Serving: a low-latency service with model and preprocessing in one artifact, precomputed features from the store, and a hard timeout with a conservative fallback to rules if the model does not respond in budget.

Deployment: shadow mode first to compare against rules on live traffic, then canary, then percentage rollout with a kill switch.

Monitoring: feature drift, score distribution, decline rate, challenge rate, review-queue precision, and delayed chargeback-based metrics — alerting on score-distribution shifts, since those surface before labels do.

Feedback loop: declined transactions never produce labels, so I would keep a small random allow-through control group and use review outcomes as a faster proxy. Retraining: frequent and scheduled, since fraud is adversarial so concept drift is the norm, plus drift-triggered.

30-second version

Clarify latency budget and label delay first. Three-way decision (approve/challenge/decline), velocity features from a feature store, GBDT plus anomaly-score features, PR-AUC with a cost-based threshold, time-based splits with an embargo, shadow then canary rollout, and a random control group to escape the feedback loop.

What’s being tested

Whether you can run a design round end to end. The signals that matter most: asking about latency and label delay upfront, the three-way decision, the feature store, the embargoed time split, and the feedback-loop problem. Most candidates describe a model and stop.

02Your model performed well for three months, then degraded. Diagnose it.debuggingdriftskewtrap＋
Strong answer

I would separate “the world changed” from “our system broke”, because the second is more common and much faster to check.

  1. Is it actually the model? Check pipeline health — schema changes, a new null pattern, an upstream job failing silently, a unit change, a timezone bug, a new category value mapped to a default. A silent data-pipeline change is the single most frequent cause of sudden degradation.
  2. Training/serving skew — did a feature’s computation change on one side only? Compare logged serving-time feature distributions against training.
  3. Covariate drift — P(x) moved: new customer segments, a new marketing channel, seasonality the model never saw. Detectable from inputs alone via PSI or KS tests per feature.
  4. Concept drift — P(y|x) moved: behaviour genuinely changed, a policy change altered incentives, or in an adversarial domain the adversaries adapted. The dangerous case, requiring labels to confirm.
  5. Label shift — the base rate moved, breaking calibration and making the threshold wrong even if the model is fine; often fixable by re-tuning the threshold alone.
  6. Feedback loop — the model’s own decisions have narrowed the data distribution, so its successor was trained on a biased sample.

To distinguish them: a sharp step change points to a pipeline or deployment event — correlate with the change log — while gradual decay points to drift. Fixes in order of cost: re-tune the threshold, retrain on recent data, add features capturing the new regime, or re-frame the problem. And I would close the loop by adding the monitoring that would have caught this earlier.

30-second version

Check the boring causes first — pipeline breakage and training/serving skew — then covariate drift, concept drift, label shift and feedback loops. A sharp step change means a deployment event; gradual decay means drift.

What’s being tested

Systematic production debugging, and specifically whether you check infrastructure before the interesting statistical explanations. The step-change-versus-gradual-decay heuristic is a strong practical detail.

03Data drift vs concept drift. How do you detect each?driftPSImonitoring＋
Strong answer

Data (covariate) drift is a change in the input distribution P(x) while P(y|x) holds — your users changed but the underlying relationship did not. It is detectable immediately from inputs alone: per-feature population stability index, Kolmogorov–Smirnov tests, KL or Jensen–Shannon divergence against a training reference, or a domain classifier trained to distinguish training data from recent production data — if it succeeds, they differ.

Concept drift is a change in P(y|x) — the relationship itself moved, so the model now approximates the wrong function. This is the more dangerous kind and it requires labels to confirm, so it is only directly detectable after your label delay. Meanwhile you monitor proxies: prediction-distribution shift, business KPI movement, human override or appeal rates, and agreement with a review team.

Label shift is worth naming as a third case: P(y) moved, which invalidates calibration and your threshold even when the model is otherwise fine, and is often correctable by threshold re-tuning alone.

Responses differ accordingly — covariate drift may only need retraining on recent data or reweighting; concept drift needs retraining and often new features; label shift may need only recalibration.

30-second version

Covariate drift is P(x) moving, detectable immediately from inputs via PSI or KS tests. Concept drift is P(y|x) moving and needs labels, so only detectable after your label delay — meanwhile watch prediction distribution and business KPIs.

What’s being tested

Precision on a distinction routinely blurred. The label-delay asymmetry in detectability is the key insight.

04What is training/serving skew and how do you prevent it?skewfeature storepipeline＋
Strong answer

It is when the features a model receives at serving time differ from those it was trained on, even though both are nominally “the same feature”. Common causes: training features computed in a notebook or SQL batch job while serving computes them in application code, so two implementations drift apart; different handling of missing values or default sentinels; different units, encodings or timezones; a categorical vocabulary that has grown since training so new values hit an unhandled path; and aggregation windows computed over different periods. The model is fine — it is being fed a different distribution than it learned from.

Prevention: serialize all preprocessing inside the model artifact so there is literally one code path — an sklearn Pipeline or equivalent, saved and loaded as one object. Use a feature store so each feature is defined once and served identically to training and inference. Log serving-time feature values and continuously compare their distributions against the training reference, which detects skew even when you did not anticipate its cause. Add schema validation and range checks at the serving boundary that fail loudly rather than silently defaulting.

And write an integration test that scores a fixed set of rows through the production path and asserts the outputs match the training-time predictions exactly. That test is cheap and catches most instances of this class of bug before release.

30-second version

Serving features differing from training features — two code paths, different defaults, units, timezones or category vocabularies. Prevent with one serialized pipeline, a feature store, logged serving-time distributions, and a fixed-row integration test.

What’s being tested

Whether you have operated a model in production. The “one serialized code path” answer plus the fixed-row integration test are the practitioner signals.

05How often should you retrain?retrainingcadencetrap＋
Strong answer

It depends on how fast the relationship changes and what retraining costs, so I would derive it rather than assert a number. The empirical method: train on a historical window, then evaluate on rolling forward windows and plot performance decay over time. That curve tells you how long a model stays acceptable, and you retrain at a cadence comfortably inside it.

Domain heuristics: adversarial settings like fraud and abuse drift fastest and may need daily or weekly retraining, since adversaries adapt deliberately; consumer behaviour models typically weekly to monthly; physical or biological processes may be stable for years.

Beyond the schedule, add drift-triggered retraining — retrain when PSI on key features or a monitored metric crosses a threshold — so you react to unexpected regime changes rather than only to the calendar.

Two cautions worth raising: retraining is not risk-free, since each new model needs validation, calibration and threshold re-tuning, and a badly-timed automatic retrain can bake in a data-quality incident — so any automatic pipeline needs the same offline gates and canary rollout as a manual release. And more frequent retraining does not fix concept drift caused by a genuinely new regime; if the new pattern is not in your features, more recent data will not help.

30-second version

Derive it from a measured decay curve — train on a window, evaluate on rolling forward windows, retrain inside the acceptable horizon. Add drift-triggered retraining, and treat every retrain as a release needing gates, because it can bake in a data incident.

What’s being tested

Whether you derive the cadence from measured decay rather than guessing, and whether you recognize retraining as a release with its own risk. The “automatic retrain can bake in an incident” point is a strong senior signal.

06How do you safely deploy a new model version?deploymentshadowcanaryA/B test＋
Strong answer

Progressively, with a rollback plan at every stage.

Offline gates first: the new model must beat the incumbent on the primary offline metric using a time-based holdout the incumbent’s tuning never touched, with segment-level checks so an aggregate win does not hide a regression on an important subgroup, plus calibration and fairness checks if applicable.

Shadow mode: run the new model on live traffic in parallel without acting on its outputs, comparing its predictions against the incumbent’s and against production feature distributions. This catches training/serving skew and latency problems with zero user risk — and it is the step people skip.

Canary: route a small slice of real traffic (1–5%) to the new model, monitoring latency, error rates, prediction distribution and any immediately available business signal.

A/B test: scale to a proper randomized split and measure the business metric, not the model metric — offline gains often fail to translate, and the experiment is the only way to know. Run it long enough for the relevant labels to materialize.

Progressive rollout with automated guardrails that halt or revert on threshold breach. Throughout: keep the previous version deployable and warm so rollback is a config change rather than a redeploy; version the model artifact together with the exact preprocessing and feature definitions; and log which version scored each prediction so you can attribute any incident. I would also define the rollback criteria before the rollout starts, since deciding under pressure is how bad calls get made.

30-second version

Offline gates with segment checks, then shadow mode on live traffic without acting, then a 1–5% canary, then a randomized A/B test on the business metric, then progressive rollout with automated guardrails — and rollback criteria defined in advance.

What’s being tested

Deployment discipline. Shadow mode, business-metric A/B testing, and pre-defined rollback criteria are the three things that mark real experience.
