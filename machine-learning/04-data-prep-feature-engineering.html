Data Preparation, EDA & Feature Engineering

This is where real projects are won and lost, and interviewers know it. It is the highest-yield module in this curriculum for applied and take-home rounds.

🎯
Your interview goal

Recognise all five kinds of leakage on sight, defend a split-then-transform order, encode a 40,000-category column without leaking, and know that the pipeline — not the model — is what ships.

1 · From the ground up

🧩
In plain words

Every transformation you apply — scaling, filling missing values, encoding a category, picking features — learns something from data. A mean, a standard deviation, a category list, a ranking. The single rule that governs this entire module is: anything learned may only ever be learned from training data, and then applied unchanged to validation and test. Break that rule and your offline score becomes fiction. Every one of the five faces of leakage is a version of breaking it.

Why a scaler is a model

StandardScaler feels like a utility, but it has parameters — a mean and a standard deviation — that it learns from whatever you hand it. If you hand it the full dataset before splitting, then the mean it learned contains information from your test rows, that information is baked into every training row, and your test score is now measuring a model that has already seen the test set. The effect is usually small enough to be invisible and large enough to be dishonest, which is the worst combination.

The same argument applies to imputing with a median, to target encoding a category, to selecting the top-k features by correlation with the target, and to fitting PCA. All of them learn. All of them must be fitted inside the split.

So what: the fix is not discipline, it is structure. Put every step in a Pipeline and pass the pipeline to cross-validation, so the fitting order is enforced by the code rather than by your memory.
The most common leak in machine learning: fitting before splitting

The gap between 0.94 and 0.87 is not noise — it is the leak. Pass a Pipeline to cross-validation and the fitting order becomes impossible to get wrong, because every fold refits the scaler on that fold's training portion only.

The five faces of leakage, all the same mistake

Every one of these is “the model saw something it will not have at prediction time”.

  • Preprocessing leakage — fitting a scaler, imputer, encoder or feature selector before the split, as above.
  • Temporal leakage — a random split on time-ordered data, so the model trains on the future to predict the past. Also any feature computed with a window that reaches forward.
  • Target leakage — a feature that is a consequence of the target rather than a cause. discount_given when predicting churn, if discounts were offered because the customer was about to churn. This is the one that produces an AUC of 0.99 and a useless model.
  • Group leakage — the same patient, user or device appearing in train and test. The model recognises the entity, not the pattern. Fix with grouped splitting.
  • Duplicate leakage — exact or near-duplicate rows straddling the split. Deduplicate before splitting, not after.
So what: the universal detector is one question asked per feature — would I know this value at the moment I need the prediction? If not, it is a leak regardless of how much it helps.

Missing values: the pattern is the information

Do not start with a filling strategy, start with why it is missing. If a sensor dropped packets at random, filling with a median is harmless. If income is missing because high earners decline to answer, then missingness carries signal and the fill will erase it — so add a binary was_missing flag and keep the information. If a value is missing because it does not exist for that row — no last purchase date for a new customer — then imputation is a category error and you should represent “not applicable” explicitly.

The three standard names are worth using precisely: MCAR (missing completely at random, safe), MAR (explainable by other observed columns, so model-based imputation works), MNAR (the missingness depends on the unobserved value itself, which no imputation can fix — you can only flag it). And gradient-boosted trees learn a default direction for missing values natively, which is often better than any imputation you would invent.

Encoding categories, in order of what to reach for

Low cardinality (under ~15 levels): one-hot. Simple, no assumptions, and drop one level for linear models to avoid the dummy-variable trap. Naturally ordered (small/medium/large): map to integers, since the ordering is real information. High cardinality (10,000 postcodes): one-hot explodes the feature space, so use target encoding — replace the category with the mean target for that category — but compute it out-of-fold or you have leaked the target directly into a feature, which is the single most common way experienced people leak. Add smoothing towards the global mean so a category seen twice does not get a confident extreme value. Unseen categories at prediction time are a certainty, not an edge case: decide the fallback now, usually the global mean or an explicit “unknown” bucket.

Feature engineering is where domain knowledge enters

The model can only combine what you give it. A linear model cannot invent a ratio; a tree can approximate one only crudely with staircase splits. So the value you add is encoding relationships the model cannot discover cheaply: ratios (debt to income beats both columns separately), differences and deltas (change since last month), aggregations (this transaction's amount versus this customer's 30-day average, which is how fraud features are actually built), cyclical time (hour-of-day as sine and cosine, so 23:00 and 00:00 are adjacent rather than maximally distant), and counts of rare events. Each of these is a hypothesis about the domain, which is exactly why interviewers treat feature engineering as a domain-reasoning question.

Analogy — leakage is an exam where the answer key was accidentally printed faintly on the back of the paper. Every student scores 95%, the school celebrates, and then the same students fail the real interview. The score was never measuring what everyone thought it measured — and, importantly, nothing about the students got worse afterwards. That is why leakage is so dangerous: it does not look like a bug, it looks like success.

2 · What to learn

Understanding and cleaning

  1. Systematic EDA: shapes, dtypes, missingness pattern, cardinality, target distribution, bivariate relationships, correlation structure, duplicates.
  2. Target definition and label quality — how the label was generated, by whom, with what delay.
  3. Data lineage: which columns exist at prediction time versus only after the fact.
  4. Missing-data mechanisms: MCAR, MAR, MNAR — and why the mechanism dictates the fix.
  5. Imputation: mean/median/mode, constant sentinel, missing-indicator column, KNN, iterative/MICE, and native handling in XGBoost and LightGBM.
  6. Outliers: detection, and the four responses — keep, cap, transform, remove — each with a stated reason.

Transformations

  1. Scaling: standardization, min-max, robust, max-abs.
  2. Skew handling: log, log1p, Box–Cox, Yeo–Johnson, quantile transform.
  3. Categorical encoding: one-hot, ordinal, target/mean encoding computed out-of-fold, frequency, hashing, CatBoost ordered statistics, embeddings.
  4. High-cardinality categoricals — the practical hard case.
  5. Datetime features: cyclical sin/cos encoding, lags, rolling windows, time-since-event.
  6. Text features: bag-of-words, TF-IDF, n-grams, and modern embedding features.
  7. Interactions, polynomials, binning, ratios and domain-derived features.

Discipline

  1. Data leakage — every form of it. The single most-tested concept in this module.
  2. Train/serve consistency: fitting all transformers inside a pipeline, on training folds only.
  3. sklearn Pipeline + ColumnTransformer as the correct default structure.
  4. Feature selection: filter, wrapper, embedded, and permutation importance.
  5. Multicollinearity: VIF, correlated-pair pruning, or just using a model that does not care.

3 · Leakage — the five faces

Leakage is any information in your features that would not be available, in that form, at prediction time. It is the number-one cause of “97% in the notebook, 61% in production”.

  1. Target leakage — a feature computed from the outcome. total_amount_paid when predicting default; discharge_date when predicting readmission.
  2. Train/test contamination — fitting a scaler, imputer, encoder or selector on the full dataset before splitting, so test statistics inform training.
  3. Temporal leakage — using future information for a past prediction. Random K-fold on time-ordered data does this by construction.
  4. Group leakage — the same entity (patient, user, device) in both train and test, so the model memorizes the entity rather than the pattern. Fix with GroupKFold.
  5. Duplicate leakage — exact or near-duplicate rows split across train and test.
🧭
A sixth worth naming

Leakage through feature selection or hyperparameter tuning performed on all the data. Selecting features using the full dataset is leakage even if the model never sees test rows directly.

4 · The correct split-then-transform order

pipeline_order.txt
1. Define the target and confirm every feature is available at prediction time
2. Remove duplicates and obvious corruption
3. SPLIT  ← everything below happens per-fold, fit on train only
4. Fit imputers            on train  → transform train, val, test
5. Fit encoders            on train  → transform train, val, test
6. Fit scalers             on train  → transform train, val, test
7. Fit feature selectors   on train  → transform train, val, test
8. Fit model               on train
9. Evaluate on val (tune), then ONCE on test (report)

Steps 4–8 belong inside a Pipeline so cross-validation re-fits them per fold automatically. If your CV loop does not re-fit preprocessing every fold, your CV score is optimistic.

5 · Core intuitions

Target encoding is a leakage machine unless done out-of-fold

Replacing a category with the mean target for that category uses the label, so computing it on the full training set lets each row see its own target. Compute it out-of-fold (or with CatBoost’s ordered scheme), smooth toward the global mean for rare categories, and handle unseen categories explicitly.

Missingness is often informative

Before imputing, ask whether the fact of absence carries signal. Income missing on a loan application is not random. The safest general recipe: impute and also add a binary was_missing indicator, so the model can use both the filled value and the absence.

“Handle outliers” is a decision with a reason, not a step

A sensor reading of 10,000 °C is a data error — remove it. A legitimate £2M transaction in a fraud dataset is the most important row in the file — do not touch it. The only wrong answer is a blanket policy applied without asking which kind you have.

The pipeline is the deliverable, not the model

If your preprocessing lives in notebook cells above model.fit, it cannot be reproduced at serving time, and you have a training/serving skew bug waiting to happen. Everything — imputation, encoding, scaling, selection — goes inside a fitted Pipeline serialized with the model.

6 · Hands-on drill

  1. Take any messy public dataset and build one Pipeline with ColumnTransformer handling numeric and categorical branches, imputation with indicators, scaling, and one-hot or target encoding. Cross-validate it.
  2. Then deliberately introduce each of the five leakage types, measure how much the CV score inflates for each, and write the number down.
  3. Having a concrete figure — “leakage cost me 14 AUC points” — makes your interview answers vivid and credible.
⚠️
Gotchas that fail candidates
  • StandardScaler().fit(X) before train_test_split. Instantly disqualifying in a code round.
  • SMOTE applied before splitting — synthetic points interpolated from test neighbours land in train.
  • Target encoding fitted on all training rows without out-of-fold computation.
  • Dropping rows with missing values by default — often discards 40% of the data and biases the sample.
  • One-hot encoding a 50,000-category column, then wondering why the model is slow and overfits.
  • Not noticing a feature that is too good. A single feature with 0.99 AUC is a leakage alarm, not a win.

7 · Interview questions

6 questions
01Your model gets 0.97 AUC in cross-validation and 0.61 in production. Diagnose it.leakagedebuggingproductiontrap＋
Strong answer

I would work a fixed checklist out loud, most likely first. (1) Leakage — is any feature computed from or after the outcome? Is any preprocessing fitted before the split? Sort features by importance and interrogate the top few; a single dominant feature is the classic signature. (2) Split design — random K-fold on temporal data, or the same entity in both folds, both inflate the estimate. (3) Training/serving skew — is production computing features the same way, with the same defaults, units, timezone and category vocabulary? (4) Distribution shift — production traffic may differ, either because the world moved or because the training set was selected non-randomly, such as training only on approved loans then scoring all applicants. (5) Label definition — production may be scored against labels defined differently from training.

To confirm: a strictly time-based holdout, a feature-by-feature train-versus-production distribution comparison, and an ablation dropping suspicious features.

30-second version

Leakage first, then split design, training/serving skew, distribution shift, label definition. Confirm with a time-based holdout evaluated through the exact serving-time feature computation.

What’s being tested

Systematic debugging under uncertainty. One of the most common 2026 applied questions, and the expected answer leads with leakage.

Likely follow-up: “Which single check first?” — a strictly time-based holdout evaluated with the exact serving-time feature computation. It catches leakage, temporal leakage and skew simultaneously.
02Name five distinct kinds of data leakage.leakagefundamentals＋
Strong answer

Target leakage — a feature derived from the outcome. Preprocessing contamination — fitting transformers before splitting. Temporal leakage — future information in a past prediction. Group leakage — the same entity in train and test. Duplicate leakage — identical or near-identical rows across the split. A sixth worth naming is leakage through feature selection or tuning performed on all the data, which is leakage even when the model never sees test rows directly.

30-second version

Target, preprocessing contamination, temporal, group, and duplicate — plus selection or tuning performed on the full dataset.

What’s being tested

Depth on the highest-consequence topic in applied ML. Naming five with a concrete example each is a strong answer.

03You have a 60-category city column and a 40,000-category merchant_id. How do you encode each?encodingcardinalitytrap＋
Strong answer

They need different treatments precisely because of cardinality. For city at 60 categories, one-hot is fine for a linear model; for tree ensembles, native categorical support in LightGBM or CatBoost, or ordinal encoding, avoids 60 sparse columns.

For merchant_id at 40,000, one-hot is out — it explodes dimensionality and each column carries almost no signal. In rough order: out-of-fold target encoding with smoothing toward the global mean so rare merchants are shrunk; frequency or count encoding, which often carries surprising signal; grouping — keep the top-N and bucket the tail into other; hashing for a fixed-width representation under memory constraints; learned embeddings if already using a neural model; or CatBoost, designed for exactly this via ordered target statistics that avoid naive target-encoding leakage.

I would also engineer merchant-level aggregates — mean transaction amount, transaction count, days active — which often beat the ID encoding itself.

30-second version

Scale the method to the cardinality. One-hot or native categorical for 60; out-of-fold target encoding, frequency encoding, tail-grouping or CatBoost for 40,000 — plus merchant-level aggregate features.

What’s being tested

Whether you scale your method to cardinality, and whether you know target encoding’s leakage hazard. Mentioning out-of-fold computation unprompted is the key signal.

Likely follow-up: “What about a merchant unseen at serving time?” — you need an explicit fallback: the global prior for target encoding, an unknown bucket for grouping, and a monitoring alert on the unseen-category rate.
04MCAR, MAR, MNAR. Why does the distinction matter?missing datastatistics＋
Strong answer

MCAR — missingness independent of everything, so dropping rows is unbiased, just wasteful. MAR — missingness depends on observed variables, for example income missing more often for younger applicants, so it can be modelled and multiple imputation from the observed features is principled. MNAR — missingness depends on the unobserved value itself, such as high earners declining to state income, so no imputation from observed data recovers it without bias and the missingness itself must be modelled as a feature.

Practically: MCAR is rare, most real data is MAR or MNAR, and the safe default is impute plus indicator, so the model can exploit the missingness pattern rather than having it smoothed away.

30-second version

MCAR lets you drop rows unbiased; MAR can be imputed from observed features; MNAR cannot be recovered and the missingness must itself become a feature. Default to impute-plus-indicator.

What’s being tested

Statistical literacy plus practical judgment. The impute-plus-indicator recommendation shows you have done this for real.

Likely follow-up: “What does XGBoost do with missing values?” — it learns a default direction per split, trying all missing left then all right and keeping whichever gives more gain. That is data-driven missingness handling, and one reason boosted trees are strong on messy tabular data.
05Walk me through your EDA on a dataset you have never seen.EDAprocessapplied＋
Strong answer

A fixed sequence, narrating why each step exists. Shape and dtypes. Target distribution, including class balance, which decides my metrics. Missingness by column and its pattern — columns missing together often reveal a join problem. Cardinality of every categorical, to plan encoding. Univariate distributions, looking for skew, spikes at defaults like 0 or −999, and impossible values. Bivariate relationships against the target. A correlation matrix for multicollinearity and for suspiciously perfect correlations. Duplicates and near-duplicates. Any temporal or group structure that dictates the split strategy.

Finally, and most importantly, a column-by-column check that each feature is genuinely available at prediction time. I would end by writing down the three biggest data risks — that list is what a senior interviewer is listening for.

30-second version

Shape, target distribution, missingness pattern, cardinality, univariate and bivariate views, correlations, duplicates, temporal or group structure — then an availability-at-prediction-time audit and a written list of the top three data risks.

What’s being tested

Whether you have a repeatable process rather than improvising. The availability check and the risk list are the differentiators.

06Should you always remove outliers?outliersjudgmenttrap＋
Strong answer

No — you should always investigate them, then decide with a reason. Three cases: measurement error, such as a negative age or a 10,000 °C reading, so fix or remove; legitimate extreme values that matter, such as large fraudulent transactions or luxury property prices, so keep, because they may be the signal you are paid to find; and legitimate extremes that destabilize a specific model, so keep the row but reduce its leverage with a log or Yeo–Johnson transform, winsorizing, or a robust loss.

Note that trees are largely insensitive to feature outliers because splits are rank-based, whereas OLS, K-Means and distance-based methods are highly sensitive. So “do I need to handle this outlier?” partly depends on which model you are about to fit.

30-second version

Never blanket-remove — investigate, then decide. Errors go; legitimate extremes usually stay, because in fraud they are the signal. And sensitivity depends on the model: trees barely care, OLS and K-Means do.

What’s being tested

Whether you apply recipes or reasoning. “Drop anything beyond three sigma” is the wrong answer.

2026 additions. Data questions moved from “how would you impute” to “here is a suspicious result, find the leak” — plus the feature-store and training/serving-skew questions that come with owning a model in production.
07A colleague reports 0.99 AUC on churn prediction. You are suspicious. What do you check, in order?2026leakagedebugging＋
Strong answer

I would treat 0.99 on churn as a bug report, not a result — that number is far above what the problem's inherent noise allows, and the prior should be leakage until proven otherwise.

  1. Look at the top features first. One feature carrying almost all the importance is the signature. Then ask of it the only question that matters: would this value exist, with this value, at the moment I need the prediction? Fields like cancellation_reason, account_closed_date, final_invoice_flag or retention_offer_sent are consequences of churn, not predictors of it.
  2. Check the split for time. Churn is inherently temporal. A random split lets the model learn from customers who churned in December to predict churns in June. Re-score with a time-forward split and watch the number fall.
  3. Check for group leakage. One customer with many rows — monthly snapshots — landing on both sides means the model is recognising the customer, not the behaviour. GroupKFold on customer ID.
  4. Check preprocessing order. Was any scaler, imputer, target encoder or feature selector fitted before the split, or outside the CV fold? Target encoding fitted in-fold is the most common expert-level version of this.
  5. Check duplicates. Exact or near-duplicate rows straddling the split, which is common after joins that fan out.
  6. Check the label definition itself. If the label is derived from a snapshot taken after the prediction date, the whole dataset is retrospectively contaminated regardless of the split — and this is the one that takes longest to find.

The fastest decisive test: drop the top feature and refit. If 0.99 collapses to 0.71, you have found it. The second-fastest: build a strict time-forward split with a realistic prediction horizon and see whether the number survives.

30-second version

0.99 on churn is a leak until proven otherwise. Check the top features for anything that only exists after churn happens, check whether the split respects time, check for the same customer on both sides, check that preprocessing was fitted inside the fold, check duplicates, and check whether the label was derived from a post-prediction snapshot. Fastest test: drop the top feature and refit.

What’s being tested

Calibrated suspicion, and an ordered debugging process. Interviewers use this because it is exactly what happens in real teams. Knowing the plausible AUC range for a business problem is itself a signal.

Likely follow-up: “Everything checks out and it is still 0.99.” — then question the problem definition rather than the pipeline. Is the label trivially determined by a business rule you are also feeding in as a feature? Is the population filtered to customers already flagged for churn, making the base rate near 50% and the task easy? Is the target computed from the same table as a feature? A genuinely easy problem is possible, but it should be explainable in one sentence, and you should be able to say what the model knows that the existing rule does not.
08Offline metrics are strong, online metrics are worse, and the model is unchanged. What is your first hypothesis?2026MLOpsskew＋
Strong answer

Training/serving skew — the model is receiving different feature values in production from the ones it was trained on. This causes more launch failures than drift does, and unlike drift it is present from day one.

The concrete mechanisms, which are worth naming because each has a different fix. Two implementations of the same feature — the training version written in SQL over a warehouse table, the serving version rewritten in Python in the request path, and the two disagree on rounding, time zone, null handling or a filter clause. Different defaults — training imputed the median while serving sends a zero, or serving sends a null the encoder maps to an unknown bucket. Point-in-time incorrectness — the training row used a customer attribute as it is today, while serving sees it as it was at request time, which is the subtle one and requires point-in-time-correct joins to fix. Latency-driven degradation — a feature that times out in production and silently falls back to a default for 5% of requests, which offline data never contains. Unseen categories at serving time hitting a fallback path that was never evaluated.

How I would confirm it in an hour: log the actual served feature vectors, then replay those exact vectors through the offline model and compare its predictions with what production emitted. If they differ, it is skew and not the model. Then diff the served feature distributions against the training distributions, feature by feature, and the culprit usually falls out immediately.

The structural prevention is a feature store — compute each feature once with one definition, serve it to both training and inference, and get point-in-time-correct joins for historical rows. Where a feature store is not available, the cheaper version is a shared feature-computation library used by both paths, plus schema and distribution assertions that fail loudly rather than defaulting silently.

30-second version

Training/serving skew — usually two implementations of the same feature, differing defaults, or a point-in-time-incorrect join. I would log the served feature vectors, replay them through the offline model, and diff served against training distributions. Fix structurally with a feature store or one shared feature library, plus assertions that fail loudly instead of silently defaulting.

What’s being tested

Whether you have shipped a model. Candidates who have not ship-debugged reach for drift or retraining; candidates who have reach for the feature vectors. Logging and replaying served features is the answer interviewers are listening for.

Likely follow-up: “How do you get point-in-time correctness right?” — every training row must be built only from data whose timestamp precedes that row's prediction time, which means joins keyed on entity and as-of time rather than on entity alone. In practice: event-sourced feature tables with valid-from and valid-to columns, an as-of join to construct the training set, and a rule that no aggregate window may extend past the label's cut-off — plus an embargo gap if labels take days to mature.
09Walk me through the features you would build for card fraud detection from a raw transaction log.2026feature engineeringdomain＋
Strong answer

The key insight, and I would lead with it: a single transaction is almost never diagnostic — fraud lives in the deviation from that cardholder's own normal. ₹40,000 is unremarkable for one customer and a screaming anomaly for another. So the raw columns matter far less than features that compare this transaction to a history.

The families I would build:

  • Relative amount — this amount divided by the cardholder's 30-day mean, and its z-score against their own history. Turns an absolute number into a personalised one.
  • Velocity — count and total value of transactions in the last 1 minute, 1 hour, 24 hours and 7 days. Card testing shows up here before it shows up anywhere else.
  • Novelty flags — first time at this merchant, this merchant category, this country, this device; time since the last transaction at this merchant. Fraud is disproportionately first-time-anything.
  • Geo-velocity — implied travel speed between consecutive transactions. Two purchases 2,000 km apart 10 minutes apart is a physically impossible feature and one of the strongest signals available.
  • Cyclical time — hour of day and day of week encoded as sine and cosine so 23:00 sits next to 00:00, plus deviation from that cardholder's usual hours rather than from a global usual.
  • Entity-level aggregates — the merchant's own recent fraud rate and chargeback rate, computed strictly out-of-fold and with a lag, because this is the highest-yield family and also the easiest to leak with.

Then the discipline that makes it real, which is most of the score. Every window must be computed as of the transaction's own timestamp and must never reach forward — that is the whole ballgame, and a naive groupby.mean() over the full table leaks the future into every row. Any merchant-level or cardholder-level target statistic must be out-of-fold and lagged. Validation must be time-forward with an embargo, because labels arrive days or weeks later via chargebacks, so the model must be evaluated on the label maturity it will actually have. And every feature must be computable within the authorisation latency budget, which rules out anything requiring a slow join — the usual answer being streaming aggregates maintained in a low-latency store rather than computed at request time.

30-second version

Fraud is deviation from that cardholder's own normal, so the features are relative: amount versus their 30-day average, velocity counts over 1 minute to 7 days, first-time-merchant and first-time-country flags, implied geo travel speed, cyclical time versus their usual hours, and lagged out-of-fold merchant fraud rates. Every window computed as of the transaction's timestamp, never reaching forward, validated time-forward with an embargo for chargeback lag, and computable inside the authorisation latency budget.

What’s being tested

Domain reasoning plus leakage discipline in the same answer. Feature engineering is where interviewers look for evidence you have worked on a real problem, and the “as of this timestamp, never reaching forward” constraint is the line that separates practitioners from tutorial readers.

Likely follow-up: “Fraud is 0.1% of transactions. How does that change the plan?” — it changes evaluation and thresholding, not the features. PR-AUC and precision@k rather than accuracy or ROC-AUC; the threshold from the cost of a blocked legitimate transaction versus a missed fraud, which are wildly asymmetric and include a customer-experience cost that is not in the loss function. Any resampling stays inside the fold, and if I resample I must recalibrate afterwards. I would also expect concept drift to be fast here, because adversaries adapt — so a short retraining cadence and monitoring on the fraud pattern mix, not just the rate.
