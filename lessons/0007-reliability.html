Lesson 7 · Making it reliable

Reliability and safe termination

⏱ ~3.5 h total 25 min read · 90 min build · 55 min break/debug · 30 min interview Prereq · Lesson 6 Next · Lesson 8
🎯
By the end of this lesson you will be able to
  • Answer "your agent loops forever in production — debug it" from experience, not theory.
  • Distinguish identical repeats from oscillation, and detect both.
  • Say what a timeout actually does — and what it does not do.
  • Say which failures are worth retrying and which are not, and why.
  • Handle the failure nobody plans for: the call that partly worked.
  • Guarantee that every run ends in a named outcome a human can act on.
💡
This is the lesson that gets you hired

Lessons 1–6 built something that works. Everything from here is about what happens when it doesn't. Interviewers spend most of their time in this territory, because a demo proves nothing and a failure mode proves everything.

1 · Five controls, five questions

ControlAnswers
Repeat detection"have I already done exactly this?"
Oscillation detection"am I going round in a circle?"
Timeout"how long am I prepared to wait?"
Retry budget"how many attempts is this worth, and how spaced?"
Safe termination"if I give up, what does the caller get?"

The last one is the one people skip and the one that matters most. An agent that cannot finish must still return something a human can act on. Silence and a stack trace are both worse than "I could not establish the facts; escalating, and here is what I did establish."

2 · Giving up needs to be an action

The new tool is escalate, and the reason it exists is structural:

🔑
An agent with no escalation path has only two options

Guess, or loop. Both are worse than handing over. "It cannot cope with this" is only a failure if there is nowhere for it to go.

And note the one design rule on it: escalation must never fail. It is the fallback for every other failure, and a fallible fallback is not a fallback. So escalate() does no lookups, touches no external system, and validates nothing beyond its own arguments.

3 · The four failures that actually happen

faults.py injects them, so you can watch rather than imagine:

FaultWhat it modelsControl it tests
slowthe tool answers, eventuallytimeout
flakyfails N times, then worksretry budget + backoff
unavailablealways failsfallback, safe termination
partialsucceeds, returns incomplete datanothing, until you build it

Fault injection lives outside the tools on purpose: the tools stay honest, and the controller is what gets exercised.

4 · What a timeout is, precisely

future = _POOL.submit(_call, tool, args)
result = future.result(timeout=timeout_s)
⚠️
A timeout stops you waiting. It does not stop the work.

The thread runs on. That is not a flaw in this code — it is what a timeout is on any platform without cancellation. Two consequences:

1 · A hung tool leaks a thread. Hence the bounded pool. A real system needs cancellable I/O, not just a wait limit.

2 · For anything with side effects, a timeout means you do not know whether it happened. That is Lesson 8's whole problem, and it is why our timeout message says so explicitly: "Whether it took effect is unknown."

Saying this out loud in an interview is worth real credit, because most candidates describe a timeout as though it cancels something.

And note what we do not do: a timeout is not retried. The slow thing is still slow, and now two of them are running. Retrying a timeout is how a struggling dependency becomes a dead one.

5 · Retry only what can succeed

except (ConnectionError, OSError) as exc:      # transient -> retry with backoff
    delay = BACKOFF_BASE_S * (2 ** (attempt - 1))
...
except ToolError as exc:                       # bad argument -> return immediately
    return {"error": "invalid_call", "message": str(exc)}, notes

A malformed call cannot succeed on attempt two. Retrying it three times burns the budget and produces the identical error, slower. Classify the failure before deciding the response — the same 4xx-versus-5xx instinct you already have.

Note also that the notes record the difference: "lookup_order succeeded on attempt 3". A run that works but retries constantly looks identical to a healthy one unless you record it, and "it works, with 40% retries" is a real incident waiting to become an outage.

6 · Repeats and oscillation are different bugs

counts[sig] = counts.get(sig, 0) + 1
if counts[sig] > REPEAT_LIMIT:          # same tool, same arguments, third time
    return finish(BLOCKED, ...)

return (window[-1] == window[-3] and window[-2] == window[-4]
        and window[-1] != window[-2])   # A,B,A,B

Repeat detection catches "same call again". Oscillation catches the subtler version: two calls alternating forever, each one novel to a check that only compares against the immediately previous call. An agent with contradictory instructions produces this, and it will burn a 40-step budget looking busy.

7 · Break it — five worlds, one goal

cd teach-agents/project
python steps/l08_safe_refund.py --faults

  healthy
    outcome   : resolved  (needs_human=False)
    tools     : read_ticket -> lookup_order -> search_kb -> draft_reply

  lookup_order flaky (2 failures)
    outcome   : resolved  (needs_human=False)
    control   : lookup_order attempt 1 failed (...); retry in 0.05s
    control   : lookup_order attempt 2 failed (...); retry in 0.10s
    control   : lookup_order succeeded on attempt 3

  search_kb unavailable
    outcome   : escalated  (needs_human=True)
    control   : search_kb failed all 3 attempts
    answer    : Escalated TCK-1001 to a human (high urgency): Could not complete search_kb…

  lookup_order slow, 1s limit
    outcome   : escalated  (needs_human=True)
    control   : lookup_order timed out after 1.0s; not retried

  lookup_order partial data
    outcome   : escalated  (needs_human=True)
    control   : lookup_order returned incomplete data

  step budget of 2
    outcome   : exhausted  (needs_human=True)
    answer    : Stopping without a resolution: the step budget ran out.
                Established so far: read_ticket, lookup_order.

Every row ends in a named outcome — resolved, escalated, exhausted, blocked — and needs_human tells the caller whether to queue it. None ends in silence or a traceback.

Note the last one carries "Established so far: read_ticket, lookup_order". A human picking this up should not have to redo work the agent already did. A bare "failed" throws all of it away.

8 · The failure nobody plans for

🐛
A real bug from building this lesson

With partial injection, lookup_order returned a well-shaped result missing refund_eligible. Nothing raised. The controller noted "returned incomplete data" — and the run still finished resolved, with this in the answer:

Order ORD-5581 totals 120.0 USD and refund_eligible=None.

A customer-facing summary asserting eligibility it never actually read, reported as a success.

The fix needed two layers, and that is the lesson: the controller detects the incomplete result; the agent's own rules refuse to proceed on it. Detection without a policy that acts on it is decoration.

incomplete = [name for name, res in observed.items() if res.get("_partial")]
if incomplete:
    return ToolCall("escalate", {..., "reason":
        f"{', '.join(incomplete)} returned incomplete data, so "
        "eligibility could not be confirmed."})

Partial success is the most dangerous failure mode in any distributed system, and agents make it worse: a missing field becomes None, None gets formatted into prose, and prose reads as fact.

9 · The drill: "your agent loops forever in production"

You will be asked this. Do it now, with real output.

1 · Reproduce the identical repeat. Write a backend that always returns the same tool call, and run it with max_steps=20:

outcome  : blocked
control  : blocked repeat: read_ticket called 3x identically

Notice it stopped at 3 steps, not 20. A control that only fires when the budget runs out is a limit in name only — by then you have paid for the whole run.

2 · Reproduce the oscillation. Alternate two ticket ids. Repeat detection never fires; oscillation detection does.

3 · Now answer the question out loud, in this order: get the trace; look at the sequence, not the final output; classify it as identical-repeat, oscillation, drift or missing-termination; then say what fires and where. Then the part that scores: "40 steps means the budget was too generous. A 4-step task should not have a 40-step budget."

10 · The production concern

Reliability is mostly refusing to continue in states you cannot reason about. There is very little cleverness in control.py — no automatic recovery, no self-healing. That is deliberate. An agent that works around a broken dependency is an agent producing answers on unknown foundations.

Four things to add in a real system, which we do not have yet: a circuit breaker so a dead dependency is not retried by every run; idempotency so a retry is safe (Lesson 8); persistence so a crash at step 3 does not lose the work (Lesson 14); and alerting on outcome ratios — a rising escalation rate is the earliest signal you have.

🧰
You already know this

Retry budgets with exponential backoff, classify-then-respond, timeouts that do not cancel, partial failure, bulkheads, graceful degradation with a named fallback. This is resilience engineering, pointed at a probabilistic caller. Your existing instincts are the valuable part — say so in an interview, because "I treated the model as an unreliable remote dependency" is exactly the right framing.

11 · Interview practice

Two-minute answer — "Your agent loops forever in production. Diagnose and fix it."

🎤

"First, is it bounded at all? If termination depends on the model choosing to stop, it isn't — so a step limit is the actual bound and I'd check that exists before anything else.

Then I'd get the trace and look at the sequence rather than the output. Four patterns. Identical repeats: same tool, same arguments — usually a failing tool whose error the agent can't act on, or state that conflates 'not tried' with 'tried and failed'. Oscillation: A, B, A, B — contradictory instructions, and it's invisible to a check that only compares against the previous call. Drift: plausible but unrelated calls, which is context dilution, so compaction and a tighter budget. Missing termination: it has the answer and keeps going, because nothing told it what done looks like.

The fixes are a repeat counter keyed on tool-plus-arguments, a cycle check over a small window, and tracking attempted calls separately from successful ones. Both controls have to fire well before the step budget — a limit that only trips after you've paid for the run isn't protecting you.

And the honest answer underneath: 40 steps means the budget was set too high, or the tools are too fine-grained. Fewer, coarser tools and a realistic budget prevent more incidents than better loop detection does."

Q System design · Design reliability for an agent calling five internal services with different SLAs. ›

Per-tool policy, not one global setting — a 50ms cache lookup and a 3s report generator cannot share a timeout. For each: a timeout from that service's p99, a retry budget (and only for transient classes), and a fallback that is either degraded data or escalation.

Then the system-level parts. Circuit breaker per dependency, so a dead service is not retried by every concurrent run — otherwise your retries become its outage. A total budget for the run in wall-clock and cost, because five well-behaved timeouts still add up past a user's patience. Bulkheads so one slow tool cannot exhaust the pool every tool shares. Idempotency on anything with side effects.

Then observability: outcome ratios per tool, retry rates, and alerting on the escalation rate rather than on errors, since a healthy-looking agent that escalates 60% of tickets is broken in a way no error count shows.

Q Debugging · A tool call times out. Did it happen? ›

You don't know — and that is the correct answer. A timeout means you stopped waiting, not that the work stopped. For a read that's merely wasteful. For anything with side effects it is the hardest case in the lesson.

So you design for it in advance rather than resolving it after: an idempotency key derived from the request means a follow-up call is safe whichever way the first one landed. Absent that, your only options are to risk a double effect or to strand the request — and choosing between them at incident time, with a customer waiting, is how mistakes get made.

Also: don't retry the timeout itself. Two slow calls are worse than one. Check state, then act.

Q Coding · Add loop detection to an agent. ›

Compute a stable signature per call — tool name plus arguments serialised with sorted keys, so argument ordering doesn't create false novelty. Count signatures; block above a small threshold. Separately keep a window of recent signatures and check for an A,B,A,B cycle. On either, terminate with a named outcome and a reason, not an exception.

Details that signal experience: sorted-key serialisation; a threshold above 1, because a legitimate retry exists; blocking well before the step budget; and recording which control fired, so the trace explains itself.

Q Senior follow-up · How do you decide the retry budget and backoff? ›

From the dependency's failure profile, not a default. Transient network blips justify two or three attempts with exponential backoff and jitter — jitter matters, because synchronised retries from many concurrent runs are a thundering herd. Anything non-transient gets zero retries.

Then the constraint people miss: the retry budget interacts with the user's latency budget. Three attempts with backoff on a 2s timeout is potentially 6s of one step in a run that has a total budget. Retries have to be spent from the same pot as everything else, otherwise a resilient agent is an unusably slow one.

And measure the retry rate. A steady 30% success-after-retry is a broken dependency masquerading as a healthy agent.

Q Senior follow-up · Should the agent recover automatically from a failing tool? ›

Rarely, and never silently. Substituting a different tool, or proceeding on partial data, means producing an answer on foundations you did not verify — and the answer will not carry a warning label by the time a customer reads it.

The tiered approach: retry transient failures; degrade explicitly where degradation is meaningful and say so in the output; otherwise escalate. What I would not do is let the agent invent a workaround, because that converts a visible failure into an invisible one. Our partial-data bug is the small version — refund_eligible=None formatted into a sentence that read as fact.

12 · Recap

  • Five controls: repeat, oscillation, timeout, retry budget, safe termination.
  • Escalation is an action, and it must never fail — everything else falls back to it.
  • A timeout stops you waiting, not the work. For side effects, that means "unknown".
  • Retry transient failures; never retry a timeout or a malformed argument.
  • Repeats and oscillation are different bugs needing different detectors.
  • Controls must fire well before the step budget, or they protect nothing.
  • Partial success is the worst failure: nothing raises, and a missing field becomes prose. It took two layers to fix — detect, then refuse.
  • Every run ends in a named outcome, and reports what it did establish.
