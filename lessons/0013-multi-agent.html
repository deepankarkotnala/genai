Lesson 13 · Protocols and scale

Multi-agent, A2A, and the measurement

⏱ ~4 h total · plan a weekend block 30 min read · 90 min build (60–90 hands-on A2A) · 55 min debug · 30 min interview Prereq · Lesson 12 Next · Lesson 14
🎯
By the end of this lesson you will be able to
  • Distinguish an agent from a tool, and say why the confusion is expensive.
  • Build a supervisor with specialists — and measure it against the single agent.
  • Answer "when does multi-agent hurt?" with numbers from your own run.
  • Explain A2A: Agent Cards, tasks, artifacts, lifecycle — and how it differs from MCP.
  • Explain why a peer agent can recommend but never authorise.
  • Explain shared versus isolated context, and why a handoff is a brief.
💡
This lesson is deliberately sceptical

Multi-agent is the pattern people reach for first and justify least. We build it properly, measure it honestly, and find it worse on this workload. That negative result is the most useful thing here — and the ability to produce it is what separates a candidate who has used the pattern from one who has read about it.

1 · An agent is not a tool

ToolAgent
Isa functiona loop with its own model calls
Costsa dictionary lookupone or more model calls
Failsdeterministicallyin all the ways Lesson 7 covered
Hasargumentsits own context and budget
🐛
The most common multi-agent mistake

Making something an agent that could have been a tool. A "summariser agent" that always does one thing with no decisions is a function with a latency problem — and now it also has a context window, a step budget and its own failure modes.

The test: does it make a decision that depends on what it discovers? If not, it is a tool.

2 · When a supervisor genuinely earns its place

Three good reasons, and one bad one people use instead.

Different tool sets. Combining them would hurt selection accuracy — Lesson 3: more tools, worse choices.

Different permissions. Lesson 9's least privilege. Only the refund specialist should reach issue_refund.

Different owners and release cycles. Two teams shipping independently need a boundary, and an agent boundary is a reasonable one.

The bad reason: "the task has several parts." That is a routing problem, and routing costs one model call (Lesson 4), not a fleet.

3 · Build the supervisor

agent/supervisor.py. Each specialist sees a narrowed tool set:

SPECIALISTS = {
    "billing":   ["read_ticket", "lookup_order", "search_kb", "draft_reply", "escalate"],
    "refund":    ["read_ticket", "lookup_order", "search_kb", "issue_refund", "escalate"],
    "technical": ["read_ticket", "search_kb", "draft_reply", "escalate"],
    "general":   ["read_ticket", "search_kb", "draft_reply", "escalate"],
}

Only refund holds issue_refund, and a test asserts exactly that. Note that a narrower agent is not a more powerful one: the refund specialist still gets dry_run=True by default and still cannot mint an approval token.

The handoff is a brief, not a transcript

brief = (
    f"{goal}\n"
    f"[handoff from supervisor] category={...}, priority={...}, tier={...}. "
    f"You are the {route} specialist."
)
🔑
This is the whole art of multi-agent

A specialist handed the supervisor's entire context inherits its context-window problem (Lesson 6) and its confusion — and you have paid two model calls for one agent's judgement. Isolated context is the benefit; sharing it away is the classic mistake.

There is a test asserting the brief stays under 400 characters, because this is the thing that silently grows.

📉
Same outcomes. Strictly more expensive.

On this workload the supervisor is worse on every measure and better on none. Multi-agent is a cost you justify, not a default.

Note the comparison counts the supervisor's own model call. It would have been easy to omit it and make the split look free — count honestly or the measurement lies in the pattern's favour, and there is a test asserting the supervisor's read appears in the tool list.

It would start to pay when the specialists need genuinely different tool sets or permissions at a scale where selection accuracy degrades, or when they ship on different schedules. None of that is true of four routes over six tools.

5 · A2A — talking to a peer

MCP connects an agent to tools. A2A connects an agent to a peer — another agent, possibly owned by another team or company, which you cannot call as a function because you do not run it.

MCPA2A
Boundarytoolpeer
Unita call with a return valuea task with a lifecycle
Discoverytools/listAgent Card
Outputcontent blocksartifacts, plus messages
Durationa requestminutes, with clarification

Why a peer needs a different protocol from a tool: a tool call is request-and-response. A peer may take minutes, need clarification halfway, stream partial results, and produce several durable outputs. So A2A is built around a task with a state machine rather than a function with a return value.

Four concepts

AGENT CARD   published metadata: who I am, what I can do, how to authenticate
MESSAGE      a turn of conversation between two agents
TASK         submitted -> working -> input_required -> completed | failed | canceled
ARTIFACT     a durable output (a recommendation, a report, a draft)

Artifacts are separate from messages on purpose. The conversation is how two agents coordinated; the artifact is the thing you keep, review and audit. Conflating them buries a recommendation in chat history instead of making it a record.

6 · Run the two-agent demonstration

python steps/l13_protocols.py --a2a

  1 · Agent Card
      name       refund-specialist v1.0.0
      skill      assess_refund: Checks an order against refund policy…
      accepts    ['order_id', 'amount', 'reason']
      WILL NOT   ['execute a payment', 'issue or obtain an approval token',
                  'override policy']

  2 · delegate, without stating the amount
      discovered refund-specialist v1.0.0, skill assess_refund
      task task_c5d3214d3d -> submitted -> working -> input_required
      peer asked for input; supplying the order total
      task task_00048be6f7 -> submitted -> working -> completed

  4 · artifact
      refund-recommendation (recommendation)
        policy_allows              True
        tool_status                requires_approval
        refunded                   False
        idempotency_key            idem_da82f933944f95f0
        next_step                  A human must approve this amount…
🔑
Two details to notice

The Agent Card publishes willNot. The honest half of a contract is the refusal — a caller reading this card cannot plan a workflow in which the specialist pays anybody.

input_required is what makes this more than a function call. The peer stopped, asked for the amount rather than assuming the order total, and the task resumed. A tool call has nowhere to put that.

7 · Delegation moves work, never authority

python steps/l13_protocols.py --boundary
🛡️
The single most important sentence in this lesson

An agent that could grant itself permission by asking another agent has no permissions at all.

Three reasons the specialist cannot pay, in order of strength:

1 it calls issue_refund in dry-run mode, which is structurally incapable of moving money;
2 it holds no approval token and has no way to obtain one;
3 its card publishes that it will not — a contract, and the weakest of the three.

Note the ordering. The card is documentation; the dry run is architecture. If you ever find yourself relying on reason 3, you have built the security model backwards.

And the triage agent verifies rather than trusts:

for artifact in task.artifacts:
    if artifact.content.get("refunded"):
        notes.append("!! peer reported a completed payment -- boundary violated")

If that line ever fires, a peer has exceeded its published limits and the run is an incident, not a result. Trust the boundary, verify the claim — a peer's word is not evidence. There are two tests: one that no execution appears in the audit log after delegation, and one that a completed task cannot be resurrected, so a late duplicate response cannot reopen finished work.

8 · Break it

1 · Make the specialist pay. Add "dry_run": False to its issue_refund call. It still cannot: approval_required, because it has no token. Now try to give it one — you will find grant_approval is not reachable from the tool registry, by design (Lesson 8). Feel how many layers you have to defeat.

2 · Delete the willNot field. Nothing breaks; the boundary still holds architecturally. Then ask what a caller has lost: the ability to know, before delegating, that this peer will never pay. That is what a card is for.

3 · Share the whole context. Replace the brief with the supervisor's full transcript. Re-run --compare. Tokens rise, the outcome does not improve, and you have paid for the specialist to read things it does not need. This is the mistake the brief exists to prevent.

4 · Give every specialist every tool. Set all four routes to the full registry. Now the split has no benefit at all — same tools, same behaviour, one extra model call — which is exactly the "multi-agent for its own sake" configuration you will meet in real codebases.

5 · Resurrect a completed task. Call task.transition("working") after completion. It raises. Then remove the guard and consider a late duplicate response arriving after a task finished — the same class of bug idempotency prevents for payments.

9 · The production concern

Failure propagation. If a specialist escalates, does the supervisor escalate? Ours returns the specialist's outcome directly, which is the honest default — a supervisor that "handles" a specialist's failure by trying something else is producing answers on foundations it did not verify (Lesson 7).

Cost multiplies, and so does latency. Each agent has its own step budget. Two agents at six steps is a twelve-step worst case, and the user waits for all of it. Budget the system, not each agent.

Attribution. When a multi-agent run misbehaves you need to know which agent did it, which means the correlation id from Lesson 11 propagates across the handoff. Without it, debugging is guesswork.

Loops between agents. Lesson 7's repeat detection is per-run. Two agents that hand back and forth can loop between runs, which no single-run control catches. Bound the handoff depth explicitly.

🧰
You already know this

Service decomposition, and every argument you have had about microservices applies verbatim: independent deployment and clear ownership on one side, network hops, distributed debugging and cascading failure on the other. The right first question is the same one — "could this be a function?"

Two things are worse here than in microservices. Each hop costs a model call, not just a network round trip. And the components are non-deterministic, so the same input can take different paths through your topology — which makes distributed debugging harder than anything you have done.

10 · Interview practice

Two-minute answer — "When does multi-agent hurt?"

🎤

"Almost always, unless you can name the specific thing it buys. I built a supervisor with four specialists over our triage agent and measured it: same outcomes, one extra model call and about 50 extra tokens per ticket. Strictly worse on every measure and better on none — and I counted the supervisor's own call, because omitting that is how these comparisons end up flattering the pattern.

It hurts in four specific ways. Cost and latency multiply, since each agent has its own step budget and each hop is a model call, not just a network hop. Debugging gets harder, because non-deterministic components mean the same input can take different paths through the topology. Failures propagate unless you decide deliberately what a supervisor does when a specialist escalates. And loops can form between agents, which per-run loop detection doesn't catch.

It earns its place when specialists need genuinely different tool sets — enough tools that selection accuracy degrades — or different permissions, or when they're owned by different teams shipping independently. Those are real reasons. 'The task has several parts' isn't; that's routing, and routing costs one model call.

The mistake I'd call out is making something an agent that could have been a tool. A summariser agent that always does one thing is a function with a latency problem, and now it has a context window and its own failure modes too."

Q System design · Design a multi-agent system for a support organisation with billing, technical and returns teams. ›

I'd start by pushing back on the premise: the org chart is not an argument for an agent topology. Three human teams can be served by one agent with a router, and I'd want a reason not to do that first.

The reasons that would convince me: the teams have genuinely different tool sets and permissions — returns needs the refund path, technical needs incident tooling, and giving one agent all of it would both degrade selection accuracy and violate least privilege. And the teams own their own runbooks and want to ship changes independently.

Given that: a thin router (one cheap classification call), three specialists with narrowed tool sets and separate credentials, briefs rather than shared transcripts, and escalation to the human team that owns the queue. A shared read-only MCP server for tickets and orders, since all three need it and none should own it.

Then the operational parts that decide whether it works: one correlation id propagated across handoffs so attribution is possible; a bounded handoff depth so agents cannot ping-pong; a system-level cost and latency budget rather than per-agent ones; and per-specialist golden sets, because a regression in the returns specialist is invisible to billing's metrics.

And I'd measure it against the single-agent baseline before committing, expecting the split to cost more — then decide whether the permission separation is worth that.

Q Debugging · A multi-agent run gave a wrong answer. Which agent was responsible? ›

If you cannot answer that, the finding is your observability, not the agent. You need one correlation id spanning the whole run with each span tagged by agent name and version — Lesson 11's trace, propagated across the handoff.

With that, look at the handoff boundary first, because it is where most multi-agent bugs live: did the supervisor route correctly, and did the brief contain what the specialist needed? A specialist given an incomplete brief produces a confidently wrong answer, and the fault is upstream.

Then the specialist's own trajectory, exactly as in Lesson 7 — wrong tool, bad arguments, missing facts. Then whether the supervisor mangled the specialist's output on the way back, which is easy to miss because the specialist looks correct in isolation.

The systemic fix is per-agent evaluation rather than only end-to-end: with end-to-end tests alone you know the system failed and not which part.

Q Coding · Implement a supervisor handoff. ›

Classify to a route, look up that route's tool allowlist, build a short brief containing the goal plus the few facts the specialist needs, run the specialist with the narrowed tool set, and return its outcome along with the route taken.

Say while writing: "the handoff is a brief, not a transcript, so the specialist doesn't inherit the supervisor's context window"; "the tool set is narrowed per specialist, which is both a selection-accuracy and a least-privilege decision"; and "I count the supervisor's own model call when reporting cost".

Q Senior follow-up · How do you stop a peer agent exceeding its remit? ›

You do not rely on its cooperation. Three layers, weakest last: give it no capability to do the thing — our specialist calls the refund tool in dry-run mode and holds no approval token, so the payment path is structurally closed; enforce authorisation on your side of the boundary, since a peer's claim about who it is or what it may do is untrusted input; and publish and check the contract in the Agent Card, which is documentation rather than enforcement.

Then verify rather than trust its report: our triage agent checks the artifact's refunded flag and treats a claimed payment as an incident. And confirm independently — the audit log is the record, not the peer's message.

If the peer is another company's, add the dependency posture from Lesson 12: pinned version, reviewed card, sandboxed, and no path from its output to an irreversible action without a human.

Q Senior follow-up · Your team wants to adopt a multi-agent framework. What do you ask? ›

What measurement made multi-agent the answer — and if there isn't one, that is the first thing to produce, because I have a baseline showing the split costing more for identical outcomes.

Then, assuming it is justified: how are tool sets and permissions separated per agent; what does the handoff carry, a brief or a transcript; what bounds the handoff depth; how is a run attributed to an agent when it misbehaves; and what happens when a specialist escalates.

On the framework specifically: what does it do that twenty lines of routing plus a narrowed tool list does not? I built all of this without a framework, so I'd want the framework to be earning its place on durable state, resumability or a graph I actually need — Lesson 14's comparison — rather than on giving names to control flow.

11 · Recap

  • An agent is a loop with model calls; a tool is a function. Making a tool into an agent is the common, expensive mistake.
  • Supervisors earn their place on different tool sets, different permissions, or different owners — not on "several parts".
  • Measured: +1 model call, +51 tokens, identical outcomes. Count the supervisor's own call or the comparison flatters the pattern.
  • The handoff is a brief. Sharing the full transcript gives away the only benefit.
  • MCP is the tool boundary; A2A is the peer boundary. Task with a lifecycle, not a call with a return value.
  • Agent Cards publish willNot. The honest half of a contract is the refusal.
  • input_required is what a function call cannot express.
  • Delegation moves work, never authority. Capability first, authorisation second, contract last.
  • Verify the peer's claim. A completed task cannot be resurrected.
