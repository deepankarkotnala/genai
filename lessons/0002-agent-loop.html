Lesson 2 · Foundations

The agent loop, written out in full

⏱ ~3 h total 25 min read · 75 min build · 40 min break/debug · 30 min interview Prereq · Lesson 1 Next · Lesson 3
🎯
By the end of this lesson you will be able to
  • Write the agent loop from memory, with no framework.
  • Distinguish a prompt, a chain, a workflow and an agent — and say which one a problem needs.
  • Answer "when would you not build an agent?" convincingly.
  • Name every way a loop can terminate, and explain why the step limit is not optional.
  • Read an execution trace and say what the agent knew at each step.

1 · Four things people all call "an agent"

Interviewers ask this to find out whether you reach for an agent by default. The distinction is who decides what happens next.

ShapeWho decides the next stepUse when
Promptnobody — one call in, one answer outthe task is a single transformation: summarise, classify, rewrite
Chainyou, at build time — fixed sequencethe steps are always the same: extract → validate → format
Workflowyou, with branches — code branches on resultsthe paths are known and finite, and you want them auditable
Agentthe model, at run timeyou genuinely cannot enumerate the paths in advance
⚠️
When not to build an agent

When you can draw the flowchart. If you can draw it, write it — a workflow is cheaper, faster, reproducible, and debuggable with a stack trace. Handing the flowchart to a model buys nothing and costs you determinism.

Also avoid an agent when: every run must take the identical path for audit reasons; the latency budget is tight (each step is another model round-trip); or a wrong action is expensive and you have no approval gate yet (Lesson 8).

The strongest answer names the real cost: an agent trades predictability for flexibility. Only pay that when you need the flexibility.

2 · The loop

Everything else in this course is a variation on five steps:

① Perceive — the model sees the goal plus everything discovered so far.

② Decide — it chooses one next action, or decides it can answer.

③ Act — your code runs the requested tool.

④ Observe — the result is appended to the conversation.

⑤ Repeat — until an answer, or until a limit stops it.

✅
In plain English

Look → think → do → look again → repeat. It feels powerful only because "do" can touch real systems and "look again" lets the next decision use what just happened.

3 · Build it

Open project/agent/loop.py. This is the core, with nothing removed:

for n in range(1, max_steps + 1):
    # 1. DECIDE -- the only place a model is consulted.
    decision = brain.decide(messages, specs)

    # 2. If it chose to answer, we are done.
    if decision.final_text is not None:
        return RunResult(answer=decision.final_text, steps=steps,
                         stopped_because="final_answer", ...)

    # 3. ACT -- run the tool it asked for.
    call = decision.tool_call
    try:
        result = execute(call.name, call.arguments)
    except ToolError as exc:
        result = {"error": "invalid_call", "message": str(exc)}

    steps.append(Step(n=n, kind="tool_call", tool_name=call.name,
                      arguments=dict(call.arguments), result=result, ...))

    # 4. OBSERVE -- the result becomes part of what the model sees next.
    messages.append(Message("assistant", f"Calling {call.name} with {call.arguments}"))
    messages.append(Message("tool", json.dumps(result), tool_name=call.name))

# 5. The limit, not the model, ended this run.
return RunResult(answer="Stopped after ... Escalating to a human.",
                 steps=steps, stopped_because="max_steps")

That is an agent. No framework, no graph, no orchestrator class.

Three decisions worth defending

The step limit is the only real bound. A loop that exits when the model decides to stop is not bounded, because "the model decides" is the part you don't control. Note that stopped_because is returned, not just the answer — and that the milestone script exits 1 on a truncated run. A truncated run reported as a finished one is how silent failures reach production.

Tool errors are fed back, not raised. A missing ticket is information. Turning it into an exception ends the run; putting it in the conversation lets the agent try something else or escalate honestly. Recoverable and fatal are different, and the loop must know which is which.

Every step is recorded. Step keeps the tool name, arguments, result and telemetry. Without it, "it did something odd yesterday" is not a bug report. Lesson 11 turns this into real tracing.

The first tool

search_kb is deliberately primitive — keyword overlap, tags weighted higher than body text:

terms = [t for t in query.lower().replace(",", " ").split() if len(t) > 2]
score = tag_hits * 3 + body_hits

Starting crude is intentional. You should watch keyword search fail in an obvious way before meeting embeddings, so that in Lesson 5 embeddings arrive as the answer to a problem you have personally seen rather than as a technology you were told to use.

Read the trace properly — this is a job skill

Step 2 is the interesting one. Nothing told the agent about ORD-5581. It appeared in the body of the ticket returned by step 1. The agent could only decide to look it up because step 1's result was fed back in.

That is the loop earning its keep. A chain would have needed the order id up front.

5 · Break it, then debug it

1 · A ticket with no order.

python steps/l02_loop.py TCK-1005

Two tool calls, not three — lookup_order is skipped. Why? Because the decision to look up an order comes from finding an ORD- token in the ticket body, and TCK-1005 has none. The path is driven by content, not by a step counter.

2 · Starve the loop.

python steps/l02_loop.py TCK-1001 --max-steps 2

It stops mid-investigation with stopped_because: max_steps and exit code 1. Notice what it does not do: pretend to have an answer. Compare with what a caller would see if the loop just returned whatever it had.

3 · A ticket that doesn't exist.

python steps/l02_loop.py TCK-9999

read_ticket returns {"error": "not_found", ...}, the agent escalates instead of guessing, and the run still terminates cleanly.

🐛
This case was a real bug, found by a test

The first version of this lesson's code hit the step limit on TCK-9999. The reason is worth studying: failed tool results were filtered out of the observed state, so "I have no ticket" stayed true no matter how many times reading it failed — and the agent retried read_ticket until the budget ran out.

The fix was to track attempted tools separately from successful results:

if ticket is None and "read_ticket" not in attempted and "read_ticket" in available:
    ...
if ticket is None:
    return _summarise(None, None, None)   # no path forward: say so

Retrying a call that already failed identically is the most common way an agent burns its step budget. Lesson 7 builds a proper controller for this. Notice the shape of the bug: the loop was fine; the state model conflated "unknown" with "known to be unavailable".

6 · The production concern

Four things this loop still lacks, each a later lesson: no timeout on a tool call (7), no detection of identical repeated calls (7), no cost ceiling (11), and no persistence — crash at step 3 and all work is lost (14).

What it does have is the property that matters most: it always terminates, and it always says how.

🧰
You already know this

max_steps is a redelivery limit. Feeding tool errors back is error handling that distinguishes retryable from fatal. Recording every step is request logging. You have built all three; the loop is just where they go in an agent.

7 · Interview practice

Two-minute answer — "Explain how an agent works."

🎤

"An agent is a loop around a model with tools. Each turn, the model sees the goal plus every result so far and picks one next action. My code executes it, appends the result to the conversation, and calls the model again. It ends when the model produces an answer or when a step limit stops it.

Two details I'd flag. The step limit isn't a safety net, it's the actual bound — if termination depends on the model choosing to stop, the loop isn't bounded. And tool failures go back into the conversation as results rather than raised as exceptions, because a missing record is information the agent can act on, whereas an exception just ends the run.

The reason to use the loop instead of a workflow is that the second step can depend on what the first one returned. In our triage agent the order id only exists inside the ticket body, so nothing could have looked it up in advance."

Q System design · Support wants automated triage for 10,000 tickets a day. Agent or workflow? ›

Start by refusing the false choice: most of that volume is a workflow, and the agent earns its place on the remainder.

Classify first with one cheap model call. Tickets matching known shapes — password reset, invoice copy, delivery status — go down deterministic paths: fast, auditable, roughly free. Route only the ambiguous or multi-step ones to the agent.

Then the numbers, because at 10k/day they dominate. Each agent step is a round trip; 4 steps at 2s is 8s per ticket plus 4× the token cost of a single call. If the agent handles 15% that's 1,500 runs a day, which is a budget you can state. Add per-run step and cost ceilings, and make escalation a first-class outcome rather than a failure.

The trap: "use an agent for everything" signals you haven't costed it.

Q Debugging · An agent in production runs 40 steps and times out. Walk me through it. ›

Get the trace and look at the sequence, not the final output. Four patterns and their fixes:

Identical repeated calls — same tool, same arguments. Usually a failing tool whose error the agent can't act on, or state that conflates "not tried" with "tried and failed". Fix: track attempted calls; on a repeat, stop or escalate.

Two-call oscillation — A, B, A, B. The agent has contradictory instructions or a tool result it can't interpret. Fix: detect a repeated cycle, and check the tool descriptions.

Genuine drift — plausible but unrelated calls. The goal has been diluted by 40 steps of tool output in the context window. Fix: compaction (Lesson 6) and a tighter step budget.

Missing termination — it has the answer and keeps going. The system prompt never said what "done" looks like, or there's no way to signal it.

Then the real answer: 40 steps means max_steps was too high or absent. A 4-step task should never have a 40-step budget — a limit that only trips after the damage is a limit in name only.

Q Coding · Implement a tool-calling loop from scratch in 15 minutes. No framework. ›

Ship these, in this order: the message list; the bounded for loop; call the model; branch on tool-call vs final answer; dispatch through a dictionary (never getattr or eval on a model-supplied name); catch tool errors and feed them back; append both the decision and the result; return a result object carrying why it stopped.

Say out loud while writing: "the step limit bounds the loop", "a dictionary lookup means a hallucinated tool name is a clean error", "the error goes back to the model rather than up the stack".

Common failures: while True; dispatching with eval; letting a tool exception escape; and returning only a string, so the caller can't tell a finished run from a truncated one.

Q Senior follow-up · How do you set max_steps for a real workload? ›

Measure, don't guess. Run the golden set, take the distribution of steps for successful runs, and set the limit a little above the tail — say p99 plus a small margin. Our triage agent finishes in 3–4 steps, so 6 is generous and 40 would be negligent.

Then make it not a single number: budget by cost and wall-clock as well as steps, because one expensive step can cost more than five cheap ones. Alert on the rate of limit-hits — a rise means either the tasks changed or the agent regressed, and both are worth knowing before a customer tells you.

Q Senior follow-up · The same tool call is issued three times in one run. Is that a bug? ›

Depends on idempotency and on whether the arguments changed. Three identical reads are wasteful but harmless — still worth fixing, since it usually means the result isn't reaching the model in a usable form. Three calls with different arguments may be legitimate investigation.

Three identical writes are an incident. That's why Lesson 8 attaches an idempotency key to the refund path: the fix isn't "stop the agent repeating itself", it's "make the repeat harmless". Prevention at the loop layer and protection at the tool layer are different defences, and irreversible actions need both.

8 · Recap

  • Prompt / chain / workflow / agent differ by who decides the next step. If you can draw the flowchart, write the workflow.
  • The loop is perceive → decide → act → observe → repeat. Forty lines, no framework.
  • The step limit is the real bound, and the run must report why it stopped.
  • Tool errors are observations, not exceptions.
  • The loop earns its keep when step N+1 depends on what step N returned — like an order id that only exists inside a ticket body.
  • Conflating "not attempted" with "attempted and failed" causes infinite retries. That was a real bug here, caught by a test.
