Lesson 6 · Making it competent

Context, state and memory

⏱ ~2.5 h total 25 min read · 60 min build · 35 min break/debug · 30 min interview Prereq · Lesson 5 Next · Lesson 7
🎯
By the end of this lesson you will be able to
  • Name the seven things people call memory, and say which two this agent needs.
  • State the state vs memory distinction in one sentence, with a test for telling them apart.
  • Budget a context window, and cap a tool result at the source.
  • Compact a transcript without losing the goal — and refuse a compaction that would not help.
  • Explain why "memory vs RAG" is a trick question.

1 · Seven things called "memory"

Naming all seven is interview-useful. Building all seven is not.

StoreHoldsBuilt here?
Conversation historythe message list for this runyes
Workflow statestep, budget, facts gatheredyes — state.py
Working memoryscratch notes inside one stepno
Long-term memoryfacts that outlive the runyes — prior tickets
User profiledurable per-customer preferencesno
Retrieval storedocumentsyes — Lesson 5
Audit historywhat was done, immutablyLesson 8

The three unbuilt ones are not hard; they are unnecessary for this agent. An agent carrying stores it does not use is slower, dearer and harder to debug — and "I only built what the workflow needed" is a better answer than a diagram with seven boxes.

2 · State is not memory

🔑
The distinction, and the test

State belongs to one run: where am I, what have I gathered, what budget is left. Discarded when the run ends.

Memory outlives the run: what do we know about this customer from last month.

The test: if it would be wrong to still have this tomorrow, it is state.

Conflating them produces two opposite bugs. Treat state as memory and last week's half-finished investigation leaks into today's answer. Treat memory as state and the agent forgets the customer between tickets while insisting it remembers.

RunState also finally fixes something properly. Lesson 2's infinite-retry bug was patched inside the backend, which had to infer from the transcript whether a tool had been tried. Now it is explicit:

def record(self, tool, result):
    self.tools_attempted.append(tool)          # grows even on failure
    if not result.get("error"):
        self.facts[tool] = result              # only successes become facts

"Not attempted" and "attempted and failed" are now different states, which is what stops the retry loop. Lesson 7 builds a real controller on this.

3 · The context window is a budget

Two budgets, not one:

token_budget: int = 6000
tokens_used: int = 0
max_steps: int = 6

Steps alone are a poor bound, because one expensive call can cost more than five cheap ones. Lesson 11 adds money as a third.

⚠️
Our token count is an estimate, and says so

CHARS_PER_TOKEN = 4 is a rule of thumb, not a tokeniser. Good enough for budget decisions and honest about it. In production use the provider's own counter — being 20% wrong about your budget is how you get a truncation error at 2 a.m.

4 · Cap at the source

Here is the thing most treatments of this topic miss. Watch a real run with a deliberately small 300-token budget:

python steps/l05_retrieval.py --memory TCK-1001

  step 1: +  78 tokens  transcript=  115  budget=300  [ok]
  step 2: +  55 tokens  transcript=  175  budget=300  [ok]
  step 3: + 297 tokens  transcript=  309  budget=300  [OVER]

Step 3 is the retrieval call from Lesson 5, and on its own it is bigger than the entire budget. No amount of summarising older messages fixes that, because the problem is the newest message.

def add(self, message):
    """Append, capping an oversized tool result before it ever lands."""
    if message.role == "tool" and estimate_tokens(message.content) > MAX_TOOL_RESULT_TOKENS:
        ...  # truncate, and record that we did
        self.truncations += 1
🔑
Two mechanisms, not one

Cap handles a single oversized result. Compact handles accumulation across many steps. Most people reach for compaction alone, then find it cannot help — because the newest message is the bulk of the prompt and compaction is designed to keep recent messages verbatim.

Note the second-order effect: KEEP_RECENT = 2, not 4. A generous "keep the recent turns" setting sounds safer and protects exactly the messages that caused the problem.

5 · Compact without losing the thread

Order of operations, and every line of it is a decision:

System prompt stays verbatim — those are the instructions.

The goal stays verbatim — drop it and the agent is answering a question it can no longer see. This is the single most common compaction bug.

Recent turns stay verbatim — they are what the next decision is about.

The middle becomes one summary line per tool that ran.

  compacted 309 -> 224 tokens (4 messages)

    system       You are a support-ticket triage agent.
    user         Triage ticket TCK-1001.
    assistant    Summary of earlier steps (compacted to fit the context window):
                 - read_ticket: ticket_id=TCK-1001; category=Billing; priority=High
    assistant    Calling search_kb
    search_kb    {"query": "billing refund", "chunks_searched": 17, ...

Summarising is lossy on purpose. The alternative — dropping the oldest messages blindly — loses the same information without recording that anything was lost, which is how an agent re-runs a tool it already ran.

🐛
Two real bugs found while building this

1 · The summariser silently did nothing. The demo serialised tool results with str(result) while the loop uses json.dumps. A Python dict repr uses single quotes, json.loads failed, and every summary line fell back to a raw 90-character truncation. The summary looked plausible, which is why it survived a first reading. Any summariser needs a test that asserts the summary contains parsed values, not just that it exists.

2 · Compaction made the transcript bigger. Summarising a span of short messages produced a summary longer than the span — spending a model call to grow the prompt. The fix is a guard, and it is a better lesson than the original code:

if after >= before:
    return f"compaction skipped: would grow {before} -> {after} tokens"

"Compact when full" is the instinct. "Compact when it helps" is the rule.

6 · Long-term memory, and one honest label

recall_prior_tickets() is long-term memory in one function — and it is a lookup, not a mystery:

  TCK-1008  Billing    Question about proration
  TCK-1004  Returns    Want to return the annual plan
  basis: matched on customer_tier (the fixture has no customer id)

That last line matters. The fixture has no customer id, so this matches on tier — "same tier" is not "same person", and the function says so in its own output rather than letting a reader assume otherwise. An honest memory reports the basis of its recall.

🔑
"Memory vs RAG" is a trick question

They are the same machinery with different purposes. Retrieval searches documents; memory searches history. Both chunk, index, rank and inject. If you answer "memory is different from RAG" you have missed it; the interesting question is what you write, and when.

Our write rule is deliberately extreme: nothing is written at all. The tickets are the record. Agents that write their own memories need a policy for what is worth keeping and a way to correct a wrong one — and an agent that confidently recalls something false is worse than one that recalls nothing. Lesson 8 adds the first thing this agent genuinely writes, and it is append-only for exactly that reason.

7 · Break it

1 · Drop the goal. In compact(), remove goal from the kept list. Run a long trajectory. The agent still has instructions and recent results, and no idea what it was asked. This is the bug to recognise on sight.

2 · Raise KEEP_RECENT to 6. Then re-run --memory. Compaction now saves almost nothing, because the messages it is allowed to touch are the small early ones. Being generous with "recent" protects the wrong messages.

3 · Disable the cap. Set MAX_TOOL_RESULT_TOKENS = 100_000. Step 3 goes back to 297 tokens, the transcript to 476, and compaction saves 40 tokens against a 300-token budget. Watch the two mechanisms fail independently.

4 · Make memory lie. In recall_prior_tickets, delete the basis field. Nothing breaks and the output looks better — which is the point. Now a reader will believe those are the same customer's tickets. Removing a caveat is the cheapest way to make a system look more capable than it is.

8 · The production concern

Long conversations are where agents die. Not with an error — with drift, as the goal becomes a rounding error in a transcript of tool output. That is not the model being stupid; it is you having diluted the prompt.

Compaction is a model call, so it costs money and can itself fail. Ours is deterministic string assembly precisely so it cannot; a real summariser needs a fallback for when the summary call errors.

State needs to be persistable, which is why RunState has to_json/from_json already. Lesson 14 uses it to resume a run that crashed at step 3.

Memory is a privacy surface. Anything an agent remembers is data you now retain, must be able to delete on request, and must not surface across tenants. "We store conversation history" is a compliance statement, not just a feature.

🧰
You already know this

A token budget is a memory budget. Capping a tool result is response-size limiting on an API. Compaction is log rotation with a digest. State-vs-memory is request scope versus session store — you have made that decision in every web app you have built.

9 · Interview practice

Two-minute answer — "Your agent hits the context limit mid-run. What do you do?"

🎤

"First I'd find out why, because there are two different problems. Either one tool result is enormous, or many small ones have accumulated — and they need opposite fixes.

For a single oversized result, cap it at the source: truncate before it enters the transcript and record that you did. Compaction can't help there, because compaction deliberately keeps recent messages verbatim and the newest message is the problem.

For accumulation, compact: keep the system prompt, keep the goal, keep the last couple of turns, and replace the middle with one summary line per tool that ran. Keeping the goal is the part people get wrong — drop it and the agent is answering a question it can no longer see. And I'd guard the compaction: if the summary isn't smaller than the span it replaces, skip it, because otherwise you pay a model call to grow the prompt.

Longer term I'd reduce what enters the context at all — tighter tool results, fewer steps via routing — since managing a budget is better than repeatedly rescuing it. And I'd track a budget in tokens as well as steps, because one expensive call can cost more than five cheap ones."

Q System design · Design memory for a support agent handling repeat customers across months. ›

Separate the stores by lifetime and by who owns them. Run state: ephemeral, persisted only for crash recovery, deleted on completion. Ticket history: already your system of record — query it, do not copy it into a second store that can disagree with it. Customer profile: a small, explicit, human-auditable set of durable facts (preferred language, accessibility needs, tier). Written by rule, not by model whim.

Then the parts that make it real. Write policy: what earns a place in the profile, and who can correct it — an agent that writes "customer is abusive" from one bad exchange has created a durable, wrong, consequential record. Retention and deletion: a subject-access or deletion request must reach every store, which is an argument for fewer stores. Tenant isolation: memory keyed so cross-customer leakage is structurally impossible, not merely filtered. Injection: anything written from ticket text is attacker-controlled — Lesson 9.

Say what you would not build: freeform model-written memories, because the failure mode is confident false recall and there is no cheap way to detect it.

Q Debugging · At step 15 the agent starts making unrelated tool calls. Diagnose. ›

Classic context dilution. Get the actual prompt at step 15 and measure the ratio: how many tokens are the goal and instructions, and how many are accumulated tool output? If the goal is 2% of the prompt, the model is not ignoring it — it is outvoted.

Check in order: is compaction running at all; is it keeping the goal; is one tool returning far more than the others; has the transcript been truncated by the provider rather than by you — because provider-side truncation usually drops the oldest messages, which is where your system prompt lives.

Then the structural answer: 15 steps for this task probably means the step budget is too generous and the tools too fine-grained. Coarser tools and routing reduce steps, and fewer steps is a better fix than better compaction.

Q Coding · Implement transcript compaction. ›

Partition the messages into system, goal, recent tail, and middle. Summarise the middle to one line per tool result. Reassemble in order. Return a description of what happened, and guard: if the result is not smaller, do not apply it.

Details that signal experience: keep the goal explicitly (not "the first message"); count tokens before and after and report both; record how many compactions have happened, because a run compacting five times is telling you something about your tool sizes; and make the summariser's parsing failure loud rather than silently falling back to raw truncation.

Q Senior follow-up · Should the agent write its own memories? ›

Rarely, and never without a correction path. The appeal is obvious; the failure mode is a durable false belief that shapes every future interaction and that nobody knows to look for. In support, a wrong memory about a customer is worse than no memory, because it produces confidently wrong personalisation.

If it must happen: constrain writes to a fixed schema rather than freeform text, require a confidence threshold or human confirmation for anything consequential, timestamp and source every entry so it can be audited, expire entries by default, and make deletion trivial. And measure it — treat recall precision as an eval metric, not an assumption.

Q Senior follow-up · Bigger context windows are coming. Does this lesson stop mattering? ›

No, for three reasons. Cost scales with tokens, so a 1M-token window you actually fill is a bill, not a feature. Attention degrades over long contexts — models reliably lose material in the middle, so a fact present in the prompt is not a fact used. And latency rises with prompt size, which users feel.

What changes is the threshold at which you intervene, not the discipline. The framing that survives: context is a budget you spend deliberately, and the question is always "does this token earn its place", not "does it fit".

10 · Recap

  • Seven stores get called "memory". This agent needs two. Building unused stores costs speed, money and clarity.
  • If it would be wrong to still have this tomorrow, it is state.
  • Budget tokens as well as steps; one expensive call outweighs five cheap ones.
  • Two mechanisms: cap a single oversized result at the source, compact accumulation. Compaction cannot rescue a huge newest message.
  • A generous KEEP_RECENT protects exactly the messages that caused the problem.
  • Compaction keeps the system prompt and the goal. Dropping the goal is the classic bug.
  • Compact when it helps, not when it is full — and skip it when the summary would be bigger.
  • Memory and RAG are the same machinery; what differs is what you write. Ours writes nothing, and reports the basis of its recall.
