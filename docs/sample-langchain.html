Module 10 · Frameworks track

LangChain

You have written model calls, retrieval and an agent loop by hand. LangChain does not add a new idea about language models. It gives the components you already wrote one shared interface, so you can replace any one of them without rewriting the others.

1 · What you already know

In module 06 you built retrieval by hand: load a document, split it, embed the chunks, search them, put the results in a prompt. In module 08 you built an agent loop by hand: send messages, read the reply, run a tool, append the result, send again.

Both work. Both are code you wrote and now maintain.

2 · What breaks now

Take that hand-written code and ask it to do five ordinary things.

You are asked to…What you have to change
Use a different providerEvery line that reads the reply, because the response shape differs
Answer 200 questionsWrite the concurrency yourself, and the rate limiting with it

Retry when the API times outWrap every call site separately
See where the time wentAdd logging into every function by hand

None of these five is about language models. All five are the same problem: your steps have no common shape, so nothing can be done to all of them at once. That is the problem LangChain solves.

3 · Simple breakdown - LangChain vs LangGraph

A LangChain

Basic level

What it is. LangChain is an open-source Python framework for building LLM-based applications from reusable components such as models, prompts, retrievers, tools, and runnables.

Core purpose. It reduces the amount of application code you need to write when several LLM-related components must work together.

Execution model.

Intermediate level

Architecture under the hood. Every component implements one interface, Runnable, which defines invoke, batch, stream and their async versions. The | operator builds a RunnableSequence that runs components in order. RunnableParallel runs components at the same time and returns a dictionary. Streaming, batching and callbacks are implemented once on Runnable, so every chain gets them.

State handling. A chain is stateless. The only data that exists during a run is the value passed from one component to the next. Chat history is added with RunnableWithMessageHistory, which reads and writes a store you supply, keyed by a session id.

Limitations and advanced features. A chain is acyclic and runs forward once: no loops, no rejoining branches, no pause for approval, no recovery after a crash. Advanced features wrap any component - .with_retry(), .with_fallbacks(), .with_structured_output(), .bind_tools().

B LangGraph

Basic level

What it is. LangGraph is an open-source Python framework, built on LangChain, for writing LLM applications as a graph of nodes that read and update one shared state object.

Core purpose. It runs workflows that loop, choose the next step at run time, pause for human approval, or continue after a crash.

Execution model.

Intermediate level

Architecture under the hood. A StateGraph holds the state schema, the nodes and the edges. Compiling it produces a Pregel runtime that executes in supersteps: every node scheduled for a step runs, then their updates are merged. A reducer declared per state field decides how the merge works - overwrite by default, or add_messages to append. A checkpointer (MemorySaver, SqliteSaver, PostgresSaver) writes the state after every superstep.

State handling. One shared state object exists for the whole run. Each node returns a partial update, which the runtime merges through the reducers. With a checkpointer, every version is stored under a thread_id, which is what allows resume, replay and history.

Limitations and advanced features. More setup than a chain: a schema, node functions, edges and a compile step before anything runs. A cycle with no exit condition is easy to write, so the runtime enforces a recursion_limit. Advanced features are interrupt_before and interrupt_after for human approval, Command to route and update state in one return, subgraphs, per-node streaming, and time travel from any checkpoint.

The core differences

LangChainLangGraph
Workflow design A fixed forward sequence built with |. The order is decided before the run starts and does not change during it. Named nodes with edges evaluated while running. A conditional edge reads the state and picks the next node, so loops and branches are normal.
Error recovery .with_retry() re-runs one component from its own beginning. .with_fallbacks() swaps in a different component. Nothing is saved, so a crash loses the run. The checkpointer saves state after every node, so a failed run resumes from the last completed node instead of starting over.
Architectural paradigm A directed acyclic graph of components behind one shared interface. A state machine with a persistent shared state object.

In short - which one to choose

Choose LangChain when:

  • The steps always run in the same fixed order.
  • You want retrieval, prompting and parsing wired together with less code.
  • You expect to swap the model, the retriever or the vector store later.
  • You want streaming, batching and tracing without writing them.

Choose LangGraph when:

  • The workflow loops - call the model, run a tool, call the model again.
  • The next step depends on what the previous step returned.
  • The run must pause for a person to approve something, then continue.
  • The run must survive a crash and continue from where it stopped.

Choose neither when:

  • The whole task is one prompt and one answer. Call the model directly.
  • You have not yet built the same thing by hand once. Build it first, then replace it.
  • You cannot say in one sentence what the framework is doing for you.

5 · Runtime mechanics

Here is what happens when you call chain.invoke() on a retrieval chain. Seven steps, no framework vocabulary yet.

  1. You pass a question string in.
  2. Two things start at the same time: the retriever searches, and the question is copied through unchanged.
  3. Both results are collected into one dictionary.
  4. The prompt template fills its variables from that dictionary.
  5. The filled prompt goes to the model as one HTTPS request.
  6. The reply comes back as a message object.
  7. The parser takes the text out of that object and returns it.

6 · The components, one at a time

LangChain calls these components. Each block below runs on its own. Learn them in this order - the order matches how they are assembled later.

Model, prompt, output

1 · Model

Holds the provider, the model name and the settings. Returns an AIMessage, not a string.

2 · Prompt

A string with named variables. Filling it returns a prompt value. Nothing is sent yet.

3 · Messages

Chat models take a list of messages. Each message has a role.

4 · Output

.content holds the text. .response_metadata holds the token counts and the finish reason.

5 · Structured output

Describe the shape and you get an object back instead of text. A reply that does not fit the shape raises a validation error instead of passing bad data on.

6 · Output parser

Converts the reply into the type your code wants. A parser failure is an output problem, not a model failure - the two are debugged differently.

Composition

7 · Runnable

Every component above is a Runnable. That word means it has these methods:

MethodWhat it does
invoke(x)One input, one output.
batch([x, y])Many inputs at once, results in the same order.
stream(x)Yields pieces of the output as they arrive.
ainvoke · abatch · astreamThe same three, as coroutines.

Everything else on this page follows from every component having these four methods.

8 · RunnableSequence

| runs components in order. The output of one is the input of the next. The sequence is itself a Runnable, so it also has all four methods.

9 · RunnableParallel

Runs components at the same time and returns a dictionary with one key per component.

10 · RunnableBranch

Picks one path from a list of conditions. Only the matching path runs. The last entry is the default.

11 · RunnableLambda and RunnablePassthrough

RunnableLambda turns any function into a component. RunnablePassthrough copies its input through unchanged, which is how you keep an earlier value available further down the chain.

Getting your own data in

12 · Document loader

Reads an external source and returns Document objects. A Document holds page_content and metadata. Loading is not retrieval, embedding or searching - it is only reading.

13 · Text splitter

Cuts long Documents into chunks. chunk_size is the target length, chunk_overlap is how much of the previous chunk is repeated at the start of the next one so a sentence cut in half is still readable in one of them.

Overlap costs storage and tokens on every query. 10–20% of chunk_size is the usual starting point.

14 · Vector store

Embeds the chunks and stores each vector next to its text and metadata. It also searches: embed the query, compare, return the closest records.

15 · Retriever

Takes a question, returns Documents. It is a Runnable, so it drops into a chain with no adapter. Your chain depends on "retrieve relevant documents" and not on FAISS.

Actions

16 · Tool and tool calling

A tool is a function with a name, a description and typed arguments. bind_tools sends those definitions with the request. The model does not run the function. It returns a request naming the tool and its arguments, and your code decides whether to run it.

17 · Chain

Now they assemble, and none of them is new.

Retrieve, fill, call, parse. If you ran each component on its own first, this line contains nothing new.

7 · State and data flow

Ten questions, answered on every page in this portal that has state.

1 · What data is state?One value, handed from each component to the next.
2 · Who writes each field?Only the component that produced it. Values are returned, never edited in place.
3 · Who reads it?The next component in the sequence, and nothing else.
4 · Replaced, appended or merged?Replaced. RunnableParallel is the one exception: it merges its results into one dictionary.
5 · What reducer controls merging?None. LangChain has no reducers - that is a LangGraph idea.
6 · Only in process memory?Yes.
7 · Checkpointed?No.
8 · In a database?Only chat history, and only if the store you supply is one.
9 · How long does it survive?Until invoke returns.
10 · What key retrieves it again?Nothing. There is no key, because nothing was stored.

A chain holds no data about past calls, so one chain object is safe to share across many requests. Chat history is the exception, and it is not automatic.

LangChain does not store your conversation. It calls the store you supply. If get_session_history returns a list, the history dies on restart. If it returns a Redis or Postgres object, it does not.

9 · Break it

Ask the chain a question its documents do not answer.

There is no such policy in the handbook. Nothing raised. No warning. The retriever returned four chunks that were the closest available but not relevant, the prompt included them, and the model produced a fluent answer anyway.

This is the only failure on this page with no exception attached to it. Every other failure - a missing prompt variable, a wrong type, a timeout, a schema mismatch - raises something you can catch. This one does not.

10 · Fix it

The chain cannot detect it, so you check it yourself, before the model call.

An empty result now raises. A weak-but-non-empty result still does not, so the prompt does the rest of the work.

Now the failure is visible: either an exception, or the string NOT_IN_CONTEXT your code can test for. You cannot fix what you cannot see, and this failure was invisible by default.

RollbackVersion the prompt string. A bad prompt must be revertible without a redeploy

Neither retry nor fallback can resume a chain from the middle. Retrying the whole chain re-runs retrieval, re-fills the prompt and pays for everything again.

13 · Interview preparation

Beginner What is LangChain and why use it? ›

An orchestration framework for LLM apps that standardizes components (prompts, models, parsers, retrievers) behind a common Runnable interface, so you compose them with the pipe operator and swap parts without rewriting plumbing. It provides provider-agnosticism, free streaming/batching/async/retries, a large integration ecosystem, and tracing via LangSmith.

Beginner What does prompt | model | parser mean? ›

An LCEL chain: format the prompt with input variables, send it to the model, then parse the model's response (e.g. to a plain string). The | pipes each step's output into the next. The whole chain is itself a Runnable you can invoke/batch/stream.

Intermediate What is the Runnable interface and why does it matter? ›

The common contract - invoke, batch, stream, and async variants - implemented by every LangChain component. Because they all share it, any component is interchangeable and composable, and the framework can derive streaming, batching, and async automatically from the composition graph. It's the foundation that makes LCEL work.

Intermediate How do you build a RAG chain in LCEL? ›

Run the retriever and the question in parallel into a dict ({"context": retriever | format_docs, "question": RunnablePassthrough()}), pipe that into a prompt template, then into the model, then an output parser. The parallel dict fetches context while passing the question through; the pipes sequence prompt→model→parse. The retriever comes from vectorstore.as_retriever() and is itself a Runnable.

Senior When would you NOT use LangChain, or drop to raw SDK? ›

For a single, simple completion the abstraction adds dependency weight and indirection with no benefit - call the provider SDK. Drop to raw calls in hot paths where you need precise control over requests/streaming, or when debugging an issue the abstraction obscures. Use LangChain where composition, swappability, integrations, or tracing genuinely pay off; for cyclic/stateful agent flows, use LangGraph instead of bending LCEL. Match the tool to the complexity.

Senior How do you make a LangChain app production-ready? ›

Pin exact package versions; enable LangSmith tracing for observability and prompt/version management; add .with_retry()/.with_fallbacks() for resilience and a fallback model; use structured output for machine-consumable results; keep prompts in a versioned registry; build an eval set (Module 06/14) gating prompt/chain changes; wrap chains behind your own service boundary (FastAPI/LangServe) so you can swap the framework if needed; and set temperature/timeouts/token budgets explicitly. Treat the chain as one component in your system, not the whole architecture.

Staff · design Design a provider-agnostic LLM layer for an org using LangChain. ›

A thin internal library exposing chains built from langchain-core Runnables, with the model created by a factory driven by config (so local Ollama, OpenAI, or a gateway are interchangeable). Centralize: a versioned prompt registry; retry/fallback policies (primary → cheaper/local fallback); structured-output schemas; LangSmith tracing for per-team cost/latency and eval; and guardrails wrapping inputs/outputs (Module 14). Expose chains via a service boundary (LangServe/FastAPI) so consumers don't import LangChain directly - that keeps you free to swap or drop the framework. Gate every prompt/chain change on an eval set in CI. The goal: teams get composable, observable, swappable LLM components without lock-in to any single provider or even to LangChain itself.

14 · In short, and what comes next

Use LangChain when:

  • Three or more steps always run in the same order.
  • You expect to swap the model, the retriever or the vector store.
  • You want streaming, batching and tracing without writing them.

Do not use it when:

  • One prompt, one answer. Call the provider SDK.
  • You have not built the same thing by hand once.
  • The flow needs to loop, branch and rejoin, pause, or survive a crash.
🔑
The limitation module 12 fixes

Every gap on this page is the same one: a chain has no memory of where it is. It cannot loop back, it cannot stop and wait, and a crash loses everything because nothing was written down. LangGraph gives the run a state object and saves it after every step. That is the whole difference.
