01Derive the normal equation.derivationmatrix calculusconvexity＋
Strong answer

Minimize J(w) = ½‖y - Xw‖² = ½(y - Xw)ᵀ(y - Xw). Expand to ½(yᵀy - 2wᵀXᵀy + wᵀXᵀXw). Differentiate with respect to w: ∇J = -Xᵀy + XᵀXw. Set to zero: XᵀXw = Xᵀy, hence w = (XᵀX)⁻¹Xᵀy whenever XᵀX is invertible.

It is a genuine minimum because J is convex - its Hessian is XᵀX, positive semi-definite, and positive definite exactly when X has full column rank.

30-second version

Expand the squared loss, differentiate, set the gradient to zero: XᵀXw = Xᵀy, so w = (XᵀX)⁻¹Xᵀy. It is a minimum because the Hessian XᵀX is positive semi-definite.

What’s being tested

Whether you can do matrix calculus and whether you justify that it is a minimum. Mentioning the Hessian and convexity unprompted is the differentiator.

Likely follow-up: “When is XᵀX not invertible, and what then?” - when columns are perfectly collinear or d > n. Use the Moore–Penrose pseudo-inverse via SVD, which returns the minimum-norm solution, or add ridge: (XᵀX + λI) is always invertible for λ > 0 because it shifts every eigenvalue up by λ.
02What are the assumptions of linear regression, and which can you ignore if you only care about prediction?assumptionsinferencetrap＋
Strong answer

Linearity in the parameters, exogeneity (E[e|X] = 0), homoscedasticity, no autocorrelation of errors, no perfect multicollinearity, and - for exact small-sample inference only - normality of errors.

For a pure prediction task: violations of linearity and exogeneity are serious, because they bias the fit itself. Heteroscedasticity and non-normal errors mostly damage inference - standard errors, p-values and confidence intervals become unreliable - while coefficient estimates stay unbiased and predictions remain usable, so if you are reporting RMSE rather than p-values you can often proceed, optionally with robust standard errors. Autocorrelation matters more than it looks, because it usually signals you should be using a time-series model and that your CV is leaking. Imperfect multicollinearity is tolerable for prediction and fatal for interpretation.

30-second version

Linearity, exogeneity, homoscedasticity, no autocorrelation, no perfect collinearity - plus normality for small-sample inference only. Linearity and exogeneity bias the fit; the rest mostly damage inference, not predictions.

What’s being tested

The split between prediction and inference. Exactly the question separating candidates who memorized a list from those who understand what the list is for.

Likely follow-up: “Is normality of errors needed for OLS to be BLUE?” - no. Gauss–Markov needs linearity, zero-mean errors, homoscedasticity and no autocorrelation. Normality buys exact t and F distributions in small samples; the CLT gives an approximate version for large n.
03Explain multicollinearity. How do you detect and handle it?multicollinearityVIFridge＋
Strong answer

Two or more predictors are strongly linearly related, so the data cannot cleanly attribute the shared variance. Coefficient estimates become high-variance, can be implausibly large, and can flip sign with small sample changes; standard errors inflate, so individually significant predictors appear insignificant even while the overall F-test is strongly significant - that pattern is a classic tell.

Detection: the pairwise correlation matrix for obvious cases, VIF (1/(1-R²_j), flagged above 5 or 10) for the general case, or the condition number of X.

Handling depends on the goal - drop one of the pair, combine them into a domain-meaningful composite, use PCA, use ridge, collect more data, or, if you only need predictions from a tree ensemble, do nothing at all.

30-second version

Predictors are strongly linearly related, so coefficients become unstable and standard errors inflate - but predictions are usually fine. Detect with VIF; fix by dropping, combining, or ridge, or ignore it if you only need predictions.

What’s being tested

Whether you know this is primarily an interpretation problem. The “significant F-test, insignificant t-tests” signature is a strong detail.

Likely follow-up: “Why does ridge help specifically?” - writing X = UΣVᵀ, ridge scales each direction by σᵢ²/(σᵢ² + λ). Directions with tiny singular values - exactly the collinear ones where variance explodes - get shrunk hardest, while well-determined directions are barely touched.
04Can R² be negative? Can it decrease when you add a feature?R-squaredevaluationtrap＋
Strong answer

In-sample, on the data you fitted, R² is bounded in [0,1] and can never decrease when you add a feature - OLS can always set the new coefficient to zero and do no worse, so it is monotone in feature count. That is exactly why adjusted R² exists: it penalizes each extra parameter and can fall.

Out-of-sample, R² absolutely can be negative: 1 - SSres/SStot goes negative whenever your squared error exceeds that of simply predicting the training mean - common under distribution shift or severe overfitting. So negative R² is not a bug; it is a meaningful and fairly damning diagnostic.

30-second version

In-sample it cannot decrease with more features and stays in [0,1]. Out-of-sample it can go negative, meaning you are worse than predicting the training mean.

What’s being tested

Whether you distinguish in-sample from out-of-sample behaviour. Many candidates confidently say “no, R² is always 0 to 1”.

05When would you use gradient descent instead of the normal equation?optimizationcostscale＋
Strong answer

The normal equation is O(nd² + d³) and needs the whole XᵀX in memory, so it becomes impractical once d reaches the thousands - the d³ inversion dominates. Use gradient descent, or a conjugate-gradient or L-BFGS solver, when d is large; when n is too large for memory and you want mini-batches or online updates; when XᵀX is ill-conditioned so explicit inversion is numerically unstable; or when the loss has no closed form - which is most of them, including logistic loss, Huber, and anything with an L1 penalty. Conversely, for small-to-moderate d the normal equation is exact and needs no learning-rate tuning. In practice you would use lstsq or SVD rather than literally inverting XᵀX.

30-second version

When d is large (the d³ inversion dominates), when n exceeds memory, when XᵀX is ill-conditioned, or when the loss has no closed form - which covers logistic, Huber and anything with L1.

What’s being tested

Cost awareness, and knowing that closed forms are the exception rather than the rule.

06Why can’t you just use linear regression for classification?classificationbridgetrap＋
Strong answer

Four concrete reasons, and this is the bridge into logistic regression. (1) Unbounded output: Xw ranges over all reals, so you get predictions like −0.3 and 1.4 that cannot be probabilities. (2) Sensitivity of the boundary: squared error penalizes distance from 0/1 even for confidently-correct points, so a cluster of extreme x values drags the fitted line and moves the implied threshold - adding easy points changes your boundary. (3) Wrong noise model: a Bernoulli target has variance p(1-p), which depends on p, so errors are heteroscedastic by construction and the Gaussian-noise justification for MSE simply does not apply. (4) Wrong functional shape: a linear model implies a constant marginal effect of x on probability, but probability must saturate near 0 and 1.

The fix for all four is to model a transformed quantity that is naturally unbounded - the log-odds - and to use the Bernoulli likelihood as the loss. That is exactly logistic regression.

30-second version

Unbounded predictions outside [0,1]; a boundary dragged by far-away points; heteroscedastic Bernoulli errors that void the MSE justification; and a constant marginal effect where probabilities must saturate.

What’s being tested

Whether you can motivate logistic regression from first principles rather than asserting it. Asked constantly, and answering with these four points positions you perfectly for the log-odds questions that follow.

07In 2026, with gradient boosting and foundation models available, why would you ever ship linear regression?2026baselinejudgment＋
Strong answer

Because several things it gives you for free are expensive everywhere else. It is auditable - a regulator or a clinician can read the coefficients, and in credit, insurance and healthcare that is often a hard requirement, not a preference. It is cheap and predictable - microsecond inference, a handful of parameters, no GPU, trivially reproducible. It extrapolates monotonically, which tree ensembles simply cannot do: outside the training range a boosted tree flatlines at its last leaf value, while a linear model keeps going in the direction the domain says it should. It is stable under mild drift, because a few smooth coefficients degrade gently where a 900-tree ensemble can degrade abruptly. And it is the baseline that tells you whether the complex model earned its keep: if XGBoost beats it by 0.4% AUC, you have just learned the problem is essentially linear and you should ship the simple thing.

The honest counter-position is equally important: on wide tabular data with interactions and non-linearities you did not encode by hand, boosting will win clearly, and then you take the win.

30-second version

Auditability, microsecond inference, sane extrapolation, graceful degradation under drift - and it is the baseline that proves whether the complex model was worth its operational cost. If boosting only beats it by a fraction, the problem was linear and I ship the simple model.

What’s being tested

Engineering judgment, not knowledge. A 2026 favourite because it separates candidates who reach for the biggest model from candidates who think about total cost of ownership. Naming extrapolation is the detail few give.

Likely follow-up: “How do you decide the complexity was justified?” - set the bar before you look: a pre-agreed minimum lift on the business metric, not the offline metric, weighed against inference cost, retraining cadence, on-call burden and explainability obligations. Complexity should have to clear a threshold you wrote down in advance.
08Your model outputs one number. The business needs a range. How do you produce a trustworthy prediction interval?2026uncertaintyconformal＋
Strong answer

First separate the two intervals people confuse. A confidence interval covers the mean response at a given x; a prediction interval covers a single future observation and is therefore always wider, because it must also absorb the irreducible noise σ². The business almost always wants the prediction interval.

Three routes, in increasing order of how much I trust them. (1) The parametric formula - clean and instant, but it inherits every OLS assumption, so heteroscedasticity or non-normal errors make its coverage a fiction. (2) Bootstrap or quantile regression - refit on resamples for coefficient uncertainty, or fit the 5th and 95th conditional quantiles directly with a quantile loss, which handles the funnel-shaped-noise case honestly. (3) Split conformal prediction - the answer I would lead with in 2026: hold out a calibration set, compute the absolute residuals on it, take the empirical 90th percentile q, and emit ŷ ± q. That gives distribution-free marginal coverage guarantees under exchangeability alone, wraps any model including a boosted ensemble, and costs one extra data split.

Then I would state the catch, because it is the follow-up: conformal gives marginal coverage, not conditional - 90% overall can still mean 70% for one subgroup. Mondrian or group-conditional conformal fixes that per group, and exchangeability is broken by drift, so intervals need re-calibration on the same cadence as the model.

30-second version

Prediction interval, not confidence interval - it has to include the noise term. I would use split conformal: calibrate on held-out residuals, take the 90th percentile, emit ŷ ± q. Distribution-free, model-agnostic, one extra split. Caveat: coverage is marginal, so I would check it per subgroup too.

What’s being tested

Uncertainty quantification moved from “nice to have” to a standard 2026 question, largely because decision-support and agentic systems need to know when to abstain. Knowing conformal prediction - and knowing its marginal-coverage limitation - is a strong differentiator.

Likely follow-up: “How would you verify your intervals are actually correct?” - measure empirical coverage on a fresh time-forward holdout: what fraction of true values landed inside the nominal 90% band. Then slice that coverage by segment and by time. Coverage drifting below nominal is one of the earliest and most reliable drift alarms you can build.
09You have 2,000 rows and 50,000 features. What happens to OLS, and what do you do instead?high-dimensionalridgescenario＋
Strong answer

With d > n, XᵀX is a 50,000 × 50,000 matrix of rank at most 2,000 - singular, so the normal equation has no unique solution. In fact infinitely many weight vectors fit the training data with exactly zero error, which is the clearest possible statement of the problem: perfect training fit and no reason to expect any generalization at all. Practically, np.linalg.inv either raises or returns numerical garbage, while lstsq silently hands back the minimum-norm solution via SVD - worth knowing, because “it ran without error” is not the same as “it worked”.

What I would actually do, in order: ridge if I believe many features each contribute a little, because XᵀX + λI is invertible for any λ > 0; lasso or elastic net if I believe the truth is sparse and I want the model to pick features for me - elastic net specifically when features come in correlated groups, since pure lasso picks one arbitrarily from each group; dimensionality reduction (PCA, or a truncated SVD) if the features are dense and correlated rather than individually meaningful; or domain-driven feature selection, which usually beats all of the above. Whatever I pick, λ comes from cross-validation, and the selection step goes inside the CV fold or the reported score is leakage.

30-second version

XᵀX is singular, so infinitely many zero-training-error solutions exist - perfect fit, zero generalization. Ridge makes it invertible, lasso or elastic net if I expect sparsity, PCA if features are dense and correlated. λ by cross-validation, with selection inside the fold.

What’s being tested

Whether you connect a linear-algebra fact to a modelling decision, and whether you know that a library returning a number is not evidence of a well-posed problem.

Likely follow-up: “Why does adding λI fix invertibility?” - it shifts every eigenvalue of XᵀX up by λ. Zero eigenvalues become λ, so the matrix becomes positive definite and the inverse exists. Geometrically you have added a preference for smaller weights, which is what breaks the tie between the infinitely many perfect fits.
10A stakeholder sees “discount: +2.3” and wants to raise discounts. What do you say?2026communicationcausality＋
Strong answer

I would say what the number actually means and then name the gap they are about to fall into. It means: among historical rows, comparing two customers who match on every other feature in the model, the one with a one-unit higher discount had on average 2.3 units more of the target. It does not mean that raising a given customer's discount by one unit will produce 2.3 more.

The reason is that the coefficient is a description of the data-generating process we observed, and in that process discounts were not assigned at random - they were probably given to customers already likely to buy, or to close deals already in motion. That is confounding, and it can make the coefficient point the wrong way entirely. Two further caveats worth stating plainly: “holding all else constant” is fictional if discount is correlated with other features, and the estimate is only valid inside the range of discounts we have actually seen.

Then I would give them the path to the answer they want: an experiment. Randomise discount within a safe band on a slice of traffic, measure the effect directly, and if a live test is impossible, use a quasi-experimental design - difference-in-differences, an instrument, or a regression discontinuity if there is a policy threshold - and be explicit that it rests on assumptions. Ending on a route to the decision rather than on a refusal is the part that gets scored.

30-second version

It is an association among similar historical rows, not the effect of intervening. Discounts were not randomly assigned, so confounding can even flip the sign. If you want to act on it, run an experiment - randomise discount on a slice - or use a quasi-experimental design and state the assumptions.

What’s being tested

Two things at once: whether you know correlation is not causation at a level deeper than the slogan, and whether you can tell a stakeholder “no, but here is how to get to yes”. Communication rounds are explicitly scored in 2026 loops.

Likely follow-up: “Does the model being highly accurate make the coefficient more trustworthy?” - no, and this is the trap. Predictive accuracy and causal validity are independent. A model can predict beautifully off a pure proxy: umbrella sales predict rain very well and cause none of it.
11Offline R² is 0.82, but three months after launch the predictions are visibly worse. Debug it.2026MLOpsdebugging＋
Strong answer

I would work from cheapest-and-most-likely to most expensive, and I would not touch the model until I know which layer failed.

  1. Is it real? Confirm the degradation on the same metric, the same slice definition and the same aggregation as the offline number. A surprising share of these turn out to be a dashboard comparing different populations.
  2. Was the offline number ever honest? Look for leakage and for a random split on time-ordered data - an inflated 0.82 that never existed out of sample is the single most common cause. Re-score with a time-forward split.
  3. Training/serving skew. Compare the actual feature vectors served in production against training rows for the same entities. Different imputation defaults, a unit change, a stale join, a category the encoder never saw, a feature that is null at request time but was populated in the training table - this layer produces more incidents than genuine drift does.
  4. Which drift? Separate covariate drift (inputs moved: compare distributions, PSI or KS per feature, ranked by that feature's coefficient × its shift, since a big move in a near-zero-weight feature does not matter) from concept drift (the input–output relationship moved: same inputs, different target, which shows up as residuals developing a trend or a bias). For a linear model, refit on recent data and compare coefficients - a sign flip is concept drift stated bluntly.
  5. Feedback loop. Ask whether the model's own outputs changed the world it now sees. If low predicted demand caused less stocking, the next training set is contaminated by the previous model's decisions, and this is the failure mode that a naive retrain makes worse rather than better.

Fixes follow the diagnosis: skew is a data-contract and pipeline bug, covariate drift often only needs a refresh, concept drift needs a shorter retraining cadence or recency weighting, and a feedback loop needs logged randomised exploration so the training data still contains counterfactuals.

30-second version

Confirm it is real, then check whether the offline number was ever honest - leakage or a random split on time-series data. Then training/serving skew, which causes more incidents than drift. Then separate covariate from concept drift; for a linear model, refit on recent data and look for coefficient sign flips. Finally check for a feedback loop, because retraining makes that one worse.

What’s being tested

Production debugging under failure is now a standard round, and the signal is ordering - cheap checks first, model changes last. Candidates who open with “retrain it” lose the point immediately.

Likely follow-up: “What would you have monitored so this alerted in week one instead of month three?” - prediction distribution and per-feature input distributions daily; null and cardinality rates per feature as data contracts; residual mean and spread once labels land, sliced by segment; interval coverage if you emit intervals; and a permanently shadowed baseline model so you can tell “the world changed” from “our model broke”.
