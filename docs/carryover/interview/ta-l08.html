Two-minute answer - "How would you safely let an AI agent spend or refund money?"

🎤

"I'd start by not letting it. The tool's default is a dry run: it checks policy and returns a recommendation, and moving money needs an explicit flag plus a token. The safe path has to be the default, because the unsafe path eventually gets reached by an argument nobody validated.

Then five layers. Policy in code, not the prompt - a prompt policy is a suggestion a persuasive ticket can argue with. An idempotency key derived from the request, so a retry can't pay twice; derived, not a UUID per attempt, because a fresh key per attempt disables the mechanism you just built. An approval token bound to the exact order and amount, minted by a function the agent cannot call - a gate the caller can open itself isn't a gate. An append-only audit log including refusals, because a log of successes can't tell you the agent tried forty times. And caps on per-caller and daily amounts to bound the blast radius.

The order matters: policy and idempotency are checked before a human is asked, because asking someone to approve an impossible action trains them to click through - approval fatigue is a security failure.

The case I'd want to talk about is the timeout. If the payment call times out you don't know whether it happened. Retrying might double-pay, not retrying might strand the customer - and the idempotency key is what makes that decision safe in advance rather than at incident time. Almost none of this is AI-specific; it's payments engineering, and the only new part is a caller that may sincerely believe it hasn't already asked."

Q System design · Design an approval workflow for an agent taking customer-visible actions. ›

Tier by consequence, not uniformly - approving everything produces fatigue and fatigue produces rubber-stamping. Reversible and small: auto-execute with audit. Irreversible but bounded: single approver, token bound to the exact action. Above a threshold, or unusual: second approver.

Mechanics: the agent prepares a request containing the action, the amount, the policy verdict and the evidence it relied on - the reviewer needs to check the reasoning, not just click yes. Tokens are signed, scoped to one action, single-use, and expiring. The agent cannot mint them.

Then the parts that decide whether it works in practice: measure approval latency, because a gate that adds two days will be routed around; measure the approval rate, because 99% approvals means the gate is theatre and the threshold is wrong; and give reviewers a reject reason that feeds back into policy, so refusals improve the system instead of just stopping it.

Q Debugging · A customer was refunded twice. Walk me through the investigation. ›

Start at the audit log and count executed rows for that order. Two rows means two distinct requests reached execution; one row plus two provider payments means the provider was called twice for one request.

If two rows: compare the idempotency keys. Different keys means the requests genuinely differed - most likely the reason or the amount varied slightly, so a retry looked new. That is a key-derivation bug: too much variable material in the key. Same key with two rows means the duplicate check didn't run or the ledger write failed between them.

If one row and two payments: the failure is between us and the provider - a timeout followed by a retry at their end, which is what provider-side idempotency support exists for.

Then the systemic fix, which is the answer they want: make the payment and the ledger record one transaction, and add reconciliation against the provider so this is detected by a job rather than by a customer.

Q Coding · Implement idempotent refunds. ›

Derive a key by hashing the normalised request - uppercase the id, fix the amount to two decimals, lowercase and strip the reason. Check a durable store for that key before acting. If present, return the original outcome as a success with a duplicate flag. If absent, act, then record the key and the outcome - ideally in the same transaction as the action.

Say out loud: "derived, not random, or every retry looks new"; "the duplicate response is success, not an error, or callers build workarounds"; and "the record and the action need to be atomic, otherwise a crash between them re-opens the hole".

Q Senior follow-up · Where is your remaining exposure? ›

Name it before you are asked. The ledger is not transactional with the payment - a crash between them allows a double payment on retry. Tokens are in-memory and never expire, so a leaked token is a standing credential. No reconciliation, so a provider-side discrepancy is invisible until a customer complains. No aggregate caps, so nothing stops a hundred individually-valid refunds. And the audit log is append-only by convention, not enforcement - a file anyone can edit is not an audit trail.

Being able to enumerate your own gaps is a stronger signal than a clean-sounding design, because every real system has them and the question is whether you know where they are.

Q Senior follow-up · Would you ever let the agent refund without a human? ›

Yes, under conditions I'd state up front: a low amount cap, a category with an unambiguous policy (a confirmed duplicate charge is arithmetic, not judgement), full audit, aggregate daily limits, an anomaly alert, and a measured false-positive rate from evaluation before it ships.

The framing I'd use: the question isn't "human or not", it's "what is the cost of being wrong, times how often, versus the cost of the review". Approving thousands of £5 duplicate refunds by hand has its own failure mode - reviewers stop reading, and the gate becomes decorative while remaining expensive.

What I would not automate is anything requiring judgement about intent, anything above a threshold where a single error is material, or anything where the policy has ambiguity a model would have to resolve.
