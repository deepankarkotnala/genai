9 · Interview practice

Two-minute answer - "How do you defend an agent against prompt injection?"

🎤

"I'd start by saying what the boundary isn't: it isn't prompt wording. My primary defence is that the agent has no dangerous capability to hijack - no exec, no shell, no arbitrary file or network access - because no tool does those things. Capability absence, not filtering. An injection that succeeds perfectly still has nothing to invoke.

Then layers. Policy in code, so a persuasive ticket can't change what's permitted. Human approval on irreversible actions, so a successful injection still can't move money. Authorisation at the argument level against the request context - never against anything the model said, or an injection just claims to be an admin, which is the confused-deputy bug. Output checks for leaked secrets and fabricated citations, because the reply is itself an exfiltration channel.

Keyword screening comes last. I keep it for logging and as an intrusion signal, but it's trivially bypassed - I have a test showing the same intent reworded sails through, and another that disables the screen entirely and shows the money attacks still fail. That's how I know which layer is actually load-bearing.

The distinction I'd stress is indirect injection: content arriving through my own trusted retriever. The tool's output shape is trusted because my code made it; the content is only as trusted as its source. And the reason this is hard rather than just new is that there's no parameterised query for natural language - no way to separate instructions from data - which is exactly why the answer has to be architectural."

Q System design · Secure an agent with access to email, calendar and a CRM for 10,000 employees. ›

Start from blast radius, because email plus CRM is the classic exfiltration pair: read a document, send it out. I'd separate read and write into different agents with different permissions, and require approval for any outbound send to an external address.

Identity and scope: the agent acts as the requesting user, never as a service account with union permissions - otherwise one injection reads everyone's mail. Every tool call is authorised against that user's actual entitlements at the argument level.

Egress control: allowlist recipient domains; treat any address the model produced as untrusted; make "send to an external party" a distinct, approved capability.

Indirect injection is the main threat here - an attacker emails the employee, the agent reads it, the instruction executes with the employee's authority. So content from inbound email is untrusted at the same level as a web page, marked structurally, and never allowed to trigger a write without approval.

Then detection: log flagged content, alert on unusual read volume or recipients, and rate-limit. At 10,000 employees the question isn't whether someone gets injected, it's how fast you see it.

Q Debugging · A document in your knowledge base contains instructions. How do you find out whether it was ever acted on? ›

You need three things joined together, and if you don't have them the honest answer is "I can't tell", which is itself the finding.

Retrieval logs: which runs retrieved that chunk id, and when - chunk-level citations from Lesson 5 are what make this answerable at all. The audit log: which of those runs then attempted an action, and what the outcome was. Trace correlation: a request id linking the two, which is Lesson 11.

Then assess exposure: if the poisoned text asked for something the agent has no capability for, it was inert. If it asked for something gated by approval, check whether any approval was granted in those runs - and if one was, the more serious question is whether the reviewer saw the poisoned text in the request.

Containment: remove the document, re-index, and add a provenance check on ingestion so anyone can see who added it.

Q Coding · Implement argument-level authorisation. ›

Signature authorise(tool, args, context) -> (bool, reason). Permissions come from context, which the caller supplies. Check tool membership in an allowlist, then per-tool argument rules: scope containment for identifiers, numeric caps for amounts, and separate permissions for prepare versus execute.

Say while writing: "permissions never come from the model's arguments" - and add the negative test where an injected role: supervisor changes nothing. Also return a reason, so a refusal is debuggable and can be shown to the user without leaking policy internals.

Q Senior follow-up · Is prompt injection solvable? ›

Not in the general case, and I'd say so plainly. There is no parameterised query for natural language - no mechanism that separates instruction from data the way prepared statements separate code from values. Any defence at the text layer is heuristic, so a sufficiently novel phrasing gets through.

What is solvable is the consequence. If a successful injection can only cause things you would have been willing to let a hostile user do, you have contained it. That reframes the goal from "prevent the model being fooled" to "ensure being fooled doesn't matter" - capability restriction, approval gates, per-argument authorisation, and bounded blast radius.

Which is also why I don't rate "we added an injection classifier" as an answer on its own. It reduces frequency; it doesn't change what happens when it fails.

Q Senior follow-up · Your security review has one hour. What do you look at? ›

The tool list, first and longest. It is the complete enumeration of what the agent can do, and therefore of what any attack can achieve. Anything that executes, writes, sends or reaches the network gets scrutiny; everything else is comparatively cheap.

Then: where business policy lives (code or prompt - if prompt, stop and fix that); whether irreversible actions are gated and whether the agent can mint its own approval; whether authorisation reads the request context or model output; what enters the prompt from untrusted sources and how it is marked; what the output path can leak.

I would not spend the hour reading the system prompt for missing instructions. That is the layer that matters least, and it is where reviews tend to go because it is the easiest thing to read.
