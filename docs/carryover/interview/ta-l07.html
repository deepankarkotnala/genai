Two-minute answer - "Your agent loops forever in production. Diagnose and fix it."

🎤

"First, is it bounded at all? If termination depends on the model choosing to stop, it isn't - so a step limit is the actual bound and I'd check that exists before anything else.

Then I'd get the trace and look at the sequence rather than the output. Four patterns. Identical repeats: same tool, same arguments - usually a failing tool whose error the agent can't act on, or state that conflates 'not tried' with 'tried and failed'. Oscillation: A, B, A, B - contradictory instructions, and it's invisible to a check that only compares against the previous call. Drift: plausible but unrelated calls, which is context dilution, so compaction and a tighter budget. Missing termination: it has the answer and keeps going, because nothing told it what done looks like.

The fixes are a repeat counter keyed on tool-plus-arguments, a cycle check over a small window, and tracking attempted calls separately from successful ones. Both controls have to fire well before the step budget - a limit that only trips after you've paid for the run isn't protecting you.

And the honest answer underneath: 40 steps means the budget was set too high, or the tools are too fine-grained. Fewer, coarser tools and a realistic budget prevent more incidents than better loop detection does."

Q System design · Design reliability for an agent calling five internal services with different SLAs. ›

Per-tool policy, not one global setting - a 50ms cache lookup and a 3s report generator cannot share a timeout. For each: a timeout from that service's p99, a retry budget (and only for transient classes), and a fallback that is either degraded data or escalation.

Then the system-level parts. Circuit breaker per dependency, so a dead service is not retried by every concurrent run - otherwise your retries become its outage. A total budget for the run in wall-clock and cost, because five well-behaved timeouts still add up past a user's patience. Bulkheads so one slow tool cannot exhaust the pool every tool shares. Idempotency on anything with side effects.

Then observability: outcome ratios per tool, retry rates, and alerting on the escalation rate rather than on errors, since a healthy-looking agent that escalates 60% of tickets is broken in a way no error count shows.

Q Debugging · A tool call times out. Did it happen? ›

You don't know - and that is the correct answer. A timeout means you stopped waiting, not that the work stopped. For a read that's merely wasteful. For anything with side effects it is the hardest case in the lesson.

So you design for it in advance rather than resolving it after: an idempotency key derived from the request means a follow-up call is safe whichever way the first one landed. Absent that, your only options are to risk a double effect or to strand the request - and choosing between them at incident time, with a customer waiting, is how mistakes get made.

Also: don't retry the timeout itself. Two slow calls are worse than one. Check state, then act.

Q Coding · Add loop detection to an agent. ›

Compute a stable signature per call - tool name plus arguments serialised with sorted keys, so argument ordering doesn't create false novelty. Count signatures; block above a small threshold. Separately keep a window of recent signatures and check for an A,B,A,B cycle. On either, terminate with a named outcome and a reason, not an exception.

Details that signal experience: sorted-key serialisation; a threshold above 1, because a legitimate retry exists; blocking well before the step budget; and recording which control fired, so the trace explains itself.

Q Senior follow-up · How do you decide the retry budget and backoff? ›

From the dependency's failure profile, not a default. Transient network blips justify two or three attempts with exponential backoff and jitter - jitter matters, because synchronised retries from many concurrent runs are a thundering herd. Anything non-transient gets zero retries.

Then the constraint people miss: the retry budget interacts with the user's latency budget. Three attempts with backoff on a 2s timeout is potentially 6s of one step in a run that has a total budget. Retries have to be spent from the same pot as everything else, otherwise a resilient agent is an unusably slow one.

And measure the retry rate. A steady 30% success-after-retry is a broken dependency masquerading as a healthy agent.

Q Senior follow-up · Should the agent recover automatically from a failing tool? ›

Rarely, and never silently. Substituting a different tool, or proceeding on partial data, means producing an answer on foundations you did not verify - and the answer will not carry a warning label by the time a customer reads it.

The tiered approach: retry transient failures; degrade explicitly where degradation is meaningful and say so in the output; otherwise escalate. What I would not do is let the agent invent a workaround, because that converts a visible failure into an invisible one. Our partial-data bug is the small version - refund_eligible=None formatted into a sentence that read as fact.
