01Explain the difference between parametric and non-parametric models, with trade-offs.taxonomycapacity＋
Strong answer

A parametric model commits to a fixed-size parameter vector, so complexity is independent of training-set size; a non-parametric model’s effective complexity grows with the data. Linear and logistic regression and fixed-architecture neural networks are parametric; KNN, decision trees, Random Forests and kernel SVMs are non-parametric. Parametric models are sample-efficient, fast to train and predict and easy to interpret, but badly biased if the assumed form is wrong. Non-parametric models approximate arbitrary functions with no functional assumption, but need more data, cost more at inference, and overfit readily without explicit control - depth limits, pruning, k.

30-second version

Parametric means model size is fixed regardless of n; non-parametric means it grows with n. Structure and sample-efficiency versus flexibility and data hunger.

What’s being tested

Vocabulary precision, and whether you can attach real trade-offs to a label rather than reciting a definition.

Likely follow-up: “Is a neural network parametric?” - for a fixed architecture, yes. The interesting nuance is that with enough capacity it behaves like a non-parametric learner in practice, which is why explicit regularization matters so much.
02Discriminative vs generative models. Which would you use, and when?taxonomygenerativeGenAI＋
Strong answer

Discriminative models estimate P(y|x) or just the boundary; generative models estimate the joint P(x,y), usually via P(x|y)P(y), then apply Bayes to classify. Discriminative: logistic regression, SVM, trees, boosting, most neural classifiers. Generative: Naive Bayes, Gaussian discriminant analysis, mixture models - and in the modern sense LLMs and diffusion models. Choose generative when data is scarce (the stronger assumptions act as regularization), when you need to sample or detect out-of-distribution inputs, or when features go missing at inference. Choose discriminative when you have plentiful labels and only care about predictive accuracy, since all capacity goes to the decision boundary rather than modelling the full input distribution.

30-second version

Discriminative learns the boundary P(y|x); generative models the joint and applies Bayes. Generative for scarce data, sampling and missing features; discriminative for raw accuracy with plenty of labels.

What’s being tested

Whether you can connect classical taxonomy to the generative-model era - a very common 2026 bridge question.

Likely follow-up: “Where does an LLM sit?” - it is a generative model of token sequences trained by maximum likelihood on next-token prediction, that can be used discriminatively by prompting it to classify. That gap between how it is trained and how it is used explains much of its calibration trouble.
03Which algorithms require feature scaling, and why?scalingpreprocessingtrap＋
Strong answer

Scaling matters whenever the algorithm depends on distances, dot products or the geometry of the loss surface.

Required: KNN, K-Means, SVM with any kernel, PCA, and any regularized linear model - because a shared penalty λ is only fair across coefficients if the features share a scale. Strongly recommended: anything trained by gradient descent, including neural networks, since unscaled features produce an ill-conditioned loss surface and slow, zig-zagging convergence. Not needed: decision trees and all tree ensembles, because each split is a threshold test within one feature and is invariant to monotone rescaling.

The general principle: scaling matters exactly when features are combined into a single quantity; trees never combine them.

30-second version

Anything using distances, dot products or a loss surface: KNN, K-Means, SVM, PCA, regularized linear, neural nets. Not trees - a split is a threshold within one feature.

What’s being tested

A high-frequency question with a crisp right answer. The trap is candidates who say “always scale”, which reveals rote practice.

Likely follow-up: “Standardization or min-max?” - standardization by default and it is more robust to outliers; min-max when you need a bounded range; RobustScaler with heavy outliers. Always fit the scaler on training data only.
04New tabular dataset: 500k rows, 80 mixed-type features, binary target at 4% positive. What is your model plan?appliedplanningimbalance＋
Strong answer

Sequence it from cheapest to most complex. (1) Establish a trivial baseline - majority class and a single-feature rule - so every later number has a reference. (2) Fit a regularized logistic regression for an interpretable, fast benchmark and a sanity check that signal exists. (3) Fit gradient-boosted trees as the expected winner on tabular data: mixed types, non-linearities, interactions, and native missing-value handling. (4) Because the target is 4% positive, evaluate with PR-AUC and a business-cost-driven threshold - not accuracy, and not ROC-AUC alone. (5) Use stratified K-fold, or time-based splits if there is any temporal component. (6) Only then consider stacking or a neural approach, and only if the boosted model plateaus.

30-second version

Baseline, then regularized logistic regression, then gradient boosting. Because it is 4% positive, PR-AUC and a cost-based threshold rather than accuracy, on a stratified or time-based split.

What’s being tested

Whether you work in order of increasing complexity, and whether you noticed the 4% and adjusted your metrics. Candidates who jump straight to a neural network fail.

Likely follow-up: “What if it were 5,000 rows instead of 500k?” - shift toward regularized linear models and shallower ensembles, use repeated cross-validation because estimate variance dominates, and be far more conservative about feature count.
2026 additions. Algorithm-choice questions are now posed as constrained scenarios - few labels, latency budgets, tabular-versus-foundation-model decisions - rather than as taxonomy recall.
05You have 5 million rows and a budget to label 500 of them. What is your plan?2026semi-supervisedactive learning＋
Strong answer

The scarce resource is labels, so the plan is designed around spending them well rather than around picking a model.

First, do not spend all 500 at once. Label a small random sample - say 150 - for two reasons: it establishes the class balance and it becomes an unbiased evaluation set. That second point matters most; if every label you own was chosen because the model found it interesting, you have no honest way to measure anything.

Second, use the 5 million rows for representation, not for labels. Unsupervised structure is free: embeddings, an autoencoder, or for text a pretrained encoder. Then a simple model on top of good representations needs far fewer labels than a complex model on raw features. With 500 labels I would be fitting regularised logistic regression, not a deep network.

Third, spend the remaining labels with active learning. Train on what you have, score the unlabelled pool, and label where the model is least certain - near the decision boundary - or where a small committee of models disagrees. Diversity matters too: pure uncertainty sampling will hand you 350 near-duplicates from one dense region, so cluster the candidates and sample across clusters. In 2026 there is a fourth practical option worth naming: use an LLM to produce weak labels at scale, treat them as noisy, and spend the human budget on auditing and correcting that weak labelling rather than on labelling from scratch - programmatic weak supervision with a human in the verification loop.

30-second version

Reserve a random slice as an unbiased eval set first. Use the 5 million unlabelled rows for representations, then a simple regularised model on top. Spend the remaining budget with active learning - uncertainty sampling plus clustering for diversity. Consider LLM weak labels with humans auditing rather than labelling.

What’s being tested

Whether you treat labels as a budget. The tell of a strong candidate is reserving an unbiased evaluation set before any active learning - most candidates spend all 500 on training and then cannot measure anything.

Likely follow-up: “What is the risk of active learning?” - the training set becomes deliberately unrepresentative, concentrated near the boundary. That biases any estimate of calibration and prevalence, breaks the i.i.d. assumption behind your CV, and can lock in a blind spot if early model errors steer which points you ever look at. Keep the random eval set separate and never train on it.
06For a tabular business problem in 2026, would you reach for a tabular foundation model or gradient boosting?2026tabularjudgment＋
Strong answer

Gradient boosting remains my default, and I would want a specific reason to deviate. On tabular data the inductive bias of trees - axis-aligned splits, no assumption of smoothness, native handling of mixed types, monotone-transform invariance - matches how tabular features actually behave, and boosting has no rival on cost, training time, or tooling maturity.

The genuine exception is small data. Tabular in-context models trained on synthetic priors are strong in the regime of roughly a few thousand rows and modest feature counts, precisely because they bring a prior where you have too little data to learn one. So my rule is: under a few thousand rows, benchmark one against boosting, because it may win outright and it costs an afternoon. Above that, boosting.

Where foundation models genuinely change my architecture is not as a replacement but as a feature source. If rows contain free text, images or messy categorical soup, I use a pretrained encoder to turn that into embeddings or extracted attributes and feed those into the boosted model alongside the numeric columns. That hybrid is the architecture that wins in practice, and describing it is a stronger answer than choosing a side.

30-second version

Boosting by default - tree inductive bias fits tabular data and the tooling is mature. Exception: with a few thousand rows or fewer, a tabular in-context model brings a prior I cannot learn, so I would benchmark it. And the real win is hybrid - a pretrained encoder turning text into features for the boosted model.

What’s being tested

Whether you follow hype or follow the data regime. Naming the small-data exception and the hybrid pattern shows you have actually thought about it rather than picking a camp.

Likely follow-up: “What would make you rule the foundation model out regardless?” - a strict latency or cost budget, an on-premise or air-gapped deployment, feature counts or row counts outside the regime it was trained for, or a regulatory requirement for a model whose decision path can be audited feature by feature.
07You have a 10 ms p99 inference budget. Which algorithms does that eliminate, and why?2026latencydeployment＋
Strong answer

I would split the budget first, because the model rarely owns all 10 ms - feature fetching, network hops and serialisation usually take more than scoring does. If feature lookup costs 6 ms, the model has 4, and that reframes the whole question: the constraint often eliminates features before it eliminates algorithms.

What the budget rules out follows from where each algorithm does its work. KNN is out as a lazy learner - it defers all computation to prediction time and must search the training set; an approximate index makes it feasible but you are now maintaining an index. Kernel SVM is out at scale, since prediction costs a kernel evaluation against every support vector, and support vectors grow with the dataset. Very large boosted ensembles are borderline - 2,000 deep trees traversed sequentially adds up, though this is fixable by capping trees, capping depth, or compiling the ensemble to native code. Anything requiring a remote call per prediction - an LLM in the hot path - is out unless it is cached or moved offline.

What survives comfortably: linear and logistic regression (a dot product), Naive Bayes, a modest boosted ensemble, a small quantised network. And the architectural answer that usually wins: precompute. If predictions can be batch-scored offline and served from a key-value store, the model's complexity stops mattering; if only some features are slow, precompute those. Finally, a two-stage design - a very cheap model filtering everything, an expensive one on the small surviving set - buys accuracy inside a tight average budget.

30-second version

First split the budget: feature fetch usually costs more than scoring, so the constraint may cut features rather than models. It rules out KNN and kernel SVM, which defer work to prediction time, and anything with a remote call per request. Linear models, Naive Bayes and a capped boosted ensemble survive - and precomputing offline or a cheap-then-expensive two-stage design usually beats shrinking the model.

What’s being tested

Whether you reason about where an algorithm spends its compute - fit time versus predict time - instead of memorising a speed ranking. The precompute and two-stage answers show system thinking.

Likely follow-up: “p99, not average - does that change anything?” - substantially. Tail latency is dominated by variance, not the mean: cache misses, garbage collection, a slow feature store, and per-request work that scales with input size. You would enforce timeouts with a documented fallback prediction, avoid unbounded per-request loops, keep the model's work data-independent, and load-test at the tail rather than the average.
