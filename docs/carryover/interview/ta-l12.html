Two-minute answer - "What problem does MCP solve?"

🎤

"Before MCP, every host application had its own tool format, so N hosts and M tool providers meant N times M integrations. MCP standardises the contract so it becomes N plus M - each host speaks it once, each provider implements it once. It's USB for tools.

Three roles: the host is the application the user talks to, the client lives inside the host and speaks to one server, the server exposes tools, resources and prompts. Worth being precise that the model never speaks MCP - the host does, and passes the discovered tools into the prompt.

The value is run-time discovery: the host calls tools/list and learns names, descriptions and JSON Schemas rather than having them hard-coded, so the tool set can differ per user or per installation.

Where I'd push back is adopting it by default. If my agent always calls the same three internal services, MCP is a protocol layer buying nothing - I'd call them directly. It earns its place when the tool set isn't known at build time.

And the security point I'd lead with: tool descriptions are prompt content written by the server. A third-party server has a text channel into my model, which is indirect injection with a supply-chain delivery route. So I review MCP servers like dependencies, pin their versions, and authorise every call against the caller rather than trusting the server's credentials."

Q System design · Expose your company's internal tools to several AI applications. Design it. ›

One MCP server per bounded domain rather than one giant server - tickets, orders, knowledge base - so permissions and ownership follow team boundaries and a compromise is contained.

Split read from write. Read-only servers are cheap to expose widely. Write servers get their own review, their own approval gates and a much shorter list of permitted clients. I'd default to publishing reads and keeping anything irreversible in-process, which is the decision our own server makes about issue_refund.

Authorisation per request against the calling user's identity, not the server's credentials - otherwise you have built a confused deputy with a database key. Argument-level checks, not just tool-level.

Then: pinned versions with a deprecation policy, since a schema change breaks every client; audit logging with the caller identity and a correlation id; rate limits per client; and a golden set per server so a behaviour change without a schema change is caught.

The thing I'd raise unprompted is aggregation: once several servers are connected, the model sees the union of their tools, and individually safe capabilities compose into unsafe ones. Someone has to own the composite surface, because no individual server can see it.

Q Debugging · An agent works in-process but misbehaves through MCP. Where do you look? ›

First: are the tool schemas actually identical? If the server returns a hand-written copy rather than the same objects the agent uses, they have drifted - that is the most common cause and the reason we have a test asserting equality.

Then the descriptions, since they drive selection: if the MCP path sends different or reordered descriptions, the model makes different choices for reasons invisible in the code.

Then the tool set. MCP exposes a subset, so an agent that relied on a withheld tool now behaves differently - and correctly. Check whether the missing capability explains the symptom before assuming a bug.

Then results: MCP wraps them in content blocks, so a client that forgets to unwrap gives the model a JSON envelope instead of data. And check error mapping - an invalid_params the agent used to receive as a recoverable observation may now surface as a transport failure.

Q Coding · Implement a minimal MCP server. ›

JSON-RPC 2.0 dispatch over three methods: initialize, tools/list, tools/call. Validate the envelope, return standard error codes, treat a request with no id as a notification and answer nothing, require the handshake before anything else, and return tool results as content blocks.

Details that signal experience: an allowlist rather than a deny-list; the same schema objects your in-process agent uses; no tracebacks across the boundary; and an error message for a withheld tool that does not reveal it exists.

Q Senior follow-up · Would you connect to a third-party MCP server in production? ›

Only with the same rigour as any dependency, plus one extra concern that has no precedent: its tool descriptions land in my prompt. That is an injection channel the vendor controls, so I would read them, pin the version, and diff them on upgrade.

Practically: run it in a sandbox with least privilege - a local stdio server has my filesystem, which is easy to forget; allowlist the specific tools I want rather than accepting everything it offers; require approval for anything irreversible regardless of what it claims; and monitor for behaviour changes with a golden set, since a schema-stable server can change what it does.

What I would not do is connect a server that offers write capabilities into a flow that can reach money without a human. The composite surface is the risk, and no individual vendor is looking at it.

Q Senior follow-up · You withheld a tool from your own MCP server. Justify it. ›

The safety properties around issue_refund - policy in code, idempotency, the approval gate - live in my process. The protocol gives me no way to require a client to honour them, and a tool exposed over MCP is callable by any host that connects, including ones written after I left.

The asymmetry decides it: exposing it saves a small amount of integration work, and the downside is an unapproved payment. So reads cross the boundary and money does not, and anything needing the refund path calls my service, where the gate is.

I would also say what would change my mind: if MCP grew a way to bind a capability to a required approval flow, or if I could cryptographically constrain callers, the calculation shifts. Until then, withholding is the cheaper mistake.
