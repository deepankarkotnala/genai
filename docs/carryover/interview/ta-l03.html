Two-minute answer - "How does tool calling actually work?"

🎤

"I send the model a list of tool declarations - name, description, JSON Schema for the parameters - alongside the conversation. The model doesn't call anything; it emits a structured request naming a tool and its arguments. My code decides whether to honour it, runs the function, and appends the result as a tool message so the next decision can use it.

Two things I'd stress. The description is part of the prompt - the model never sees my code, so when a tool is picked wrongly I fix the description first. And validation is my job in two layers: schema validation for shape, then semantic validation inside the tool, because a schema-valid call can name a record that doesn't exist. Constrained decoding guarantees shape, never meaning.

Dispatch is a dictionary lookup against a fixed registry - no eval, no getattr on a model-supplied name - so a hallucinated tool is a clean error I feed back rather than an incident."

Q System design · Design the tool layer for an agent with access to 30 internal APIs. ›

Don't expose 30 tools. Selection accuracy degrades as the set grows, and the declarations alone eat the context window.

Group them by task into 5–8 coarse tools, each with a tight schema, and split by agent role rather than by API - a triage agent needs read tools; a refund specialist needs the refund path (Lesson 13). Add a discovery tool for the long tail if you need it: one list_capabilities the agent can call, so rarely-used APIs aren't in every prompt.

Then the governance points: least privilege per tool with authorisation at the argument level, not just the tool level - "may read orders" isn't the same as "may read this customer's orders". Separate read from write and gate writes behind approval. Version the declarations. And put every call through one dispatch function so validation, authorisation, timeouts and tracing exist in exactly one place.

Q Debugging · The agent keeps calling search_kb with an empty query. Diagnose. ›

Order of investigation. Does the schema require query and enforce a minLength? If not, an empty string is legal and the fault is mine, not the model's. Does the description say what a good query looks like? "Query with a topic such as 'billing', 'refund', 'shipping'" prevents this; "search the KB" does not. Is the error message actionable - if it says "invalid input", the model has nothing to repair from.

Then: is it repeating because the result is unusable? An empty result with no explanation invites a retry; returning note: "no matching article" lets the agent conclude nothing matched and move on. And is the goal even answerable from the KB - if not, the right behaviour is escalation, which means the agent needs an escalation path to choose instead (Lesson 7).

Note the shape of that answer: three of the four causes are mine.

Q Coding · Write an argument validator for a tool schema. No libraries. ›

Cover: unexpected keys when additionalProperties: false; missing required keys; type checks with a JSON-to-Python type map; minimum/maximum for numbers; minLength/enum for strings; return a cleaned copy rather than mutating the input.

Two details that mark experience: reject bool where a number is expected, because isinstance(True, int) is True in Python and silent coercion hides bugs; and collect all faults before raising, since a typo produces both an unexpected key and a missing one.

Q Senior follow-up · A tool result contains text that looks like an instruction. What do you do? ›

Name the boundary first: tool output shape is trusted because my code produced it; tool output content is only as trusted as its source. A ticket body is untrusted regardless of arriving through my own function.

Then layered defences, strongest first. Architectural: the agent has no dangerous capability to invoke, so most injections are inert - this is the real boundary. Authorisation: check permissions at the argument level against the request context, never against anything the model said. Approval: irreversible actions need a human, so a successful injection still cannot move money. Structural: mark untrusted spans in the prompt so instructions and data are visually distinct. Detection: keyword screening - useful, easily bypassed, never the primary control.

The senior-level part is being explicit that prompt wording is defence in depth and capability restriction is the boundary. Anyone answering only "I'd add instructions telling it to ignore that" has not thought about it.

Q Senior follow-up · How do you version tool schemas once agents depend on them? ›

Treat a declaration as a public API contract with a probabilistic client. Additive changes - a new optional parameter - are safe. Renaming or removing a parameter, or tightening a constraint, is breaking: run both versions side by side, migrate, then retire.

The part people miss: changing the description is a behavioural change even when the schema is identical. It alters selection. So descriptions belong under the same review and evaluation as prompts, and a wording edit should run the golden set before it ships (Lessons 10 and 14).
