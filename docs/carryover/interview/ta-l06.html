9 · Interview practice

Two-minute answer - "Your agent hits the context limit mid-run. What do you do?"

🎤

"First I'd find out why, because there are two different problems. Either one tool result is enormous, or many small ones have accumulated - and they need opposite fixes.

For a single oversized result, cap it at the source: truncate before it enters the transcript and record that you did. Compaction can't help there, because compaction deliberately keeps recent messages verbatim and the newest message is the problem.

For accumulation, compact: keep the system prompt, keep the goal, keep the last couple of turns, and replace the middle with one summary line per tool that ran. Keeping the goal is the part people get wrong - drop it and the agent is answering a question it can no longer see. And I'd guard the compaction: if the summary isn't smaller than the span it replaces, skip it, because otherwise you pay a model call to grow the prompt.

Longer term I'd reduce what enters the context at all - tighter tool results, fewer steps via routing - since managing a budget is better than repeatedly rescuing it. And I'd track a budget in tokens as well as steps, because one expensive call can cost more than five cheap ones."

Q System design · Design memory for a support agent handling repeat customers across months. ›

Separate the stores by lifetime and by who owns them. Run state: ephemeral, persisted only for crash recovery, deleted on completion. Ticket history: already your system of record - query it, do not copy it into a second store that can disagree with it. Customer profile: a small, explicit, human-auditable set of durable facts (preferred language, accessibility needs, tier). Written by rule, not by model whim.

Then the parts that make it real. Write policy: what earns a place in the profile, and who can correct it - an agent that writes "customer is abusive" from one bad exchange has created a durable, wrong, consequential record. Retention and deletion: a subject-access or deletion request must reach every store, which is an argument for fewer stores. Tenant isolation: memory keyed so cross-customer leakage is structurally impossible, not merely filtered. Injection: anything written from ticket text is attacker-controlled - Lesson 9.

Say what you would not build: freeform model-written memories, because the failure mode is confident false recall and there is no cheap way to detect it.

Q Debugging · At step 15 the agent starts making unrelated tool calls. Diagnose. ›

Classic context dilution. Get the actual prompt at step 15 and measure the ratio: how many tokens are the goal and instructions, and how many are accumulated tool output? If the goal is 2% of the prompt, the model is not ignoring it - it is outvoted.

Check in order: is compaction running at all; is it keeping the goal; is one tool returning far more than the others; has the transcript been truncated by the provider rather than by you - because provider-side truncation usually drops the oldest messages, which is where your system prompt lives.

Then the structural answer: 15 steps for this task probably means the step budget is too generous and the tools too fine-grained. Coarser tools and routing reduce steps, and fewer steps is a better fix than better compaction.

Q Coding · Implement transcript compaction. ›

Partition the messages into system, goal, recent tail, and middle. Summarise the middle to one line per tool result. Reassemble in order. Return a description of what happened, and guard: if the result is not smaller, do not apply it.

Details that signal experience: keep the goal explicitly (not "the first message"); count tokens before and after and report both; record how many compactions have happened, because a run compacting five times is telling you something about your tool sizes; and make the summariser's parsing failure loud rather than silently falling back to raw truncation.

Q Senior follow-up · Should the agent write its own memories? ›

Rarely, and never without a correction path. The appeal is obvious; the failure mode is a durable false belief that shapes every future interaction and that nobody knows to look for. In support, a wrong memory about a customer is worse than no memory, because it produces confidently wrong personalisation.

If it must happen: constrain writes to a fixed schema rather than freeform text, require a confidence threshold or human confirmation for anything consequential, timestamp and source every entry so it can be audited, expire entries by default, and make deletion trivial. And measure it - treat recall precision as an eval metric, not an assumption.

Q Senior follow-up · Bigger context windows are coming. Does this lesson stop mattering? ›

No, for three reasons. Cost scales with tokens, so a 1M-token window you actually fill is a bill, not a feature. Attention degrades over long contexts - models reliably lose material in the middle, so a fact present in the prompt is not a fact used. And latency rises with prompt size, which users feel.

What changes is the threshold at which you intervene, not the discipline. The framing that survives: context is a budget you spend deliberately, and the question is always "does this token earn its place", not "does it fit".
