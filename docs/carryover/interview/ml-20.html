01Why is random search usually better than grid search?random searchBergstratrap＋
Strong answer

Because hyperparameter importance is highly uneven, and grid search wastes budget on the unimportant ones. With d hyperparameters and m values each, a grid requires m^d fits and evaluates every combination of values for parameters that barely affect performance - so if only two of six parameters matter, most of your compute produces near-identical results. Random search with the same number of fits samples N distinct values for every parameter, exploring the important dimensions much more finely; this is the Bergstra–Bengio result, and the advantage grows with dimensionality.

There is also a clean probabilistic argument: to land within the top 5% of the search space with 95% confidence requires roughly 60 random samples, independent of the number of dimensions.

Practical additions: random search handles continuous parameters naturally rather than forcing discretization, and it can be stopped at any point with a valid result, whereas a partially completed grid is systematically biased toward whichever corner it started in.

30-second version

Importance is uneven, and a grid burns m^d fits re-testing parameters that do not matter. Random search samples N distinct values per parameter, exploring the important dimensions finely - and ~60 draws reach the top 5% regardless of dimension.

What’s being tested

Whether you know the standard result and can explain the mechanism. The “60 samples for top 5%” figure is memorable and lands well.

02What is Bayesian optimization and when is it worth it?Bayesian optimizationOptunaTPE＋
Strong answer

It builds a probabilistic surrogate model of the objective - a Gaussian process, or a tree-structured Parzen estimator in TPE - mapping hyperparameter configurations to validation score, then chooses the next configuration by maximizing an acquisition function such as expected improvement, trading off exploiting regions the surrogate predicts are good against exploring regions where it is uncertain. Each evaluation updates the surrogate, so the search gets progressively better informed - unlike random search, which never learns from its own results.

It is worth it when each fit is expensive - hours of training, large data, deep models - so sample efficiency dominates, and when the search space is moderately high-dimensional.

It is not worth it when fits are cheap, since the surrogate’s overhead and sequential dependency can cost more than they save, or when you have massive parallelism, since random search parallelizes perfectly while Bayesian optimization is inherently sequential. In practice I would use Optuna, which defaults to TPE and combines it with pruning - an implementation of successive halving killing unpromising trials early, which is often a bigger win than the surrogate itself.

30-second version

A surrogate model of the objective plus an acquisition function choosing where to sample next, so the search learns from its own results. Worth it for expensive fits; not when fits are cheap or you have massive parallelism.

What’s being tested

Whether you understand the mechanism and, more importantly, when not to use it. The Optuna pruning point shows real usage.

03Can hyperparameter tuning overfit?multiple comparisonsnested CVtrap＋
Strong answer

Yes, and it is a genuine and underappreciated problem. If you evaluate 500 configurations by cross-validation and select the best, that best score is partly real quality and partly the luck of which configuration happened to suit your particular folds - you have taken a maximum over 500 noisy estimates, and the maximum of noisy estimates is systematically biased upward. It is a multiple-comparisons problem, and the bias grows with the number of configurations tried and shrinks with dataset size.

Three consequences: the winning configuration’s CV score must never be reported as an unbiased performance estimate; you need either a final untouched test set or nested cross-validation for an honest number; and on small datasets a very large search can actively hurt you, since it will find a configuration tuned to fold-level noise.

Mitigations: prefer smaller search spaces informed by domain knowledge, use repeated CV to reduce estimate variance so selection is less noise-driven, prefer simpler configurations when scores are within noise of each other (the one-standard-error rule), and always keep a final holdout you look at exactly once.

30-second version

Yes - taking the max over many noisy CV estimates is upward-biased, so the winning score is not unbiased. Use nested CV or an untouched holdout, and prefer smaller informed search spaces.

What’s being tested

Whether you understand that model selection is itself a fitting procedure. A strong mid-to-senior differentiator, connecting back to Module 05’s nested-CV question.

04You have 4 hours of compute. How do you spend it to improve a model?prioritizationappliedtrap＋
Strong answer

Mostly not on hyperparameter tuning, and I would say so explicitly.

  1. First 30 minutes verifying the evaluation - is the split leaking, is it time- or group-aware, is the metric right? Everything downstream is worthless if this is wrong, and a leak found here is worth more than any tuning.
  2. Next 2 hours on data and features - investigate the largest errors to see what the model is systematically missing, add features encoding real domain structure, fix data-quality problems, reconsider the target definition. By far the highest expected return.
  3. Then 1 hour on model and tuning - try two or three model families with defaults, then a random or Optuna search with successive halving over the parameters that matter most, with early stopping handling n_estimators for free.
  4. Final 30 minutes on the decision layer - threshold selection from business cost, and calibration. Often the single cheapest large improvement in realized business value, and frequently ignored entirely.

If the model is still short after that, the honest conclusion is usually that I need better data or a different target definition, not more compute.

30-second version

30 minutes verifying the evaluation, 2 hours on data and features, 1 hour on model choice and tuning, 30 minutes on threshold and calibration. Tuning is the smallest slice for a reason.

What’s being tested

Prioritization. Candidates who spend the whole budget on GridSearchCV fail this. Leading with evaluation and ending with the threshold layer are both strong signals.
