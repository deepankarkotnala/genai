Memory

A language model remembers nothing between calls. Memory is something your application builds around it: what it resends, what it writes down, and what it looks up again. Interviewers ask about it because the common answers - "use a bigger context window", "the checkpointer handles it" - are wrong.

⏱ 15–30 min Difficulty · Interview essentials Prereq · 05 RAG and 06 Agentic AI

1 · The idea in one minute

A model is stateless. Each call is independent, and nothing is kept after it returns. Every chat app that seems to remember you is resending the earlier messages in every request.

Think of a doctor who sees you fresh at every visit. What makes it feel as if they remember you is two things:

  • What is said in the room today. That is short-term memory: the recent messages, sent to the model again on every turn. It lives inside the context window, the maximum amount of text one call can hold.
  • Your patient file. That is long-term memory: facts stored outside the model, such as "prefers email", and pulled back into the prompt when they are relevant.

Somebody decides what goes into the file and which page to pull out before the visit. In an LLM app, that somebody is your code.

Memory is two decisions you make in code: what to write down, and what to bring back.

2 · The parts you must know

PartWhat it doesWhat goes wrong without it
Short-term memoryThe recent messages, resent in the prompt on every turnThe model loses the thread of the conversation
Trimming and summarisingKeeps a long chat inside the context window: drop the oldest turns, or replace them with a short summaryLong chats hit the window limit, and every turn costs more because everything is resent
Long-term memory storeFacts that outlive the session, in a database or a vector storeThe assistant forgets the customer the moment the session ends
Write filterDecides what is worth keeping: facts that are still true tomorrow and would change a future answerThe store fills with small talk, and retrieval returns noise
RetrievalPulls the few relevant facts into the prompt, by similarity search (as in RAG) or by keyA fact that is stored but never retrieved is invisible - the most common "it forgot" bug
KeyStores each fact under the user and tenant (customer company) it belongs toKeyed by session, a fact is unreachable tomorrow. Without the tenant in the query, one customer can see another's data
Supersede and expireA newer fact replaces the older one; stale facts expireRetrieval returns "call me" and "email only" together, and the model picks one

The memory types interviewers name

TypeHoldsUsually stored as
WorkingThis conversation and the current taskThe message list in the prompt
EpisodicWhat happened before: "last week you asked about a refund"Past interactions, or summaries of them
SemanticFacts about the user or the world: "prefers email"Database rows or vector-store entries

Three things that are not long-term memory

  • A bigger context window. More text fits into one call. Nothing survives to the next session, and you pay for every token on every turn.
  • A checkpointer. It saves a run's state so the run can resume - LangGraph uses it for thread-level, short-term memory. It does not make a fact available to a new conversation. For that you need a long-term store keyed by user.
  • Fine-tuning. It changes behaviour and style. It cannot hold per-user facts, cannot be updated per conversation, and cannot delete one person's data on request.

3 · How it fails, and the fix

FailureWhat you seeFix
Storing every messageThousands of rows per user; retrieval returns chatter and old task stateWrite filter: keep only what is still true tomorrow and changes a future answer
Contradictions keptOld and new preferences both come backSupersede at write time: the newer fact retires the older one
Wrong keyRemembers within a chat, forgets the next dayKey by user and tenant, never by session
Written but not retrieved"I already told it that"Check the write happened, then the key, then the retrieval ranking. Log what was retrieved into each prompt
Long chat overflowsEarly details lost, cost per turn keeps risingKeep the last turns verbatim, summarise older ones, keep exact values (ids, amounts) word for word
Privacy ignoredPersonal data kept for ever, cannot be deleted on requestTreat the store as personal data: a retention limit, delete-by-user as one operation, tenant in every query

4 · Say this in the interview

🎤
A 30-second answer

"An LLM is stateless, so memory is something the application builds. Short-term memory is the recent conversation, resent in the prompt and kept inside the context window by trimming or summarising. Long-term memory is a store outside the model, keyed by user and tenant, holding durable facts like preferences. Before each call I retrieve a few relevant facts into the prompt. After each turn a write step decides what is worth keeping, and newer facts supersede older ones. A bigger context window or a checkpointer is not long-term memory. And because the store holds personal data, it needs a retention limit and per-user deletion."

5 · Interview questions

Answer each one out loud before you open it.

Q Does an LLM remember previous conversations? ›
No. Each call is independent, and the model keeps nothing after it returns. Apps that seem to remember are resending earlier messages, or retrieving stored facts into the prompt.
Q What is the difference between short-term and long-term memory? ›
Short-term memory is the current conversation, resent in the prompt each turn and lost when the session ends. Long-term memory is facts written to a store outside the model, keyed by user, and retrieved into the prompt in later sessions.
Q Does a bigger context window solve memory? ›
No. It lets more text fit into one call. Nothing survives to the next session, every resent token is paid for on every turn, and very long prompts tend to lose details in the middle.
Q Is a checkpointer, such as LangGraph's, memory? ›
It is thread-level, short-term persistence: it saves the run's state so the run can resume. It does not make facts available to a new conversation. Cross-session memory needs a separate long-term store keyed by user - LangGraph provides one as a Store.
Q How do you decide what to write to long-term memory? ›
Store a fact only if it will still be true tomorrow and would change a future answer: a preference, an entitlement, a decision. If it would be wrong to still have it tomorrow, it is task state and must not be stored.
Q How do you keep a long conversation inside the context window? ›
Keep the last few turns verbatim, replace older turns with a running summary, and copy exact values such as ids and amounts into the summary word for word. Durable facts go to the long-term store instead of riding along in the chat.
Q What are episodic, semantic and procedural memory? ›
Episodic: what happened in past interactions. Semantic: facts about the user or the world. Procedural: how to do the task, which in practice is the system prompt and the tool definitions.
Q A user says the assistant forgot what they told it. How do you debug it? ›
First check whether the fact was ever written - most "forgetting" is a write that never happened. Then check the key: a fact keyed by session is unreachable from a new chat. Then check whether retrieval ranked it out, and whether a newer fact superseded it.
Q Design memory for a multi-tenant assistant. ›
Key every fact by tenant and user, and put the tenant in the query itself rather than filtering afterwards. Store a source and timestamp with each fact, supersede contradictions at write time, expire stale facts, cap how many facts are retrieved, and make delete-by-user a single operation, because data-protection law will require it.

6 · In short

  1. The model is stateless. Every appearance of memory is your code resending or retrieving text.
  2. Short-term memory is the prompt; long-term memory is a store outside the model, keyed by user and tenant.
  3. Memory is a write decision. Keep only what is still true tomorrow and changes a future answer.
  4. Retrieve a few relevant facts, and supersede old ones, or the store turns into noise.
  5. A memory store holds personal data: retention limits and delete-by-user are part of the design.
