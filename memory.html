Foundations / Memory in LLMs

1 · What you already know

From module 01: a model call takes text and returns text, and holds nothing between calls. From page 6 of the agent section: state belongs to one run.

This page is about the facts that should outlive the run, and about why the most common assumption people make here is wrong.

2 · What breaks now

A language model has no memory. Not a small memory, not a short one: none at all. Each call is independent, and the model retains nothing after it returns.

Two calls, two seconds apart, same process. The second knows nothing about the first.

Every chat interface that appears to remember your name is re-sending your name in every request. What looks like memory is your application resending text.

What people assumeWhat is actually happening
The model remembers the conversationYour code re-sends every message, every turn
A bigger context window means longer memoryIt means more text fits in one call. Nothing persists
Checkpointing gives the model memoryIt saves your application's state. The model still sees only the prompt
Fine-tuning teaches it about this userIt changes behaviour, not per-user facts, and cannot be updated per conversation

The third row is worth stating carefully, because it is the misconception that makes people think checkpointing and memory are one feature. A checkpointer makes your run durable; it gives the model nothing.

3 · Simple breakdown - a memory store vs a longer context window

A A memory store

What it is. A memory store is a database outside the model that holds facts about a user, written by your application and retrieved back into the prompt when they are relevant.

Core purpose. It lets an application know something in March that it learned in January, without resending every conversation since.

Execution model.

Architecture under the hood. A write path that decides what is worth keeping, a store keyed by user or tenant, and a retrieval step that selects a few facts before the model runs.

State handling. Facts persist until superseded or deleted. Each one carries a source and a timestamp, so a later contradiction can supersede an earlier claim.

Limitations and advanced features. Anything not retrieved is invisible to the model. Deciding what to write is the hard part, and a store full of stale facts is worse than an empty one.

B A longer context window

What it is. A larger token limit on the model, so more of the conversation fits into one call without any storage.

Core purpose. It keeps more of the recent conversation available verbatim, with no write path and no retrieval step.

Execution model. The same single call, with more tokens permitted. Nothing about the application changes.

Architecture under the hood. Nothing to build. It is a model choice and a price.

State handling. Nothing persists. Every token is re-sent on every call, and the whole thing is gone when the session ends.

Limitations and advanced features. You pay for every token on every call. It cannot reach anything from a previous session, however large it is.

The core differences

A memory storeA longer context window
Survives the sessionYes, that is the pointNo
Cost as history growsRetrieval plus a few factsEvery token, every call
What the model seesOnly what retrieval selectedEverything, verbatim

In short - which one to choose

  • Use a memory store when a fact must survive the session, and would change a future answer.
  • Use a longer window to keep more of the current conversation verbatim. It is free engineering time, and it buys nothing across sessions.
  • They solve different problems, so the real question is never which one. It is which facts deserve to outlive this conversation.

4 · Without the technology

The simplest memory is a list you resend. This is what every chat application does.

This works, and for a short conversation it is the correct answer. Three things break as it grows.

  • Cost grows quadratically. Turn 20 re-sends all nineteen previous turns, so the conversation costs far more than the sum of its messages.
  • It ends at the window. There is no turn 34.
  • It dies with the process. Tomorrow's conversation starts from nothing, however much the customer told you today.

The first two are solved by trimming and compaction. The third is not a size problem at all, and no window is large enough to fix it.

5 · Runtime mechanics

Memory is four decisions, and only the first is about the model.

  1. What is resent. The message list, in full or trimmed, forms the conversation the model can see this turn.
  2. What is written. After a turn, your code decides whether anything learned should outlive the session.
  3. Where it is keyed. A store entry is reachable only by the key you gave it - customer, tenant, thread.
  4. What is retrieved. Before the next call, a few relevant facts are selected and placed into the prompt.

Steps 2 and 4 are separate, and both are yours. A fact that is written but never retrieved is invisible, which is the most common reason an agent appears to have forgotten something it was told.

6 · The components, one at a time

Short-term memory

The message list for this conversation. It lives in the context window, is resent every turn, and is lost when the session ends unless you persist it.

Long-term memory

Long-term memory - facts stored outside the model that should survive the session, retrieved back into the prompt when relevant.

Preferences, past decisions, entitlements. Retrieved by relevance rather than replayed verbatim, because there may be hundreds and only a few matter now.

The machinery is the machinery you already have. Chunking, embeddings, ranking and a relevance floor work here exactly as they do over a document corpus - see indexing and correcting. The difference is what you point it at: per-customer facts rather than documents.

The write decision

The test: if it would be wrong to still have this tomorrow, it is state, not memory. Writing state into a memory store is how last week's half-finished investigation leaks into today's answer.

The key

A fact keyed by session is unreachable from the next conversation, which is the most common cause of an agent that seems to forget.

Conflict and supersession

Keeping both means retrieval returns both and the model picks one. A newer fact must explicitly supersede the older one, or the store degrades as it grows.

The four agent memory types

TypeHoldsImplemented by
WorkingThe current run's transcript and findingsThe message list
EpisodicWhat happened in past runsA store of past interactions
SemanticFacts about the world or the userA vector store or a database
ProceduralHow to do the taskThe system prompt, and tool definitions

These are names for stores you have already built. An agent carrying stores it does not use is slower, dearer and harder to debug, so build the ones a real requirement asks for.

7 · State and data flow

  1. What data is state? The message list is state. The memory store is not - that is the whole distinction.
  2. Who writes each field? The loop appends messages; an explicit write step adds facts.
  3. Who reads each field? The model reads the prompt, which holds the messages plus whatever retrieval selected.
  4. Replaced, appended or merged? Messages append. Facts are appended, and superseded rather than edited.
  5. What reducer controls merging? Your supersession rule. Without one, contradictory facts accumulate.
  6. Is it only in process memory? The message list, yes. The store must not be.
  7. Is it checkpointed? The message list can be. A checkpoint is not memory: it makes a run resumable, not a customer known.
  8. Is it in a database? The store is, and it is the only part that outlives the session.
  9. How long does it survive? Messages: the session. Facts: until superseded or deleted.
  10. What thread, user or key retrieves it again? The customer id and tenant id. No key, no memory.

Rows 1 and 7 together are the idea this page exists for. Durability and memory are different features, and conflating them produces a system that resumes runs perfectly and still cannot remember a customer.

8 · Trace

The same customer, three sessions apart:

WhenWhat happenedStore after

Note what did not happen. The March conversation was not stored, because nothing in it was durable. A memory store that keeps everything is a transcript, and retrieval over a transcript returns noise.

9 · Break it

Remove the write filter, and store every message.

After six weeks, this customer has 1,847 stored facts. Now ask a simple question.

The store is full and the agent is less useful than when it was empty. Two of the five retrieved rows were run state that should have died with the session, one is a contradiction that was never superseded, and one is not a fact.

10 · Fix it

1 · Filter on the write, not the read. A fact is stored only if it would still be true tomorrow and would change a future answer.

2 · Supersede contradictions at write time, so retrieval never returns both sides.

3 · Retrieve by relevance and cap it. Five facts, not everything the customer ever said.

4 · Expire what stops being true. A preference from four years ago is a guess.

5 · Make deletion possible. A customer can ask for their facts to be removed, so store them where a delete by customer id is one statement.

13 · Interview preparation

Beginner Does a language model remember your conversation? ›

No. Each call is independent and the model retains nothing after it returns. Every interface that appears to remember is re-sending the earlier messages in the next request.

Beginner What is the difference between short-term and long-term memory here? ›

Short-term memory is the message list for this conversation, resent every turn and lost when the session ends. Long-term memory is facts written to a store outside the model and retrieved back into the prompt when relevant.

Intermediate Does a bigger context window give an agent memory? ›

No. It means more text fits into one call. Nothing persists after that call, and nothing from a previous session becomes reachable. It raises the budget for this conversation and does nothing for the next one.

Intermediate A checkpointer saves state after every step. Is that memory? ›

It is durability, not memory. A checkpointer makes a run resumable and keyed by thread. It does not make a customer known across conversations, and conflating the two produces a system that resumes runs perfectly and still cannot remember a preference.

Senior How do you decide what to write to a memory store? ›

Store a fact only if it would still be true tomorrow and would change a future answer: a preference, an entitlement, a decision. The test is the inverse - if it would be wrong to still have this tomorrow, it is run state and must not be stored. Storing everything produces a transcript that retrieval turns into noise.

Senior A customer says the agent forgot something. How do you diagnose it? ›

Establish first whether it was ever written, because most reported memory failures are writes that never happened rather than reads that failed. Then check the key: a fact keyed by session is unreachable from a new conversation. Then check whether retrieval ranked it out, and whether a later fact superseded it.

Staff · design Design memory for a multi-tenant assistant. ›

Key every fact by tenant and customer, and put the tenant in the query rather than filtering after retrieval, because a post-filter is a cross-tenant read that happens to be hidden. Carry a source and timestamp on each fact so a wrong one can be traced. Supersede contradictions at write time. Set an expiry, because facts go stale. And make delete-by-customer a single operation, because it will be a legal requirement rather than a feature request.

14 · In short, and what comes next

Remember these six:

  • A language model has no memory. Every appearance of memory is your code resending text.
  • A bigger context window holds more of this conversation and nothing from the last one.
  • A checkpointer makes a run resumable. It does not make a customer known.
  • If it would be wrong to still have this tomorrow, it is state and must not be stored.
  • Key by customer and tenant, never by session, or the fact is unreachable.
  • Supersede contradictions at write time, and cap what retrieval returns.
🔑
The one idea to remember

Memory is a write decision, not a storage problem. Storing everything produces a transcript that retrieval turns into noise, and the agent gets worse as the store grows.
