Interview Strategy

Run a 45-minute coding interview with a repeatable process instead of jumping straight into code. The candidates who pass are rarely the fastest typists — they are the ones whose thinking an interviewer can follow.

Outcome

By the end of this chapter you can take any prompt, clarify it, estimate the complexity the constraints demand, propose a brute force and its optimisation, write clean Python, and test it aloud — in that order, every time.

1 · How interviewers actually evaluate you

A coding round is not a pass/fail on whether the tests go green. Interviewers score a bundle of signals, and a working solution with poor communication often loses to a slightly-incomplete solution that was reasoned out loud. The recurring rubric:

SignalWhat "strong" looks likeWhat tanks the score
Problem solvingFinds the pattern, justifies the approach before codingGuesses, jumps between ideas, never commits
CommunicationThinks aloud at the level of ideas and invariantsSilent for minutes, or narrates every keystroke
CodingClean, idiomatic, correct on the first careful passTangled logic, unclear names, off-by-one bugs
VerificationTests edge cases without being asked"I think it works" and stops
ComplexityStates time and space, knows the trade-offCannot analyse own code
🎯
The meta-goal

Make it easy for the interviewer to conclude "I would trust this person with an ambiguous problem." Every habit in this chapter serves that one goal.

2 · The seven-step pipeline

Follow the same sequence on every problem so you never freeze wondering what to do next:

Spend the first 5–8 minutes above the keyboard. A brute force stated early is a safety net: it proves you understood the problem and gives you something to optimise from, so you are never left with a blank screen.

3 · UMPIRE, the workflow you can name

UMPIRE is a memorable spelling of the same pipeline. Saying the step names out loud signals structure to the interviewer:

UUnderstand

Do
Restate the problem, ask about input types, size, duplicates, empties, ordering.

MMatch

Do
Map the shape to a known pattern (see the signal primer below).

PPlan

Do
Sketch the approach in words and pseudo-steps; state the invariant.

IImplement

Do
Write clean Python; keep names meaningful; narrate at the idea level.

RReview

Do
Dry-run one example line by line; fix off-by-one and boundary bugs.

EEvaluate

Do
State time and space complexity, edge cases, and possible follow-ups.

4 · Read the constraints to pick the complexity

Constraints are a gift: the size of n tells you what complexity the interviewer expects, which narrows the pattern before you have any idea. Assume roughly 10⁸ simple operations per second:

Constraint on nTarget complexityLikely techniques
n ≤ 10–12O(n!) / O(2ⁿ)Backtracking, permutations, bitmask
n ≤ 20–25O(2ⁿ)Subset enumeration, meet-in-the-middle
n ≤ 500O(n³)Interval / partition DP, Floyd–Warshall
n ≤ 5,000O(n²)2D DP, nested scan
n ≤ 10⁶O(n log n)Sort, heap, binary search on the answer
n ≤ 10⁷–10⁸O(n)Two pointers, sliding window, hashing, prefix sums
n huge / streamingO(log n) / O(1)Binary search, math, formula
💡
Say it aloud

"n is up to 10⁵, so an O(n²) scan is ~10¹⁰ operations and will time out — I need O(n log n) or better." That single sentence tells the interviewer you can budget compute.

5 · Think aloud without narrating every keystroke

The skill is narrating decisions, not syntax. Compare:

✅ Idea-level

"I'll keep a running minimum price so each day I can price the best sell in O(1). The invariant is that min_price is the cheapest buy seen so far."

❌ Keystroke-level

"Now I type for, then i, then in range, open paren, len…" — this adds noise and hides your reasoning.

When you go quiet to concentrate, say so: "Let me think silently for thirty seconds." Then resume narrating.

6 · State the invariant

An invariant is a condition that stays true across every iteration. Naming it is the single highest-leverage habit in this book — it prevents most bugs and makes your loop self-documenting. Examples you will meet:

  • Sliding window: "the window [l, r] always satisfies the constraint."
  • Binary search: "the answer is always within [lo, hi]."
  • Reverse a linked list: "everything before cur is already reversed."

If you can state the invariant, you can usually write the loop. If you cannot, you are guessing.

7 · Test and debug under time pressure

Never end with "I think it works." Walk one concrete example through the code, then call out the categories of edge case that matter for this input type:

Input typeEdge cases to name
Array / listEmpty, single element, all equal, negatives, already sorted, huge
StringEmpty, one char, repeated chars, mixed case, unicode
Linked listEmpty, one node, two nodes, cycle, head/tail change
Tree / graphEmpty, single node, skewed, disconnected, cycle
Numbers0, negative, overflow assumptions, equal values

Use tiny executable assertions when a whiteboard is not enforced — they are faster than re-reading and they prove correctness:

test_habit.py
def two_sum(nums, target):
    seen = {}                     # value -> index
    for i, x in enumerate(nums):
        if target - x in seen:    # invariant: seen holds every earlier value
            return [seen[target - x], i]
        seen[x] = i
    return []

# name the edge cases, then assert them
assert two_sum([2, 7, 11, 15], 9) == [0, 1]
assert two_sum([3, 3], 6) == [0, 1]        # duplicates
assert two_sum([1], 2) == []               # too short
assert two_sum([], 0) == []                # empty
print("all tests passed")

8 · Which Python built-ins are fair game

Interviewers almost always allow the standard library — using it well is a positive signal, not cheating. Safe defaults:

Reach for these

collections.deque, collections.Counter, collections.defaultdict, heapq, bisect, sorted with a key, itertools.

Confirm first

Anything that is the problem: don't call sorted() when asked to implement a sort, or list.index when asked to implement search. Ask: "May I use the built-in, or do you want it from scratch?"

⚠️
One trap to avoid

Never use list.pop(0) as a queue — it is O(n) per call and quietly makes an O(n) loop O(n²). Use collections.deque and popleft(). This is covered in Chapter 01.

9 · How to recover after getting stuck

  1. Return to a smaller example. Solve n = 2 by hand and watch what your brain does — that procedure is the algorithm.
  2. Fall back to brute force. A correct slow solution beats an incorrect fast one; state its complexity and offer to optimise.
  3. Change the representation. Would a hash map, sorting, or a different traversal make the structure obvious?
  4. Ask a targeted question. "Can I assume the array fits in memory?" often unlocks the intended approach.
  5. Say what you know. "I know this is a graph reachability question; I'm deciding between BFS and union-find." Interviewers frequently nudge from there.

11 · Study routes: 4, 8 and 12 weeks

4-week sprint

For a soon deadline. 00, 01, then 02–04, 06–08, 10, 12, 15, 18. One chapter every 2–3 days, 6–8 problems each, daily mixed review. Skip 14, 16, 20, 24.

8-week standard

All core chapters plus 09, 11, 13, 17, 19, 21. Add a weekly timed mock from 23. One chapter every 3–4 days.

12-week thorough

Everything, including the strongly-recommended and one advanced pass (14, 16, 20, 24). Two full mocks per week in the last month.

12 · Diagnostic: where should you start?

Answer honestly — the goal is to find your weakest link, not to score well.

The array has up to 10⁵ elements and you wrote two nested loops. Your first move is to…
Submit and hope the tests are small
Estimate ~10¹⁰ operations, recognise it will time out, and look for a hash-map or two-pointer O(n) approach
Rewrite the loops in C-style syntax to go faster
