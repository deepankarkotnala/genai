Chapter 01 · Foundations

Python DSA Foundations

The behaviour of Python objects, references and containers decides whether your code is correct, fast and memory-safe. This chapter is the language layer every later pattern silently depends on.

Outcome

Predict mutation and aliasing, spot hidden O(n) operations, choose the right container, avoid needless copies, and analyse time and auxiliary space the way an interviewer expects.

1 · Objects, references, mutability and aliasing

A Python variable is a name bound to an object, not a box holding a value. Assignment copies the reference, never the object. Two names can alias the same list, so mutating through one is visible through the other:

aliasing.py
a = [1, 2, 3]
b = a               # b and a name the SAME list object
b.append(4)
assert a == [1, 2, 3, 4]        # the mutation is visible through a
assert a is b                   # identity: same object

c = a[:]            # slice makes a NEW (shallow) list
c.append(5)
assert a == [1, 2, 3, 4]        # a is unaffected
assert a is not c

# the classic default-argument trap: the default is created ONCE
def bad(x, acc=[]):             # do NOT do this
    acc.append(x)
    return acc
assert bad(1) == [1]
assert bad(2) == [1, 2]         # surprise: state leaked between calls

def good(x, acc=None):
    acc = [] if acc is None else acc
    acc.append(x)
    return acc
assert good(1) == [1] and good(2) == [2]
print("aliasing ok")
⚠️
Mutable default argument

def f(acc=[]) reuses one list across every call — a real bug that appears in interviews. Default to None and build inside.

2 · List over-allocation and amortised append

A Python list is a dynamic array of pointers. It over-allocates capacity, so most appends are O(1); occasionally it resizes and copies, which is O(n) — but averaged over many appends the cost is amortised O(1). Two consequences interviewers probe:

  • list.append(x) and list.pop() (from the end) are amortised O(1).
  • list.insert(0, x) and list.pop(0) are O(n) — everything shifts. Use collections.deque for a queue.
queue_choice.py
from collections import deque

q = deque()
q.append(1); q.append(2)     # enqueue at the right — O(1)
assert q.popleft() == 1      # dequeue at the left — O(1)

# a list as a queue is a hidden O(n) per step -> O(n^2) overall
slow = [1, 2, 3]
assert slow.pop(0) == 1      # correct, but shifts all remaining elements
print("queue ok")

stdlib_tools.py
from collections import Counter, defaultdict
import heapq, bisect

# frequency counting in one line
assert Counter("banana") == {"a": 3, "b": 1, "n": 2}

# grouping without key-exists checks
groups = defaultdict(list)
for word in ["ate", "eat", "tea"]:
    groups["".join(sorted(word))].append(word)
assert groups["aet"] == ["ate", "eat", "tea"]

# min-heap: k largest via a bounded heap of size k
def k_largest(nums, k):
    h = []
    for x in nums:
        heapq.heappush(h, x)
        if len(h) > k:
            heapq.heappop(h)         # drop the smallest, keep k largest
    return sorted(h, reverse=True)
assert k_largest([3, 1, 5, 2, 4], 2) == [5, 4]

# bisect: insertion point into a sorted list — O(log n)
assert bisect.bisect_left([1, 3, 5, 7], 5) == 2
print("stdlib ok")

4 · Hashability and collision assumptions

Dict and set keys must be hashable — immutable in practice. Tuples of immutables are hashable; lists and dicts are not. The O(1) average for hash operations assumes a good hash and no adversarial collisions; worst case is O(n), which is why some problems specify constraints that keep hashing safe.

hashable.py
seen = set()
seen.add((1, 2))            # tuple key is fine
assert (1, 2) in seen

try:
    seen.add([1, 2])       # list is unhashable
except TypeError as e:
    assert "unhashable" in str(e)

# freeze a grid cell as a tuple to use it as a visited key
visited = set()
visited.add((0, 0))
assert (0, 0) in visited
print("hashability ok")

5 · Slicing makes hidden copies

Slicing a list or string builds a new object of the sliced length. Inside a loop this can quietly turn an O(n) algorithm into O(n²). Prefer indices when you only need to read a range.

slicing_cost.py
# O(n^2): each recursive slice copies the remaining list
def sum_slices(nums):
    if not nums:
        return 0
    return nums[0] + sum_slices(nums[1:])    # nums[1:] copies n-1 elements

# O(n): pass an index instead of slicing
def sum_index(nums, i=0):
    if i == len(nums):
        return 0
    return nums[i] + sum_index(nums, i + 1)

assert sum_slices([1, 2, 3]) == 6 == sum_index([1, 2, 3])
print("slicing ok")

6 · Build strings with join, never += in a loop

Strings are immutable, so s += piece in a loop reallocates the whole string each time — O(n²). Accumulate pieces in a list and "".join() once at the end — O(n).

string_build.py
def repeat_bad(word, n):
    s = ""
    for _ in range(n):
        s += word          # O(n^2): each += copies the growing string
    return s

def repeat_good(word, n):
    parts = []
    for _ in range(n):
        parts.append(word)
    return "".join(parts)  # O(total length)

assert repeat_bad("ab", 3) == "ababab" == repeat_good("ab", 3)
print("strings ok")

7 · Timsort, keys and stability

Python's sorted() and list.sort() use Timsort: O(n log n), stable (equal elements keep their original order), and close to O(n) on nearly-sorted input. Sort by a key function; combine tie-breakers in a tuple.

sorting_keys.py
people = [("Ada", 36), ("Bo", 28), ("Cy", 36)]

# sort by age ascending, then name ascending as a tie-break
by_age_then_name = sorted(people, key=lambda p: (p[1], p[0]))
assert by_age_then_name == [("Bo", 28), ("Ada", 36), ("Cy", 36)]

# stability: sorting only by age keeps Ada before Cy (original order)
by_age = sorted(people, key=lambda p: p[1])
assert by_age == [("Bo", 28), ("Ada", 36), ("Cy", 36)]
print("sorting ok")

8 · Generators and streaming memory

A generator yields items lazily, holding O(1) state instead of materialising the whole sequence. This is the difference between a program that fits in memory and one that does not — central to the Data Science and GenAI chapters.

generators.py
def batched(iterable, size):
    """Yield fixed-size chunks without loading everything at once."""
    batch = []
    for item in iterable:
        batch.append(item)
        if len(batch) == size:
            yield batch
            batch = []
    if batch:
        yield batch

chunks = list(batched(range(7), 3))
assert chunks == [[0, 1, 2], [3, 4, 5], [6]]
print("generators ok")

9 · Recursion limits and iterative alternatives

CPython caps recursion at ~1000 frames by default, and each frame costs stack memory. Deep recursion (a linked list of 10⁵ nodes, a skewed tree) will raise RecursionError. Always be ready to convert to an explicit stack.

recursion.py
import sys
assert sys.getrecursionlimit() >= 1000     # default ceiling

# iterative DFS with an explicit stack avoids the frame limit entirely
def dfs_count(adj, start):
    seen, stack, count = {start}, [start], 0
    while stack:
        node = stack.pop()
        count += 1
        for nxt in adj.get(node, ()):
            if nxt not in seen:
                seen.add(nxt)
                stack.append(nxt)
    return count

graph = {0: [1, 2], 1: [3], 2: [3], 3: []}
assert dfs_count(graph, 0) == 4
print("recursion ok")
🧠
State the stack cost

When you use recursion, name its depth: "this recurses to O(h) where h is the tree height, so O(n) worst case on a skewed tree." That is part of the auxiliary space analysis interviewers expect.

10 · Integers and bit behaviour

Python integers are arbitrary precision — no 32/64-bit overflow — which removes a whole class of C/Java bugs but means you must state when a problem assumes fixed-width integers. Common bit idioms:

bits.py
x = 0b1010
assert x & 1 == 0            # test the low bit (even)
assert x >> 1 == 0b101       # divide by 2
assert x | 1 == 0b1011       # set the low bit
assert x ^ x == 0            # xor with self cancels
assert bin(13).count("1") == 3   # popcount
# clear the lowest set bit — used in Fenwick trees
assert (12 & (12 - 1)) == 8
print("bits ok")

11 · Shallow versus deep copy

A shallow copy duplicates the outer container but shares the inner objects; a deep copy duplicates everything. For a matrix (list of lists) this distinction causes real bugs.

copies.py
import copy

grid = [[0, 0], [0, 0]]
shallow = grid[:]            # outer list copied, inner rows SHARED
shallow[0][0] = 9
assert grid[0][0] == 9       # bug: the shared row was mutated

grid = [[0, 0], [0, 0]]
deep = copy.deepcopy(grid)   # every row copied
deep[0][0] = 9
assert grid[0][0] == 0       # original safe

# cheap correct pattern for a fresh matrix
rows, cols = 2, 3
fresh = [[0] * cols for _ in range(rows)]   # NOT [[0]*cols]*rows
fresh[0][0] = 7
assert fresh[1][0] == 0      # rows are independent
print("copies ok")
🚫
The [[0]*c]*r trap

[[0]*cols]*rows makes rows references to one inner list — writing one cell changes the whole column. Always use a comprehension: [[0]*cols for _ in range(rows)].

12 · Big-O and auxiliary-space conventions

Interviews use a shared vocabulary for cost. Be precise about which space you mean:

TermMeaning
Time complexityGrowth of operations as input grows, worst case unless stated
Auxiliary spaceExtra memory beyond the input and the required output
Output spaceMemory for the result — usually excluded from "space complexity"
In-placeO(1) auxiliary space; the input is mutated
Recursion stackCounts toward auxiliary space: O(depth)
📏
Memory-analysis standard used in this book

No solution is called "memory optimised" without stating baseline vs optimised auxiliary memory, whether output is excluded, whether the input is mutated, the recursion-stack cost, and any Python container/object overhead. Readable optimal code beats obscure micro-optimisation.

13 · Type hints and tiny test harnesses

Light type hints make interview code easier to read and reason about; you do not need a type checker. Pair them with executable assertions so "done" means "proven":

typed_harness.py
from typing import List

def running_max(nums: List[int]) -> List[int]:
    out, best = [], float("-inf")
    for x in nums:
        best = max(best, x)
        out.append(best)
    return out

def test() -> None:
    assert running_max([1, 3, 2, 5]) == [1, 3, 3, 5]
    assert running_max([]) == []            # empty
    assert running_max([-2, -5]) == [-2, -2] # negatives
    print("all tests passed")

test()

14 · Required drills

Do these until they are automatic — every later chapter assumes them.

  1. Predict mutation and aliasing. Given two snippets, say which lists change and why before running.
  2. Identify hidden O(n) operations. Scan a function for pop(0), in list, slicing in loops, and += on strings.
  3. Choose the container. For ten problem prompts, pick list / deque / set / dict / heap and justify it in one sentence.
  4. Remove unnecessary copies. Rewrite a slice-in-a-loop solution to pass indices instead.
  5. Rewrite recursion iteratively. Convert a recursive DFS and a recursive list sum to explicit-stack / loop versions.
Which line is the performance bug in a hot loop over a large list?
seen = set()
if x in my_list: where my_list is a Python list
result.append(x)
x in list scans linearly — O(n) per check, O(n²) across the loop. Membership tests belong on a set or dict, which are O(1) average. append is amortised O(1) and set() construction is fine.
One-page cheat sheet
  • Assignment copies a reference; slice/list()/copy make new objects.
  • Default to None for mutable default arguments.
  • Queue → deque; heap → heapq; counting → Counter; grouping → defaultdict.
  • Membership → set/dict (O(1)), never x in list in a loop.
  • Build strings with "".join(parts); build matrices with a comprehension.
  • sorted(key=…) is stable Timsort, O(n log n); tie-break with a tuple key.
  • Recursion depth counts as auxiliary space; be ready for the iterative form.
  • Python ints don't overflow — state it when a problem assumes fixed width.
