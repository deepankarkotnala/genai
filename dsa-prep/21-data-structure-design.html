Data Structure Design

Design problems ask you to build a data structure whose every operation meets a stated time bound — usually O(1) or O(log n). The craft is combining simple structures so their strengths cover each other: a hashmap for lookup plus a linked list for order, an array plus an index map, two heaps that balance, or buckets keyed by frequency. This chapter builds the recurring compositions from the ground up. Every solution is a complete, tested class in LeetCode's expected form.

Outcome

Combine primitive structures to hit O(1)/O(log n) targets: hashmap + doubly linked list (LRU/LFU), array + index map (O(1) random), two balanced heaps (streaming median), monotonic and augmented stacks, versioned stores with binary search, and bucketed structures for O(1) frequency queries.

1 · Foundations

Design problems reuse a handful of compositions. Learn these, then head to §2 Pattern library.

How to approach a design problem

Start from the operations and their required time bounds — those dictate the structure. Ask: which operation is hardest to make fast, and what structure makes it O(1)/O(log n)? Then check the others still hold, and add a second structure to cover any gap. Almost every design answer is two primitives working together.

The reusable pairings: hashmap + linked list (O(1) lookup and ordering — LRU/LFU) · array + index map (O(1) random access and deletion) · two heaps (a balanced split for the median) · value-indexed buckets (O(1) min/max-frequency).

The idea in miniature: O(1) minimum in a stack

A single stack can't return its minimum in O(1) after arbitrary pops — one variable loses history. The fix is a second, parallel stack whose top always holds the current minimum. This "augment with an auxiliary structure" move is the whole chapter in one small example.

Example — Min Stack
min_stack.py
class MinStack:
    def __init__(self):
        self.stack = []
        self.mins = []                       # top = min of everything below

    def push(self, val):
        self.stack.append(val)
        self.mins.append(min(val, self.mins[-1]) if self.mins else val)

    def pop(self):
        self.stack.pop()
        self.mins.pop()

    def getMin(self):
        return self.mins[-1]                 # O(1), always current

s = MinStack()
for v in (5, 2, 7):
    s.push(v)
print(s.getMin())                            # 2
Output2

The workhorse: hashmap + doubly linked list

The most important design composition. A hashmap gives O(1) access to any element; a doubly linked list gives O(1) removal and reinsertion once you hold a node. Together they maintain an ordering (by recency, by frequency) with every operation O(1) — the backbone of LRU and LFU caches. Sentinel head/tail nodes remove the null-checking special cases.

⚠️
Design pitfalls

Confirm the required complexity for every operation before coding — a structure that's O(1) for get can be O(n) for delete. Use sentinel nodes in linked lists to avoid head/tail edge cases. Keep auxiliary structures perfectly in sync (a stale index map or frequency count is the classic bug). And for streaming medians, rebalance the heaps every insert, not lazily.

1 LC 155Min Stack Easy Parallel stack of running minimums

Problem. Design a stack supporting push, pop, top, and retrieving the minimum — all in O(1). LeetCode 155 ↗

Clarify: getMin must be O(1)? (Yes.) Duplicates allowed? (Yes.)

Hint 1
A single value can't track the min after pops — you need history.
Hint 2
Keep a parallel stack whose top is always the current minimum.

How to think about it Alongside the main stack, keep a mins stack whose top is the minimum of everything currently stored. On push, append min(val, current min); on pop, pop both. Every query is then a direct O(1) read — no scanning.

min_stack.py
class MinStack:
    def __init__(self):
        self.stack = []
        self.mins = []                       # running minimum, parallel to stack

    def push(self, val):
        self.stack.append(val)
        self.mins.append(val if not self.mins else min(val, self.mins[-1]))

    def pop(self):
        self.stack.pop()
        self.mins.pop()

    def top(self):
        return self.stack[-1]

    def getMin(self):
        return self.mins[-1]

All ops O(1) · Space O(n). Carrying an auxiliary stack of extremes is the go-to for 'O(1) min/max alongside a stack'.

2 LC 232Implement Queue using Stacks Easy Two stacks · amortised O(1)

Problem. Implement a FIFO queue using only two LIFO stacks (push, pop, peek, empty). LeetCode 232 ↗

Clarify: Only stack operations allowed? (Yes.) Amortised O(1) acceptable? (Yes.)

Hint 1
Push onto an 'inbox' stack.
Hint 2
Only when the 'outbox' is empty, flip the inbox into it — this reverses order to FIFO.

How to think about it Use an inbox for incoming elements and an outbox for outgoing. Pop/peek draw from the outbox; when it's empty, pour the entire inbox into it, reversing LIFO into FIFO. Each element moves at most twice, giving amortised O(1).

queue_using_stacks.py
class MyQueue:
    def __init__(self):
        self.inbox = []                      # newest pushed here
        self.outbox = []                     # oldest popped from here

    def push(self, x):
        self.inbox.append(x)

    def pop(self):
        self.peek()
        return self.outbox.pop()

    def peek(self):
        if not self.outbox:                  # flip only when outbox is empty
            while self.inbox:
                self.outbox.append(self.inbox.pop())
        return self.outbox[-1]

    def empty(self):
        return not self.inbox and not self.outbox

Amortised O(1) · Space O(n). The lazy-transfer trick (flip only when needed) is what keeps it amortised constant.

3 LC 225Implement Stack using Queues Easy One queue · rotate on push

Problem. Implement a LIFO stack using a single FIFO queue (push, pop, top, empty). LeetCode 225 ↗

Clarify: A single queue is fine? (Yes.) Push may be O(n)? (Yes.)

Hint 1
After enqueuing a new element, rotate the older elements behind it.
Hint 2
Then the newest element sits at the front, ready to pop like a stack.

How to think about it Keep one queue. On push, enqueue the element, then rotate every earlier element to the back (dequeue and re-enqueue). This leaves the newest element at the front, so pop/top behave as LIFO. Push is O(n); the other operations are O(1).

stack_using_queues.py
from collections import deque

class MyStack:
    def __init__(self):
        self.q = deque()

    def push(self, x):
        self.q.append(x)
        for _ in range(len(self.q) - 1):     # rotate so newest is at the front
            self.q.append(self.q.popleft())

    def pop(self):
        return self.q.popleft()

    def top(self):
        return self.q[0]

    def empty(self):
        return not self.q

Push O(n), rest O(1) · Space O(n). Front-loading the cost into push keeps reads trivial.

4 LC 705Design HashSet Easy Buckets + chaining

Problem. Design a hash set (add, remove, contains) without using built-in set types. LeetCode 705 ↗

Clarify: Keys are non-negative integers? (Yes.) Handle collisions? (Yes.)

Hint 1
Hash the key to a bucket index with modulo.
Hint 2
Store each bucket as a list and search within it (separate chaining).

How to think about it Build the classic hash table: a fixed array of buckets, each a list. Map a key to key % size and handle collisions by chaining within that bucket's list. add appends if absent, remove deletes if present, contains scans the (short) bucket.

design_hashset.py
class MyHashSet:
    def __init__(self):
        self.size = 1000
        self.buckets = [[] for _ in range(self.size)]

    def add(self, key):
        b = self.buckets[key % self.size]
        if key not in b:
            b.append(key)

    def remove(self, key):
        b = self.buckets[key % self.size]
        if key in b:
            b.remove(key)

    def contains(self, key):
        return key in self.buckets[key % self.size]

Avg O(1) · Space O(n). Separate chaining is the textbook collision strategy — understanding it demystifies Python's own dict/set.

5 LC 706Design HashMap Easy Buckets of key-value pairs

Problem. Design a hash map (put, get, remove) without built-in dict types. LeetCode 706 ↗

Clarify: Keys are non-negative integers? (Yes.) get returns −1 if absent? (Yes.)

Hint 1
Same bucket-chaining as a hash set, but store (key, value) pairs.
Hint 2
put overwrites an existing key; get scans the bucket for the key.

How to think about it Identical structure to the hash set, but each bucket holds (key, value) pairs. put updates in place if the key exists, else appends; get scans the bucket and returns the value or −1; remove drops the matching pair.

design_hashmap.py
class MyHashMap:
    def __init__(self):
        self.size = 1000
        self.buckets = [[] for _ in range(self.size)]

    def put(self, key, value):
        b = self.buckets[key % self.size]
        for i, (k, _) in enumerate(b):
            if k == key:
                b[i] = (key, value)
                return
        b.append((key, value))

    def get(self, key):
        for k, v in self.buckets[key % self.size]:
            if k == key:
                return v
        return -1

    def remove(self, key):
        b = self.buckets[key % self.size]
        for i, (k, _) in enumerate(b):
            if k == key:
                b.pop(i)
                return

Avg O(1) · Space O(n). Storing pairs instead of bare keys is the only change from HashSet.

6 LC 933Number of Recent Calls Easy Sliding window with a deque

Problem. Count how many of the recent ping requests fall within the last 3000 ms of the newest ping. LeetCode 933 ↗

Clarify: Pings arrive with strictly increasing timestamps? (Yes.) Window is [t−3000, t]? (Yes.)

Hint 1
Keep timestamps in a queue in arrival order.
Hint 2
On each ping, drop from the front everything older than t − 3000.

How to think about it Maintain a deque of timestamps. Each ping appends the new time, then evicts from the front every call older than t − 3000. Because times only increase, the deque stays sorted and the window count is just its length.

recent_counter.py
from collections import deque

class RecentCounter:
    def __init__(self):
        self.calls = deque()

    def ping(self, t):
        self.calls.append(t)
        while self.calls[0] < t - 3000:      # drop calls outside the 3000ms window
            self.calls.popleft()
        return len(self.calls)

Amortised O(1) · Space O(window). A deque is the natural structure for a time-based sliding window.

7 LC 1603Design Parking System Easy Three counters

Problem. Design a parking system with fixed counts of big, medium, and small slots; addCar parks a car of a given type if a slot is free. LeetCode 1603 ↗

Clarify: Three fixed capacities set at construction? (Yes.) Return whether the car could park? (Yes.)

Hint 1
Just track remaining slots per type.
Hint 2
Index by carType (1/2/3) to keep addCar branch-free.

How to think about it The simplest design: store the three capacities, indexed by car type (1=big, 2=medium, 3=small) so addCar is a single decrement-if-available. Return whether a slot was free. A gentle reminder that many 'design' problems need only a couple of counters.

parking_system.py
class ParkingSystem:
    def __init__(self, big, medium, small):
        self.slots = [0, big, medium, small]  # 1=big, 2=medium, 3=small

    def addCar(self, carType):
        if self.slots[carType] > 0:
            self.slots[carType] -= 1
            return True
        return False

All ops O(1) · Space O(1). Not every design problem needs a fancy structure — sometimes counters suffice.

8 LC 146LRU Cache Medium Hashmap + doubly linked list

Problem. Design a Least-Recently-Used cache with O(1) get and put; evict the least-recently-used key when over capacity. LeetCode 146 ↗

Clarify: Both get and put must be O(1)? (Yes.) get and put both count as 'use'? (Yes.)

Hint 1
A hashmap gives O(1) lookup; a doubly linked list gives O(1) reordering.
Hint 2
Move a used node to the front; evict from the back when over capacity.

How to think about it The cornerstone design: a hashmap from key to node, plus a doubly linked list ordered by recency (front = most recent). get/put unlink the node and re-insert it at the front in O(1); when size exceeds capacity, drop the node just before the tail sentinel. Sentinel head/tail nodes remove edge cases. (Python's OrderedDict packages this.)

lru_cache.py
class LRUCache:
    class _Node:
        __slots__ = ("key", "val", "prev", "next")

        def __init__(self, key=0, val=0):
            self.key, self.val = key, val
            self.prev = self.next = None

    def __init__(self, capacity):
        self.cap = capacity
        self.cache = {}
        self.head = self._Node()             # sentinel: most-recently used side
        self.tail = self._Node()             # sentinel: least-recently used side
        self.head.next, self.tail.prev = self.tail, self.head

    def _remove(self, node):
        node.prev.next, node.next.prev = node.next, node.prev

    def _add_front(self, node):
        node.next, node.prev = self.head.next, self.head
        self.head.next.prev = node
        self.head.next = node

    def get(self, key):
        if key not in self.cache:
            return -1
        node = self.cache[key]
        self._remove(node)                   # move to front (most recent)
        self._add_front(node)
        return node.val

    def put(self, key, value):
        if key in self.cache:
            self._remove(self.cache[key])
        node = self._Node(key, value)
        self.cache[key] = node
        self._add_front(node)
        if len(self.cache) > self.cap:       # evict the least-recently used
            lru = self.tail.prev
            self._remove(lru)
            del self.cache[lru.key]

All ops O(1) · Space O(capacity). Hashmap-for-lookup + DLL-for-order is the single most important design pattern in this chapter.

9 LC 380Insert Delete GetRandom O(1) Medium Array + index map · swap to end

Problem. Design a set with average O(1) insert, remove, and getRandom (uniformly random element). LeetCode 380 ↗

Clarify: getRandom must be uniform over current elements? (Yes.) All three O(1) average? (Yes.)

Hint 1
getRandom needs a dense array for O(1) indexing; removal from an array is O(n) unless…
Hint 2
…you swap the victim with the last element, then pop the end.

How to think about it Combine a dense array (for O(1) random indexing) with a hashmap from value to its array index. The trick for O(1) removal: overwrite the victim's slot with the last element, fix that element's index, then pop the tail. getRandom just picks a random array position.

randomized_set.py
import random

class RandomizedSet:
    def __init__(self):
        self.vals = []                       # dense array for O(1) random pick
        self.idx = {}                        # value -> its index in vals

    def insert(self, val):
        if val in self.idx:
            return False
        self.idx[val] = len(self.vals)
        self.vals.append(val)
        return True

    def remove(self, val):
        if val not in self.idx:
            return False
        i, last = self.idx[val], self.vals[-1]
        self.vals[i] = last                  # swap the victim with the last element
        self.idx[last] = i
        self.vals.pop()
        del self.idx[val]
        return True

    def getRandom(self):
        return random.choice(self.vals)

Avg O(1) · Space O(n). 'Swap-with-last then pop' is the reusable trick for O(1) array deletion when order doesn't matter.

10 LC 707Design Linked List Medium Nodes + size, index walks

Problem. Implement a singly linked list supporting get, addAtHead, addAtTail, addAtIndex, and deleteAtIndex. LeetCode 707 ↗

Clarify: 0-indexed positions? (Yes.) Out-of-range index is a no-op / −1? (Yes.)

Hint 1
Track the head and a size count for bounds checks.
Hint 2
For index operations, walk to the node just before the target.

How to think about it A straightforward nodes-and-pointers implementation with a cached size for O(1) bounds checks. Each index operation walks to the predecessor of the target position and splices. Handling index == 0 (new head) separately keeps the pointer surgery clean.

design_linked_list.py
class MyLinkedList:
    class _Node:
        def __init__(self, val):
            self.val = val
            self.next = None

    def __init__(self):
        self.head = None
        self.size = 0

    def get(self, index):
        if index < 0 or index >= self.size:
            return -1
        cur = self.head
        for _ in range(index):
            cur = cur.next
        return cur.val

    def addAtHead(self, val):
        self.addAtIndex(0, val)

    def addAtTail(self, val):
        self.addAtIndex(self.size, val)

    def addAtIndex(self, index, val):
        if index > self.size or index < 0:
            return
        node = self._Node(val)
        if index == 0:
            node.next, self.head = self.head, node
        else:
            prev = self.head
            for _ in range(index - 1):
                prev = prev.next
            node.next, prev.next = prev.next, node
        self.size += 1

    def deleteAtIndex(self, index):
        if index < 0 or index >= self.size:
            return
        if index == 0:
            self.head = self.head.next
        else:
            prev = self.head
            for _ in range(index - 1):
                prev = prev.next
            prev.next = prev.next.next
        self.size -= 1

Ops O(index) · Space O(n). Implementing the list itself cements the pointer manipulation behind every linked-list problem.

11 LC 622Design Circular Queue Medium Fixed array + head & count

Problem. Design a fixed-capacity circular (ring) queue supporting enQueue, deQueue, Front, Rear, isEmpty, isFull. LeetCode 622 ↗

Clarify: Fixed capacity k? (Yes.) Reuse freed slots by wrapping around? (Yes.)

Hint 1
Store a head index and a count; compute the tail as (head + count) % k.
Hint 2
Wrapping with modulo reuses vacated slots without shifting.

How to think about it Back it with a fixed array plus a head index and a count. The next free slot is (head + count) % k and the rear is (head + count − 1) % k; dequeue just advances head modulo k. Modular arithmetic makes the ring reuse space with no shifting.

circular_queue.py
class MyCircularQueue:
    def __init__(self, k):
        self.q = [0] * k
        self.cap = k
        self.head = 0
        self.count = 0

    def enQueue(self, value):
        if self.isFull():
            return False
        self.q[(self.head + self.count) % self.cap] = value
        self.count += 1
        return True

    def deQueue(self):
        if self.isEmpty():
            return False
        self.head = (self.head + 1) % self.cap
        self.count -= 1
        return True

    def Front(self):
        return -1 if self.isEmpty() else self.q[self.head]

    def Rear(self):
        return -1 if self.isEmpty() else self.q[(self.head + self.count - 1) % self.cap]

    def isEmpty(self):
        return self.count == 0

    def isFull(self):
        return self.count == self.cap

All ops O(1) · Space O(k). The head-plus-count ring buffer underpins bounded queues and streaming buffers.

12 LC 1146Snapshot Array Medium Versioned history + binary search

Problem. Design an array that supports set, snap (take a snapshot, returning its id), and get(index, snap_id). LeetCode 1146 ↗

Clarify: snap_id increases by one each snapshot? (Yes.) get reads the value as of that snapshot? (Yes.)

Hint 1
Storing a full array per snapshot is wasteful — record only changes.
Hint 2
Per index, keep a sorted list of (snap_id, value); binary-search the right version on get.

How to think about it Store, per index, a history of (snap_id, value) pairs — only writes create entries. snap just bumps a counter. get binary-searches for the latest entry with snap_id ≤ the requested id. This keeps memory proportional to the number of writes, not snapshots × length.

snapshot_array.py
import bisect

class SnapshotArray:
    def __init__(self, length):
        self.snap_id = 0
        self.history = [[(0, 0)] for _ in range(length)]   # per index: (snap, val)

    def set(self, index, val):
        self.history[index].append((self.snap_id, val))

    def snap(self):
        self.snap_id += 1
        return self.snap_id - 1

    def get(self, index, snap_id):
        hist = self.history[index]
        i = bisect.bisect_right(hist, (snap_id, float("inf"))) - 1   # last snap ≤ id
        return hist[i][1]

set/snap O(1) · get O(log writes) · Recording deltas plus binary search is the standard versioned-store design.

13 LC 981Time Based Key-Value Store Medium Per-key sorted (time, value) list

Problem. Design a store where set(key, value, timestamp) records a value and get(key, timestamp) returns the value with the largest timestamp ≤ the query. LeetCode 981 ↗

Clarify: Timestamps for a key strictly increase? (Yes.) Return "" if none qualifies? (Yes.)

Hint 1
Per key, append (timestamp, value) pairs — they arrive sorted.
Hint 2
get binary-searches for the newest timestamp ≤ the query.

How to think about it Keep a hashmap from key to a list of (timestamp, value) pairs. Since timestamps arrive increasing, the list is naturally sorted, so get binary-searches for the rightmost entry with timestamp ≤ the query. Absent or too-early queries return the empty string.

time_map.py
import bisect
from collections import defaultdict

class TimeMap:
    def __init__(self):
        self.store = defaultdict(list)       # key -> [(timestamp, value)], sorted

    def set(self, key, value, timestamp):
        self.store[key].append((timestamp, value))

    def get(self, key, timestamp):
        arr = self.store[key]
        i = bisect.bisect_right(arr, (timestamp, chr(127))) - 1   # newest ≤ timestamp
        return arr[i][1] if i >= 0 else ""

set O(1) · get O(log n) · The 'sorted timeline + binary search' pattern recurs in any point-in-time lookup.

14 LC 355Design Twitter Medium Timestamped tweets + follow sets

Problem. Design a mini-Twitter: postTweet, getNewsFeed (10 most recent from self + followees), follow, unfollow. LeetCode 355 ↗

Clarify: Feed is the 10 most recent tweets across self and followees? (Yes.) Ordered newest first? (Yes.)

Hint 1
Timestamp every tweet with a global counter so recency is comparable across users.
Hint 2
For the feed, gather the relevant users' tweets and take the 10 newest (a heap-merge scales better).

How to think about it Store each user's tweets as (time, tweetId) using a global tick, plus a follow-set per user. getNewsFeed collects tweets from the user and their followees and returns the 10 newest by timestamp. (For large feeds, a k-way heap-merge of the per-user lists avoids sorting everything.)

design_twitter.py
from collections import defaultdict

class Twitter:
    def __init__(self):
        self.time = 0
        self.tweets = defaultdict(list)      # user -> [(time, tweetId)]
        self.following = defaultdict(set)

    def postTweet(self, userId, tweetId):
        self.tweets[userId].append((self.time, tweetId))
        self.time += 1

    def getNewsFeed(self, userId):
        candidates = []
        for u in self.following[userId] | {userId}:
            candidates.extend(self.tweets[u])
        candidates.sort(reverse=True)        # newest first
        return [tid for _, tid in candidates[:10]]

    def follow(self, followerId, followeeId):
        self.following[followerId].add(followeeId)

    def unfollow(self, followerId, followeeId):
        self.following[followerId].discard(followeeId)

Feed O(t log t) · Composing timestamped logs with follow sets is a realistic system-design-in-miniature.

15 LC 173Binary Search Tree Iterator Medium Controlled in-order via a stack

Problem. Implement an iterator over a BST that returns values in ascending order via next() and hasNext(), using O(h) memory. LeetCode 173 ↗

Clarify: next returns the in-order successor? (Yes.) Space should be O(height), not O(n)? (Yes.)

Hint 1
An in-order traversal visits nodes in sorted order — but do it lazily.
Hint 2
Keep a stack of the leftmost spine; on next(), pop and push the popped node's right spine.

How to think about it Simulate in-order traversal with an explicit stack holding the current leftmost spine. next pops the smallest unseen node, then pushes the left spine of its right subtree; hasNext checks the stack. Only a root-to-leaf path is ever stored, so memory is O(height).

bst_iterator.py
class TreeNode:
    def __init__(self, val=0, left=None, right=None):
        self.val = val
        self.left = left
        self.right = right

class BSTIterator:
    def __init__(self, root):
        self.stack = []
        self._push_left(root)

    def _push_left(self, node):
        while node:                          # leftmost chain = smallest unseen
            self.stack.append(node)
            node = node.left

    def next(self):
        node = self.stack.pop()
        self._push_left(node.right)          # then its right subtree's left spine
        return node.val

    def hasNext(self):
        return len(self.stack) > 0

next amortised O(1) · Space O(h) · Pausing a traversal with an explicit stack is the key to lazy iterators over trees.

16 LC 901Online Stock Span Medium Monotonic stack of (price, span)

Problem. Design a spanner: for each daily price, return how many consecutive prior days (including today) had a price ≤ today's. LeetCode 901 ↗

Clarify: Span counts the run back to the first higher price? (Yes.) Streaming input? (Yes.)

Hint 1
Days with a price ≤ today's are absorbed into today's span.
Hint 2
Keep a decreasing stack of (price, span); pop and accumulate spans while the top ≤ today.

How to think about it Keep a monotonic stack of (price, span) pairs. For a new price, pop every top with price ≤ today's, accumulating their spans into today's — those days are dominated by today. Push the merged (price, span). Each day is pushed and popped once, so it's amortised O(1).

stock_spanner.py
class StockSpanner:
    def __init__(self):
        self.stack = []                      # (price, span) monotonic stack

    def next(self, price):
        span = 1
        while self.stack and self.stack[-1][0] <= price:
            span += self.stack.pop()[1]      # absorb spans of smaller/equal days
        self.stack.append((price, span))
        return span

Amortised O(1) · Space O(n). A streaming monotonic stack — the online cousin of 'next greater element'.

17 LC 1381Design a Stack With Increment Operation Medium Lazy increments

Problem. Design a capped stack with push, pop, and increment(k, val) that adds val to the bottom k elements. LeetCode 1381 ↗

Clarify: increment affects the bottom k elements? (Yes.) push beyond maxSize is ignored? (Yes.)

Hint 1
Applying increment to k elements each call is O(k) — defer it instead.
Hint 2
Store a lazy increment per level; on pop, push the pending increment down to the element below.

How to think about it Keep a parallel inc array where inc[i] is a pending add for everything at level i and below. increment(k, val) tags only index min(k, size) − 1 in O(1). On pop, propagate the top's pending increment to the level beneath before returning value + increment. This makes every operation O(1).

custom_stack.py
class CustomStack:
    def __init__(self, maxSize):
        self.maxSize = maxSize
        self.stack = []
        self.inc = []                        # lazy increment carried per level

    def push(self, x):
        if len(self.stack) < self.maxSize:
            self.stack.append(x)
            self.inc.append(0)

    def pop(self):
        if not self.stack:
            return -1
        if len(self.inc) > 1:                # push this level's increment down
            self.inc[-2] += self.inc[-1]
        add = self.inc.pop()
        return self.stack.pop() + add

    def increment(self, k, val):
        i = min(k, len(self.inc)) - 1        # tag only the bottom-most element
        if i >= 0:
            self.inc[i] += val

All ops O(1) · Space O(n). Lazy propagation — defer bulk updates and push them down on access — is a widely reusable optimisation.

18 LC 384Shuffle an Array Medium Fisher-Yates shuffle

Problem. Design a class that can reset an integer array to its original order or return a uniformly random permutation. LeetCode 384 ↗

Clarify: All permutations equally likely? (Yes.) reset restores the initial array? (Yes.)

Hint 1
Keep an untouched copy for reset.
Hint 2
Shuffle with Fisher-Yates: for each i from the end, swap with a random index in [0, i].

How to think about it Store the original array for reset. For shuffle, apply the Fisher-Yates algorithm: walking from the last index down, swap each element with a uniformly random index at or before it. This produces every permutation with equal probability in O(n).

shuffle_array.py
import random

class Solution:                              # LC 384 Shuffle an Array
    def __init__(self, nums):
        self.original = nums[:]
        self.nums = nums[:]

    def reset(self):
        self.nums = self.original[:]
        return self.nums

    def shuffle(self):
        arr = self.nums
        for i in range(len(arr) - 1, 0, -1):     # Fisher–Yates
            j = random.randint(0, i)
            arr[i], arr[j] = arr[j], arr[i]
        return arr

shuffle/reset O(n) · Space O(n). Fisher-Yates is the only correct, unbiased in-place shuffle — naive random swaps are biased.

19 LC 1352Product of the Last K Numbers Medium Prefix products · reset on zero

Problem. Design a structure with add(num) and getProduct(k) returning the product of the last k added numbers. LeetCode 1352 ↗

Clarify: Numbers can be zero? (Yes.) getProduct is over the most recent k? (Yes.)

Hint 1
Keep prefix products; the last-k product is prefix[-1] / prefix[-1-k].
Hint 2
A zero breaks division — reset the prefix list whenever a 0 is added.

How to think about it Maintain a list of prefix products so the product of the last k is prefix[-1] / prefix[-1-k] in O(1). Since a zero would poison the running product (and division), reset the prefix list on every 0; then if k reaches back past the reset, the answer is simply 0.

product_of_numbers.py
class ProductOfNumbers:
    def __init__(self):
        self.prefix = [1]                    # prefix products; reset on a zero

    def add(self, num):
        if num == 0:
            self.prefix = [1]                # any product spanning a 0 is 0
        else:
            self.prefix.append(self.prefix[-1] * num)

    def getProduct(self, k):
        if k >= len(self.prefix):            # a zero sits within the last k
            return 0
        return self.prefix[-1] // self.prefix[-1 - k]

add/getProduct O(1) · Space O(n). Prefix products give O(1) range products; the zero-reset sidesteps division-by-zero.

20 LC 295Find Median from Data Stream Hard Two balanced heaps

Problem. Design a structure that ingests a stream of numbers and returns the running median in O(log n) per add. LeetCode 295 ↗

Clarify: Median of even count is the average of the middle two? (Yes.) addNum is O(log n)? (Yes.)

Hint 1
Split the numbers into a lower half and an upper half.
Hint 2
Use a max-heap for the lower half and a min-heap for the upper; keep their sizes balanced.

How to think about it Keep a max-heap (small) for the lower half and a min-heap (large) for the upper. Each addNum pushes then rebalances so small has the extra element when the count is odd. The median is small's top (odd) or the average of both tops (even) — all in O(log n).

median_finder.py
import heapq

class MedianFinder:
    def __init__(self):
        self.small = []                      # max-heap (negated) of the lower half
        self.large = []                      # min-heap of the upper half

    def addNum(self, num):
        heapq.heappush(self.small, -num)
        heapq.heappush(self.large, -heapq.heappop(self.small))   # balance values
        if len(self.large) > len(self.small):                    # keep sizes even
            heapq.heappush(self.small, -heapq.heappop(self.large))

    def findMedian(self):
        if len(self.small) > len(self.large):
            return -self.small[0]
        return (-self.small[0] + self.large[0]) / 2

addNum O(log n) · findMedian O(1) · The two-heap balance is the canonical streaming-median (and sliding-window-median) design.

21 LC 460LFU Cache Hard Frequency buckets of ordered keys

Problem. Design a Least-Frequently-Used cache with O(1) get and put; ties broken by least-recently-used. LeetCode 460 ↗

Clarify: Evict the least frequent, breaking ties by least recent? (Yes.) Both ops O(1)? (Yes.)

Hint 1
Track each key's frequency and, per frequency, an LRU-ordered collection of keys.
Hint 2
Maintain the current minimum frequency so eviction is O(1).

How to think about it Three maps: key→value, key→frequency, and frequency→OrderedDict of keys (preserving LRU order within a frequency). A tracked min_freq lets eviction pop the oldest key of the least-frequent bucket in O(1). Every access bumps a key to the next frequency bucket, updating min_freq when its old bucket empties.

lfu_cache.py
from collections import defaultdict, OrderedDict

class LFUCache:
    def __init__(self, capacity):
        self.cap = capacity
        self.key_val = {}
        self.key_freq = {}
        self.freq_keys = defaultdict(OrderedDict)   # freq -> keys in LRU order
        self.min_freq = 0

    def _bump(self, key):
        f = self.key_freq[key]
        del self.freq_keys[f][key]
        if not self.freq_keys[f]:
            del self.freq_keys[f]
            if self.min_freq == f:
                self.min_freq += 1
        self.key_freq[key] = f + 1
        self.freq_keys[f + 1][key] = None

    def get(self, key):
        if key not in self.key_val:
            return -1
        self._bump(key)
        return self.key_val[key]

    def put(self, key, value):
        if self.cap <= 0:
            return
        if key in self.key_val:
            self.key_val[key] = value
            self._bump(key)
            return
        if len(self.key_val) >= self.cap:    # evict least-frequent, then least-recent
            evict, _ = self.freq_keys[self.min_freq].popitem(last=False)
            del self.key_val[evict]
            del self.key_freq[evict]
        self.key_val[key] = value
        self.key_freq[key] = 1
        self.freq_keys[1][key] = None
        self.min_freq = 1

All ops O(1) · Space O(capacity). LFU layers a frequency dimension on top of LRU — buckets of ordered keys plus a min-freq pointer.

22 LC 432All O`one Data Structure Hard Doubly linked list of count buckets

Problem. Design a structure with inc(key), dec(key), getMaxKey, getMinKey — all in O(1). LeetCode 432 ↗

Clarify: Keys are grouped by count? (Yes.) getMax/getMin return any key at the extreme count? (Yes.)

Hint 1
Group keys by their current count into buckets, kept in a sorted doubly linked list.
Hint 2
inc/dec move a key to the adjacent count bucket, creating/removing buckets as needed; the ends give max/min.

How to think about it Maintain a doubly linked list of count buckets in increasing order, each holding the set of keys with that count, plus a map from key to its bucket. inc/dec move a key to the neighbouring bucket (inserting one if the adjacent count is missing, deleting an emptied bucket). The list's ends give the max/min keys instantly.

all_one.py
class AllOne:
    class _Node:
        def __init__(self, count):
            self.count = count
            self.keys = set()
            self.prev = self.next = None

    def __init__(self):
        self.head = self._Node(float("-inf"))    # sentinels bracket a sorted DLL
        self.tail = self._Node(float("inf"))
        self.head.next, self.tail.prev = self.tail, self.head
        self.key_node = {}

    def _insert_after(self, node, count):
        new = self._Node(count)
        nxt = node.next
        node.next, new.prev = new, node
        new.next, nxt.prev = nxt, new
        return new

    def _remove(self, node):
        node.prev.next, node.next.prev = node.next, node.prev

    def inc(self, key):
        if key in self.key_node:
            node = self.key_node[key]
            nxt = node.next
            if nxt.count != node.count + 1:
                nxt = self._insert_after(node, node.count + 1)
            nxt.keys.add(key)
            self.key_node[key] = nxt
            node.keys.discard(key)
            if not node.keys:
                self._remove(node)
        else:
            first = self.head.next
            if first.count != 1:
                first = self._insert_after(self.head, 1)
            first.keys.add(key)
            self.key_node[key] = first

    def dec(self, key):
        node = self.key_node[key]
        if node.count == 1:
            del self.key_node[key]
        else:
            prev = node.prev
            if prev.count != node.count - 1:
                prev = self._insert_after(node.prev, node.count - 1)
            prev.keys.add(key)
            self.key_node[key] = prev
        node.keys.discard(key)
        if not node.keys:
            self._remove(node)

    def getMaxKey(self):
        return next(iter(self.tail.prev.keys)) if self.tail.prev is not self.head else ""

    def getMinKey(self):
        return next(iter(self.head.next.keys)) if self.head.next is not self.tail else ""

All ops O(1) · Space O(n). An ordered DLL of value-buckets is the structure behind O(1) min/max-frequency queries.

23 LC 895Maximum Frequency Stack Hard Frequency-indexed stacks

Problem. Design a stack where pop removes the most frequent element (ties broken by most recent push). LeetCode 895 ↗

Clarify: pop returns the most frequent, then most recently pushed on ties? (Yes.) Both ops O(1)? (Yes.)

Hint 1
Track each value's frequency, and for each frequency a stack of values at that frequency.
Hint 2
Push adds to group[freq]; pop takes from the highest non-empty group.

How to think about it Keep a frequency map and, for each frequency level, a stack of the values that have reached it (group[f]). Pushing x increments its frequency and appends it to group[freq], updating max_freq. Popping takes the top of group[max_freq] — the most recent among the most frequent — and lowers max_freq when that level empties.

freq_stack.py
from collections import defaultdict

class FreqStack:
    def __init__(self):
        self.freq = defaultdict(int)         # value -> current frequency
        self.group = defaultdict(list)       # frequency -> stack of values
        self.max_freq = 0

    def push(self, val):
        self.freq[val] += 1
        f = self.freq[val]
        self.max_freq = max(self.max_freq, f)
        self.group[f].append(val)            # most-recent at that frequency on top

    def pop(self):
        val = self.group[self.max_freq].pop()
        self.freq[val] -= 1
        if not self.group[self.max_freq]:
            self.max_freq -= 1
        return val

All ops O(1) · Space O(n). Stacking values by frequency elegantly encodes both the frequency and recency tie-break at once.

4 · Interview playbook

  • List operations and their time bounds first. The hardest-to-speed-up operation dictates the primary structure.
  • Think in pairs: hashmap + DLL (order with O(1) access), array + index map (O(1) delete + random), two heaps (median), buckets by count (O(1) frequency).
  • LRU = hashmap + doubly linked list; LFU adds a frequency dimension (buckets of ordered keys + a min-freq pointer).
  • O(1) random from a set ⇒ dense array + index map, deleting by swap-with-last.
  • Point-in-time queries ⇒ append a sorted timeline and binary-search; bulk updates ⇒ lazy propagation.

6 · Review

Cheat sheet
  • O(1) min/max/span with a stack → parallel augmented stack.
  • FIFO from LIFO → two stacks (lazy transfer); ring buffer → array + head + count.
  • O(1) get/put with eviction by recency → hashmap + doubly linked list (LRU).
  • Add frequency + recency eviction → LFU (freq buckets of ordered keys + min-freq).
  • O(1) insert/delete/getRandom → array + index map, swap-with-last delete.
  • Running median → two balanced heaps.
  • Point-in-time / snapshot reads → append sorted timeline + binary search.
  • O(1) min/max-frequency key → ordered DLL of count buckets.

Concept checks

Why does an LRU cache need both a hashmap and a doubly linked list?
The hashmap gives O(1) lookup of any key's node, and the doubly linked list gives O(1) removal and reinsertion to maintain recency order — neither structure provides both on its own
The hashmap sorts the keys and the list stores the values
Two structures are used only to save memory
A hashmap alone can't maintain an ordering; a linked list alone can't locate a key in O(1). Combining them — map key→node, and splice that node within the list — gives O(1) get, put, and eviction. A singly linked list won't do: removing a node in O(1) needs the previous pointer.
In the O(1) RandomizedSet, why remove an element by swapping it with the last array element before popping?
Deleting from the middle of an array is O(n) due to shifting; swapping the victim with the last element and popping the end is O(1), and order doesn't matter for the set
Because the last element is always the smallest
To keep the array sorted for getRandom
getRandom needs a dense array for O(1) indexing, but arbitrary deletion from an array normally costs O(n). Since a set has no required order, you can overwrite the victim's slot with the last element (fixing its index in the map) and pop the tail — O(1). Keeping the index map in sync is the crucial detail.
