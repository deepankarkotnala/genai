1 Â· Why we don't measure time with a stopwatch

Your laptop is fast, so a bad algorithm still looks fine on a small input. The question that matters in interviews and in production is not "how many seconds did it take on my machine?" but "how does the cost grow as the input gets bigger?" That growth is independent of your hardware, the weather, or what else is running.

Think of two recipes. One gets a little slower as guests double; the other quadruples. At a dinner for four, both feel instant. At a wedding for four hundred, one is still fine and the other never finishes. Complexity analysis is how we spot the second recipe before the wedding.

growth_not_seconds.py
# We count "operations" instead of timing, so the answer doesn't
# depend on your CPU. Same task, two ways, measured in work done.

def linear_work(n):
    steps = 0
    for _ in range(n):        # touches each item once
        steps += 1
    return steps

def quadratic_work(n):
    steps = 0
    for _ in range(n):        # for every item...
        for _ in range(n):    # ...touch every item again
            steps += 1
    return steps

assert linear_work(10) == 10
assert quadratic_work(10) == 100        # 10x more input -> 100x work? no: n*n
assert linear_work(1000) == 1000        # grew 100x
assert quadratic_work(1000) == 1000000  # grew 10000x â€” this is the wedding
print("growth ok")

2 Â· Counting operations

The starting move is simple: give each basic step a rough cost of "1", then add up how many steps run as a function of the input size, which we call n. Straight-line code with no loops is a fixed number of steps no matter how big n is. A loop over n items runs its body n times.

counting_ops.py
# Count the "steps" as a function of n by incrementing a counter
# exactly where real work happens.

def straight_line(nums):
    steps = 0
    steps += 1            # read the first element
    steps += 1            # read the last element
    steps += 1            # one comparison
    return steps          # always 3, whatever len(nums) is  -> constant

def one_loop(nums):
    steps = 0
    for _ in nums:
        steps += 1        # one unit of work per item
    return steps          # equals len(nums)  -> grows with n

def loop_with_k_work(nums, k):
    steps = 0
    for _ in nums:
        for _ in range(k):
            steps += 1    # k units per item
    return steps          # equals k * len(nums)

assert straight_line([9, 9, 9, 9, 9]) == 3      # size didn't matter
assert one_loop([1, 2, 3, 4]) == 4              # equals n
assert loop_with_k_work([1, 2, 3], k=5) == 15   # equals k * n
print("counting ok")

3 Â· Big-O: keep the dominant term

Once you have a step count like 3n + 5 or nÂ² + n, you simplify it. Big-O is the shape of the growth after you drop constants and lower-order terms and keep only the dominant one. It answers "what does this look like when n is large?"

  • Drop constant multipliers: 2n, 5n, 100n are all O(n) â€” they grow in a straight line.
  • Drop lower-order terms: nÂ² + n + 7 is O(nÂ²) â€” for large n, the nÂ² dwarfs the rest.
  • Keep the biggest: a function is only as expensive as its most expensive part.

It is like describing a road trip as "about 5 hours". You don't add the 30 seconds you waited at a stop sign â€” it doesn't change the shape of the answer.

O(1) â€” constant

The work does not depend on n at all. Reading one array slot, a dictionary lookup, or pushing onto a stack all take the same time whether the collection holds 10 or 10 million items.

constant.py
def first(nums):
    return nums[0]            # jump straight to slot 0 â€” no scanning

def has_key(d, key):
    return key in d           # dict lookup, average O(1)

big = list(range(1_000_000))
assert first(big) == 0        # same cost as first([5])
assert has_key({"a": 1}, "a") is True
print("O(1) ok")

O(log n) â€” logarithmic

Each step throws away half the remaining work, so the number of steps is roughly logâ‚‚ n: 1000 items take only ~10 steps, a million take ~20. This is the "higher / lower" guessing game â€” you never check every number.

logarithmic.py
def binary_search(sorted_nums, target):
    lo, hi, steps = 0, len(sorted_nums) - 1, 0
    while lo <= hi:
        steps += 1
        mid = (lo + hi) // 2
        if sorted_nums[mid] == target:
            return mid, steps
        if sorted_nums[mid] < target:
            lo = mid + 1         # discard the left half
        else:
            hi = mid - 1         # discard the right half
    return -1, steps

nums = list(range(1_000_000))
idx, steps = binary_search(nums, 987_654)
assert idx == 987_654
assert steps <= 20               # ~log2(1e6) â‰ˆ 20, not a million
print("O(log n) ok")

O(n) â€” linear

You touch every item a constant number of times. Double the input, double the work. Most single scans live here.

linear.py
def total(nums):
    s = 0
    for x in nums:               # one pass over all n items
        s += x
    return s

def maximum(nums):
    best = nums[0]
    for x in nums:               # another single pass
        if x > best:
            best = x
    return best

assert total([1, 2, 3, 4]) == 10
assert maximum([3, 9, 2, 7]) == 9
print("O(n) ok")

O(n log n) â€” linearithmic

You split the problem in half repeatedly (the log n part) but still touch every item at each level (the n part). Comparison sorting cannot beat this, so sorted() is your workhorse here.

linearithmic.py
# Python's built-in sort (Timsort) is O(n log n).
data = [5, 2, 9, 1, 7, 3]
assert sorted(data) == [1, 2, 3, 5, 7, 9]

# merge sort shows the shape: split in half (log n levels),
# merge all n items at each level (n work per level) -> n log n.
def merge_sort(nums):
    if len(nums) <= 1:
        return nums
    mid = len(nums) // 2
    left = merge_sort(nums[:mid])
    right = merge_sort(nums[mid:])
    merged, i, j = [], 0, 0
    while i < len(left) and j < len(right):
        if left[i] <= right[j]:
            merged.append(left[i]); i += 1
        else:
            merged.append(right[j]); j += 1
    merged.extend(left[i:]); merged.extend(right[j:])
    return merged

assert merge_sort([5, 2, 9, 1, 7, 3]) == [1, 2, 3, 5, 7, 9]
print("O(n log n) ok")

O(nÂ²) â€” quadratic

For every item you do work proportional to every item â€” a nested loop. Fine for small n, painful past a few thousand. Picture everyone in a room shaking hands with everyone else.

quadratic.py
def has_duplicate_slow(nums):
    for i in range(len(nums)):
        for j in range(i + 1, len(nums)):   # compare every pair
            if nums[i] == nums[j]:
                return True
    return False

# the inner loop shrinks each time: (n-1)+(n-2)+...+1 = n(n-1)/2
# that is still O(n^2) â€” halving a quadratic is quadratic.
assert has_duplicate_slow([1, 2, 3, 2]) is True
assert has_duplicate_slow([1, 2, 3, 4]) is False
print("O(n^2) ok")

O(2â¿) and O(n!) â€” the brute-force explosions

These appear when a naive solution tries every combination or every ordering. They are usually a signal that you need a smarter idea (dynamic programming, pruning, greedy). Shown here so you recognise and avoid them.

exponential.py
# O(2^n): naive Fibonacci recomputes the same values exponentially often.
calls = {"n": 0}
def fib(n):
    calls["n"] += 1
    if n < 2:
        return n
    return fib(n - 1) + fib(n - 2)

assert fib(10) == 55
assert calls["n"] > 100          # 177 calls for just n=10 â€” it explodes

# O(2^n): the number of subsets of n items is 2^n.
def all_subsets(items):
    result = [[]]
    for x in items:
        result += [subset + [x] for subset in result]   # doubles each step
    return result

assert len(all_subsets([1, 2, 3])) == 8      # 2^3

# O(n!): the number of orderings (permutations) of n items is n!.
from itertools import permutations
assert len(list(permutations([1, 2, 3]))) == 6   # 3! = 6
print("exponential ok")

5 Â· Sequential vs nested loops â€” add vs multiply

Two rules cover most code you'll analyse:

  • Loops one after another add: O(n) + O(n) = O(2n) = O(n).
  • Loops inside each other multiply: O(n) Ã— O(n) = O(nÂ²).
add_vs_multiply.py
def sequential(nums):          # two separate passes -> n + n = O(n)
    s = 0
    for x in nums:
        s += x                 # first pass
    m = nums[0]
    for x in nums:
        m = max(m, x)          # second pass, runs AFTER the first
    return s, m

def nested(nums):              # loop inside a loop -> n * n = O(n^2)
    pairs = 0
    for a in nums:
        for b in nums:
            pairs += 1
    return pairs

def mixed(nums):               # a loop, then a nested loop -> O(n) + O(n^2) = O(n^2)
    total(nums)                # O(n)
    return nested(nums)        # O(n^2) dominates

assert sequential([1, 2, 3]) == (6, 3)
assert nested([1, 2, 3]) == 9          # 3 * 3
def total(x):                          # tiny helper used above
    return sum(x)
print("loops ok")

"Two loops" is not automatically O(nÂ²)

Only nested loops multiply. Two loops written one after the other are still O(n). Look at the indentation, not the loop count.

6 Â· Where log n comes from

Any time each step halves the remaining work, the number of steps is about logâ‚‚ n. That's binary search, and it's why balanced trees and heaps have log n operations.

halving.py
def halving_steps(n):
    steps = 0
    while n > 1:
        n //= 2               # throw away half each time
        steps += 1
    return steps

assert halving_steps(8) == 3          # 8 -> 4 -> 2 -> 1
assert halving_steps(1024) == 10      # log2(1024) = 10
assert halving_steps(1_000_000) <= 20 # ~log2(1e6) â‰ˆ 20
print("log ok")
ðŸ§ 
Halving vs halving-and-touching-everything

Halving the problem once per step â†’ O(log n). Splitting and still visiting every element at each level â†’ O(n log n) (that's sorting). One extra factor of n makes all the difference.

7 Â· Worst, average and best case

The same algorithm can cost different amounts depending on the input. Linear search is the classic example: the target might be first (lucky), missing (unlucky), or somewhere typical.

cases.py
def linear_search(nums, target):
    comparisons = 0
    for i, x in enumerate(nums):
        comparisons += 1
        if x == target:
            return i, comparisons
    return -1, comparisons

data = [10, 20, 30, 40, 50]
assert linear_search(data, 10)[1] == 1     # BEST: found first  -> O(1)
assert linear_search(data, 50)[1] == 5     # WORST: found last  -> O(n)
assert linear_search(data, 99)[1] == 5     # WORST: not present -> O(n)
print("cases ok")

Interviews assume worst case

Unless you say "average case" or "amortised", state the worst case. For linear search that's O(n), even though the best case is O(1).

8 Â· Amortised cost

Sometimes a single operation is occasionally expensive but cheap almost every other time. Averaged over a long sequence of operations, it's still cheap â€” that average-per-operation guarantee is called amortised cost.

The canonical example is Python's list.append. A list keeps spare capacity; most appends just drop the item into a free slot (O(1)). Occasionally it's full and must copy everything into a bigger block (O(n)) â€” but that happens rarely enough that the average is amortised O(1).

amortised.py
# Building a list of n items with append is O(n) total,
# i.e. amortised O(1) per append â€” even though a few appends
# trigger an expensive internal resize.
def build(n):
    out = []
    for i in range(n):
        out.append(i)        # amortised O(1)
    return out

assert build(5) == [0, 1, 2, 3, 4]
assert len(build(1000)) == 1000
print("amortised ok")
ðŸ§ 
Amortised â‰  average-case

Average-case is about random inputs. Amortised is a guarantee across a sequence of operations â€” no matter the input, a run of n appends costs O(n) total. More on Python's list growth in 01 Â· Python DSA Foundations.

9 Â· What space complexity means

Space complexity is the same idea applied to memory: how does the extra memory you use grow with the input? Split memory into three buckets:

BucketWhat it isCounted?
Input spaceThe data you were handedUsually not counted
Auxiliary spaceExtra memory your algorithm allocates to do its jobYes â€” this is what we optimise
Output spaceMemory for the result you must returnUsually excluded
space.py
# O(1) auxiliary space: one running total, no matter how big nums is.
def sum_in_place(nums):
    s = 0                    # a single number of extra memory
    for x in nums:
        s += x
    return s

# O(n) auxiliary space: we build a brand-new list of size n.
def doubled(nums):
    out = []                 # grows to len(nums)
    for x in nums:
        out.append(x * 2)
    return out

assert sum_in_place([1, 2, 3]) == 6          # O(1) extra memory
assert doubled([1, 2, 3]) == [2, 4, 6]       # O(n) extra memory
print("space ok")

Memory-analysis standard used in this book

No solution is called "memory optimised" without stating baseline vs optimised auxiliary memory, whether the output is excluded, whether the input is mutated, the recursion-stack cost, and any Python container/object overhead. Readable optimal code beats obscure micro-optimisation.

10 Â· The recursion stack is memory too

Every time a function calls itself, the paused call stays on the call stack until it returns. Those pending frames use memory, so recursion depth counts as auxiliary space â€” even when you never allocate a list.

recursion_stack.py
# This uses O(n) auxiliary space even though it builds nothing:
# there are n nested calls waiting on the stack at the deepest point.
def rec_sum(nums, i=0):
    if i == len(nums):
        return 0
    return nums[i] + rec_sum(nums, i + 1)   # one stacked frame per element

# The loop version is O(1) auxiliary space â€” no stack growth.
def loop_sum(nums):
    s = 0
    for x in nums:
        s += x
    return s

assert rec_sum([1, 2, 3, 4]) == 10 == loop_sum([1, 2, 3, 4])
print("stack ok")

When you use recursion, name its depth: "this recurses to O(h) where h is the tree height, so O(n) worst case on a skewed tree." That's part of the auxiliary-space analysis interviewers expect. See 01 Â· Python DSA Foundations.

11 Â· Timeâ€“space trade-offs

Here's the move that turns complexity from trivia into a tool: you can often spend memory to save time, or save memory by doing more work. Interviewers want to hear you weigh both.

Take Two Sum â€” find two numbers that add to a target. The brute force checks every pair; the hash-map version remembers what it has seen.

two_sum_tradeoff.py
# Brute force: O(n^2) time, O(1) auxiliary space.
def two_sum_slow(nums, target):
    for i in range(len(nums)):
        for j in range(i + 1, len(nums)):
            if nums[i] + nums[j] == target:
                return [i, j]
    return []

# Hash map: O(n) time, O(n) auxiliary space.
# We trade memory (the 'seen' dict) for speed (one pass, O(1) lookups).
def two_sum_fast(nums, target):
    seen = {}                       # value -> index
    for i, x in enumerate(nums):
        need = target - x
        if need in seen:            # O(1) average lookup
            return [seen[need], i]
        seen[x] = i
    return []

assert two_sum_slow([2, 7, 11, 15], 9) == [0, 1]
assert two_sum_fast([2, 7, 11, 15], 9) == [0, 1]
print("two sum ok")

Brute force (nested loop)O(nÂ²)O(1)Tiny input, or memory is precious
Hash map (one pass)O(n)O(n)Almost always â€” huge time win

A second, smaller example: reversing a list in place costs O(1) auxiliary space; building a reversed copy costs O(n).

reverse_tradeoff.py
# In-place: O(1) auxiliary space, but mutates the caller's list.
def reverse_in_place(nums):
    i, j = 0, len(nums) - 1
    while i < j:
        nums[i], nums[j] = nums[j], nums[i]
        i += 1; j -= 1
    return nums

# Copy: O(n) auxiliary space, leaves the input untouched.
def reverse_copy(nums):
    return nums[::-1]

original = [1, 2, 3, 4]
assert reverse_copy(original) == [4, 3, 2, 1]
assert original == [1, 2, 3, 4]              # copy left it alone
assert reverse_in_place(original) == [4, 3, 2, 1]
assert original == [4, 3, 2, 1]              # in-place changed it
print("reverse ok")

There is rarely one "best"

There's the best solution for the given constraints. State the trade-off â€” "O(nÂ²) time but O(1) space, or O(n)/O(n) with a hash map" â€” and let the interviewer tell you what they're optimising for.

12 Â· A repeatable analysis recipe

Apply this to any function and you'll never freeze on "what's the complexity?":

  1. Name the input size(s). Usually n; sometimes two, like n rows and m columns.
  2. Count the loops. Nested â†’ multiply. Sequential â†’ add.
  3. Spot hidden costs. x in list is O(n); slicing copies; s += piece on strings is O(n); sorted() is O(n log n). (Details in 01 Â· Python DSA Foundations.)
  4. Drop constants and lower-order terms. Keep the dominant one.
  5. Do the same for memory. Extra allocations + recursion depth = auxiliary space.
  6. State it. "O(_) time, O(_) auxiliary space, worst case, because â€¦".

13 Â· Common beginner traps

âš ï¸
"Two loops = O(nÂ²)"

Only if they're nested. Two loops in sequence are O(n).

âš ï¸
Sorting hidden inside a loop

Calling sorted() once is O(n log n). Calling it inside a loop over n items is O(nÂ² log n) â€” the log factor multiplies through.

âš ï¸
x in my_list is not free

Membership in a list scans it â€” O(n). Inside a loop that's a silent O(nÂ²). Use a set or dict for O(1) membership.

ðŸš«
Calling recursion "O(1) space"

Even with no allocations, n nested calls hold n frames on the stack â€” that's O(n) auxiliary space. Don't forget the stack.

ðŸ§­
Counting the output as auxiliary space

If a problem requires returning a list of n items, that O(n) is output space, usually excluded from "space complexity". Auxiliary space is the extra memory beyond the required output.

One-page cheat sheet
  • Growth order, best â†’ worst: O(1) < O(log n) < O(n) < O(n log n) < O(nÂ²) < O(2â¿) < O(n!).
  • Pictures: constant = one page; log = halving guess; linear = read every page; n log n = sort a deck; quadratic = everyone shakes hands.
  • Simplify by dropping constants and lower-order terms; keep the dominant one.
  • Nested loops multiply; sequential loops add. Halving each step â†’ log n.
  • Interviews assume worst case unless you say otherwise; amortised = averaged over a sequence of operations.
  • Auxiliary space excludes input and required output; recursion depth counts toward it.
  • Trade-off move: spend memory to save time (hashing), or save memory by doing more work (in-place).
  • Interview sentence template: "O(_) time, O(_) space, worst case, because _."
