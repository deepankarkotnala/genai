Python, NumPy & Pandas Performance

Correct code that's 100× too slow fails just as surely as wrong code — especially on real data. This chapter is a catalogue of slow-vs-fast recipes: the naive version, why it's slow, and the idiomatic fix, each with a measured speedup. The throughline is one idea — push the hot loop out of interpreted Python into a set, a built-in, or a vectorised C routine. Every recipe's two versions are verified to produce identical results.

Outcome

Recognise the common Python/NumPy/Pandas performance traps and apply the idiomatic fix: the right container (set/dict/deque/Counter), comprehensions and built-ins over manual loops, NumPy vectorisation/broadcasting/reductions, and pandas column operations, groupby, merge, and boolean indexing instead of row iteration.

1 · Foundations

One idea underlies every recipe: move the inner loop out of interpreted Python. Read this, then browse the recipes in §2 and §3.

Why Python loops are slow — and how to escape them

CPython is an interpreter: every iteration of a Python for loop dispatches bytecode, checks types, and boxes objects. That per-element overhead is fine for hundreds of items and ruinous for millions. The three escape routes, in order of preference: pick a data structure with the right complexity (a set lookup instead of a list scan); use a built-in or C-level helper (sum, join, Counter); or vectorise so the loop happens inside NumPy/pandas' compiled code.

Before optimising, know the two questions: What's the complexity? (a hidden x in list inside a loop is O(n²)) and Where's the loop running? (Python bytecode vs compiled C). Fix the complexity first, then push the loop into C.

Complexity first: the accidental O(n²)

The biggest wins come from algorithmic fixes, not micro-tuning. A membership test inside a loop is the classic trap — switching the container from a list to a set changes O(n²) to O(n), often a 100×+ speedup with a one-line change.

Example — the same task, list vs set
membership.py
# Slow: `in` on a list scans all n items, for each of q queries -> O(q*n)
def count_present(items, queries):
    return sum(1 for q in queries if q in items)          # items is a list

# Fast: build a set once, then each lookup is O(1) -> O(q + n)
def count_present_fast(items, queries):
    lookup = set(items)
    return sum(1 for q in queries if q in lookup)
Measured≈500× faster on 5,000 items × 5,000 queries

Then vectorise: let C run the loop

Once the complexity is right, the second lever is where the loop runs. NumPy and pandas store data in contiguous typed buffers and provide operations that loop over them in compiled C — no per-element Python overhead. Expressing a computation as whole-array/column operations (not a Python loop over elements or rows) routinely buys 10–1000×.

Example — element-wise work, loop vs vectorised
vectorise.py
import numpy as np

a = np.random.random(1_000_000)
b = np.random.random(1_000_000)

# Slow: Python loop, one boxed float at a time
c = np.array([a[i] + b[i] for i in range(len(a))])

# Fast: one vectorised C loop over contiguous memory
c = a + b                                                 # ~100x faster
⚠️
Performance pitfalls

Measure before optimising — profile to find the real hot spot rather than guessing. Beware the accidental O(n²) (membership in a loop, list.pop(0), np.append in a loop). In pandas, iterrows is almost always the wrong tool. And don't sacrifice clarity for a 1.2× win — save the effort for the 100× ones.

Tier 1 · Python core — containers, idioms, the right built-in (8)
1 Membership test: list → set Core `x in list` is O(n); `x in set` is O(1)

The slow way. Repeatedly checking x in items where items is a list scans the whole list every time.

Why it's slow: Each in on a list is a linear scan, so q queries over n items cost O(q·n).

Gotcha
This is the single most common accidental quadratic in Python code — a membership check hidden inside a loop.

The fix Convert the container to a set (or dict) once. Hashing makes each lookup O(1), turning O(q·n) into O(q + n).

membership.py
# --- Slow ---
def membership_slow(items, queries):
    return [q in items for q in queries]         # `in` on a list is O(n)

# --- Fast ---
def membership_fast(items, queries):
    lookup = set(items)                          # set membership is O(1)
    return [q in lookup for q in queries]
Measured≈500× faster (5k items × 5k queries)

Any time you test membership more than a couple of times, build a set first. The lookup difference dwarfs almost every other micro-optimisation.

2 String building: += → join Core Repeated += rebuilds the string each time

The slow way. Concatenating with s += w inside a loop looks harmless but is quadratic.

Why it's slow: Python strings are immutable, so s += w allocates and copies a brand-new string every iteration — O(n²) total.

Gotcha
CPython sometimes optimises simple += in place, but you can't rely on it; join is always safe and clear.

The fix Collect the pieces and call "".join(parts) once — a single allocation sized to the final length.

concat.py
# --- Slow ---
def concat_slow(words):
    s = ""
    for w in words:
        s += w                                   # builds a new string each step ⇒ O(n²)
    return s

# --- Fast ---
def concat_fast(words):
    return "".join(words)                        # single allocation
Measured≈12× faster (100k pieces)

str.join is the idiomatic way to assemble strings. The same lesson applies to building large byte strings or lists you'll join.

3 Counting: manual dict → Counter Core collections.Counter counts in C

The slow way. Tallying frequencies with an if key in d / else branch works but runs entirely in Python bytecode.

Why it's slow: The per-element branch and dictionary lookups are interpreted; a specialised counter does the same work in optimised C.

Gotcha
Counter also gives you .most_common(k) for free — no need to sort the items yourself.

The fix Use collections.Counter(items). It's clearer and moves the hot loop into C.

count.py
from collections import Counter

# --- Slow ---
def count_slow(items):
    counts = {}
    for x in items:
        if x in counts:
            counts[x] += 1
        else:
            counts[x] = 1
    return counts

# --- Fast ---
def count_fast(items):
    return dict(Counter(items))                  # C-level counting
Measured≈3× faster (200k items)

Reach for the specialised containers in collections — Counter, defaultdict, deque — before hand-rolling the same logic.

4 Grouping: dict → defaultdict Core Drop the membership check per key

The slow way. Grouping values by key with an if k not in groups: groups[k] = [] guard before every append.

Why it's slow: Every element pays for an extra membership test and branch; it also clutters the logic.

Gotcha
Don't over-use defaultdict for reads — accessing a missing key silently creates it, which can mask bugs.

The fix Use defaultdict(list) so a missing key auto-initialises; the loop body becomes a single append.

group.py
from collections import defaultdict

# --- Slow ---
def group_slow(pairs):
    groups = {}
    for k, v in pairs:
        if k not in groups:
            groups[k] = []
        groups[k].append(v)
    return groups

# --- Fast ---
def group_fast(pairs):
    groups = defaultdict(list)
    for k, v in pairs:
        groups[k].append(v)                      # no membership check
    return dict(groups)
Measured≈1.3× faster + much cleaner (200k pairs)

A modest speed win but a big readability win — the intent (bucket values by key) reads directly, which matters more than the microseconds here.

5 Ordered dedupe: list-scan → dict.fromkeys Core A 'seen' list is O(n²); dict keys are O(n)

The slow way. Removing duplicates while preserving order by checking x not in seen against a growing list.

Why it's slow: The not in seen test scans a list that grows to size n, so the whole pass is O(n²).

Gotcha
A plain set deduplicates but loses order; dict.fromkeys preserves first-seen order (dicts are ordered since 3.7).

The fix list(dict.fromkeys(items)) keeps first-occurrence order with O(1) membership behind the scenes — O(n) overall.

dedupe.py
# --- Slow ---
def dedupe_slow(items):
    seen, out = [], []
    for x in items:
        if x not in seen:                        # O(n) scan of a list ⇒ O(n²)
            seen.append(x)
            out.append(x)
    return out

# --- Fast ---
def dedupe_fast(items):
    return list(dict.fromkeys(items))            # ordered dict keys are unique, O(n)
Measured≈110× faster (3k items)

When you need ordered uniqueness, dict.fromkeys is the one-liner; a set is fine when order doesn't matter.

6 Transform: loop append → comprehension Core List comprehensions run the loop in C

The slow way. Building a result list by out = [] then out.append(...) in a Python for loop.

Why it's slow: Each iteration pays interpreter overhead for the loop and a method lookup for append.

Gotcha
Don't force a comprehension when you only need a side effect or an aggregate — use a plain loop or a built-in like sum.

The fix A list comprehension expresses the same mapping and runs its loop in optimised C, avoiding the repeated append lookup.

comprehension.py
# --- Slow ---
def squares_slow(nums):
    out = []
    for x in nums:
        out.append(x * x)                        # per-iteration append + bytecode
    return out

# --- Fast ---
def squares_fast(nums):
    return [x * x for x in nums]                 # comprehension runs in C
Measured≈1.5× faster (1M elements)

Comprehensions (and generator expressions) are both faster and more idiomatic than manual accumulation for building sequences.

7 Queue: list.pop(0) → deque Core Popping the front of a list is O(n)

The slow way. Using a list as a queue and calling list.pop(0) to dequeue from the front.

Why it's slow: pop(0) shifts every remaining element left by one, so draining n items is O(n²).

Gotcha
list.append/pop() from the end are O(1) — a list is a fine stack, just not a queue.

The fix Use collections.deque, which offers O(1) append and popleft at both ends.

queue.py
from collections import deque

# --- Slow ---
def queue_slow(values):
    q = []
    for v in values:
        q.append(v)
    out = []
    while q:
        out.append(q.pop(0))                     # list.pop(0) shifts everything ⇒ O(n)
    return out

# --- Fast ---
def queue_fast(values):
    q = deque(values)
    out = []
    while q:
        out.append(q.popleft())                  # deque popleft is O(1)
    return out
Measured≈140× faster (8k items)

Any FIFO / BFS workload should use a deque. This is exactly why the graph chapters reach for it.

8 k smallest: repeated min → heapq Core Don't re-scan for each of k extremes

The slow way. Finding the 3 smallest by calling min, removing it, and repeating.

Why it's slow: Each min plus remove is a full O(n) pass, so k of them is O(k·n) — and mutates the input.

Gotcha
For a single min/max just call min/max; heapq shines when you want the top/bottom k.

The fix heapq.nsmallest(k, nums) (or nlargest) does it in one O(n log k) pass without mutating the data.

k_smallest.py
import heapq

# --- Slow ---
def smallest3_slow(nums):
    nums = list(nums)
    out = []
    for _ in range(3):
        m = min(nums)                            # full O(n) scan each time
        nums.remove(m)
        out.append(m)
    return out

# --- Fast ---
def smallest3_fast(nums):
    return heapq.nsmallest(3, nums)              # single heap pass
Measured≈2.4× faster (200k items)

For 'top/bottom k' use heapq.nsmallest/nlargest; for a full sort use sorted. Rarely hand-roll selection.

Tier 2 · NumPy — vectorise, broadcast, reduce, index (9)
9 Element-wise math: loop → vectorised NumPy Add whole arrays, not elements

The slow way. Adding two arrays with a Python for loop indexing element by element.

Why it's slow: Every element crosses the Python↔C boundary and pays interpreter and boxing overhead.

Gotcha
Indexing a NumPy array in a Python loop is slower than a plain list loop — always vectorise instead.

The fix Operate on whole arrays: a + b runs the loop in compiled C over contiguous memory.

np_add.py
import numpy as np

# --- Slow ---
def npadd_slow(a, b):
    return np.array([a[i] + b[i] for i in range(len(a))])

# --- Fast ---
def npadd_fast(a, b):
    return a + b                                 # vectorised element-wise add
Measured≈120× faster (1M elements)

The golden rule of NumPy: express computation as whole-array operations. If you're writing for i in range(len(arr)), stop and vectorise.

10 Filtering: loop → boolean mask NumPy Select with a boolean array

The slow way. Filtering elements with a Python list comprehension over a NumPy array.

Why it's slow: The comprehension iterates in Python, discarding NumPy's vectorised comparison and selection.

Gotcha
A boolean mask copies the selected elements; if you only need the count, use (a > thr).sum() directly.

The fix Build a boolean mask with a vectorised comparison and index with it: a[a > thr].

np_filter.py
import numpy as np

# --- Slow ---
def npfilter_slow(a, thr):
    return np.array([x for x in a if x > thr])

# --- Fast ---
def npfilter_fast(a, thr):
    return a[a > thr]                            # boolean mask
Measured≈12× faster (1M elements)

Boolean masking is the NumPy idiom for filtering, and it composes: combine conditions with &, |, ~ (parenthesised).

11 Conditional: loop → np.where NumPy Branch-free element selection

The slow way. Applying an if/else to each element with a Python loop (e.g. clamp negatives to zero).

Why it's slow: Per-element branching in Python is slow and can't use the CPU's vectorised paths.

Gotcha
np.where(cond, a, b) evaluates both a and b fully — fine for arrays, but don't hide expensive side effects in them.

The fix np.where(condition, value_if_true, value_if_false) selects element-wise in C.

np_where.py
import numpy as np

# --- Slow ---
def npwhere_slow(a):
    out = np.empty_like(a)
    for i in range(len(a)):
        out[i] = a[i] if a[i] > 0 else 0
    return out

# --- Fast ---
def npwhere_fast(a):
    return np.where(a > 0, a, 0)                 # branch-free selection
Measured≈70× faster (1M elements)

np.where (and np.select for many conditions) replaces per-element if/else. It's the vectorised ternary.

12 Pairwise work: loops → broadcasting NumPy Let shapes expand instead of nesting loops

The slow way. Computing all pairwise distances with a double for loop over points.

Why it's slow: An O(n²) Python double loop with per-pair array ops is brutally slow for even a few hundred points.

Gotcha
Broadcasting an (n,1,d) against (1,n,d) allocates an (n,n,d) temporary — watch memory for large n.

The fix Reshape to broadcast: pts[:,None,:] - pts[None,:,:] forms every pair at once, then reduce along the last axis.

np_broadcast.py
import numpy as np

# --- Slow ---
def npdist_slow(pts):
    n = len(pts)
    out = np.zeros((n, n))
    for i in range(n):
        for j in range(n):
            out[i, j] = np.sqrt(((pts[i] - pts[j]) ** 2).sum())
    return out

# --- Fast ---
def npdist_fast(pts):
    diff = pts[:, None, :] - pts[None, :, :]     # broadcasting builds all pairs
    return np.sqrt((diff ** 2).sum(axis=2))
Measured≈110× faster (150 points)

Broadcasting is NumPy's superpower for pairwise/outer computations — reshape with None (newaxis) so the shapes align, then operate.

13 Reductions: loops → axis aggregate NumPy sum/mean/max take an axis

The slow way. Computing per-column means with nested loops accumulating sums by hand.

Why it's slow: The double loop is interpreted; NumPy's reductions are single vectorised passes.

Gotcha
Mind the axis: axis=0 collapses rows (per-column result), axis=1 collapses columns (per-row).

The fix Use the built-in reduction with an axis argument: m.mean(axis=0).

np_reduce.py
import numpy as np

# --- Slow ---
def npcolmean_slow(m):
    rows, cols = m.shape
    out = np.zeros(cols)
    for j in range(cols):
        s = 0.0
        for i in range(rows):
            s += m[i, j]
        out[j] = s / rows
    return out

# --- Fast ---
def npcolmean_fast(m):
    return m.mean(axis=0)                         # reduce along an axis
Measured≈140× faster (500×200 matrix)

sum, mean, max, argmax, std … all take axis. Reductions along an axis replace almost every manual accumulation loop.

14 Matrix product: triple loop → @ NumPy Use BLAS, don't reimplement it

The slow way. Multiplying two matrices with the textbook triple for loop.

Why it's slow: An O(n³) loop in Python is thousands of times slower than the optimised, cache-aware, multi-threaded BLAS routines NumPy calls.

Gotcha
Use @ (or np.matmul) for matrix products; * is element-wise, a common and silent bug.

The fix A @ B dispatches to BLAS — hand-tuned assembly you can't beat in Python.

np_matmul.py
import numpy as np

# --- Slow ---
def npmatmul_slow(A, B):
    n, k = A.shape
    _, mm = B.shape
    out = np.zeros((n, mm))
    for i in range(n):
        for j in range(mm):
            for t in range(k):
                out[i, j] += A[i, t] * B[t, j]
    return out

# --- Fast ---
def npmatmul_fast(A, B):
    return A @ B                                  # BLAS-backed matrix product
Measured≈1000× faster (60×50 · 50×40)

Never reimplement linear algebra. @, np.linalg.solve, svd, etc. all route to battle-tested numerical libraries.

15 Building arrays: np.append → preallocate NumPy Growing an ndarray in a loop is O(n²)

The slow way. Accumulating results by calling np.append(arr, x) inside a loop.

Why it's slow: Unlike a Python list, a NumPy array can't grow in place — every np.append allocates and copies the entire array, giving O(n²).

Gotcha
Python list.append is amortised O(1); the trap is specifically np.append in a loop.

The fix Vectorise the whole computation (np.arange(n)**2), or preallocate with np.empty(n) and fill by index.

np_grow.py
import numpy as np

# --- Slow ---
def npgrow_slow(n):
    arr = np.array([], dtype=float)
    for i in range(n):
        arr = np.append(arr, i * i)               # reallocates the whole array each call
    return arr

# --- Fast ---
def npgrow_fast(n):
    return (np.arange(n) ** 2).astype(float)      # build it in one vectorised shot
Measuredover 1000× faster (15k elements)

If you must build incrementally, append to a Python list and call np.array once at the end — never grow an ndarray element by element.

16 Gather: loop → fancy indexing NumPy Index with an array of positions

The slow way. Collecting elements at a list of indices with a Python comprehension.

Why it's slow: The gather loop runs in Python, one boxed element at a time.

Gotcha
Fancy indexing returns a copy, not a view — assigning through it (a[idx] = ...) is a scatter, which is also vectorised.

The fix Pass the index array directly: a[idx] gathers all positions in one vectorised operation.

np_gather.py
import numpy as np

# --- Slow ---
def npgather_slow(a, idx):
    return np.array([a[i] for i in idx])

# --- Fast ---
def npgather_fast(a, idx):
    return a[idx]                                 # fancy indexing
Measured≈27× faster (1M indices)

Fancy indexing (and its scatter counterpart) covers most 'reorder / select by position' needs without an explicit loop.

17 Prefix sum: loop → cumsum NumPy Cumulative ops are one call

The slow way. Computing a running total with a Python loop and an accumulator.

Why it's slow: The sequential loop is interpreted; NumPy computes the scan in C.

Gotcha
cumsum is inherently sequential, but NumPy still runs it far faster than a Python loop; np.diff is its inverse.

The fix Use np.cumsum(a) (and np.cumprod, np.diff) for cumulative and difference operations.

np_cumsum.py
import numpy as np

# --- Slow ---
def npprefix_slow(a):
    out = np.empty_like(a)
    run = 0
    for i in range(len(a)):
        run += a[i]
        out[i] = run
    return out

# --- Fast ---
def npprefix_fast(a):
    return np.cumsum(a)                           # vectorised prefix sum
Measured≈40× faster (500k elements)

Prefix sums, running products, and adjacent differences all have vectorised forms — reach for them before writing an accumulator loop.

Tier 3 · Pandas — kill the row loop, group, join, mask (7)
18 Row work: iterrows → vectorised columns Pandas iterrows is the classic pandas trap

The slow way. Computing a new column by looping over rows with df.iterrows().

Why it's slow: iterrows builds a Python Series object for every row — the slowest way to touch a DataFrame.

Gotcha
itertuples is much faster than iterrows, but true column arithmetic beats both by orders of magnitude.

The fix Operate on columns directly: df['a'] + df['b'] runs vectorised over the underlying NumPy arrays.

pd_column.py
import numpy as np
import pandas as pd

# --- Slow ---
def pd_addcol_slow(df):
    res = []
    for _, row in df.iterrows():                  # iterrows is extremely slow
        res.append(row["a"] + row["b"])
    return np.array(res)

# --- Fast ---
def pd_addcol_fast(df):
    return (df["a"] + df["b"]).to_numpy()         # column arithmetic
Measured≈1000× faster (15k rows)

If you're iterating rows in pandas, there's almost always a vectorised column expression instead. This is the number-one pandas performance lesson.

19 Aggregation: iterrows → groupby Pandas Let pandas do the split-apply-combine

The slow way. Summing a value per key by looping rows and accumulating into a dict.

Why it's slow: Row iteration plus per-row dict updates in Python is far slower than pandas' C-level hash aggregation.

Gotcha
groupby skips NaN keys by default — pass dropna=False if you need them counted.

The fix df.groupby('k')['v'].sum() performs the split-apply-combine in optimised C.

pd_groupby.py
import numpy as np
import pandas as pd

# --- Slow ---
def pd_groupsum_slow(df):
    sums = {}
    for _, row in df.iterrows():
        sums[row["k"]] = sums.get(row["k"], 0) + row["v"]
    return sums

# --- Fast ---
def pd_groupsum_fast(df):
    return df.groupby("k")["v"].sum().to_dict()   # hash aggregation in C
Measured≈600× faster (15k rows)

groupby(...).agg(...) is the workhorse of pandas analytics — expressive and vastly faster than manual grouping.

20 Joining: dict-lookup loop → merge Pandas Relational joins are built in

The slow way. Attaching a column from another table by building a lookup dict and mapping ids in a loop.

Why it's slow: Manual per-row lookups run in Python; a hash/merge join runs in C and handles keys, duplicates, and join types correctly.

Gotcha
Check the join how ('left'/'inner'/'outer') and watch for key duplication that can multiply rows unexpectedly.

The fix Use left.merge(right, on='id', how='left') — a proper relational join.

pd_merge.py
import numpy as np
import pandas as pd

# --- Slow ---
def pd_join_slow(left, right):
    lookup = {r["id"]: r["name"] for _, r in right.iterrows()}
    return np.array([lookup.get(i) for i in left["id"]], dtype=object)

# --- Fast ---
def pd_join_fast(left, right):
    return left.merge(right, on="id", how="left")["name"].to_numpy()
Measured≈27× faster (15k × 1k rows)

merge (and join on the index) is the correct, fast tool for combining tables — don't hand-roll lookups.

21 Mapping values: apply → .map Pandas Dict remap without a lambda

The slow way. Translating values via series.apply(lambda x: mapping[x]).

Why it's slow: apply calls the Python lambda once per element; map with a dict does the lookup in optimised code.

Gotcha
map turns keys missing from the dict into NaN; use .replace or a defaultdict-style fill if that's not wanted.

The fix Pass the dict straight to series.map(mapping).

pd_map.py
import numpy as np
import pandas as pd

# --- Slow ---
def pd_map_slow(s, mapping):
    return s.apply(lambda x: mapping[x]).to_numpy()

# --- Fast ---
def pd_map_fast(s, mapping):
    return s.map(mapping).to_numpy()              # dict lookup, vectorised
Measured≈6× faster (50k elements)

For value remapping use .map (Series) or .replace; reserve apply for genuinely custom per-element logic.

22 Filtering rows: iterrows → boolean index Pandas Mask rows, don't loop them

The slow way. Selecting rows that meet a condition by looping and collecting matches.

Why it's slow: Row iteration is the slow path; a boolean mask filters the whole frame in one vectorised step.

Gotcha
Combine conditions with &/| and parenthesise each — Python's and/or don't work element-wise on Series.

The fix Build a boolean Series and index with .loc: df.loc[df['v'] > thr, 'v'].

pd_filter.py
import numpy as np
import pandas as pd

# --- Slow ---
def pd_filter_slow(df, thr):
    keep = []
    for _, row in df.iterrows():
        if row["v"] > thr:
            keep.append(row["v"])
    return np.array(keep)

# --- Fast ---
def pd_filter_fast(df, thr):
    return df.loc[df["v"] > thr, "v"].to_numpy()  # boolean indexing
Measured≈800× faster (15k rows)

Boolean indexing is the pandas equivalent of NumPy masking — the standard, fast way to subset rows.

23 String ops: apply → .str Pandas Vectorised string accessor

The slow way. Transforming text with series.apply(lambda x: x.upper()).

Why it's slow: The lambda invokes the Python method per element; the .str accessor applies it in a single vectorised call and handles NaN.

Gotcha
For pure-Python string methods the speed gain can be small, but .str is cleaner, NaN-safe, and chains (.str.strip().str.lower()).

The fix Use the vectorised string accessor: series.str.upper().

pd_str.py
import numpy as np
import pandas as pd

# --- Slow ---
def pd_upper_slow(s):
    return s.apply(lambda x: x.upper()).to_numpy()

# --- Fast ---
def pd_upper_fast(s):
    return s.str.upper().to_numpy()               # vectorised string method
Measuredcleaner + NaN-safe; scales better (50k)

The .str accessor exposes most string methods vectorised — prefer it to apply for readability and correctness even when the raw speed is similar.

24 Multi-branch: apply → np.select Pandas Vectorise if/elif/else over a column

The slow way. Bucketing values with apply and a nested if/elif/else lambda.

Why it's slow: The lambda runs per element in Python; np.select evaluates the conditions as vectorised boolean arrays.

Gotcha
Conditions in np.select are checked in order — put the most specific first; the final argument is the default.

The fix np.select([cond1, cond2], [val1, val2], default) applies the branches vectorised.

pd_select.py
import numpy as np
import pandas as pd

# --- Slow ---
def pd_bucket_slow(s):
    return s.apply(lambda x: "low" if x < 10 else ("mid" if x < 20 else "high")).to_numpy()

# --- Fast ---
def pd_bucket_fast(s):
    return np.select([s < 10, s < 20], ["low", "mid"], "high")   # vectorised branches
Measured≈8× faster (50k elements)

For multi-way conditional columns, np.select (or pd.cut for numeric bins) replaces a slow apply with vectorised logic.

4 · Interview playbook

  • Profile before you optimise. Say "I'd measure with timeit / a profiler to find the hot spot" — interviewers want evidence, not guesses.
  • Fix complexity first. Spot the accidental O(n²): membership in a loop, list.pop(0), growing an ndarray with np.append.
  • Reach for the right container: set/dict for lookup, Counter/defaultdict for tallies, deque for a queue.
  • Vectorise: whole-array NumPy ops, broadcasting for pairwise work, axis reductions — no Python loop over elements.
  • In pandas, never iterate rows when a column op, groupby, merge, or boolean mask will do — it's typically 100–1000× faster.

5 · Role notes

SDE / Python backend

These idioms decide whether a batch job finishes in seconds or hours. Container choice and avoiding accidental quadratics are everyday code-review points; vectorisation matters wherever you touch arrays or dataframes in a service.

Data Science / ML / AI / GenAI

This is the daily craft: vectorised NumPy and pandas are the difference between an interactive notebook and one that hangs. Feature engineering, data cleaning, and metric computation all live or die by avoiding the row loop.

6 · Review

Cheat sheet
  • Membership / counting / grouping / FIFO in a loop → set / Counter / defaultdict / deque.
  • Manual accumulation or string building → sum / join / comprehension / heapq.
  • Element-wise math, filtering, conditionals → vectorised NumPy (arrays, masks, np.where).
  • Pairwise/outer work, per-axis aggregates → broadcasting and axis reductions.
  • Matrix products → @ / BLAS; never a triple loop.
  • Growing arrays → preallocate or build a list then convert; never np.append in a loop.
  • Pandas per-row work → column ops, groupby, merge, boolean indexing.
  • Value remap / multi-branch column → .map / np.select / pd.cut.

Concept checks

Why is checking x in my_list inside a loop often the biggest hidden performance bug?
Each in on a list is an O(n) scan, so doing it inside a loop of n items is O(n²); converting the list to a set makes each lookup O(1), collapsing it to O(n)
Because lists use more memory than sets
Because the loop variable is copied each iteration
The cost is algorithmic, not constant-factor: membership in a list is linear, and nesting it in a loop squares the work. A one-line change to a set (or dict) makes lookups hash-based and O(1). Fixing complexity like this dwarfs any micro-optimisation.
Why is a + b on two NumPy arrays so much faster than a Python loop adding them element by element?
The vectorised operation runs a single loop in compiled C over contiguous typed memory, avoiding the per-element interpreter overhead and object boxing of a Python loop
Because NumPy caches the result of the addition
Because Python loops always run on a single core and NumPy always uses the GPU
NumPy arrays store raw typed values contiguously, and a + b dispatches to a C routine that loops over them without creating Python objects per element. A Python-level loop pays bytecode dispatch and boxing on every iteration — that overhead, not the arithmetic, is what dominates.

Mastery checklist

  • I choose the right container (set/dict/Counter/deque) to avoid accidental O(n²).
  • I prefer built-ins and comprehensions over manual accumulation loops.
  • I vectorise element-wise NumPy work instead of looping.
  • I use broadcasting and axis reductions for pairwise and aggregate work.
  • I replace pandas row iteration with column ops, groupby, merge, and masks.
  • I profile to find the real hot spot before optimising.
