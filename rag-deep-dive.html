RAG, end to end

Retrieval-augmented generation puts text into the prompt before the model answers. That is the whole idea. Everything hard about it is in the two words "which text" - and in noticing when the retrieved text was wrong.

⏱ Study + practice · 24–36 h Difficulty · Advanced Prereq · Modules 04, 05

1 · What you already know

From module 04: chunks become vectors, and similarity search returns the nearest ones - always, whether or not any are relevant. From module 05: an approximate index makes that search fast, and recall is invisible unless measured.

You have the retrieval half. This page adds the generation half, and then spends most of its length on the part between them, where the failures live.

2 · What breaks now

A model cannot answer from documents it has never seen.

Generic, and useless. The model has no access to your handbook. Three ways to change that:

ApproachHow the model learns itCost of a change
Fine-tuneAdjust weights on your documentsAnother training run
Long contextPaste the whole handbook every timeTokens on every request, forever
RAGFind the relevant paragraphs and paste thoseRe-index the changed document

RAG wins because knowledge changes and weights do not. A policy updated this morning is answerable this afternoon, which is not true of the other two.

3 · Simple breakdown - RAG vs fine-tuning

A RAG

Basic level

What it is. RAG is a pattern in which the application retrieves relevant text at request time and includes it in the prompt, so the model answers from supplied evidence rather than from its weights.

Core purpose. It gives a model access to private or changing information without retraining it, and makes each answer traceable to a source.

Execution model.

Intermediate level

Architecture under the hood. Two pipelines that run at different times. Indexing: load, split, embed, store - offline, once per document version. Querying: embed the question, retrieve, optionally rerank with a cross-encoder, assemble the prompt, generate, attach citations. The retriever and the generator are separate systems and fail separately, which is why they are evaluated separately.

State handling. The index is persistent state, keyed by chunk id and valid only for the embedding model that built it. Per request nothing persists: the question, the retrieved chunks and the answer live for one call. Conversation history is a separate concern the application carries.

Limitations and advanced features. Retrieval failure is silent - the index always returns something. The model can also ignore correct evidence and answer from its weights, which no retrieval fix addresses. Latency is at least two network calls, plus 100–300 ms if reranking. Advanced features are hybrid search, query rewriting, parent-document retrieval, CRAG and Self-RAG.

B Fine-tuning

Basic level

What it is. Fine-tuning continues training an already pre-trained model on a smaller task-specific dataset, changing the weights so the model behaves differently.

Core purpose. It changes behaviour, format and tone - not knowledge.

Execution model.

Intermediate level

Architecture under the hood. The same forward pass, loss and optimizer as module 01. Full fine-tuning updates every parameter; LoRA freezes the base and trains small low-rank matrices per layer, producing an adapter of a few hundred megabytes. Preference methods such as DPO train on chosen-versus-rejected pairs rather than single targets.

State handling. The output is weights. Nothing is retrieved at request time and nothing changes between requests until you train again.

Limitations and advanced features. A poor way to add facts: the model absorbs the style of the training data while still getting details wrong, and there is no citation to check. Every update needs another run. Too many steps on a narrow dataset degrade general ability. It is excellent at format, tone, domain vocabulary and reliable structured output.

The core differences

RAGFine-tuningLong context
Workflow design Index offline, retrieve per request. Updating knowledge means re-indexing one document. Train offline, serve directly. Updating knowledge means another training run. No index. Paste everything into every request, until it stops fitting.
Error recovery Wrong evidence is inspectable - you can read what was retrieved and see why. Retrieval failure is silent unless you check it. Wrong output has no evidence trail. The only fix is more data and another run. Nothing to inspect. Accuracy degrades on facts buried in the middle of a long context.
Architectural paradigm Request-time evidence supply. Weight modification. Brute-force context stuffing.

In short - which one to choose

Choose RAG when:

  • The knowledge is private, large, or changes more often than you could retrain.
  • Answers must cite a source.
  • You need to remove a document and have it stop being answerable immediately.

Choose fine-tuning when:

  • You need a consistent format or tone that prompting cannot hold.
  • Domain vocabulary is unusual enough that the base model misreads the question.
  • A smaller tuned model would be cheaper than a large prompted one at your volume.

Choose neither when:

  • The corpus fits in the context window and is stable. Just paste it.
  • You have not tried a better prompt first.
  • You are choosing between them as alternatives - they solve different problems and production systems often use both.

4 · Without the technology

The simplest thing that works, with no retrieval at all.

This is a real strategy and it is correct for small, stable corpora. It fails on four counts as things grow:

  • Cost. 40,000 input tokens on every request, including "what are your opening hours".
  • Latency. The whole handbook is read on every call, and the prefill is linear in its length.
  • The ceiling. At 400,000 tokens it does not fit at all.
  • Accuracy. Facts in the middle of a very long context are recalled less reliably than facts near either end.

RAG is this, with a step that decides which 2,000 tokens of the 400,000 to send. That is the only difference.

5 · Runtime mechanics

Indexing, offline, once per document version:

  1. A loader reads each source into text plus metadata.
  2. A splitter cuts it into chunks, keeping the metadata on each.
  3. Each chunk is embedded, with the model recorded alongside.
  4. Vectors, chunk text and metadata are written to the store under a stable id.

Querying, per request:

  1. The question is optionally rewritten - pronouns resolved, or expanded into several queries.
  2. It is embedded and searched, usually returning 20–50 candidates.
  3. A reranker scores each candidate against the question with a cross-encoder and reorders them.
  4. Chunks above a threshold are kept, up to a token budget.
  5. They are assembled into a prompt with instructions that constrain the model to the supplied evidence.
  6. The model generates, and the answer is returned with the chunk ids it was given.

Steps 6 and 7 are why retrieval and reranking are separate. Retrieval is cheap and approximate over millions; reranking is expensive and accurate over fifty.

6 · The components, one at a time

Indexing

1 · Loader

Source to text plus metadata. Metadata set here is what a citation later shows, so record the file, page and section now.

2 · Chunk size

Decides what one vector represents. Too small and a chunk lacks the context to be understood; too large and its vector averages several topics into a direction that matches none of them.

SizeGood forFails at
200–400 tokensFAQs, short policies, precise lookupAnything needing surrounding context
500–800 tokensGeneral prose. The usual defaultVery long procedures
1,000–1,500 tokensNarrative, legal clausesPrecision - the vector blurs

3 · Chunk overlap

Repeat the tail of one chunk at the head of the next, so a sentence split across a boundary is intact in at least one of them. 10–20% of chunk size.

4 · Structure-aware splitting

Split at headings, paragraphs or function definitions rather than at a character count. A recursive splitter tries separators in order and only falls back to raw length.

Retrieving

5 · Dense retrieval

Module 04. Handles paraphrase, poor at exact identifiers.

6 · Hybrid retrieval

Dense plus BM25, fused by rank. This is the single highest-value upgrade over the naive version above, and it is roughly twenty lines.

7 · Query rewriting

The user's question is often not a good search query. Two useful forms - resolving pronouns against the conversation, and expanding one question into several.

8 · Reranking

A cross-encoder reads question and chunk together and scores the pair. Far more accurate than cosine, and impossible to precompute - so retrieve 50 cheaply, rerank those, keep 4.

9 · Parent-document retrieval

Index small chunks for precision, then send the model the larger parent section. Best of both, at the cost of storing the relationship.

10 · Metadata filtering

Restrict before searching - by team, date, document type. Module 05 covers how. It is the authorisation boundary.

Generating

11 · The grounding prompt

Three instructions, and all three earn their place.

The third is the one people omit, and without it the model has no permitted way to say it does not know.

12 · Citations

Number the chunks in the prompt and require the number in the answer. Then verify the cited chunk actually contains the claim - a model can cite the wrong number.

13 · Context ordering

Put the strongest evidence first and last. Accuracy on material in the middle of a long context is measurably worse, which matters once you send more than a few chunks.

Correcting

14 · CRAG - corrective RAG

Baseline RAG trusts whatever came back. CRAG grades the retrieved evidence first and acts on the grade.

The refinement step is worth noting on its own: a "relevant" chunk of 700 tokens may hold two useful sentences, and sending only those raises the signal the model sees.

15 · Self-RAG

CRAG grades the evidence. Self-RAG also grades the answer, and decides whether retrieval was needed at all. Four checks:

  1. Does this question need retrieval, or can it be answered directly?
  2. Are the retrieved documents relevant?
  3. Is the answer grounded in them - is every claim supported?
  4. Does the answer actually address the question?

A failed check routes to rewriting the query, retrieving again, or regenerating - bounded by an attempt limit, because these loops can otherwise run forever. This is a graph, not a chain, which is why module 12 exists.

7 · State and data flow

1 · What data is state?The index. Per request: question, retrieved chunks, prompt, answer.
2 · Who writes each field?Ingestion writes the index. Query time writes nothing.
3 · Who reads it?Retrieval reads vectors; the prompt builder reads chunk text and metadata.
4 · Replaced, appended or merged?Chunks replaced by id. Retrieved evidence is assembled fresh per request.
5 · What controls merging?The chunk id, derived from document id and index - see module 05.
6 · Only in memory?The per-request data, yes. The index, no.
7 · Checkpointed?No. A failed RAG call is retried from the start.
8 · In a database?The vectors, chunk text and metadata.
9 · How long does it survive?The index until re-ingested; everything else until the response returns.
10 · What key retrieves it again?Chunk id. Log the ids used for every answer - it is the only way to explain one later.

9 · Break it

Ask about something the corpus does not cover, on a naive version with no relevance floor.

There is no such policy. Four chunks came back because four always come back, none was relevant, and the model wrote a plausible policy and cited chunk 1 for it. Nothing raised. The citation is present and wrong.

Four distinct failures hide behind one symptom, and they need different fixes:

FailureWhere it happensHow you tell
The answer is not in the corpusNowhere - it never existedTop rerank score below the floor
It is there but was not retrievedRetrievalGrep for it; if present, retrieval missed it
It was retrieved but ranked below the cutRankingRaise k and re-check
It was in the prompt and the model ignored itGenerationRead the prompt; the evidence is there and the answer contradicts it

You cannot fix any of these without knowing which one it is, and the naive pipeline gives you no way to tell them apart.

10 · Fix it

1 · Calibrate a floor from labelled questions, then enforce it: drop any chunk that scores below it.

2 · Permit refusal in the prompt, and treat NOT_IN_CONTEXT as a status rather than an answer.

3 · Verify the citation instead of trusting it.

4 · Separate the two evaluations, so you know which half failed.

Those two numbers are the most useful diagnostic in this whole page. High recall and low groundedness means fix the prompt or the model. Low recall means fix chunking, hybrid search or reranking. Chasing the wrong one is the most common way weeks are lost on a RAG system.

13 · Interview preparation

Beginner What is RAG and why use it over fine-tuning? ›

RAG retrieves relevant text at request time and puts it in the prompt, so the model answers from supplied evidence rather than its weights. Fine-tuning changes the weights, which changes behaviour and format but is a poor way to add facts. The deciding factor is usually change rate and traceability: a policy updated this morning is answerable this afternoon with RAG, and every answer can cite the chunk it came from. They are not alternatives - production systems often fine-tune for format and use RAG for knowledge.

Beginner Walk me through a RAG pipeline. ›

Two pipelines. Indexing, offline: load the source, split into chunks, embed each chunk, store the vector with its text and metadata. Querying, per request: embed the question, retrieve candidates, rerank them with a cross-encoder, keep those above a score floor within a token budget, build a prompt that constrains the model to that evidence and permits refusal, generate, and return the answer with the chunk ids used. The two pipelines run at different times and fail in different ways.

Intermediate How do you choose chunk size and overlap? ›

Chunk size decides what one vector represents. Too small and the chunk lacks the context to be understood on its own; too large and its vector averages several topics into a direction matching none of them. I start at 500–800 tokens for prose with 10–20% overlap so a sentence split across a boundary survives intact in one chunk, and I split on structure - headings, paragraphs - rather than a character count. Then I measure retrieval recall on a labelled set and adjust, because the right number is corpus-specific and no default survives contact with real documents.

Intermediate Your RAG system gives a wrong answer. How do you debug it? ›

First separate the two halves, because four different failures produce the same symptom. Check whether the evidence exists in the corpus at all - grep for it. If it is there, check whether retrieval returned it; if not, that is a chunking, hybrid-search or reranking problem. If it was returned but ranked below the cut, raise k and re-check. If it was in the prompt and the answer contradicts it, that is generation, and the fix is the prompt or the model. I track retrieval recall and groundedness as separate metrics precisely so this question is answerable in one look rather than by guesswork.

Intermediate Why add a reranker when you already have similarity search? ›

Similarity search uses a bi-encoder: query and document are embedded separately, so documents can be embedded in advance and the search is cheap over millions. A reranker is a cross-encoder that reads the question and the chunk together, which is far more accurate but cannot be precomputed. So you use the cheap one to get 50 candidates out of millions and the expensive one to order those 50. On my measurements that costs about 210 ms and is usually the single largest quality gain in the pipeline.

Senior How do you stop a RAG system answering when it should not? ›

Retrieval always returns something, so the pipeline must decide whether what came back is good enough. Three layers. A score floor calibrated on labelled answerable and unanswerable questions, enforced in code - not guessed. A grounding prompt that explicitly permits refusal, returning a sentinel like NOT_IN_CONTEXT. And a distinct status in the response so "no evidence", "refused" and "answered" are three different things the caller handles differently. The failure I am guarding against is an off-corpus question producing a fluent invented answer with a citation attached, which looks more verified than an uncited one.

Senior When would you use CRAG or Self-RAG? ›

CRAG grades the retrieved evidence as correct, ambiguous or incorrect, and either refines it, supplements it with web search, or replaces it entirely. Self-RAG adds checks on the answer - is it grounded in the evidence, does it address the question - and loops back to rewrite the query if a check fails. I would reach for CRAG when corpus coverage is patchy and an external fallback is acceptable, and Self-RAG when a wrong answer is expensive enough to justify three to nine model calls per query instead of one. Both need bounded attempts, and both are graphs rather than chains, so LangGraph rather than LCEL.

Staff · design Design RAG over confidential documents with per-user access control. ›

Authorisation belongs at retrieval, as a metadata filter derived from the caller's identity, with the filtered fields payload-indexed - post-filtering means you already searched data the user cannot see, and it also silently breaks top-k. Redact PII at ingestion, not at generation, because once it is in the index it is retrievable. Store the permission attributes on the chunk at index time and re-index when they change; a document losing a permission must stop being retrievable immediately, which means deletion by document id, not a soft flag. Log the question, retrieved chunk ids, scores and prompt version for every answer, since the chunk ids are the only way to explain an answer during an audit months later. Gate prompt and model changes on an eval set measuring retrieval recall and groundedness separately, and alert on the refusal rate - a sudden drop usually means the index broke, not that the questions got easier.

14 · In short, and what comes next

Remember these six:

  • Retrieval always returns something. A calibrated score floor is not optional.
  • Measure retrieval recall and groundedness separately, or you cannot tell which half broke.
  • Hybrid search plus a reranker is the production default. Naive RAG is a prototype.
  • Permit refusal in the prompt, and treat it as a status, not an answer.
  • Log the retrieved chunk ids with every answer - it is the only way to explain one later.
  • CRAG grades the evidence; Self-RAG also grades the answer. Both cost model calls.
🔑
The one idea to remember

RAG is prompt construction with a search step, and every hard problem in it is deciding whether the search result deserves to be in the prompt. Chunking, hybrid search, reranking, floors, CRAG and Self-RAG are all answers to that one question at increasing cost.
