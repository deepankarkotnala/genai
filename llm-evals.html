Deep Dives / LLM Evals - evaluating LLM apps

1 · What you already know

You can build a retrieval pipeline, an agent loop, guardrails and an approval gate. Each of those pages made a claim about what its mechanism prevents.

None of those claims has been measured. This page is about turning them into numbers, and about the two properties of language models that make ordinary testing not work.

2 · What breaks now

You change one line of a prompt to improve tone, run three examples by hand, and ship it.

Two weeks later, refusals have fallen from 12% to 2%. The application stopped saying it did not know and started answering off-corpus questions from whatever retrieval returned.

The obvious fix is to write a test. It does not work, for two reasons:

Ordinary softwareAn LLM application
Deterministic: one input, one outputProbabilistic: the same input can give different, equally valid answers
One benchmark: is it correctMany: factual, grounded, complete, in format, appropriate in tone, fast, affordable
assert result == expectedAn exact-match assertion fails on a correct answer worded differently

You cannot assert on the string. What you can assert on is a property of it: does it cite a real document, does it contain the right order id, did it refuse when it should have.

3 · Simple breakdown - an evaluation suite vs manual review

A An evaluation suite

What it is. An evaluation suite is a fixed set of cases, each declaring an input and what a correct result looks like, run against the application on every change.

Core purpose. It detects regressions before users do, and turns quality from an opinion into a number you can compare with last week's number.

Execution model.

Architecture under the hood. A golden dataset of cases, a runner that executes each one, scorers that grade the output, and a gate that fails the build when a metric drops.

State handling. The cases and the recorded results of each run, keyed by code and prompt version, so a regression can be attributed to a change.

Limitations and advanced features. It measures only what the cases cover. A judge-based scorer costs money per case and drifts across model versions, so it needs its own calibration.

B Manual review

What it is. Reading a sample of outputs and deciding whether they look acceptable.

Core purpose. It gives an immediate, high-quality judgement on the cases a person actually reads.

Execution model. A person runs the application, reads the output, and forms an opinion.

Architecture under the hood. Nothing to build. Somebody's attention, and whatever notes they keep.

State handling. Whatever the reviewer remembers. Nothing is recorded in a comparable form.

Limitations and advanced features. It does not scale past a few dozen cases, is not reproducible between reviewers or weeks, and cannot see the tool calls that produced the answer.

The core differences

An evaluation suiteManual review
ReproducibleYes, the same verdict every runNo, not even between two reviewers
Cases per changeHundreds, in minutesA handful, in an hour
Sees how the answer was reachedYes, if trajectory is scoredRarely - the output scrolls past

In short - which one to choose

  • Use an evaluation suite as the gate. It is what stops a regression reaching production, and it must fail the build to be worth anything.
  • Use manual review to decide what the suite should measure, and to calibrate a judge against cases a person has scored.
  • Every production failure becomes a case before the fix is written. That is how the suite gets better at the things that actually break.

4 · Without the technology

Manual review is where every project starts, and for the first week it is right.

Three properties make it stop working:

  • It does not scale. Forty cases is an hour of reading, so after a fortnight it stops happening before every change.
  • It is not comparable. "Looks fine" last Tuesday and "looks fine" today are not the same measurement, so you cannot tell whether the change helped.
  • It only sees the answer. The tool calls scroll past, so a correct answer produced by reading another customer's order passes.

The third is the one that matters most and is the hardest to notice, because the output looks exactly like a good result.

5 · Runtime mechanics

One evaluation run has four stages.

  1. Load the golden set. Each case declares an input, the expected outcome, and any rules about the path.
  2. Execute. Every case runs against the current code and prompt version, with the full trace captured.
  3. Score twice. The outcome against what was expected, and the trajectory against which tools were allowed to run.
  4. Aggregate and gate. Per-metric numbers, compared with the previous run, and a non-zero exit if a threshold is breached.

Stage 4 is what makes it a gate rather than a report. A suite that cannot fail the build is a notebook.

6 · The components, one at a time

The golden dataset

Golden dataset - a curated set of representative inputs with reviewed expectations, used to score the application repeatably across versions.

Thirty to fifty cases is a workable start. Balance decides what it can detect.

A set where every case is answerable cannot detect an application that stopped saying no.

Outcome scoring

Did the answer contain the right value, the right identifier, the right status? Exact where possible, containment where not.

Trajectory scoring

This is the half most suites are missing, and it is where security and cost regressions appear.

Reference-free metrics

For RAG, the two that matter are independent and must be tracked separately.

One number hides which half broke. A groundedness score of 0.9 with recall of 0.4 means the application is faithfully summarising the wrong documents.

LLM-as-judge

Use one only where a rule genuinely cannot work - tone, faithfulness, explanation quality. "Did it call issue_refund?" is a set membership test, and asking a model is slower, dearer and less reliable than in.

7 · State and data flow

  1. What data is state? The golden set, and the recorded result of every run.
  2. Who writes each field? You write the cases; the runner writes the results.
  3. Who reads each field? The comparison step, and whoever reviews the difference.
  4. Replaced, appended or merged? Results append, one row per run. Nothing is overwritten.
  5. What reducer controls merging? None. Each run is its own record.
  6. Is it only in process memory? No. Results must be durable to compare across runs.
  7. Is it checkpointed? Each run is a record keyed by code and prompt version.
  8. Is it in a database? Or a committed file. Either works if it is versioned.
  9. How long does it survive? Indefinitely. Old results are how you show a trend.
  10. What thread, user or key retrieves it again? The version pair: the code commit and the prompt version.

Row 10 is what makes a regression attributable. A result that does not record which prompt produced it cannot tell you which change caused the drop.

9 · Break it

Now a run the suite passes and production fails. Replace the trajectory checks with a judge.

The run being judged did this.

The answer is correct, so the judge passed it. It did not notice that three orders were read to answer a question about one, because the rubric never mentioned how many lookups were appropriate.

A judge measures what the rubric names, and nothing else. Counting calls is not a judgement.

10 · Fix it

1 · Assert anything decidable. Three lookups where one was needed is arithmetic.

2 · Keep the judge for what a rule cannot express, and give it a written rubric rather than a question.

3 · Calibrate before trusting it. Score twenty runs by hand, have the judge score the same twenty, and measure agreement.

4 · Version the rubric with the results. Changing a rubric moves every score, so a comparison across a rubric change is meaningless unless you know it happened.

5 · Add the production failure as a case before writing the fix, so the fix is verifiable and the regression cannot return unnoticed.

13 · Interview preparation

Q. Why can't you unit-test an LLM app the way you test normal software?

Because LLMs are probabilistic (same input → different valid outputs), so exact-match assertions fail; and quality is multi-dimensional (factuality, relevance, groundedness, tone, latency, cost), not a single correctness bit. You test properties of the output using references, rubrics, classifiers or a judge model.

Q. What is a golden dataset and why does it matter?

A curated, reviewed set of representative input/expected-output examples used to score the app repeatably and compare versions. It's the foundation - your evals are only as good as this set. ~30–50 examples covering common and edge cases is a solid POC size.

Q. What is LLM-as-a-judge and what are its risks?

Using a second LLM to score outputs against criteria, returning a score + reason. It scales open-ended judgement. Risks: bias (position/verbosity/self-preference) and inconsistency - mitigate with temperature 0, a clear rubric, structured output, and calibration against a few human-labeled examples.

Q. How do you evaluate a RAG system?

Separate retrieval from generation. Retrieval: context precision/recall on a set with known supporting docs. Generation: faithfulness/groundedness, answer relevance, citation correctness. This tells you whether a failure is a retrieval problem or a generation problem.

Q. How is evaluating an agent different?

You evaluate the trajectory, not just the final answer: task-completion rate, tool-selection accuracy, efficiency (loops/retries/wasted steps) and correct handoffs - all read from execution traces.

Q. A model update improved your average score. Ship it?

Not on the average alone. Check the worst cases and failure categories for regressions - especially safety and factuality - plus latency and cost. A higher mean can hide a new critical failure.

Q. Give a real example of shipping without evals going wrong.

Air Canada's chatbot hallucinated a refund policy and the airline was held liable; a Chevrolet dealer bot was jailbroken into "selling" a car for $1; a lawyer filed ChatGPT-fabricated legal cases and was fined. All preventable with grounding/safety evals and guardrails.

14 · In short, and what comes next

Remember these six:

  • You cannot assert on the string. Assert on a property of it.
  • Outcome scoring checks the answer; trajectory scoring checks the path.
  • A right answer reached through a forbidden path must fail, and only trajectory catches it.
  • Track retrieval recall and groundedness separately, or one number hides which half broke.
  • A judge measures what its rubric names. Anything countable is an assertion instead.
  • Non-zero exit, and every production failure becomes a case before the fix.
🔑
The one idea to remember

A prompt change is a code change. Shipping one without running the suite is deploying without tests, and the failure it causes is usually silent - the application keeps answering, just less honestly.
