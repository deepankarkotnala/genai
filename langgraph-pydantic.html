Pydantic for LangGraph

LangGraph state is typed, and the type you choose decides whether a bad value stops at the boundary or travels three nodes before it breaks something. This page is about that choice, and about the validation that makes tool arguments safe.

⏱ Study + practice · 4–6 h Difficulty · Intermediate Prereq · Python typing basics

1 · What you already know

From module 10 you have used model.with_structured_output(Ticket) and got an object back instead of text. Ticket was a Pydantic model, and you used it without needing to know why.

Module 12 needs more than that: graph state is declared as a schema, and the schema decides what is checked and when. This page is that choice, made deliberately.

2 · What breaks now

A node returns a value that is the wrong type. Nothing stops it.

The mistake was in parse_urgency. The exception surfaced in route, possibly several nodes later, with a traceback that points at the wrong function.

Worse, if the comparison happens to work - "9" > "8" is True as strings - nothing raises at all, and the routing is wrong for values above 9.

The question this page answers: where should a wrong value be caught, and what does each option cost?

3 · Simple breakdown - Pydantic model vs dataclass

A Pydantic model

Basic level

What it is. A Pydantic model is a Python class declaring named fields with types, which validates and converts input data at the moment an instance is created.

Core purpose. It moves type errors to the boundary where data enters your program, instead of to wherever the bad value is eventually used.

Execution model.

Intermediate level

Architecture under the hood. At class-creation time Pydantic v2 compiles the field definitions into a validator implemented in Rust (pydantic-core). Validation runs there, not in Python, which is why it is fast enough for a request path. The compiled schema also emits JSON Schema, which is exactly what tool calling and with_structured_output send to the model.

State handling. An instance holds its validated fields. By default validation happens only at construction - later assignment is unchecked unless you set validate_assignment=True. Models are mutable unless frozen.

Limitations and advanced features. Construction costs more than a plain dict, which matters in a hot loop but not on a call that also hits a model. Default coercion is lenient: the string "9" becomes 9 silently, which is convenient at an HTTP boundary and dangerous inside a graph. Advanced features are field_validator and model_validator, Field constraints, discriminated unions, model_config with strict=True, and computed_field.

B dataclass

Basic level

What it is. A dataclass is a standard-library decorator that generates __init__, __repr__ and __eq__ from annotated class attributes.

Core purpose. It removes boilerplate from classes that mostly hold data, with no dependency and no runtime cost.

Execution model.

Intermediate level

Architecture under the hood. The decorator reads __annotations__ and writes ordinary methods as source, which are then compiled once at class definition. There is no validation layer at all - the generated __init__ is a sequence of attribute assignments.

State handling. A plain object holding whatever was assigned. frozen=True makes it immutable and hashable; slots=True removes the instance dictionary and saves memory.

Limitations and advanced features. Annotations are documentation to the interpreter, so a wrong type is stored without complaint and a static checker is the only thing that would have caught it. There is no JSON Schema, so it cannot describe a tool to a model. Mutable defaults need field(default_factory=list), and forgetting that is a classic bug. Advanced features are __post_init__, field(compare=False), and pydantic.dataclasses.dataclass, which keeps the syntax and adds validation.

The core differences

In short - which one to choose

Use a Pydantic model when:

  • Data comes from outside your program - an API request, a file, or a model's output.
  • You need JSON Schema for tool calling or structured output.
  • Graph state carries values that a wrong type would corrupt quietly.

Use a dataclass when:

  • The data never leaves your own code and a static checker already covers it.
  • You want zero dependencies, or you are in a hot loop where construction cost shows.
  • You need a frozen, hashable value object.

Use a TypedDict when:

  • You are writing LangGraph state and want the default, lightest option.
  • You accept that nothing is checked at run time - see section 9 before deciding.

4 · Without the technology

Hand-written validation is what Pydantic replaces.

Ten lines for two fields, and it reports one error at a time - a caller with three bad fields fixes them across three round trips. It also cannot describe itself to a model, which is what tool calling needs.

The same two fields, declared.

5 · Runtime mechanics

What happens on Ticket(**data). Seven steps.

  1. The compiled Rust validator for Ticket is looked up - it was built once, when the class was defined.
  2. Each field is located in the input by name or alias.
  3. Missing fields take their default, or are recorded as an error.
  4. Each value is coerced to the declared type in lax mode - "9" becomes 9. In strict mode it is an error instead.
  5. Field constraints run: ge, le, min_length, pattern.
  6. Your field_validator functions run, then any model_validator, which sees all fields together.
  7. If anything failed, one ValidationError is raised listing every problem. Otherwise you get the instance.

Step 7 is the practical difference from hand-written checks. All errors arrive together, with the path to each bad field, which is what makes a retry prompt to a model useful.

6 · The components, one at a time

1 · BaseModel

Subclass it and annotate the fields. A field without a default is required.

2 · Field

Adds constraints, a default and a description. The description is sent to the model when this becomes a tool schema, so it is functional, not decorative.

3 · Optional and defaults

Optional[X] means the value may be None. It does not make the field optional - that is what a default does.

4 · field_validator

Runs after that field is coerced. Return the value, changed or not.

5 · model_validator

Runs once with every field available, which is the only place a rule spanning two fields can live.

6 · Nested models

A field typed as another model validates recursively, and the error path names the nested field.

7 · Strict mode

Turns off coercion. "9" is then an error rather than 9.

Use lax at an HTTP boundary, where everything arrives as a string. Use strict inside a graph, where a string in an int field means a node returned the wrong thing.

9 · Schema for tool calling

This is the connection back to module 10: model_json_schema() is what with_structured_output and bind_tools send.

10 · TypedDict, for comparison

A dict with annotations. Zero runtime cost, zero runtime checking, and LangGraph's default state type.

11 · Pydantic state in LangGraph

Pass a model instead of a TypedDict and every node's returned update is validated as it is merged.

A node returning {"urgency": 99} now raises at that node, naming the field - instead of failing two nodes later in a comparison.

7 · State and data flow

1 · What data is state?The validated field values on the instance.
2 · Who writes each field?Construction. Later assignment writes without checking unless validate_assignment=True.
3 · Who reads it?Any code holding the instance, as ordinary attributes.
4 · Replaced, appended or merged?Replaced per field. In LangGraph the reducer decides, and validation runs after the merge.
5 · What controls merging?Outside LangGraph, nothing. Inside it, the field's reducer.
6 · Only in memory?Yes. A model is an ordinary Python object.
7 · Checkpointed?Only via model_dump(), which is what a LangGraph checkpointer serialises.
8 · In a database?Only if you dump it there.
9 · How long does it survive?Normal Python lifetime.
10 · What key retrieves it again?None at this layer; the thread_id in LangGraph.

Row 2 is the one that surprises people. Validation is a construction-time event by default, so ticket.urgency = 99 succeeds even though Ticket(urgency=99) would not.

9 · Break it

Use a TypedDict for the same graph and run the same bad update.

That one at least raises, two nodes downstream. The silent version is worse - compare strings and it works, wrongly.

An urgency of 10 is the most urgent ticket you have, and it just went to the automated reply. No exception, no log line, no test failure unless someone thought to test the value 10.

10 · Fix it

Type the state with a Pydantic model in strict mode, and the same update fails at the node that produced it.

For values that genuinely arrive as text - an HTTP form, a CSV - keep coercion but put it at the boundary, not in the graph.

Coerce at the edge, validate strictly inside. That one rule covers almost every case on this page.

13 · Interview preparation

Q Pydantic vs dataclass? ›
A dataclass primarily generates ordinary class boilerplate and is lightweight. Pydantic builds validated/parsed runtime models, JSON schema, and rich serialization, at extra runtime cost.
Q Validation vs serialization? ›
Validation transforms/checks input into a trusted model. Serialization converts the trusted model into Python/JSON output according to rules and field inclusion settings.
Q Why forbid extra fields? ›
It detects typos and unexpected input early and is valuable for commands/security-sensitive payloads. For forward-compatible public APIs you may deliberately choose a different policy, but it should be explicit.
Q When would you not use Pydantic for LangGraph state? ›
When state is internal/trusted, high-volume, or frequently updated and recursive validation cost is not justified; also when you require every intermediate update to be validated automatically, because current documented behaviour does not provide that guarantee.
Q How do you validate LLM structured output safely? ›
Define a constrained schema, parse/validate the model output, reject or repair only under a bounded policy, distinguish validation failures from provider failures, and never execute side effects until the validated object passes authorization/domain checks.
Q What is a discriminated union? ›
A union whose member is selected by a known tag field. It produces clearer errors and deterministic tool/event routing compared with ambiguous untagged unions.

14 · In short, and what comes next

Remember these five:

  • Pydantic validates at construction. A dataclass and a TypedDict never validate.
  • Lax mode coerces "9" to 9. Strict mode makes it an error.
  • Coerce at the edge, validate strictly inside.
  • Assignment is unchecked unless validate_assignment=True.
  • model_json_schema() is what tool calling actually sends to the model.
🔑
The one idea to remember

Typing graph state with Pydantic moves the error from wherever the bad value is used to the node that produced it. That is the difference between a traceback that names the bug and one that names its victim.
