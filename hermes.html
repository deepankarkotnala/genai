Hermes and open local models

Module 03 got a model running. This page is about choosing one and trusting it. Hermes is a fine-tune of Llama built for structured tool calling, and testing whether its tool calls are reliable is the work that decides if a local model can sit inside an agent at all.

⏱ Study + practice · 4–7 h Difficulty · Intermediate Prereq · Module 03, Ollama installed

1 · What you already know

From module 03: you can pull a model, check ollama ps shows 100% GPU, and call the endpoint from Python. You know that a 7B model at Q4 needs about 4 GB.

You also know the base-versus-instruct distinction. Hermes is what happens when someone takes that fine-tuning step further and optimises specifically for returning structured output and tool calls.

2 · What breaks now

Take the agent loop from module 08 and point it at a local model.

The model described the tool call in prose instead of emitting one. Your parser finds no tool_calls, the loop does nothing, and the agent stalls.

This is the failure that decides whether a local model is usable in an agent, and it is not about intelligence. A model that answers questions well can still be unable to produce a schema-valid call reliably. Tool-calling reliability is a separate property from answer quality, and it has to be measured separately.

3 · Simple breakdown - Ollama vs vLLM

A Ollama

Basic level

What it is. Ollama is a local model runner that wraps llama.cpp, stores models as quantised GGUF files, and exposes them over an HTTP endpoint on port 11434.

Core purpose. It makes one machine serve one user's models with a single install command and no configuration.

Execution model.

Intermediate level

Architecture under the hood. One Go server over llama.cpp. Weights are memory-mapped rather than copied, so start-up is fast and the OS page cache does the work. Layers are assigned to the GPU until memory runs out and the remainder execute on the CPU. A Modelfile pins a system prompt and sampling defaults into a named model.

State handling. The loaded model is the only resident state, and it is evicted after roughly five idle minutes. Per request there is a KV cache and nothing else. Conversation history is the caller's responsibility.

Limitations and advanced features. Concurrency is limited - parallel requests are largely queued, and each one that does run needs its own KV cache. Throughput on a shared GPU is far below a batching server. Advanced use is Modelfile definitions, OLLAMA_KEEP_ALIVE to stop eviction, and the OpenAI-compatible endpoint at /v1.

B vLLM

Basic level

What it is. vLLM is an inference server that holds model weights in GPU memory and serves many concurrent requests using paged attention and continuous batching.

Core purpose. It maximises how many requests one GPU can serve at once, rather than how easily one person can start a model.

Execution model.

Intermediate level

Architecture under the hood. Paged attention stores the KV cache in fixed-size blocks instead of one contiguous allocation, which removes the fragmentation that otherwise wastes most of the memory reserved per request. Continuous batching rebuilds the batch every decoding step, so a request that finishes frees its slot immediately. Weights are usually fp16 or an AWQ/GPTQ quantisation, not GGUF.

State handling. Weights stay resident for the process lifetime - there is no eviction. KV blocks are pooled and reused across requests, and identical prompt prefixes can share blocks.

Limitations and advanced features. Needs a real GPU; there is no CPU offload to fall back on, so a model that does not fit simply will not start. Setup is a deployment task rather than a command. Advanced features are tensor parallelism across GPUs, prefix caching, structured-output decoding and speculative decoding.

The core differences

OllamavLLM
Workflow design One model, loaded on demand, largely one request at a time. Swapping models is free; concurrency is not. One model, pinned at start-up, many requests interleaved every step. Concurrency is free; swapping is a restart.
Error recovery A model too large silently spills to CPU and gets slow. Failures are local and reproducible. A model too large fails to start, loudly, at boot. Under load, requests queue or are rejected rather than degrading silently.
Architectural paradigm A desktop application with an HTTP endpoint. A throughput-oriented inference server.

In short - which one to choose

Use Ollama when:

  • One person is using the model - development, this course, a local tool.
  • You want to switch between several models during a session.
  • The machine has no discrete GPU and CPU offload is the only option.

Use vLLM when:

  • More than a handful of concurrent users hit the same model.
  • Cost per token on your own hardware is a number someone tracks.
  • The model is pinned and the deployment is long-lived.

Use neither when:

  • You need the strongest available reasoning - that is still a hosted model.
  • Traffic is spiky and hardware would sit idle.
  • Nobody will own GPU drivers and dependency upgrades.

4 · Without the technology

Before models were fine-tuned for tool calling, you asked for JSON in the prompt and parsed whatever came back.

Three failure points in four lines: the model wraps the JSON in prose, it emits a code fence, or it invents a field. Every one needs a retry, and the retries are what made early local agents unusable.

A tool-calling fine-tune replaces "hope" with a trained behaviour - and this page is about measuring how well the training took.

5 · Runtime mechanics

What happens when a tool-calling model receives a request. Seven steps.

  1. Your framework serialises the tool definitions into JSON Schema.
  2. The schemas are inserted into the prompt in the format the fine-tune was trained on - for Hermes, inside <tools> tags.
  3. The chat template wraps everything with the role markers the model expects.
  4. The model generates. Because it was trained on this format, it emits a <tool_call> block rather than prose.
  5. The server parses that block out of the raw text.
  6. Your code validates the arguments against the schema and decides whether to run it.
  7. The result goes back into the messages and the model runs again.

Step 3 is where local tool calling usually breaks. A model served with the wrong chat template produces text that looks reasonable and parses as nothing, because the markers it was trained on never appeared.

6 · The components, one at a time

1 · The base model

Hermes 3 is a fine-tune of Llama 3.1, in 3B, 8B and 70B sizes. It inherits Llama's knowledge and context window; the fine-tune changes behaviour, not facts - module 01, section 3.

2 · The fine-tune's purpose

Trained on instruction following, multi-turn dialogue, structured JSON output and tool calls, with less refusal behaviour than the base instruct model. That last point matters for agents, which frequently ask a model to do dull mechanical things it might otherwise decline.

3 · The chat template

The exact text format wrapping each turn. It ships inside the GGUF, and Ollama applies it automatically. Using a raw completion endpoint bypasses it, which is why the same model can work through /api/chat and fail through /api/generate.

4 · Tool schema

JSON Schema describing the function. The description is not documentation - it is the only thing the model reads to decide whether this tool applies.

5 · The tool call

What the model returns instead of text: a name and an arguments object. It has not run anything - your code decides whether to.

6 · Parallel tool calls

A model may return several calls in one reply.

7 · Structured output

Separate from tool calling: constrain the whole reply to a schema. Ollama supports it through format, which uses grammar-constrained decoding - invalid tokens are masked out, so the output cannot be malformed.

Grammar constraint guarantees the shape but not the meaning. A valid object can still hold a wrong category.

8 · Quantisation choice

Q4_K_M is the default. For tool calling specifically, test Q5 or Q8 as well - argument formatting degrades noticeably before prose quality does.

10 · Licence

"Open weights" is not "open source". Llama's licence has an acceptable-use policy and a user threshold above which you must ask permission. Check it before the model reaches production, not after.

7 · State and data flow

1 · What data is state?The resident weights, and the message list you send on every turn.
2 · Who writes it?Your application appends assistant and tool messages.
3 · Who reads it?The model, in full, on every call.
4 · Replaced, appended or merged?Appended. Tool results are ordinary messages with role tool.
5 · What controls merging?Your code. The server merges nothing.
6 · Only in memory?Yes, in your process.
7 · Checkpointed?No - that is what LangGraph adds in module 12.
8 · In a database?Only if you put it there.
9 · How long does it survive?The lifetime of your variable.
10 · What key retrieves it again?None at this layer.

The message list grows by two entries per tool call - the assistant's call and the tool result. A ten-step agent run re-sends twenty extra messages on its final call, which is why local agents hit the context window sooner than expected.

Two model calls for one question, and the second sent everything the first did plus two more messages. Tool calling doubles the number of forward passes at minimum - which on a local model at 35 tokens per second is the difference between a 2-second and a 5-second answer.

9 · Break it

One successful tool call proves nothing.

Both models answer ordinary questions well. One of them is usable inside an agent and one is not, and no amount of reading the answers would have told you which - the failures are in the shape of the reply, not its content.

10 · Fix it

Three fixes, in the order to try them.

1 · Use the chat endpoint and pass tools properly. Most "the model cannot call tools" reports are a raw completion call that skipped the chat template.

2 · Write the description for the model, not for the reader. Say when to use it, not only what it does - wrong_tool counts drop sharply.

3 · Constrain the output when the model still will not comply. Grammar-constrained decoding makes the malformed reply unrepresentable rather than unlikely.

And keep the audit as a test, so a model swap cannot quietly regress.

That threshold is the decision. Below roughly 90%, a local model belongs in a fixed workflow rather than an agent loop, because every failure compounds across steps.

13 · Interview preparation

Beginner What is Hermes and how does it differ from Llama? ›

Hermes 3 is a fine-tune of Llama 3.1, available in 3B, 8B and 70B. The base knowledge and context window come from Llama; the fine-tune changes behaviour - instruction following, structured JSON output, tool calling, and a lower refusal rate. It adds no new facts, because fine-tuning changes how a model responds rather than what it knows.

Beginner Why would you run a model locally at all? ›

Four reasons: the data is not permitted to leave the network; volume is high enough that per-token pricing dominates; you need output that reproduces months later; or you are working offline. If none of those apply, a hosted model is usually the better default - local serving trades a hard memory ceiling for those four properties.

Intermediate A local model will not call your tools. How do you debug it? ›

Check the endpoint first: tools must go through the chat endpoint so the model’s chat template is applied. A raw completion call bypasses the template and the model never sees the markers it was trained on. Then check the reply shape - prose in content with an empty tool_calls means it described the call instead of making it. Then improve the tool description to say when to use it. Only after those three would I consider a different model or grammar-constrained output.

Intermediate How do you choose between Ollama and vLLM? ›

By concurrency. Ollama serves one user well, swaps models freely, and falls back to CPU when a model does not fit - which makes it right for development and single-user tools. vLLM pins one model in GPU memory and uses paged attention with continuous batching, so a finished request frees its slot mid-flight and one GPU serves many users. The cost is that setup is a deployment task and a model that does not fit simply fails to start.

Senior How do you decide whether a local model is good enough for an agent? ›

Measure tool-call reliability separately from answer quality, because they are different properties and reading the answers will not reveal the difference. I run each prompt variant twenty times and count four outcomes: correct call, described-but-not-called, wrong tool, malformed arguments. Below roughly 90% correct calls the model goes in a fixed workflow rather than an agent loop, because each failure compounds across steps - at 90% per step, a five-step run succeeds about 59% of the time. That audit runs in CI so a model or quantisation change cannot regress it silently.

Senior What operational risks come with open-weight models? ›

Licence first - open weights is not open source, and Llama’s licence carries an acceptable-use policy and a user threshold requiring permission above it. Then version drift: an upstream re-tag can change tool-call reliability with no signal, so pin name, size and quantisation together. Then quantisation quality, which degrades argument formatting before it degrades prose, so the audit has to run per quantisation. Then capacity, because there is no elastic scaling - you own the queue. I would pair it with a hosted fallback triggered by repeated empty tool calls.

14 · In short, and what comes next

Remember these five:

  • Answer quality and tool-call reliability are different properties. Measure both.
  • An empty content with a populated tool_calls is the shape you want.
  • Most local tool-calling failures are a skipped chat template, not a weak model.
  • The tool description is a prompt the model reads, not documentation.
  • Below about 90% call reliability, use a fixed workflow rather than an agent loop.
🔑
The one idea to remember

A local model earns its place in an agent by returning the right shape reliably, not by writing good prose. The audit in section 9 is a twenty-line script and it is the difference between choosing a model and hoping about one.
