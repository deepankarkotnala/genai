Frameworks / LangGraph & its components

1 · What you already know

From module 12 you can write a graph: a state schema, nodes that return partial updates, edges that decide what runs next, and compile() to get a runnable application.

This page goes through those parts one at a time, and adds the three that make LangGraph worth its cost: reducers, the checkpointer, and interrupt.

2 · What breaks now

You have a working graph. Then four requirements arrive, and none of them is about adding a node.

What is asked forWhy the graph as written cannot do it
Remember the conversation across turnsEach invoke starts from the input you passed; nothing is retained
Wait for a human to approve a deleteinvoke either returns or raises. There is no pause
Survive a crash halfway throughNothing was written down, so there is nothing to resume from
Append to a message list from two nodesReturning a field replaces it, so the second node erases the first

The last row is a bug you will hit within an hour of writing your first graph. The other three are the same missing thing: the run has no durable record of where it is.

3 · Simple breakdown - a checkpointer vs holding state in your own process

A The LangGraph checkpointer

What it is. A checkpointer is a storage backend that LangGraph writes the whole state object to after every superstep, keyed by a thread_id you supply.

Core purpose. It makes a run durable. The same graph can then remember across turns, pause for a person, and resume after a crash, without you writing persistence.

Execution model.

Architecture under the hood. A BaseCheckpointSaver implementation - MemorySaver, SqliteSaver, PostgresSaver - passed to compile(). Each write stores a snapshot plus the pending next steps.

State handling. The full state after each superstep, versioned per thread. Reading a thread returns the latest snapshot; the history is retained and addressable.

Limitations and advanced features. Every superstep costs a write, so state size drives latency. Snapshots hold whatever the state holds, including customer data. interrupt and time-travel are built on the same snapshots.

B Holding state in your own process

What it is. Keeping the run's data in local variables or a dictionary that lives only inside the function handling the request.

Core purpose. It runs a graph with no storage dependency and no write per step.

Execution model. The state object is passed from node to node in memory and discarded when the call returns.

Architecture under the hood. Nothing beyond the state object itself. There is no store and no thread key.

State handling. In process memory only, for the lifetime of one call.

Limitations and advanced features. A crash loses the run. There is no pause that outlives the request, and nothing to resume from, so approval has to happen outside the graph.

The core differences

The LangGraph checkpointerHolding state in your own process
Survives a crash mid-runYes, resumes from the last superstepNo, the run is lost
Pause for hours, then resumeYes, interrupt plus a thread idNo
Cost per superstepOne write to the storeNone

In short - which one to choose

  • Use a checkpointer when a run must survive a crash, pause for a person, or remember across turns.
  • Use process state when every run completes inside one request and a failure can simply be retried.
  • In development, MemorySaver gives you the interrupt and time-travel behaviour with no database. It is not durable, so it is not the production answer.

4 · Without the technology

Write the same control flow by hand, with no framework.

This is a correct ReAct agent in fifteen lines, and for a run that completes inside one request it is easier to debug than any graph.

Now add the four requirements from section 2:

  • Memory across turns means persisting state under a key, and reloading it on the next call.
  • Approval means returning from the middle of the loop, storing everything needed to continue, and having a second entry point that resumes.
  • Crash recovery means writing that state after every iteration, not just at the pause.
  • Two nodes appending means deciding, per field, whether an update replaces or merges.

Those four are what LangGraph sells. The graph notation is the smaller half; durable execution is the reason to adopt it.

5 · Runtime mechanics

The unit of execution is not the node. It is the superstep.

  1. The runtime loads the current state for this thread_id from the checkpointer.
  2. Every node the edges have made ready runs. If two are ready, they run in the same superstep.
  3. Each node returns a partial update - a dict of only the fields it changed.
  4. The runtime merges each field using that field's reducer, or replaces it if the field has none.
  5. The new state is written to the checkpointer, together with what runs next.
  6. The edges select the next nodes, and another superstep begins, until an edge reaches END.

Step 3 is the rule people get wrong. A node returns what changed, never the whole state, and returning the whole state is how you accidentally overwrite another node's work.

6 · The components, one at a time

State

A TypedDict declaring every field the graph carries. It is the only channel between nodes: a node cannot see another node's local variables.

Reducers

Reducer - a function attached to a state field that decides how an update combines with the existing value.

No reducer means replace. That default is why two nodes writing the same list means the second one wins.

Nodes

A function from state to a partial update. Nothing else. A node that performs I/O should be async, as the previous page showed.

Edges

A conditional edge is where a chain cannot follow: the destination is computed from the state at run time.

The checkpointer

The second call passes no history. The thread_id is what retrieved it. Swap MemorySaver for PostgresSaver and the same code survives a restart.

interrupt

interrupt only works because the checkpointer wrote the state first. Pause and durability are the same feature.

Subgraphs

A compiled graph can be a node in another graph. That is how a supervisor delegates to a specialist without flattening everything into one state schema.

7 · State and data flow

  1. What data is state? Every field in the TypedDict, and nothing else.
  2. Who writes each field? Any node may return it; the reducer decides how it lands.
  3. Who reads each field? Every node receives the whole state.
  4. Replaced, appended or merged? Per field. No annotation means replaced.
  5. What reducer controls merging? The one in Annotated[type, reducer]. add_messages for messages, operator.add for lists and numbers.
  6. Is it only in process memory? Only without a checkpointer. With one, every superstep is written.
  7. Is it checkpointed? Yes, after every superstep, with the pending next steps.
  8. Is it in a database? With SqliteSaver or PostgresSaver, yes. MemorySaver is a dictionary and disappears with the process.
  9. How long does it survive? Until you delete the thread. Snapshot history is kept, which is what makes time-travel possible.
  10. What thread, user or key retrieves it again? The thread_id in configurable. No thread id, no memory.

Row 10 is the most common production mistake here. A thread_id derived from a session rather than a customer loses the conversation the moment the session ends.

Two details worth reading twice. steps is 2, not 1, because operator.add summed two updates of 1. And superstep 2 ended without a return value: the process could have been restarted between supersteps 2 and 3 with no loss, because the state was on disk.

9 · Break it

Remove one annotation. Just the reducer on messages.

The graph compiles. The types are still correct.

Every node erased the conversation it was supposed to extend. No exception was raised, because replacing a field is the documented default and each node did exactly what it returned.

10 · Fix it

1 · Annotate the field. The fix is the annotation.

2 · Return partial updates, never the whole state. This is the habit that prevents the same class of bug.

3 · Choose the reducer per field, deliberately:

FieldReducerWhy
messagesadd_messagesAppends, and de-duplicates by message id
findingsoperator.addConcatenates lists from parallel nodes
steps, costoperator.addAccumulates across supersteps
status, answernoneThe latest value is the right one

4 · Test with two nodes writing the same field. A single-node graph cannot show this bug, which is why it survives to production.

11 · Production version

ConcernWhat you do
Durable checkpointerPostgresSaver or SqliteSaver. MemorySaver is a development tool
Thread keyDerived from the customer or tenant, never the session. Include the tenant, or threads collide across tenants
State sizeEvery superstep writes the whole state. Keep large payloads out of it and store references instead
Recursion limitSet recursion_limit explicitly. A cyclic graph with no exit hits it rather than running for ever
Snapshot retentionCheckpoints hold conversation content. Set a retention period and enforce deletion
Interrupt expiryA paused thread waits indefinitely. Time out abandoned approvals and record the outcome
Idempotent nodesA resumed superstep may re-run a node. Any side effect in one must be safe to repeat
Reducer reviewEvery field's merge behaviour is a decision. Unannotated means replace, and that is rarely what a list wants
Async nodesUse ainvoke and async nodes for I/O, and keep blocking calls off the loop

13 · Interview preparation

Beginner What is a reducer in LangGraph? ›

A function attached to a state field that decides how an update combines with the existing value. add_messages appends to a message list; operator.add concatenates or sums. A field with no reducer is replaced by each update.

Beginner What does a node return? ›

A partial update: a dict holding only the fields it changed. It never returns the whole state. Returning the whole state rewrites fields other nodes updated in the same superstep.

Intermediate What is a superstep, and why does the distinction matter? ›

One round of execution: every node the edges have made ready runs, all their updates are merged through their reducers, and one checkpoint is written. It matters because two nodes ready at once run in the same superstep and their updates merge, rather than one overwriting the other.

Intermediate What does the checkpointer actually give you? ›

Three things from one mechanism: memory across turns keyed by thread_id, the ability to pause inside a node and resume later, and recovery after a crash. All three exist because the full state is written after every superstep.

Senior Your message list keeps losing history. What is wrong? ›

The field has no reducer, so every update replaces it instead of appending. Annotate it as Annotated[list, add_messages]. This is invisible in a single-node graph, which is why it survives to production - test with two nodes writing the same field.

Senior How do you make a resumable graph safe when a node has side effects? ›

Assume a resumed superstep may re-run the node. Derive an idempotency key from the request rather than generating one per attempt, record completed effects in a durable ledger, and check that ledger before acting. The checkpointer guarantees the state is recoverable; it does not guarantee an effect happened only once.

Staff · design When would you not use LangGraph? ›

When every run completes inside one request and a failure can just be retried. Then the hand-written loop is about fifteen lines, debuggable with a stack trace, and carries no framework upgrade path. Adopt LangGraph for the requirement it actually serves - durable execution, human-in-the-loop pauses, resumable runs across workers - and name that requirement rather than calling it more advanced.

14 · In short, and what comes next

Remember these six:

  • The unit of execution is the superstep, not the node.
  • A node returns only what it changed. Returning the whole state overwrites other nodes.
  • No reducer means replace, which is why an unannotated message list erases itself.
  • The checkpointer is the product: memory, pause and crash recovery are one feature.
  • No thread_id, no memory. Key it by customer or tenant, never by session.
  • A resumed superstep can re-run a node, so any side effect must be idempotent.
🔑
The one idea to remember

LangGraph sells durable execution, not graph notation. The nodes and edges are a way of writing down control flow you could write by hand; the checkpointer is the part that would take you weeks.
