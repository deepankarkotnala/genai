Exceptions, Modules & Packaging

Exception handling questions look easy and are not. The interviewer is checking whether you catch specific errors or blanket everything, and whether you have ever debugged an import problem in a real project.

18 questionsTechnical + code review roundChecked July 2026
⌁
What the interviewer is really testing

Two things. First, that you catch the narrowest exception you can actually handle and let the rest crash loudly — silent failures are worse than crashes. Second, that you have shipped a Python project and know what a virtual environment, a lock file and an editable install are for.

18 questions

Exceptions and error handling

01What is the full try statement, including else and finally?exceptionsbasicshigh-frequency＋
Simple answer

try holds the risky code, except handles specific failures, else runs only if nothing raised, and finally always runs — even on return or an unhandled exception. The else block is underused: it keeps the success path out of the try, so you do not accidentally catch an exception from code that was never meant to be guarded.

try.py
try:
    conn = connect()
except ConnectionError as exc:
    log.warning("connect failed: %s", exc)
    raise
else:
    use(conn)          # only runs if connect() succeeded
finally:
    cleanup()          # always runs
Say this in 30 seconds

try guards, except handles, else runs on success only, finally always runs. else keeps unrelated code out of the try block.

Likely follow-up: What happens if finally contains a return?
02Why is a bare except: a problem?exceptionsanti-patternhigh-frequency＋
Simple answer

It catches everything, including KeyboardInterrupt and SystemExit, so you cannot stop the program with Ctrl-C and shutdown handlers break. It also hides bugs — a typo raising NameError looks identical to the network error you meant to handle. Catch the specific exception, or except Exception at a top-level boundary where you log and re-raise.

Say this in 30 seconds

It swallows KeyboardInterrupt and SystemExit and hides real bugs. Catch specific exceptions, or except Exception only at a boundary.

Likely follow-up: Where in an application is a broad catch actually correct?
03How do you define and use a custom exception?exceptionsdesign＋
Simple answer

Subclass Exception, give it a clear name ending in Error, and attach the context a caller would need to act on. Define one base exception per package so callers can catch everything from your library with a single class. Do not subclass BaseException — that is reserved for things that should not be caught.

custom_exc.py
class RetrievalError(Exception):
    """Base for everything this package raises."""

class IndexUnavailable(RetrievalError):
    def __init__(self, index: str):
        self.index = index
        super().__init__(f"index {index!r} is unavailable")
Say this in 30 seconds

Subclass Exception, name it clearly, attach useful context, and give the package one base exception callers can catch.

Likely follow-up: How should a library decide what to raise versus what to return?
04What is the difference between raise, raise X and raise X from Y?exceptionschaining＋
Simple answer

Bare raise inside an except re-raises the current exception with its original traceback intact. raise X starts a new exception, and Python still shows the original as context. raise X from Y makes the causal link explicit, which is what you want when translating a low-level error into your own domain error.

chaining.py
try:
    row = db.fetch(id)
except psycopg.Error as exc:
    raise RecordUnavailable(id) from exc   # keeps the real cause
Say this in 30 seconds

Bare raise re-raises with the original traceback; from records the cause explicitly when wrapping a low-level error.

Likely follow-up: What does raise X from None do, and when is it right?
05What is the difference between an error and an exception in Python?exceptionsbasics＋
Simple answer

In Python they are the same mechanism — ValueError, TypeError and the rest are all exception classes. The useful distinction is syntax errors, which are raised while parsing before anything runs, versus runtime exceptions, which happen during execution and can be caught. You cannot catch a SyntaxError in the file that contains it.

Say this in 30 seconds

They are the same thing in Python. The real split is syntax errors, caught at parse time, versus runtime exceptions you can handle.

Likely follow-up: Can you ever catch a SyntaxError?
06What is an exception group, and why was it added?exceptionsmodern pythonasyncio＋
Simple answer

Added in Python 3.11, an ExceptionGroup carries several exceptions at once, and except* handles them by type. It exists because concurrent code can fail in more than one way simultaneously — an asyncio.TaskGroup where three tasks fail differently used to lose all but one. It is mostly something you consume rather than raise.

Say this in 30 seconds

A 3.11 feature that carries several exceptions at once, handled with except*. It exists because concurrent tasks can fail in parallel.

Likely follow-up: How does TaskGroup use exception groups?
07How should exceptions be handled in a production API?exceptionsproductiondesign＋
Simple answer

Let errors propagate up to one boundary — a middleware or exception handler — that maps them to a status code, logs with a request ID and stack trace, and returns a safe message. Never leak internal details or stack traces to the client. Catching and swallowing errors deep inside a service is how bugs reach production invisible.

Say this in 30 seconds

Handle at one boundary that maps to status codes, logs with a correlation ID, and returns a safe message. Do not swallow errors deep in the stack.

Likely follow-up: How do you distinguish an expected 4xx from an unexpected 5xx in that handler?
08What are the most common built-in exceptions and when do they appear?exceptionsbasics＋
Simple answer

ValueError for a right-typed but wrong-valued input, TypeError for a wrong type, KeyError and IndexError for missing lookups, AttributeError for a missing attribute — often on None, FileNotFoundError for missing paths, and ZeroDivisionError. Knowing which one to raise matters as much as knowing how to catch them.

Say this in 30 seconds

ValueError for bad values, TypeError for wrong types, KeyError and IndexError for lookups, AttributeError usually from None.

Likely follow-up: Should a function raise ValueError or return None for bad input?
09How do you retry an operation that may fail transiently?exceptionsretryproduction＋
Simple answer

Retry only the exceptions you know are transient — timeouts, 5xx, connection resets — never a validation error. Use exponential backoff with jitter so retries do not stampede, cap the attempts, and make sure the operation is idempotent before you retry it at all. Libraries like tenacity do this properly; hand-rolled loops usually forget the jitter and the cap.

Say this in 30 seconds

Retry only transient errors, with capped exponential backoff and jitter, and only when the operation is idempotent.

Likely follow-up: How would you make a payment call safe to retry?

Modules, imports and environments

10What is the difference between a module and a package?modulesbasics＋
Simple answer

A module is one .py file. A package is a directory of modules, usually with an __init__.py that marks it and can expose a curated public API. Since Python 3.3 namespace packages can skip __init__.py, but including it is still the clearer default for application code.

Say this in 30 seconds

A module is a file, a package is a directory of modules with an __init__.py defining its public surface.

Likely follow-up: What should and should not go inside __init__.py?
11What is the difference between an absolute and a relative import?importsbasics＋
Simple answer

An absolute import names the full path from the project root, like from myapp.services import auth. A relative import uses dots — from .services import auth — and resolves against the current package. Absolute imports are recommended because they are unambiguous and survive files being moved; relative ones break when a module is run directly as a script.

Say this in 30 seconds

Absolute names the full path and is preferred; relative uses dots and breaks when the module is run as a script.

Likely follow-up: Why exactly does a relative import fail when you run the file directly?
12What causes a circular import, and how do you fix it?importsgotchadesign＋
Simple answer

Two modules importing each other, so one is still half-initialised when the other reads from it — you get ImportError or a mysterious AttributeError. Quick fixes are moving the import inside the function or using TYPE_CHECKING for type-only imports. The real fix is usually that the shared piece belongs in a third module both can depend on.

circular.py
from typing import TYPE_CHECKING

if TYPE_CHECKING:          # not imported at runtime
    from .orders import Order

def total(order: "Order") -> float: ...
Say this in 30 seconds

Two modules importing each other, so one is half-built. Move the import into the function, use TYPE_CHECKING, or extract the shared part.

Likely follow-up: Why does the function-level import work when the top-level one does not?
13What happens the first time a module is imported, and the second time?importsruntime＋
Simple answer

The first import finds the file, compiles it, executes the whole module top to bottom, and caches the resulting module object in sys.modules. Every later import of the same name just returns the cached object without re-running anything. That is why module-level code runs exactly once, and why it is a reasonable place for one-time setup — and a terrible place for slow work.

Say this in 30 seconds

It executes the file once and caches the module in sys.modules; later imports return the cache. Module-level code runs exactly once.

Likely follow-up: How would you force a module to actually reload?
14What is a virtual environment and why does every project need one?environmentstoolinghigh-frequency＋
Simple answer

An isolated directory with its own Python and its own installed packages, so two projects can need different versions of the same library without conflict. Without it you install into the system Python, versions collide, and “works on my machine” becomes unavoidable. Create one with python -m venv .venv, or let uv or Poetry manage it.

Say this in 30 seconds

An isolated per-project package directory, so projects with conflicting dependency versions can coexist.

Likely follow-up: How does a virtual environment relate to a Docker image — do you need both?
15What is the difference between requirements.txt and a lock file?packagingdependencies＋
Simple answer

requirements.txt usually lists direct dependencies with loose version ranges. A lock file — poetry.lock, uv.lock, or a pinned requirements.txt from pip-compile — records the exact resolved version of every package including transitive ones, with hashes. You need the lock file for reproducible builds; without it, a deploy six months later installs different code.

Say this in 30 seconds

requirements.txt lists what you want; a lock file pins every resolved version including transitive ones, which is what makes builds reproducible.

Likely follow-up: How do you keep a lock file up to date without breaking production?
16What does an editable install (pip install -e .) do?packagingtooling＋
Simple answer

It installs your project by linking to the source directory instead of copying it, so code changes take effect immediately without reinstalling. It is the normal way to work on a library or a multi-package repo locally. In production you install the built package, not an editable one.

Say this in 30 seconds

It links the package to your source tree so edits apply immediately. For local development only.

Likely follow-up: Why is an editable install a bad idea inside a production container?
17What is pyproject.toml, and what replaced setup.py?packagingmodern python＋
Simple answer

pyproject.toml is the standard project file: build system, metadata, dependencies, and tool configuration for ruff, mypy and pytest all in one place. It replaced the scattered setup.py, setup.cfg and per-tool config files. setup.py still works but a new project in 2026 has no reason to use it.

Say this in 30 seconds

The single standard file for build config, metadata, dependencies and tool settings. It replaced setup.py and setup.cfg.

Likely follow-up: What goes in the [build-system] table and why does it matter?
18How does Python find a module when you import it?importsruntime＋
Simple answer

It checks sys.modules for a cached copy first, then searches the paths in sys.path in order — the script's directory, then PYTHONPATH, then the installed site-packages. The first match wins, which is why naming a local file random.py or email.py shadows the standard library and produces baffling errors.

Say this in 30 seconds

sys.modules cache first, then sys.path in order — script directory, PYTHONPATH, site-packages. First match wins, so local files can shadow stdlib.

Likely follow-up: How would you debug an import that is picking up the wrong file?
