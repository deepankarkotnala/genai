Backend Python, APIs & Databases

“How would you scale a Python backend service?” is a standing question for anyone with backend experience. It is not really about Python — it is about whether you have watched a service fall over and understood why.

22 questionsBackend + AI engineering rolesChecked July 2026
⌁
What the interviewer is really testing

Production instincts. Do you put timeouts on external calls? Do you know what an N+1 query is? Can you explain what happens to your service when the database gets slow? Answer with a specific failure you have seen, not with a list of technologies.

22 questions

Web frameworks and API design

01Why would you pick FastAPI over Django or Flask?fastapiframeworkshigh-frequency＋
Simple answer

FastAPI for JSON APIs and AI services: it is async-native, validates request and response bodies with Pydantic, and generates OpenAPI docs from your type hints. Django when you want a full product with an ORM, admin panel and auth included. Flask when the service is tiny and you want no opinions. For an AI backend calling LLMs, FastAPI's async support is the deciding factor.

Say this in 30 seconds

FastAPI for async JSON APIs with Pydantic validation and free OpenAPI docs. Django when you want the batteries. Flask when it is tiny.

Likely follow-up: What does FastAPI actually run on underneath?
02What is the difference between WSGI and ASGI?asgiframeworks＋
Simple answer

WSGI is the older synchronous interface between a web server and a Python app — one request occupies one worker until it finishes. ASGI is the async successor, so a worker can handle many concurrent requests while they wait on I/O, and it also supports WebSockets and long-lived connections. FastAPI is ASGI, run under uvicorn; Django and Flask are traditionally WSGI, run under gunicorn.

Say this in 30 seconds

WSGI is synchronous, one request per worker. ASGI is async and supports WebSockets, so one worker handles many waiting requests.

Likely follow-up: Can you run a WSGI app under an ASGI server?
03In FastAPI, when should an endpoint be def and when async def?fastapiasynciogotcha＋
Simple answer

Use async def when everything inside awaits — an async HTTP client, an async database driver. Use plain def when the work is blocking, because FastAPI runs those in a threadpool and keeps the event loop free. The dangerous combination is async def containing a blocking call: that stalls every other request on the worker.

Say this in 30 seconds

async def if the internals are awaitable, plain def if they block — FastAPI threadpools those. Never block inside an async endpoint.

Likely follow-up: How would you spot a blocking call in an async endpoint during review?
04What does Pydantic give you in an API?pydanticvalidation＋
Simple answer

Runtime validation and coercion at the boundary from your type hints, with clear structured errors, so bad input is rejected before it reaches your logic. It also generates the OpenAPI schema and serialises responses. Using response models matters as much as request models — it stops you accidentally returning a password hash because it happened to be on the object.

Say this in 30 seconds

Validation and coercion at the boundary from type hints, plus schema generation. Response models also prevent leaking fields.

Likely follow-up: What changed between Pydantic v1 and v2 that matters?
05How do you design a good REST API?api designrest＋
Simple answer

Nouns for resources and HTTP verbs for actions, correct status codes, and consistent error bodies. Version it from day one. Paginate every list endpoint, because the one that returns everything is fine until the table grows. Make writes idempotent where you can, and document it — an API that needs a person to explain it is not finished.

Say this in 30 seconds

Resource nouns, proper verbs and status codes, versioning, pagination on every list, consistent errors, and idempotent writes.

Likely follow-up: How would you version an API without breaking existing clients?
06What is idempotency and why does it matter?api designreliabilitysenior＋
Simple answer

An idempotent operation gives the same result whether it runs once or five times. It matters because clients retry — on a timeout the caller does not know whether the request succeeded, so it sends it again. For creates, accept an idempotency key, store it with the result, and return the original response on a repeat instead of charging the customer twice.

Say this in 30 seconds

Repeating the call produces the same result. Essential because clients retry on timeouts. Use an idempotency key for creates.

Likely follow-up: Which HTTP methods are idempotent by definition?
07How do you handle authentication and authorization in a Python API?securityapi＋
Simple answer

Authentication proves who the caller is — usually a JWT or session validated in middleware. Authorization decides what they may do, and it must be checked per resource, not just per route. The common failure is checking the role but not the ownership, so any logged-in user can read another tenant's record by changing an ID. Never put secrets or roles in a token you do not verify.

Say this in 30 seconds

Authentication in middleware, authorization per resource. The classic bug is checking the role but not whether the record belongs to that user.

Likely follow-up: How would you enforce tenant isolation in a multi-tenant database?
08How would you add rate limiting to an API?apiproduction＋
Simple answer

Track requests per client key in a shared store like Redis, using a sliding window or token bucket, and return HTTP 429 with a Retry-After header. It must be shared state, not in-process, or each replica enforces its own separate limit. For AI endpoints, limit tokens or cost rather than request count, since one request can be a thousand times more expensive than another.

Say this in 30 seconds

Token bucket in Redis so it is shared across replicas, returning 429 with Retry-After. For LLM endpoints, limit tokens rather than requests.

Likely follow-up: Where would you put the limit — application, gateway, or both?

Databases and data access

09What is an N+1 query problem?ormdatabasehigh-frequency＋
Simple answer

You fetch a list with one query, then loop over it and trigger one more query per row — 1 plus N. It is invisible in development with ten rows and catastrophic in production with ten thousand. ORMs cause it through lazy loading; the fix is eager loading with a join, or fetching the related rows in one query and joining in memory.

n_plus_one.py
# N+1 — one query per order
for order in session.query(Order).all():
    print(order.customer.name)

# one query
for order in session.query(Order).options(joinedload(Order.customer)):
    print(order.customer.name)
Say this in 30 seconds

One query for the list plus one per row from lazy loading. Fix it with eager loading or a single join.

Likely follow-up: How would you detect one in a service you did not write?
10When would you use an ORM, and when would you write raw SQL?ormdatabasedesign＋
Simple answer

An ORM for ordinary create-read-update-delete work, where it removes boilerplate and keeps things safe. Raw SQL for complex analytical queries, bulk operations, and anything where you need control of the query plan — an ORM-generated query for a five-table aggregation is usually both slower and harder to read. Mixing both is normal; parameterise either way.

Say this in 30 seconds

ORM for routine CRUD, raw SQL for complex analytics and bulk work. Mixing them is normal, as long as everything is parameterised.

Likely follow-up: How does SQLAlchemy let you drop to raw SQL safely?
11What is a database transaction and what does ACID mean?databasetransactions＋
Simple answer

A transaction groups operations so they all succeed or all roll back. ACID is atomicity (all or nothing), consistency (constraints hold), isolation (concurrent transactions do not see each other's partial work), and durability (committed data survives a crash). In practice the one to discuss is isolation, because its level decides which concurrency anomalies you can hit.

Say this in 30 seconds

All-or-nothing grouping of operations. Atomicity, consistency, isolation, durability — isolation is the one with real trade-offs.

Likely follow-up: What anomaly does READ COMMITTED still allow?
12How do database indexes work, and when do they hurt?databaseperformance＋
Simple answer

An index is a sorted structure that lets the database find rows without scanning the table, turning a linear lookup into a logarithmic one. They cost write speed and disk, since every insert updates every index. They also do not help if the query does not match the leading columns of a composite index, or if you wrap the column in a function. Read the query plan rather than guessing.

Say this in 30 seconds

A sorted lookup structure that avoids full scans, paid for on every write. Check the query plan — an unused index is pure cost.

Likely follow-up: Why does a composite index on (a, b) not help a query filtering only on b?
13What is connection pooling and why does it matter?databaseproduction＋
Simple answer

Opening a database connection is expensive, so a pool keeps a set of them open and hands them out. The pool size is a real capacity limit: if every request holds a connection while it waits on something slow, the pool empties and every other request queues behind it. That is the usual mechanism by which one slow query takes down a whole service.

Say this in 30 seconds

Reusing open connections instead of creating them per request. Pool size is a hard capacity limit, and exhausting it stalls everything.

Likely follow-up: How would you size a pool for 4 workers and a 100-connection database limit?
14When would you choose a NoSQL database over PostgreSQL?databasedesign＋
Simple answer

Rarely, and only for a specific reason: genuinely schemaless documents, extreme write throughput at a scale where sharding is unavoidable, or a key-value access pattern where you never join. PostgreSQL handles JSON, full-text search and vectors through pgvector, so it covers most cases people reach for NoSQL to solve. Default to Postgres and justify moving away.

Say this in 30 seconds

Default to PostgreSQL — it does JSON, search and vectors. Move to NoSQL only for a specific scale or access-pattern reason.

Likely follow-up: What would make you add a separate vector database alongside Postgres?
15How would you handle a long-running task in a web request?queuesarchitecturehigh-frequency＋
Simple answer

Do not do it in the request. Accept the job, put it on a queue — Celery with Redis or RabbitMQ, or a managed queue — return 202 with a job ID, and let the client poll or receive a webhook. Workers process it separately with retries and a dead-letter queue for repeated failures. This is exactly the pattern for document ingestion and batch LLM work.

Say this in 30 seconds

Queue it. Return 202 with a job ID immediately, process it in a worker with retries, and let the client poll or get a webhook.

Likely follow-up: How do you make sure a job is not processed twice?
16What is caching in a backend, and what would you cache?cachingperformance＋
Simple answer

Storing a result so the expensive path is skipped — Redis for shared cache, in-process for tiny hot data. Cache reads that are expensive and change slowly: reference data, computed aggregates, embeddings, LLM responses for identical prompts. Always set a TTL, always include everything the result depends on in the key, and decide what invalidates it before you add it.

Say this in 30 seconds

Redis for shared, in-process for tiny hot data. Cache expensive slow-changing reads, always with a TTL and a complete key.

Likely follow-up: How would you avoid a cache stampede when a popular key expires?

Scaling and running services

17How would you scale a Python backend service?scalingarchitecturehigh-frequency＋
Simple answer

Measure first to find whether you are limited by CPU, I/O, the database or an external API — the answer changes everything. Then: run multiple workers behind a load balancer, keep the app stateless so it scales horizontally, move slow work to a queue, add caching for hot reads, and fix the database with indexes, pooling and read replicas. Rewriting in another language is the last resort, not the first idea.

Say this in 30 seconds

Find the actual bottleneck, then scale horizontally with stateless workers, queue the slow work, cache hot reads, and tune the database.

Likely follow-up: Your service is slow but CPU is at 10%. What is happening?
18How many workers should you run, and why?deploymentscaling＋
Simple answer

For CPU-bound sync workloads, roughly the number of cores — more just adds context switching. For I/O-bound async workloads, fewer workers each handling many concurrent connections is better. The real constraint is usually downstream: database connections, memory per worker, or an external rate limit. Load test rather than copying a formula.

Say this in 30 seconds

Around core count for CPU-bound sync work, fewer for async I/O. The binding constraint is usually database connections or memory.

Likely follow-up: What happens if you run 16 workers against a 20-connection database?
19What makes a service horizontally scalable?architecturescaling＋
Simple answer

Statelessness. If a request can be served by any replica, you scale by adding replicas. That means no in-memory session data, no local file storage, no in-process cache holding something that must be consistent, and no background scheduler running in every replica. Push state to Redis, a database or object storage.

Say this in 30 seconds

Being stateless — any replica can serve any request. No local sessions, local files, or per-replica schedulers.

Likely follow-up: Where would you put a scheduled job so it runs only once across replicas?
20How do you configure a Python app across environments?configproduction＋
Simple answer

Environment variables, loaded and validated once at startup — Pydantic's BaseSettings is the standard way, so a missing or malformed value crashes on boot rather than at 3am. Never commit secrets; pull them from a secrets manager. And never branch on an environment name deep in the code — pass the behaviour in as config.

Say this in 30 seconds

Environment variables validated at startup with Pydantic settings, secrets from a manager, and no if env == 'prod' buried in the code.

Likely follow-up: Why is failing at startup better than failing on first use?
21What would you put in a production Dockerfile for a Python service?dockerdeployment＋
Simple answer

A pinned slim base image, a multi-stage build so build tools do not ship, dependencies installed from a lock file in their own layer for caching, a non-root user, and no secrets baked in. Add a health check endpoint and handle SIGTERM so in-flight requests finish during a rolling deploy. Avoid latest tags anywhere.

Say this in 30 seconds

Pinned slim base, multi-stage build, lock-file install in its own layer, non-root user, health check, and graceful SIGTERM handling.

Likely follow-up: Why does installing dependencies before copying the code speed up builds?
22What do you monitor in a production Python service?observabilityproduction＋
Simple answer

The four that matter: request rate, error rate, latency at p95 and p99 rather than the average, and saturation of CPU, memory and the connection pool. Add structured logs with a correlation ID and distributed traces so you can follow one request across services. For AI services, add token usage, cost per request and model latency as first-class metrics.

Say this in 30 seconds

Rate, errors, p95 and p99 latency, and saturation — plus traces and correlation IDs. For AI, token cost and model latency too.

Likely follow-up: Why is the average latency a misleading metric?
