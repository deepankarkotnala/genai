Memory, Garbage Collection & Performance

“How does Python memory management work?” is a standing question for anyone with two or more years of experience. The answer is two mechanisms, not one, and the second is the part candidates forget.

15 questionsMid to senior · systems depthChecked July 2026
⌁
What the interviewer is really testing

Reference counting frees most objects instantly; a separate cycle collector cleans up the objects that reference each other. Say both. Then be ready to explain how you would actually find a memory leak or a slow function in a running service, because that follow-up is where the real signal is.

15 questions

How Python manages memory

01How does Python memory management work?memorygchigh-frequency＋
Simple answer

Two mechanisms. Every object carries a reference count, and when it drops to zero the object is freed immediately — that handles the vast majority of memory. A separate generational garbage collector periodically finds groups of objects that reference each other but are unreachable from your code, since their counts never reach zero. On top of that, CPython pools small allocations so it does not ask the OS for memory on every object.

Say this in 30 seconds

Reference counting frees objects the moment nothing points at them, and a generational cycle collector cleans up reference cycles that counting cannot.

Likely follow-up: Give me an example of a cycle that reference counting cannot free.
02What is a reference cycle, and how does Python handle it?gcmemory＋
Simple answer

Two or more objects pointing at each other — a parent holding children that hold the parent, or a list containing itself. Their counts never reach zero even after your last reference is gone, so reference counting alone would leak them. The cycle collector walks tracked objects, finds groups unreachable from the outside, and frees them.

cycle.py
a, b = Node(), Node()
a.peer = b
b.peer = a          # each keeps the other alive
del a, b            # counts stay at 1 — the cycle collector handles it
Say this in 30 seconds

Objects referencing each other, so their counts never hit zero. The generational garbage collector detects and frees them.

Likely follow-up: How would you avoid creating the cycle in the first place?
03What does 'generational' mean in Python's garbage collector?gcmemory＋
Simple answer

New objects start in generation 0 and are scanned often; those that survive move to generation 1, then 2, which are scanned progressively less. The assumption is that most objects die young, so scanning the young ones frequently catches most garbage for very little work. You can inspect and tune this with the gc module, though tuning is rarely the right fix.

Say this in 30 seconds

Objects are grouped by age; young ones are checked often, old ones rarely, because most objects die young.

Likely follow-up: When would disabling the GC actually help performance?
04What is a weak reference and when would you use one?memoryweakref＋
Simple answer

A reference that does not increase the reference count, so it never keeps the object alive. Use it for caches and observer registries where you want the entry to disappear when the real owner drops the object — weakref.WeakValueDictionary is the usual tool. It also breaks parent-child cycles: keep the child's link back to the parent weak.

Say this in 30 seconds

A reference that does not keep the object alive. Used for caches and to break parent-child cycles.

Likely follow-up: What happens when you access a weak reference after the object is gone?
05How would you find a memory leak in a Python service?memorydebuggingproduction＋
Simple answer

Confirm it first — plot resident memory over time; steady growth under steady load is a leak, a sawtooth is normal. Then use tracemalloc to snapshot allocations at two points and diff them, which shows the lines allocating what is not being freed. objgraph or gc.get_objects() helps find what is holding the references. In practice the cause is usually an unbounded cache, a growing module-level list, or a closure holding a large object.

tracemalloc.py
import tracemalloc

tracemalloc.start()
snap1 = tracemalloc.take_snapshot()
# ... run the workload here ...
snap2 = tracemalloc.take_snapshot()
for stat in snap2.compare_to(snap1, "lineno")[:10]:
    print(stat)
Say this in 30 seconds

Confirm growth under steady load, diff two tracemalloc snapshots to find the allocating lines, then look for an unbounded cache or a growing global.

Likely follow-up: What is the most common cause you have personally seen?
06Does Python return freed memory to the operating system?memorycpython＋
Simple answer

Not always. Small objects come from CPython's internal pools, and those pools are only released when an entire arena is empty, which fragmentation often prevents. So a process that briefly loaded a huge list can keep a high resident size afterwards. If memory must come back, do the heavy work in a separate process and let it exit.

Say this in 30 seconds

Often not — small-object pools are only returned when fully empty, so peak usage tends to stick. Isolate heavy work in a subprocess.

Likely follow-up: How does that change how you size a container's memory limit?
07What is interning, and where does Python do it?memoryinterningcpython＋
Simple answer

Reusing one object for a value instead of creating duplicates. CPython interns small integers from -5 to 256 and short identifier-like strings, so those comparisons with is can appear to work. It saves memory and speeds up dict lookups, but it is an implementation detail you must never depend on.

Say this in 30 seconds

Reusing one object for common values — small ints and identifier-like strings. It is a CPython optimisation, not a guarantee.

Likely follow-up: How would you deliberately intern a string, and why might you?

Making Python faster

08How do you find out why Python code is slow?profilingperformancehigh-frequency＋
Simple answer

Measure before changing anything. cProfile gives per-function call counts and cumulative time, which finds the hot function. line_profiler narrows it to the line. For a live service, a sampling profiler like py-spy attaches to a running process with almost no overhead. Guessing at the bottleneck is how people optimise the wrong 5% of the code.

profile.sh
python -m cProfile -s cumtime app.py | head -20
py-spy top --pid 4242          # live process, no restart
Say this in 30 seconds

cProfile for per-function cost, line_profiler to narrow it down, py-spy to profile a running process. Always measure first.

Likely follow-up: What is the difference between total and cumulative time in cProfile output?
09What are the biggest wins when optimising Python?performancepractical＋
Simple answer

Fix the algorithm first — an O(n²) loop replaced by a dict lookup beats any micro-optimisation. Then move work out of loops, use built-ins and comprehensions which run in C, and batch I/O and database calls instead of calling per item. Only after that consider NumPy vectorisation, caching, or pushing hot code into C or Rust.

Say this in 30 seconds

Algorithm first, then batching I/O, then built-ins and comprehensions, then vectorisation. Micro-optimisation is last.

Likely follow-up: You have a loop doing one database query per item — what do you do?
10Why is a list membership test slow and a set test fast?performancecomplexityhigh-frequency＋
Simple answer

x in list scans item by item, so it is O(n). x in set hashes x and jumps to a slot, so it is O(1). Inside a loop that difference turns a linear job into a quadratic one — converting the lookup collection to a set is the single most common real speedup in ordinary Python code.

membership.py
# O(n * m)
[x for x in items if x in blocklist]          # blocklist is a list

# O(n)
blocked = set(blocklist)
[x for x in items if x in blocked]
Say this in 30 seconds

Lists scan linearly, sets hash directly. Converting a lookup list to a set is the most common real-world speedup.

Likely follow-up: When would building the set cost more than it saves?
11Why is string concatenation in a loop slow?performancestrings＋
Simple answer

Strings are immutable, so every += allocates a new string and copies everything so far — n concatenations copy roughly n²/2 characters. Collect the pieces in a list and "".join() once, which allocates a single result. CPython sometimes optimises the simple case in place, but that is fragile and disappears the moment another name references the string.

Say this in 30 seconds

Each += copies the whole string because strings are immutable, making it quadratic. Collect in a list and join once.

Likely follow-up: What about building large strings with io.StringIO?
12When does __slots__ actually help?performancememoryslots＋
Simple answer

When you create very many small instances. Removing the per-instance __dict__ can cut memory substantially and speed up attribute access. At a few thousand objects it is noise; at a few million it is the difference between fitting in memory and not. Measure with sys.getsizeof or tracemalloc rather than assuming.

Say this in 30 seconds

Only at large object counts — it drops the per-instance dict, saving real memory across millions of instances.

Likely follow-up: What do you lose by adding __slots__?
13How do you speed up code that is genuinely CPU-bound?performancecpu-bound＋
Simple answer

First check whether the work can be vectorised with NumPy or expressed in Pandas, which pushes the loop into C. If not, use multiprocessing to use more cores, since threads will not help while the GIL exists. Beyond that, compile the hot path with Numba or Cython, or call a library written in C or Rust. Rewriting everything is almost never the answer — one function usually dominates.

Say this in 30 seconds

Vectorise with NumPy, then multiprocessing for more cores, then Numba, Cython or a native library for the one hot function.

Likely follow-up: Why will threads not help a CPU-bound Python loop?
14What is caching, and where does it go wrong?performancecaching＋
Simple answer

Storing an expensive result so later calls are cheap — lru_cache in-process, Redis across processes. It goes wrong through staleness when the source changes and nothing invalidates, through unbounded growth when there is no maxsize or TTL, and through caching per-user data under a shared key, which is a data-leak bug rather than a performance one. Always define what invalidates an entry before you add the cache.

Say this in 30 seconds

Store expensive results, but always define the invalidation rule, a size limit, and make sure the key includes everything the result depends on.

Likely follow-up: How would you cache per-tenant data safely?
15How would you process a file that is larger than available memory?memorygeneratorspractical＋
Simple answer

Stream it. Iterating a file object yields one line at a time, so memory stays flat regardless of file size. For structured data, read in chunks — pandas.read_csv(chunksize=...) or a columnar format like Parquet that lets you read only the columns you need. Never call .read() or readlines() on a file you did not size first.

Say this in 30 seconds

Stream it line by line or in chunks, and use a columnar format to read only the columns you need. Never read the whole file at once.

Likely follow-up: How would you do a group-by aggregation over a file that does not fit in memory?
