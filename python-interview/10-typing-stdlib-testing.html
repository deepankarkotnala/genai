What the interviewer is really testing

Whether your habits are professional. Do you type-hint public functions? Do you know what a fixture is? Can you mock a dependency without mocking the thing you are trying to test? These questions rarely have clever answers — they just reveal experience.

Type hints and modern typing

01What are type hints and what do they actually do at runtime?typinghigh-frequency＋
Simple answer

They annotate expected types and Python ignores them completely at runtime — nothing is checked or converted. Their value is in static checkers like mypy catching mistakes before you run, in editors giving real autocomplete, and in making function contracts readable. Libraries such as Pydantic and FastAPI do enforce them, but that is the library reading the annotations, not Python.

Say this in 30 seconds

Annotations for tools and humans. Python ignores them at runtime; mypy checks them statically and Pydantic enforces them deliberately.

Likely follow-up: How would you gradually add typing to a large untyped codebase?
02How do you write modern type hints in Python 3.10+?typingmodern python＋
Simple answer

Use built-in generics — list[str], dict[str, int] — rather than importing from typing. Use X | None instead of Optional[X], and X | Y instead of Union. Reserve typing imports for things with no built-in form: Protocol, TypeVar, Literal, Callable, Any.

hints.py
def top_chunks(
    query: str,
    docs: list[dict[str, float]],
    limit: int | None = None,
) -> list[str]:
    ...
Say this in 30 seconds

Built-in generics like list[str], and X | None instead of Optional. typing is only for Protocol, TypeVar, Literal and friends.

Likely follow-up: What is the difference between Any and object?
03What is a Protocol, and how is it different from an ABC?typingprotocolsdesign＋
Simple answer

A Protocol defines a structural contract: any class with the right methods satisfies it, with no inheritance and no registration. That is duck typing made checkable. An ABC requires the class to actually inherit from it. Use a Protocol when you do not control the classes that must fit — including third-party ones.

protocol.py
from typing import Protocol

class SupportsEmbed(Protocol):
    def embed(self, text: str) -> list[float]: ...

def index(model: SupportsEmbed) -> None: ...   # any class with embed() fits
Say this in 30 seconds

A Protocol is structural — anything with the right methods matches, no inheritance needed. An ABC requires explicit subclassing.

Likely follow-up: Can you check a Protocol at runtime with isinstance?
04What is TypeVar and when do you need a generic function?typinggenerics＋
Simple answer

A TypeVar links types across a signature: it says the return type is the same as an argument type, whatever that turns out to be. Without it you would annotate Any and lose all checking. Python 3.12 added cleaner syntax — def first[T](items: list[T]) -> T — with no import required.

Say this in 30 seconds

It ties the return type to an argument type, so a generic helper keeps type information instead of degrading to Any.

Likely follow-up: How would you constrain a TypeVar to only numbers?
05How useful is mypy in practice, and how do you introduce it?typingmypytooling＋
Simple answer

Very, once it is enforced. Introduce it gradually: run it in non-strict mode over the whole codebase, fix what it finds, add it to CI so nothing regresses, then turn on strictness module by module starting with new code. Turning on strict mode everywhere on day one produces thousands of errors and gets the tool switched off.

Say this in 30 seconds

Start non-strict across the codebase, wire it into CI so it cannot regress, then tighten module by module starting with new code.

Likely follow-up: What do you do about a third-party library with no type stubs?

Standard library essentials

06Which standard library modules do you reach for most?stdlibpractical＋
Simple answer

pathlib for file paths, json for serialisation, datetime and zoneinfo for time, collections for Counter and defaultdict, itertools for lazy iteration, functools for caching and decorators, logging for output, dataclasses for records, and subprocess for shelling out. Naming these and saying why beats reciting the module index.

Say this in 30 seconds

pathlib, json, datetime with zoneinfo, collections, itertools, functools, logging and dataclasses. Those cover most day-to-day work.

Likely follow-up: Which one has saved you the most time and why?
07Why use pathlib instead of os.path?stdlibfiles＋
Simple answer

pathlib gives you path objects with methods rather than string manipulation, so path / "sub" / "file.txt" replaces nested os.path.join calls and works on every platform. It bundles reading, writing, globbing and existence checks onto the object. os.path still works, but new code has no reason to prefer it.

pathlib.py
from pathlib import Path

config = Path("app") / "config" / "settings.json"
if config.exists():
    data = json.loads(config.read_text(encoding="utf-8"))
Say this in 30 seconds

Path objects with methods and a / operator, cross-platform, with read, write and glob built in.

Likely follow-up: How do you handle paths that come from user input safely?
08How should you configure logging in an application?loggingproductionhigh-frequency＋
Simple answer

Get a logger per module with logging.getLogger(__name__), configure handlers and levels once at the application entry point, and never call print in library code. In production, log JSON to stdout so the platform collects it, include a request or correlation ID, and never log secrets or personal data. Libraries should log but not configure.

logging_setup.py
import logging

log = logging.getLogger(__name__)
log.info("indexed %s chunks for %s", count, tenant_id)   # lazy formatting
Say this in 30 seconds

One logger per module, configured once at the entry point, JSON to stdout in production, with a correlation ID and no secrets.

Likely follow-up: Why pass arguments to log.info instead of using an f-string?
09What are the common date and time mistakes in Python?datetimegotchaproduction＋
Simple answer

Using naive datetimes with no timezone, then comparing them to aware ones, which raises. Using datetime.now() when you meant UTC — use datetime.now(timezone.utc). Storing local time in the database instead of UTC, and converting only for display. And assuming a day is always 24 hours, which daylight saving breaks.

Say this in 30 seconds

Store and compute in UTC with aware datetimes, convert only for display, and never mix naive and aware objects.

Likely follow-up: How would you store a future appointment across a daylight-saving change?
10What is the difference between JSON and pickle?serializationsecurity＋
Simple answer

JSON is text, language-independent, and limited to basic types. Pickle is Python-specific binary that can serialise almost any object — including code references, which is exactly why unpickling untrusted data can execute arbitrary code. Use JSON for anything crossing a trust boundary; use pickle only inside your own process boundary, like multiprocessing.

Say this in 30 seconds

JSON is portable text for basic types; pickle is Python-only binary and unsafe on untrusted input because it can execute code.

Likely follow-up: How would you serialise a NumPy array or a dataclass to JSON?
11How do you read a large JSON or CSV file safely?filesmemorypractical＋
Simple answer

For CSV, iterate with csv.DictReader or read in chunks with Pandas — never readlines(). For JSON, the standard library only parses whole documents, so either switch the format to JSON Lines and parse one object per line, or use a streaming parser like ijson. Always open with an explicit encoding.

Say this in 30 seconds

Stream it. CSV row by row or in chunks; for JSON, use JSON Lines or a streaming parser, because json.load reads everything.

Likely follow-up: Why is JSON Lines a better format for large data exports?

Testing, mocking and code quality

12What makes a good unit test?testinghigh-frequency＋
Simple answer

It tests one behaviour, has a name that says what should happen, runs fast, and does not depend on the network, the clock, or other tests. It should fail for exactly one reason. Test the public behaviour rather than internal implementation — a test that breaks every time you refactor is costing you more than it protects.

Say this in 30 seconds

One behaviour, a descriptive name, fast, isolated, and testing public behaviour rather than internals.

Likely follow-up: How do you test something that depends on the current time?
13What is a pytest fixture?pytesttesting＋
Simple answer

A function marked @pytest.fixture that produces test setup, which pytest injects into any test that names it as an argument. Fixtures can yield, so anything after the yield is teardown that runs even if the test fails. Scopes — function, module, session — control how often the setup is repeated.

fixture.py
@pytest.fixture
def db_session():
    session = Session()
    yield session            # test runs here
    session.rollback()       # teardown, always runs

def test_insert(db_session):
    ...
Say this in 30 seconds

Reusable setup injected by name, with teardown after a yield and a scope controlling how often it runs.

Likely follow-up: What does conftest.py do?
14How do you test the same logic against many inputs?pytesttesting＋
Simple answer

@pytest.mark.parametrize runs the test once per input set, and each case reports separately so you know exactly which one failed. That is much better than a loop inside one test, which stops at the first failure and hides the rest. Include the edge cases — empty, zero, negative, unicode — as explicit parameters.

parametrize.py
@pytest.mark.parametrize("raw,expected", [
    ("", 0),
    ("a,b", 2),
    ("a,,b", 3),
])
def test_field_count(raw, expected):
    assert count_fields(raw) == expected
Say this in 30 seconds

@pytest.mark.parametrize, so each case runs and reports as its own test instead of stopping at the first failure.

15How do you test code that calls an external API?testingmockinghigh-frequency＋
Simple answer

Do not hit the real API. Inject the client as a dependency so tests can pass a fake, or patch it with unittest.mock, or intercept at the HTTP layer with responses or respx. Then test both the happy path and the failures — timeout, 500, malformed body — since those are the paths that actually break in production. Keep a small number of real contract tests outside the unit suite.

Say this in 30 seconds

Inject or patch the client, or intercept at the HTTP layer, and test the failure paths too. Real calls belong in a separate contract test.

Likely follow-up: What is the risk of mocking too much?
16What is the difference between a mock, a stub and a fake?testingmocking＋
Simple answer

A stub returns canned answers. A mock also records how it was called so you can assert on the interaction. A fake is a real working implementation that is simply lighter — an in-memory dictionary standing in for a database. Fakes usually give the most reliable tests, because mocks can pass while the real integration is broken.

Say this in 30 seconds

Stubs return canned data, mocks also record calls, fakes are lightweight real implementations. Fakes give the most trustworthy tests.

Likely follow-up: How would you build a fake for a vector database?
17Where do you patch when using unittest.mock.patch?testingmockinggotcha＋
Simple answer

Patch where the object is used, not where it is defined. If myapp.service does from myapp.client import fetch, you patch myapp.service.fetch, because the import bound a separate name in that module. Getting this wrong is the single most common reason a mock silently has no effect.

Say this in 30 seconds

Patch where it is looked up, not where it is defined — myapp.service.fetch, not myapp.client.fetch.

Likely follow-up: How does that change if the module imports the whole module instead of the name?
18Is 100% test coverage a good goal?testingqualityopinion＋
Simple answer

No. Coverage tells you which lines ran, not whether the behaviour is correct — you can hit every line and assert nothing. Aim for high coverage of the logic that matters, especially branches and error paths, and accept low coverage on glue code. A team chasing 100% starts writing tests for getters instead of for the tricky conditional.

Say this in 30 seconds

No — coverage measures lines executed, not correctness. Cover the logic and error paths that matter, not every line.

Likely follow-up: What would you measure instead to know the suite is good?
19What is the testing pyramid, and does it apply to AI applications?testingdesignai＋
Simple answer

Many fast unit tests, fewer integration tests, very few slow end-to-end tests. It still applies to AI systems, with one addition: model output is non-deterministic, so you unit-test the deterministic parts — chunking, parsing, retrieval, prompt assembly — and evaluate the model separately against a graded dataset rather than asserting on exact strings.

Say this in 30 seconds

Mostly unit, some integration, few end-to-end. For AI, unit-test the deterministic parts and evaluate model output separately with a graded dataset.

Likely follow-up: How would you write a regression test for a RAG pipeline?
20How do you debug a problem you cannot reproduce locally?debuggingproduction＋
Simple answer

Start from evidence rather than guesses: logs with correlation IDs, a traceback, metrics around the time of failure, and the exact input if you can capture it. Add structured logging around the suspect path and ship it. Reproduce in staging with production-shaped data. pdb and breakpoint() are for local work; in production you rely on what you instrumented beforehand.

Say this in 30 seconds

Work from logs, traces and metrics with a correlation ID, capture the failing input, then reproduce in staging with realistic data.

Likely follow-up: What would you add to the code so the next occurrence is easier to diagnose?
21What tools would you put in a Python project's CI?qualitytoolingci＋
Simple answer

ruff for linting and formatting since it replaces flake8, isort and black in one fast tool, mypy for type checking, pytest with coverage for tests, and a dependency vulnerability scan. Run them as pre-commit hooks locally and again in CI, and make the build fail rather than warn — a warning nobody reads is not a check.

Say this in 30 seconds

ruff for lint and format, mypy for types, pytest with coverage, plus a dependency scan. Enforced in CI, not just warned about.
