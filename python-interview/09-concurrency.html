Threads, Processes & Asyncio

The GIL question is asked in almost every Python interview above fresher level, and it is usually answered badly. The strong answer is not what the GIL is — it is which of the three concurrency tools you would pick, and why.

18 questionsHigh frequency · backend and AI rolesChecked July 2026
⌁
What the interviewer is really testing

One decision rule: I/O-bound work goes to asyncio, or threads if the library is not async; CPU-bound work goes to multiprocessing. Lead with that rule, then explain the GIL as the reason behind it. Candidates who explain the GIL for two minutes without reaching the decision have missed the question.

18 questions

The GIL and choosing a model

01What is the GIL, and how does it affect your code?gilconcurrencyhigh-frequency＋
Simple answer

The Global Interpreter Lock is a mutex in CPython that lets only one thread execute Python bytecode at a time, because CPython's reference counting is not thread-safe. So threads give you no speedup on CPU-bound work. It does not hurt I/O-bound work, because the GIL is released while a thread waits on the network, disk or a database — and C extensions like NumPy release it during heavy computation too.

Say this in 30 seconds

A lock letting only one thread run Python bytecode at a time. It blocks CPU parallelism in threads but not I/O concurrency, because it is released during waits.

Likely follow-up: So when would you still use threads?
02When do you choose threads, processes or asyncio?concurrencydecisionhigh-frequency＋
Simple answer

Asyncio for large numbers of concurrent I/O operations — API calls, web serving, database queries — as long as the libraries are async. Threads for I/O when the library is blocking and has no async version, or for a handful of background tasks. Multiprocessing for CPU-bound work, because separate processes have separate GILs. The question to ask is always: is this waiting, or is this computing?

choosing.py
# I/O-bound, async libraries -> asyncio
results = await asyncio.gather(*(fetch(u) for u in urls))

# I/O-bound, blocking library -> threads
with ThreadPoolExecutor(max_workers=8) as pool:
    results = list(pool.map(blocking_fetch, urls))

# CPU-bound -> processes
with ProcessPoolExecutor() as pool:
    results = list(pool.map(heavy_compute, chunks))
Say this in 30 seconds

Waiting means asyncio, or threads if the library blocks. Computing means multiprocessing. That one question decides it.

Likely follow-up: You have 500 HTTP calls and one blocking client library. What do you do?
03What is the difference between concurrency and parallelism?concurrencyconcepts＋
Simple answer

Concurrency is dealing with many things at once by interleaving them — progress is made on several tasks, but not necessarily at the same instant. Parallelism is doing many things at literally the same instant on multiple cores. Asyncio gives concurrency on one thread; multiprocessing gives real parallelism.

Say this in 30 seconds

Concurrency interleaves tasks, parallelism runs them simultaneously on multiple cores. Asyncio is concurrency; multiprocessing is parallelism.

Likely follow-up: Can you have parallelism without concurrency?
04What is free-threaded Python, and does it remove the GIL?gilmodern pythonsenior＋
Simple answer

PEP 703 added an experimental build of CPython, from 3.13, that runs without the GIL, so threads can execute Python bytecode in parallel. It is being rolled out gradually because removing the GIL costs single-threaded speed and requires C extensions to be made thread-safe. Knowing it exists shows you follow the language; assuming it is the default in production does not.

Say this in 30 seconds

An experimental no-GIL build from Python 3.13 under PEP 703. Real, but still opt-in, and extensions must be made thread-safe.

Likely follow-up: What would you have to change in your code if the GIL disappeared?
05Why does multiprocessing help where threading does not?multiprocessinggil＋
Simple answer

Each process is a separate Python interpreter with its own GIL and its own memory, so they genuinely run on different cores at the same time. The cost is that starting processes is slow and nothing is shared — every argument and result must be pickled and copied between them. That overhead is why multiprocessing loses on small tasks and wins on big ones.

Say this in 30 seconds

Each process has its own interpreter and GIL, so they use real cores. The cost is startup time and pickling data between them.

Likely follow-up: What kinds of objects cannot be sent to a worker process?
06What are the risks of using threads with shared state?threadingrace conditions＋
Simple answer

Race conditions, where two threads read-modify-write the same value and one update is lost, and deadlocks, where two threads each hold a lock the other wants. The GIL does not save you — it protects the interpreter's internals, not your logic, so counter += 1 is still not atomic. Protect shared mutable state with a lock, or better, avoid sharing it and pass messages through a queue.Queue.

Say this in 30 seconds

Race conditions and deadlocks. The GIL does not make your code thread-safe — use a lock, or share nothing and pass messages via a queue.

Likely follow-up: Why is counter += 1 not atomic?
07What is a thread pool, and how do you size it?threadingpractical＋
Simple answer

A fixed set of reusable worker threads fed from a queue, so you avoid creating a thread per task. For I/O-bound work you can size it well above the core count, since threads spend most of their time waiting — but bound it to what the downstream service can take, or you turn your concurrency into their outage. ThreadPoolExecutor is the standard way.

Say this in 30 seconds

Reusable workers fed from a queue. For I/O you can go well above core count, but size it to what the downstream service tolerates.

Likely follow-up: How would you handle one task in the pool raising an exception?
08What is concurrent.futures and why is it useful?concurrencystdlib＋
Simple answer

A single high-level interface over both thread pools and process pools. Because ThreadPoolExecutor and ProcessPoolExecutor share an API, you can switch between them by changing one line — which is exactly what you want when you are unsure whether the workload is I/O- or CPU-bound. submit returns futures; as_completed lets you handle results as they arrive.

Say this in 30 seconds

One API over thread and process pools, so you can swap between them by changing one class name.

Asyncio

09How does asyncio work, in one explanation?asynciohigh-frequency＋
Simple answer

A single thread runs an event loop. When a coroutine hits an await on something that would block, it yields control back to the loop, which runs another ready coroutine and resumes the first when its I/O completes. There is no parallelism and no thread switching — just cooperative hand-offs at await points, which is why it scales to thousands of concurrent connections cheaply.

Say this in 30 seconds

One thread, one event loop. Coroutines yield control at await, the loop runs something else, and resumes them when the I/O is ready.

Likely follow-up: What happens if a coroutine never awaits anything?
10What is the difference between a coroutine, a task and a future?asyncioconcepts＋
Simple answer

A coroutine is what an async def call returns — it does nothing until awaited. A task wraps a coroutine and schedules it on the event loop, so it starts running concurrently right away. A future is the lower-level object representing a result that is not ready yet; a task is a subclass of it. The practical point is that calling a coroutine does not run it — await or create_task does.

tasks.py
coro = fetch(url)                    # nothing has run yet
task = asyncio.create_task(coro)     # now it is scheduled
result = await task                  # wait for it
Say this in 30 seconds

A coroutine is inert until awaited; a task schedules it to run concurrently; a future is the underlying result placeholder.

Likely follow-up: What warning do you get if you never await a coroutine?
11What does blocking the event loop mean, and how do you avoid it?asynciogotchaproduction＋
Simple answer

Running synchronous work — a CPU-heavy loop, time.sleep, or a blocking database driver — inside a coroutine. Since there is one thread, everything else stops until it finishes, so one slow call stalls every other request. Move blocking calls to a thread with asyncio.to_thread, and CPU-heavy work to a process pool.

to_thread.py
# bad — freezes the whole loop
rows = legacy_db.query(sql)

# good — runs in a worker thread
rows = await asyncio.to_thread(legacy_db.query, sql)
Say this in 30 seconds

Running sync work inside a coroutine stalls every other task, because there is only one thread. Push it to asyncio.to_thread or a process pool.

Likely follow-up: How would you detect that this is happening in production?
12What is the difference between asyncio.gather and TaskGroup?asynciomodern python＋
Simple answer

gather runs awaitables concurrently and returns a list of results, but its error handling is awkward — by default one failure leaves the other tasks running. asyncio.TaskGroup, from Python 3.11, cancels the remaining tasks when one fails and raises an ExceptionGroup, which is what you almost always actually want. Use TaskGroup on 3.11+.

taskgroup.py
async with asyncio.TaskGroup() as tg:
    a = tg.create_task(fetch(url1))
    b = tg.create_task(fetch(url2))
# both done here; if either failed, the other was cancelled
Say this in 30 seconds

gather collects results but leaves siblings running on failure; TaskGroup cancels them and raises an ExceptionGroup. Prefer TaskGroup.

Likely follow-up: What does return_exceptions=True change about gather?
13How do you add a timeout to an async operation?asynciotimeoutsproduction＋
Simple answer

async with asyncio.timeout(5): on Python 3.11+, or asyncio.wait_for before that. Both cancel the operation and raise TimeoutError. Every external call in production should have one — without a timeout, a hanging dependency quietly exhausts your connection pool and takes the whole service down.

Say this in 30 seconds

asyncio.timeout on 3.11+, or wait_for. Every external call needs one, or a hung dependency takes your service with it.

Likely follow-up: What is the difference between a connect timeout and a read timeout?
14How does cancellation work in asyncio?asynciocancellationsenior＋
Simple answer

Cancelling a task raises CancelledError inside it at its next await. Your cleanup should live in finally blocks or async context managers so it still runs. Never swallow CancelledError — catch it only to clean up, then re-raise, or timeouts and shutdown stop working.

Say this in 30 seconds

It raises CancelledError at the next await. Clean up in finally, and always re-raise rather than swallowing it.

Likely follow-up: How do you make sure cleanup itself does not get cancelled?
15How do you limit how many async operations run at once?asynciobackpressureproduction＋
Simple answer

An asyncio.Semaphore — acquire it inside each task so only N run concurrently. This matters because gather over ten thousand URLs will happily open ten thousand connections and get you rate-limited or blocked. Bound concurrency to what the downstream service can actually take.

Concept excerpt. fetch() and urls come from the surrounding application.

semaphore.py
import asyncio

sem = asyncio.Semaphore(20)

async def fetch_limited(url):
    async with sem:
        return await fetch(url)

async def main():
    results = await asyncio.gather(*(fetch_limited(u) for u in urls))
    return results

if __name__ == "__main__":
    asyncio.run(main())
Say this in 30 seconds

A Semaphore around each task. Without it, gather over thousands of items opens thousands of connections at once.

Likely follow-up: How would you also add a rate limit in requests per second?
16Can you mix async and sync code in one application?asynciopractical＋
Simple answer

Yes, but carefully. Call sync code from async with asyncio.to_thread; call async code from sync with asyncio.run at the top level only. What you must not do is call asyncio.run inside a running loop, or block the loop with a sync call. In FastAPI, defining an endpoint with def instead of async def makes the framework run it in a threadpool for you — which is the right choice when your driver is blocking.

Say this in 30 seconds

Yes — to_thread to call sync from async, asyncio.run once at the top for the reverse. In FastAPI, a plain def endpoint is run in a threadpool.

Likely follow-up: In FastAPI, when should an endpoint be def rather than async def?
17What is an async generator and when would you use one?asynciogenerators＋
Simple answer

An async def function with yield, consumed with async for. It lets you stream results that arrive over I/O — paginated API responses, rows from an async cursor, tokens streaming back from an LLM — without collecting everything first. It is the async equivalent of a generator pipeline.

Concept excerpt. client, start and process() come from the surrounding application.

async_gen.py
import asyncio

async def stream_pages(client, url):
    while url:
        page = await client.get(url)
        yield page.items
        url = page.next_url

async def main():
    async for items in stream_pages(client, start):
        process(items)

if __name__ == "__main__":
    asyncio.run(main())
Say this in 30 seconds

A generator you await, consumed with async for. Used for paginated APIs, async cursors and streaming LLM tokens.

Likely follow-up: How do you make sure an async generator is closed properly?
18What is a common asyncio mistake you have seen in production?asyncioproductionsenior＋
Simple answer

Fire-and-forget tasks. Calling create_task without keeping a reference means the task can be garbage collected mid-run, and any exception inside it is never seen — the work silently does not happen. Keep a reference, add a done-callback that logs failures, or use a TaskGroup that surfaces the error properly.

Say this in 30 seconds

Fire-and-forget create_task with no reference kept — the task can be collected and its exceptions vanish silently.
