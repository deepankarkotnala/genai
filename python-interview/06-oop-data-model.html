OOP & the Python Data Model

“Explain inheritance, abstraction, encapsulation and polymorphism with Python examples” is asked almost verbatim in Indian interviews. Have a single small example ready that shows all four, rather than four disconnected definitions.

What the interviewer is really testing

Definitions get you a pass; examples get you the job. For every OOP term, give one sentence of definition and one line of code from something you have built. And be ready for the harder half of this page — MRO, dunder methods and dataclasses — which is where senior candidates are separated from mid-level ones.

23 questions

Classes and the four OOP pillars

01Explain inheritance, encapsulation, abstraction and polymorphism in Python.ooppillarshigh-frequency＋
Simple answer

Inheritance: a class reuses another class's behaviour. Encapsulation: data and the methods that work on it live together, with internals marked private by convention. Abstraction: callers use a simple interface and never see the messy implementation. Polymorphism: different classes respond to the same method call in their own way. Python leans on duck typing, so polymorphism often needs no shared base class at all.

pillars.py
class Notifier:                      # abstraction
    def send(self, msg): raise NotImplementedError

class EmailNotifier(Notifier):       # inheritance
    def __init__(self, smtp):
        self._smtp = smtp            # encapsulation
    def send(self, msg):
        self._smtp.deliver(msg)

class SlackNotifier(Notifier):
    def send(self, msg):
        post_to_slack(msg)

for n in (EmailNotifier(smtp), SlackNotifier()):
    n.send("deployed")               # polymorphism
Say this in 30 seconds

Inheritance reuses behaviour, encapsulation keeps data with its methods, abstraction hides the implementation, polymorphism lets different classes answer the same call differently.

Likely follow-up: Which of those four does Python enforce, and which are conventions?
02What is self, and why must you write it explicitly?oopbasics＋
Simple answer

self is the instance the method was called on. Python passes it automatically when you use obj.method(), but the method signature must name it because Python prefers explicit over implicit — and because a method is really just a function stored on the class. The name is convention; the position is what matters.

Say this in 30 seconds

The instance, passed automatically on attribute access. It is explicit because a method is just a function on the class.

Likely follow-up: What happens if you forget self in the definition?
03What is the difference between an instance attribute and a class attribute?oopattributesgotcha＋
Simple answer

An instance attribute is set on self and belongs to one object. A class attribute is defined in the class body and is shared by every instance. The trap is a mutable class attribute: one instance appending to a shared list changes it for all of them, which is the class-level version of the mutable-default-argument bug.

attributes.py
class Team:
    members = []            # SHARED by every Team

    def __init__(self, name):
        self.name = name    # per instance

a, b = Team("x"), Team("y")
a.members.append(1)
print(b.members)            # [1] — surprise
Say this in 30 seconds

Instance attributes live on the object, class attributes are shared by all instances. A mutable class attribute is a shared-state bug.

Likely follow-up: How does assigning to a.members differ from appending to it?
04What is the difference between @staticmethod, @classmethod and an instance method?oopmethodshigh-frequency＋
Simple answer

An instance method takes self and works on one object. A classmethod takes cls and works on the class — most often as an alternative constructor, and it respects subclasses because cls is whatever class was used. A staticmethod takes neither and is just a plain function grouped in the class for tidiness.

methods.py
class User:
    def __init__(self, name): self.name = name

    @classmethod
    def from_row(cls, row):        # alternative constructor
        return cls(row["name"])

    @staticmethod
    def is_valid_name(name):       # utility, no state needed
        return bool(name.strip())
Say this in 30 seconds

Instance methods get self, classmethods get cls and are usually alternative constructors, staticmethods get nothing and are just grouped functions.

Likely follow-up: Why would a classmethod constructor be better than a staticmethod one?
05How does Python handle private attributes?oopencapsulation＋
Simple answer

By convention, not enforcement. A single underscore means “internal, do not touch” and Python does nothing about it. A double underscore triggers name mangling — __x becomes _ClassName__x — which is designed to prevent accidental clashes in subclasses, not to provide security. Nothing in Python is truly private.

Say this in 30 seconds

One underscore is a convention meaning internal; two triggers name mangling to avoid subclass collisions. Neither is real privacy.

Likely follow-up: So when should you actually use the double underscore?
06What do one, two, and two-on-each-side underscores mean in a name?double underscorenamingname manglingconventionshigh-frequency＋
Simple answer

Three different things. A single leading underscore, _value, is a convention meaning “internal, please do not use this from outside” — Python does not stop you. A double leading underscore, __value, triggers name mangling: Python renames it to _ClassName__value so a subclass cannot clash with it by accident. Double underscores on both sides, __init__, are reserved for Python's own dunder methods, so never invent your own. A single trailing underscore, class_, is just a way to avoid clashing with a keyword.

underscores.py
class Engine:
    def __init__(self):
        self.power = 100      # public
        self._temp = 40       # internal by convention only
        self.__serial = "X1"  # name-mangled to _Engine__serial

e = Engine()
e.power        # 100
e._temp        # 40   — works fine, the underscore is only a hint
e.__serial     # AttributeError
e._Engine__serial   # 'X1'  — mangled, not hidden. Nothing is truly private.
Say this in 30 seconds

One underscore means internal by convention. Two triggers name mangling so subclasses cannot clash. Two on each side is reserved for Python's own dunder methods.

Likely follow-up: So how would you actually protect a value from being changed?
07What does super() do, and why not call the parent class directly?oopinheritancemro＋
Simple answer

super() follows the method resolution order rather than naming a specific parent, so it keeps working when the class hierarchy changes and when multiple inheritance is involved. Calling Parent.__init__(self, ...) hard-codes one path and, in a diamond hierarchy, can call the same class twice or skip one entirely.

Say this in 30 seconds

It calls the next class in the MRO rather than a hard-coded parent, which is what makes cooperative multiple inheritance work.

Likely follow-up: What is the MRO and how is it computed?
08What is the MRO, and how does Python resolve it?oopmroadvanced＋
Simple answer

The Method Resolution Order is the sequence Python searches for an attribute across a class and its bases. It is computed by the C3 linearisation algorithm, which preserves each class's own order and puts every class before its parents. You can read it with ClassName.__mro__, and if no consistent order exists Python refuses to create the class at all.

mro.py
class A: ...
class B(A): ...
class C(A): ...
class D(B, C): ...

D.__mro__   # D, B, C, A, object
Say this in 30 seconds

The order Python searches classes for an attribute, computed by C3 linearisation. Check it with __mro__.

Likely follow-up: What is the diamond problem and how does C3 solve it?
09What is an abstract base class, and when do you need one?oopabcdesign＋
Simple answer

A class using abc.ABC with @abstractmethod that cannot be instantiated and forces subclasses to implement certain methods. It is worth it when you have several implementations of one contract and want the failure to be at import time rather than in production. When there is only one implementation, or duck typing is enough, an ABC is ceremony.

abc.py
from abc import ABC, abstractmethod

class Store(ABC):
    @abstractmethod
    def get(self, key: str) -> bytes: ...

    @abstractmethod
    def put(self, key: str, value: bytes) -> None: ...
Say this in 30 seconds

A class that cannot be instantiated and forces subclasses to implement named methods. Useful with several implementations of one contract.

Likely follow-up: How is a typing Protocol different from an ABC?
10When should you prefer composition over inheritance?oopdesignsenior＋
Simple answer

Almost always, unless the subclass genuinely is the parent and can be used anywhere it can. Inheritance couples you to the parent's internals, so a change up the tree breaks children. Composition — holding an object and delegating to it — is easier to test, easier to swap, and does not create deep hierarchies nobody can follow.

Say this in 30 seconds

Prefer composition unless the child truly is-a parent. Inheritance couples you to the parent's internals; composition swaps and tests cleanly.

Likely follow-up: Give me a case where inheritance was the right call.
11What is multiple inheritance and what is a mixin?oopinheritance＋
Simple answer

Multiple inheritance lets a class have several bases, and Python resolves conflicts through the MRO. A mixin is the disciplined use of it: a small class that adds one capability, has no state of its own, and is never instantiated alone — a SerializableMixin, say. Mixins are fine; deep multiple inheritance of full classes usually is not.

Say this in 30 seconds

Several base classes, resolved by the MRO. A mixin is a small stateless class adding one capability — the safe use of it.

Likely follow-up: How would you get the same effect with composition instead?

Dunder methods and the data model

12What is a dunder method, and why are they called magic methods?dundermagic methodsspecial methodsdata modelhigh-frequency＋
Simple answer

A dunder method is one whose name has double underscores on both sides, like __init__ or __len__. You almost never call them directly — Python calls them for you when you use ordinary syntax. Writing len(x) runs x.__len__(), a + b runs a.__add__(b), and print(x) runs x.__str__(). They are called magic methods because implementing them makes your own class work with built-in syntax as if it were a built-in type.

dunder.py
class Basket:
    def __init__(self, items):     # runs on Basket([...])
        self.items = items

    def __len__(self):             # runs on len(basket)
        return len(self.items)

    def __str__(self):             # runs on print(basket)
        return f"Basket of {len(self.items)}"

basket = Basket(["apple", "pear"])
len(basket)      # 2   -> Python called __len__
print(basket)    # Basket of 2  -> Python called __str__
Say this in 30 seconds

Methods with double underscores each side that Python calls for you when you use normal syntax — len(x) calls __len__, a + b calls __add__. They let your class behave like a built-in type.

Likely follow-up: Which dunder methods would you implement first on a new class?
13What is the difference between __str__ and __repr__?dunderhigh-frequency＋
Simple answer

__str__ is for end users and should read nicely; __repr__ is for developers and should be unambiguous, ideally looking like the code that would recreate the object. print() uses __str__; the REPL, debuggers and containers use __repr__. If you only write one, write __repr__ — str falls back to it.

repr.py
class Point:
    def __init__(self, x, y): self.x, self.y = x, y
    def __repr__(self): return f"Point(x={self.x}, y={self.y})"

print([Point(1, 2)])   # [Point(x=1, y=2)] — lists use repr
Say this in 30 seconds

str is for users, repr is for developers and debugging. Write repr if you write only one; str falls back to it.

Likely follow-up: Why do lists show repr for their contents rather than str?
14What is __init__ versus __new__?dunderadvanced＋
Simple answer

__new__ creates the object and returns it; __init__ then configures the already-created object. You almost never touch __new__ — the exceptions are subclassing an immutable type such as tuple or str, and implementing singletons or caching where you want to return an existing object.

Say this in 30 seconds

__new__ allocates and returns the object, __init__ initialises it. You only override __new__ for immutable subclasses or singletons.

Likely follow-up: What happens if __new__ returns an object of a different class?
15How do you make objects of your class comparable and sortable?dundercomparison＋
Simple answer

Implement __eq__ for equality and __lt__ for ordering — sorted only needs __lt__. Add functools.total_ordering to derive the rest of the comparison operators from those two. Remember that defining __eq__ sets __hash__ to None, so add __hash__ back if the object must go in a set or dict.

Say this in 30 seconds

__eq__ plus __lt__, and total_ordering fills in the rest. Defining __eq__ kills hashability unless you restore __hash__.

Likely follow-up: Why does Python remove __hash__ when you define __eq__?
16How would you make + work on your own class?dunderoperator overloadingmagic methodsoop＋
Simple answer

Implement __add__. Python turns a + b into a.__add__(b), so defining it is all that is needed — that is operator overloading. The same pattern covers the rest: __sub__ for -, __mul__ for *, __eq__ for ==. Return NotImplemented for a type you do not handle, so Python can try the other operand's method instead of failing outright.

operators.py
class Money:
    def __init__(self, rupees):
        self.rupees = rupees

    def __add__(self, other):          # called by:  a + b
        if not isinstance(other, Money):
            return NotImplemented      # let Python try other.__radd__
        return Money(self.rupees + other.rupees)

    def __repr__(self):
        return f"Money({self.rupees})"

Money(50) + Money(70)      # Money(120)
Money(50) + 70             # TypeError — refused on purpose
Say this in 30 seconds

Define __add__, because Python turns a + b into a.__add__(b). Return NotImplemented for types you do not support so Python can fall back.

Likely follow-up: What is __radd__ for?
17Which dunder methods make an object behave like a container?dunderprotocols＋
Simple answer

__len__ for len() and truthiness, __getitem__ for indexing and slicing, __setitem__ and __delitem__ for mutation, __contains__ for in, and __iter__ for looping. Implementing just __getitem__ with integer keys already makes an object iterable through an old fallback protocol.

Say this in 30 seconds

__len__, __getitem__, __setitem__, __contains__ and __iter__. That set makes a class feel like a built-in collection.

Likely follow-up: What does __contains__ fall back to if you do not define it?
18What does __call__ do?dunderadvanced＋
Simple answer

It lets an instance be called like a function, so obj() works. It is how class-based decorators work, and it is useful for objects that are conceptually a function with configuration attached — a validator, a scoring model, a retry policy. If the object has no state, a plain function is simpler.

Say this in 30 seconds

It makes instances callable. Used for class-based decorators and for configured, function-like objects.

Likely follow-up: How would you type-hint something that just needs to be callable?
19What is the difference between __getattr__ and __getattribute__?dunderadvancedgotcha＋
Simple answer

__getattribute__ intercepts every attribute access, so overriding it is easy to get wrong and trivially causes infinite recursion. __getattr__ is only called when normal lookup has already failed, which makes it the safe hook for proxies, lazy loading and dynamic attributes.

Say this in 30 seconds

__getattribute__ runs on every access and is dangerous; __getattr__ only runs on failed lookups and is the safe hook.

Likely follow-up: How would you use __getattr__ to build a proxy object?
20What is a dataclass, and when would you use one?dataclassmodern pythonhigh-frequency＋
Simple answer

@dataclass generates __init__, __repr__ and __eq__ from typed field declarations, so a data-holding class is five lines instead of thirty. Use frozen=True to make it immutable and hashable, and field(default_factory=list) for mutable defaults — a plain = [] is rejected outright, which is Python protecting you from the shared-default bug.

dataclass.py
from dataclasses import dataclass, field

@dataclass(frozen=True, slots=True)
class Chunk:
    text: str
    score: float = 0.0
    tags: list[str] = field(default_factory=list)
Say this in 30 seconds

It generates init, repr and eq from typed fields. frozen=True makes it immutable and hashable; use default_factory for mutable defaults.

Likely follow-up: When would you choose Pydantic over a dataclass?
21What is the difference between a dataclass and a Pydantic model?dataclasspydanticpractical＋
Simple answer

A dataclass records types but never checks them — pass a string where an int is declared and nothing complains. Pydantic validates and coerces at runtime, produces structured errors, and serialises to and from JSON. Use dataclasses for internal objects you already trust, and Pydantic at the boundary: API payloads, config files, LLM structured output.

Say this in 30 seconds

Dataclasses declare types, Pydantic enforces them at runtime. Dataclasses inside, Pydantic at the boundary.

Likely follow-up: What is the performance cost of Pydantic validation on a hot path?
22What is a metaclass, and have you ever needed one?metaclassadvancedsenior＋
Simple answer

A metaclass is the class of a class — it controls how classes themselves are created, with type being the default. Frameworks use them to auto-register models or validate class definitions at import time. The honest answer most interviewers want is that you understand them but reach for __init_subclass__, decorators or composition first, because metaclasses make code hard to follow.

Say this in 30 seconds

The class of a class, controlling class creation. Frameworks use them; in application code __init_subclass__ or a decorator is almost always better.

Likely follow-up: What can __init_subclass__ do that covers most metaclass use cases?
23How do you make a class immutable?oopimmutability＋
Simple answer

The practical answer is @dataclass(frozen=True), which blocks attribute assignment and gives you a __hash__. By hand, you would override __setattr__ to raise, or subclass NamedTuple. Note that freezing is shallow — a frozen object holding a list can still have that list mutated.

Say this in 30 seconds

@dataclass(frozen=True) or a NamedTuple. Remember it is shallow — a contained list is still mutable.

Likely follow-up: How would you make it deeply immutable?
