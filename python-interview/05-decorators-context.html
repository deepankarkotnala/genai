Decorators, Context Managers & Descriptors

Expect to be asked to write a decorator on the spot — usually a timer, a retry, or one that takes arguments. Practise typing the three-level version from memory until it is automatic.

18 questionsLive-coding favouriteChecked July 2026
⌁
What the interviewer is really testing

A decorator is just a function that takes a function and returns a replacement. If you can say that sentence and then write the *args, **kwargs wrapper without hesitating, you have passed. The follow-up is almost always “now make it take an argument”, which needs one more layer of nesting.

18 questions

Decorators

01What is a decorator?decoratorshigh-frequency＋
Simple answer

A function that takes another function, wraps it with extra behaviour, and returns the replacement. @my_decorator above a def is shorthand for func = my_decorator(func). It lets you add logging, timing, caching, retries or permission checks without touching the function's own code.

decorator.py
import functools, time

def timed(func):                          # 1. takes the original function
    @functools.wraps(func)                # keeps func's name and docstring
    def wrapper(*args, **kwargs):         # 2. stands in for the original
        start = time.perf_counter()
        result = func(*args, **kwargs)    # 3. call what we wrapped
        print(f"{func.__name__} took {time.perf_counter() - start:.3f}s")
        return result                     # 4. hand the real result back
    return wrapper                        # 5. this replaces the original

@timed                                    # same as: train_model = timed(train_model)
def train_model(data): ...
Say this in 30 seconds

A function that wraps another function and returns the replacement. @d is just func = d(func).

Likely follow-up: Now write one that takes an argument, like a retry count.
02How do you write a decorator that takes arguments?decoratorscodinghigh-frequency＋
Simple answer

You need three levels: an outer function that takes the arguments, a middle one that takes the function, and an inner wrapper that takes the call's arguments. The outer function is really a decorator factory — it returns a decorator. That extra layer is the whole trick.

retry.py
import functools, time

def retry(times=3, delay=1.0):                 # LEVEL 1: takes the settings
    def decorator(func):                       # LEVEL 2: takes the function
        @functools.wraps(func)
        def wrapper(*args, **kwargs):          # LEVEL 3: takes the call args
            for attempt in range(times):
                try:
                    return func(*args, **kwargs)   # success -> done
                except Exception:
                    if attempt == times - 1:
                        raise                      # last try -> give up loudly
                    # wait 1s, then 2s, then 4s... so retries do not pile up
                    time.sleep(delay * (2 ** attempt))
        return wrapper
    return decorator

# The extra level exists purely so the decorator can take arguments:
# retry(times=5) RUNS first and returns the real decorator.
@retry(times=5, delay=0.5)
def call_api(): ...
Say this in 30 seconds

Three nested functions: the outer takes the arguments and returns the real decorator, which returns the wrapper.

Likely follow-up: How would you make it work both with and without parentheses?
03Why do you need functools.wraps?decoratorsfunctools＋
Simple answer

Without it, the thing callers now hold is the wrapper, not your function. So its __name__ is "wrapper", its docstring is gone, and anything inspecting it sees the wrapper's arguments instead of the real ones. That breaks tracebacks, help text, documentation tools, and frameworks that read signatures — FastAPI, for example, builds routes from them. One line prevents all of it.

Say this in 30 seconds

It copies the original name, docstring and metadata to the wrapper so debugging, docs and signature-reading frameworks still work.

Likely follow-up: Does wraps fix the signature for inspect.signature too?
04How do you apply more than one decorator, and in what order do they run?decoratorsordertrick question＋
Simple answer

Stacked decorators apply bottom-up: the one nearest the def wraps first, and the top one wraps last. At call time that means the top decorator's code runs first, since it is the outermost layer. This matters when order changes behaviour — authentication should sit outside caching, not inside it.

stacking.py
@log        # runs first at call time (outermost)
@cache      # applied first (innermost)
def fetch(): ...

# equivalent to: fetch = log(cache(fetch))
Say this in 30 seconds

Applied bottom-up, executed top-down. The bottom one wraps first; the top one runs first.

Likely follow-up: Where would putting the cache above the auth check cause a security bug?
05How would you decorate a class method?decoratorsoop＋
Simple answer

The same way — the wrapper just has to pass self through, which *args does automatically since self is the first positional argument. Order matters with @staticmethod, @classmethod and @property: they must be the outermost decorator, because they change what kind of object the attribute is.

Say this in 30 seconds

Identically — *args carries self through. But @staticmethod, @classmethod and @property must go on top.

Likely follow-up: What actually breaks if you put @property underneath your decorator?
06What are decorators used for in real production code?decoratorspractical＋
Simple answer

Routing in Flask and FastAPI, caching with lru_cache, retries around flaky network calls, timing and metrics, authentication and permission checks, input validation, and registering plugins into a registry. The common thread is cross-cutting concerns — behaviour that many functions need but that is not their real job.

Say this in 30 seconds

Cross-cutting concerns: routing, caching, retries, auth, metrics and validation. Behaviour many functions need but none of them own.

Likely follow-up: Give me one you actually wrote yourself and why.
07What is a class-based decorator, and when is it better?decoratorsoop＋
Simple answer

A class that stores the function in __init__ and implements __call__ so instances behave like functions. It is better when the decorator needs real state you want to inspect afterwards — a call counter, collected metrics, a cache you want to expose and clear. For simple wrapping, a function is less machinery.

class_decorator.py
class CountCalls:
    def __init__(self, func):
        functools.update_wrapper(self, func)   # copy name/docstring across
        self.func, self.count = func, 0        # state lives on the instance

    # __call__ makes the instance usable like a function,
    # so @CountCalls behaves the same as a function decorator.
    def __call__(self, *args, **kwargs):
        self.count += 1                        # inspect later: fn.count
        return self.func(*args, **kwargs)
Say this in 30 seconds

A class implementing __call__. Worth it when the decorator holds state you want to read or reset later.

Context managers

08What does the with statement do?context managerhigh-frequency＋
Simple answer

It guarantees setup and teardown around a block. On entry it calls __enter__, and on exit — normally, by return, or because of an exception — it calls __exit__. That is why with open(...) closes the file even if the body raises, which a plain close() at the end would not.

Say this in 30 seconds

It runs setup and guaranteed cleanup around a block, even if the block raises. That is why files always close.

Likely follow-up: What are the two methods a context manager must implement?
09How do you write a context manager as a class?context managercoding＋
Simple answer

Implement __enter__, returning whatever the as clause should bind, and __exit__(exc_type, exc_value, traceback) for cleanup. If __exit__ returns a truthy value it swallows the exception — almost always a mistake, so return None unless you mean it.

cm_class.py
class Timer:
    def __enter__(self):
        self.start = time.perf_counter()
        return self          # whatever you return is bound by "as"

    # Called on the way out — normally, on return, or on an exception.
    # The three arguments describe the exception, or are None if there was none.
    def __exit__(self, exc_type, exc, tb):
        self.elapsed = time.perf_counter() - self.start
        return None          # falsy -> let any exception carry on rising

# with Timer() as t:
#     slow_thing()
# print(t.elapsed)
Say this in 30 seconds

__enter__ for setup and the bound value, __exit__ for cleanup. Return None from exit so exceptions propagate.

Likely follow-up: When would you deliberately return True from __exit__?
10How do you write one with contextlib.contextmanager?context managercontextlib＋
Simple answer

Write a generator that yields exactly once: everything before the yield is setup, the yielded value is what as binds, and everything after is cleanup. Wrap the yield in try/finally so cleanup still runs when the block raises. It is far less code than the class version for simple cases.

cm_gen.py
from contextlib import contextmanager

@contextmanager
def transaction(conn):
    tx = conn.begin()        # setup: everything before the yield
    try:
        yield tx             # the body of the "with" block runs here
        tx.commit()          # reached only if the block finished cleanly
    except Exception:
        tx.rollback()        # the block raised -> undo everything
        raise                # re-raise so the caller still sees the error

# with transaction(conn) as tx:
#     tx.execute(...)        # commits on success, rolls back on failure
Say this in 30 seconds

A generator that yields once — setup before, cleanup after, wrapped in try/finally so it runs on failure too.

Likely follow-up: What happens if your generator yields twice?
11What real problems do context managers solve beyond files?context managerpractical＋
Simple answer

Database transactions that must commit or roll back, acquiring and releasing locks, opening and closing network connections, temporarily changing state such as a working directory or a log level, and timing a block. Anything with a paired “must undo this” step belongs in a context manager rather than in a finally you might forget.

Say this in 30 seconds

Transactions, locks, connections, temporary state changes, and timing. Anything with a mandatory undo step.

Likely follow-up: How would you manage two resources that must be released in order?
12What is contextlib.suppress and how is it different from a bare except?context managerexceptions＋
Simple answer

with suppress(FileNotFoundError): ignores exactly the exceptions you name and nothing else. It is a targeted, readable alternative to try/except/pass. A bare except: swallows everything including KeyboardInterrupt, which is why it is almost always wrong.

Say this in 30 seconds

It ignores only the exceptions you name, unlike a bare except which hides everything including interrupts.

13What does async with do differently?context managerasyncio＋
Simple answer

It uses __aenter__ and __aexit__, which are coroutines, so setup and teardown can await. You need it whenever acquiring or releasing the resource is itself I/O — an async database session, an HTTP client pool, an async lock. Using a plain with on such an object raises a TypeError.

Say this in 30 seconds

It awaits the setup and teardown, using __aenter__ and __aexit__. Needed when acquiring the resource is itself I/O.

Properties and descriptors

14What does @property do, and why not just use a public attribute?propertyoophigh-frequency＋
Simple answer

@property makes a method callable like an attribute, so you can add validation, computation or logging later without changing any calling code. That is the point: start with a plain attribute, and convert it to a property when you need behaviour — the public interface never changes. Getters and setters everywhere upfront is a Java habit, not a Python one.

property.py
class Account:
    def __init__(self, balance):
        self._balance = balance      # underscore = internal, use the property

    @property
    def balance(self):               # called on: account.balance
        return self._balance

    @balance.setter
    def balance(self, value):        # called on: account.balance = 50
        if value < 0:
            raise ValueError("balance cannot be negative")
        self._balance = value

# Callers still write account.balance — they never learn it became a method.
Say this in 30 seconds

It lets a method be accessed like an attribute, so you can add validation later without breaking callers. Start plain, upgrade when needed.

Likely follow-up: What happens if a property getter is expensive and called in a loop?
15What is a descriptor?descriptoradvanced＋
Simple answer

An object that defines __get__, __set__ or __delete__ and is used as a class attribute, so it controls what happens when that attribute is read or written. It is the mechanism behind property, classmethod, staticmethod and ORM model fields. You rarely write one, but knowing it explains how those work.

Say this in 30 seconds

A class attribute that intercepts get, set or delete. It is what property, classmethod and ORM fields are built on.

Likely follow-up: What is the difference between a data and a non-data descriptor?
16What is the difference between a data and a non-data descriptor?descriptoradvanced＋
Simple answer

A data descriptor defines __set__ or __delete__; a non-data one only defines __get__. It matters for lookup order: data descriptors win over the instance dictionary, non-data descriptors lose to it. That is why a property cannot be shadowed by an instance attribute but a cached method can.

Say this in 30 seconds

Data descriptors define __set__ and take priority over the instance dict; non-data ones only define __get__ and lose to it.

Likely follow-up: How does functools.cached_property use that difference?
17What is functools.cached_property?propertycachingperformance＋
Simple answer

A property that runs once and then stores the answer directly on the object, so every later read skips the method and picks up the stored value. Use it for expensive derived values on an object that does not change; do not use it if the underlying data can change, because nothing invalidates the cache.

Say this in 30 seconds

A property that computes once and caches on the instance. Only safe when the underlying data will not change.

Likely follow-up: How would you invalidate it if the data did change?
18What are __slots__ and what do they cost?slotsmemoryoop＋
Simple answer

Declaring __slots__ replaces the per-instance dictionary with a fixed set of attribute slots, cutting memory noticeably and speeding up access. The cost is that you cannot add attributes not in the list, and it complicates multiple inheritance and weak references. It is worth it when you have hundreds of thousands of small objects, and pointless otherwise.

slots.py
class Point:
    # Fixes the allowed attributes, which removes the per-instance __dict__.
    # Saves real memory once you have millions of these objects.
    __slots__ = ("x", "y")

    def __init__(self, x, y):
        self.x, self.y = x, y

# p.z = 3  ->  AttributeError: Point has no attribute 'z'
Say this in 30 seconds

They remove the per-instance dict to save memory, at the cost of not being able to add new attributes. Only worth it at large object counts.
