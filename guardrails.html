Production / Guardrails - rules before an answer

1 · What you already know

You know that an LLM app sends a prompt to a model and shows the reply to the user. You also know the model can get things wrong. It can make up facts, repeat something it should not, or wander off topic.

A guardrail is a safety check around the model. It looks at what goes in (the user's question) and what comes out (the model's answer), and decides whether to let it through.

This page is about those checks: which ones to write in code, which rules are fine to leave in the prompt, and what to do when a check fails.

2 · What breaks now

Say you build a support assistant for an online shop. The system prompt is the hidden instruction you send to the model before every user message. Yours has three rules: don't reveal internal secrets, only talk about orders, and don't invent a policy.

In the first week, all three rules are broken. None of the breaks shows up as an error:

What happenedWhy the prompt did not stop it
A secret approval token appeared in a replyThe token was inside data a tool returned, and the model was trying to be helpful
The assistant chatted about a competitor for a long timeThe user asked politely, and the rule is just text like everything else
It said the refund window was 60 daysThe search found no policy document, so the model guessed something that sounded right

The model did not ignore the rules. It weighed them against everything else in the prompt, and the rules lost. Nothing recorded that they lost, so nobody knew until a customer complained.

3 · Simple breakdown - a code-level guardrail vs a system-prompt instruction

A A code-level guardrail

What it is. A check written in your own code. It runs before the question goes to the model, or after the answer comes back, and says yes or no.

Core purpose. To enforce a rule the model cannot be talked out of. The model does not make the decision. Your code does.

Execution model.

Architecture under the hood. Three steps. An input check looks at the question. Then the model runs. Then an output check looks at the answer. Each check gives a clear decision, such as "allow" or "block".

State handling. Each decision and its reason are saved with the request's ID (the run id), so you can look it up later. The model does not remember anything about the check.

Limitations and advanced features. Every check adds a little delay. A check that uses another model costs an extra call. And if a rule is too broad, it blocks normal users. That is called a false positive, and to users it looks like the product is broken.

B A system-prompt instruction

What it is. A sentence in the system prompt that tells the model what not to do.

Core purpose. It guides the model in every situation, even ones you did not think of, and it costs only a few tokens.

Execution model. The instruction sits in the same prompt as everything else. The model reads it along with the question and any documents, and balances them all.

Architecture under the hood. Nothing extra. It is just part of the prompt. There is no separate code that runs.

State handling. None. The instruction is sent again with every request.

Limitations and advanced features. It is text competing with other text. A retrieved document or a user's message can push against it, and nothing tells you when it loses.

The core differences

A code-level guardrailA system-prompt instruction
Can a user's text talk it out of the rule?NoYes, that is how it fails
Tells you when it acts?Yes, the decision is savedNo, it fails silently
Handles cases you did not think of?Only the cases you codedYes, that is its strength

In short - which one to choose

  • Use a code-level guardrail when a mistake would be costly: secrets, personal data, who can see what, and actions that cannot be undone.
  • Use a system-prompt instruction for tone, format and general behaviour, where covering many cases matters more than a guarantee.
  • Use both for an important rule. The prompt makes the mistake rarer. The code check makes sure it never gets through.

4 · Without the technology

Without guardrails, your only protection is the system prompt, plus whatever safety filter the model provider runs on their side.

This does help. A good system prompt really does make every problem above less common, and it covers situations you never thought of. A list of checks cannot do that.

But it cannot:

  • Guarantee anything. It is text competing with other text, including text an attacker wrote.
  • Tell you when it failed. There is no alert. The first you hear of it is a customer complaint.
  • Be tested. You cannot write a test that proves the model obeyed a sentence.

A prompt makes a mistake less likely. A code check stops it. Important rules need the code check. The two work together; you do not pick one or the other.

5 · Runtime mechanics

A request with guardrails goes through five steps.

  1. Check the question. Is it on topic? Does it contain personal data? Does it look like an attack? If it clearly breaks a rule, stop here. The model is never called.
  2. Build the prompt. The system prompt states the rules, and any outside content (like retrieved documents) is labelled as "not trusted".
  3. Call the model.
  4. Check the answer. Does it leak a secret or personal data? Are its sources real? If you asked for JSON, is it valid JSON?
  5. Decide what to do if a check failed: block, redact (hide part of the answer), downgrade (replace it with an honest "I don't know"), or allow it and flag it for review.

People often skip step 5. If your only option is "block", every unclear case becomes a refusal, and users stop using a product that says no too often.

6 · The components, one at a time

Input guardrails

These check the user's question before the model sees it.

They run before the model call, so blocking a bad question costs no tokens. Checking for prompt injection (a message that tries to give the model new orders, like "ignore your instructions") belongs here. But treat it as a way to reduce attacks, not as your main defence. Attackers can always find new wording.

Output guardrails

These check the model's answer before the user sees it.

The output check matters more than the input check, because the model can produce something no input check could have predicted. Grounding here means: is every claim in the answer backed by a document we actually found?

The four responses

ResponseUse it whenThe user sees
BlockA clear rule break, an obvious attack, or illegal contentA short refusal, with no detail that helps someone get around it
RedactA secret or personal data inside an otherwise good answerThe answer, with that part replaced by [redacted]
DowngradeThe answer is not backed by a real document, or cites one that does not existAn honest "I don't have that information"
Allow and flagIt is unclear, and a person should look at it laterThe answer, with a score saved for review

How checks are implemented

There are four common ways to build a check, from cheapest to most expensive.

A classifier is a small model trained to answer one question, like "is this toxic?". A judge model is an LLM asked to score an answer against a set of rules. Pick the cheapest check that can really decide. For an API key, a regex is better than a judge, because an API key always has the same shape, while a judge only gives an opinion.

Where these decisions are recorded

Every decision is saved as a score on the request. That is exactly what a tracing platform stores. The grounding check itself is built step by step in RAG, fix it.

The record

If a redaction happens, treat it as a problem to fix. It means a secret got into the model's input in the first place, which is a bug earlier in the system.

7 · State and data flow

"State" means the data the system keeps while it works. For guardrails, it is small:

  1. What data is kept? Each check's decision and its reason. The checks themselves remember nothing.
  2. Who writes it? Each check writes its own decision.
  3. Who reads it? The pipeline, to decide what to show the user, and the audit log.
  4. Is it replaced or added to? Added to. Two checks can both fail on the same request.
  5. If two checks disagree, which one wins? The stricter one. A block beats a redaction.
  6. Is it only in memory? The decision is, while the request runs. The record must be saved somewhere permanent.
  7. Is it saved between steps? No. A guardrail decision belongs to one request only.
  8. Is it in a database? Yes: the audit log and the metrics.
  9. How long is it kept? As long as your data retention policy says.
  10. How do you find it again? By the run id, which every decision must include.

Row 5 is a real design choice. When two checks fail with different actions, you need a clear rule for which one wins. Otherwise the result depends on which check happened to run last.

8 · Trace

Compare requests 2 and 3. Request 3 cost nothing, because the input check stopped it before the model ran. Request 2 cost a model call and raised an alert, because the problem (a leaked token) only showed up in the answer.

9 · Break it

After request 2, the natural reaction is to make the input check stricter by blocking more words.

Fewer attacks get through. But so do fewer normal questions.

403 real customers were refused just to stop nine attacks, and those nine would have failed anyway, because there is no tool that can email a token. The guardrail now does far more harm than the attack it was meant to stop.

10 · Fix it

1 · Measure false positives before making a check stricter. Precision means: of everything you blocked, how much was really bad? A block count without precision tells you nothing about safety.

2 · Put the rule where it can be exact. The real worry is a token leaking in the answer. A token always has the same shape, so an output check can find it exactly.

3 · When unsure, flag instead of block. The request continues, a score is saved, and a person reviews a sample later.

4 · Remember what really protects you. The strongest defence is not giving the model a dangerous tool in the first place. Input checks only reduce noise. Tune them like a spam filter, not like a locked door.

5 · Add your attack examples to your test set, so any change to these rules shows two numbers: attacks caught, and real users blocked.

The first two rows sum it up. A prompt covers a lot but guarantees nothing. A code check covers little but cannot be talked out of it. An important rule needs both: the prompt so the check rarely fires, and the check so the rule always holds.

13 · Interview preparation

Beginner Why is a system prompt not enough on its own? ›

Because the system prompt is just text, and the model balances it against all the other text it reads, including the user's message and any documents. If an attacker writes something persuasive, the rule can lose. A prompt makes mistakes less common, but it cannot guarantee anything, and it does not tell you when it fails. For example, a support bot told "never share tokens" can still repeat a token it found in a tool result. So for important rules I add a check in code.

Beginner What is the difference between an input and an output guardrail? ›

An input guardrail checks the user's question before the model runs. For example, it blocks an off-topic question, and that costs no tokens because the model is never called. An output guardrail checks the model's answer before the user sees it. For example, it hides an API key that slipped into the reply. The output check is more important, because the model can produce things no input check could have predicted.

Intermediate A guardrail trips. What are your options? ›

I have four options, and I pick one for each rule. Block for a clear rule break, with a short refusal. Redact when a secret or personal data sits inside an otherwise good answer, so I hide just that part. Downgrade when the answer is not backed by a real document, so I reply with an honest "I don't have that information". Allow and flag when it is unclear, so the user gets the answer and a person reviews it later. If you only ever block, users get too many refusals.

Intermediate Why is a block count not a safety metric? ›

Because it doesn't tell you how many of the blocks were correct. That is called precision. In one example, a filter blocked 412 requests in a week, but only 9 were real attacks. So 403 normal customers were refused, and the 9 attacks would have failed anyway. Every time I report a block count, I put the false-positive rate next to it.

Senior Where does prompt-injection screening belong in the defence ranking? ›

Near the bottom. Prompt injection is when text tries to give the model new orders. The strongest defence is not giving the model the dangerous tool at all. Next comes a rule enforced in code, then human approval for risky actions, then checking that the user is allowed to do the action. Screening for injection only reduces noise, because attackers can always find new wording. So I tune it like a spam filter, not like a security wall.

Senior Your redaction check fires in production. Is that a success? ›

No, I treat it as an incident. The redaction did its job, but the fact that there was something to hide means a secret reached the model's input. That is a bug earlier in the system, for example a tool returning a token it should not. So I raise an alert and fix the source. If I just count it as a save, the real bug stays.

Staff · design Design the guardrail layer for a regulated assistant. ›

I start with the rules that must always hold, not with a list of tools. For each rule, I ask whether a mistake is costly enough to need code. Secrets, personal data, access control and actions that cannot be undone need code. Tone and format can stay in the prompt. For each coded rule, I pick the cheapest check that can decide it: a regex for secrets with a fixed shape, a schema check for JSON, and a judge model only for grounding. I decide which action wins when two checks fail. I save every decision with the run id. And I add all of this to the test set, so any change shows both attacks caught and real users blocked.

14 · In short, and what comes next

Remember these six:

  • A system prompt makes a mistake less likely. A code check stops it.
  • Check the question on the way in and the answer on the way out. The output check catches the surprises.
  • Pick the response for each rule: block, redact, downgrade, or allow and flag.
  • A block count without a false-positive rate is not a safety number.
  • Use the cheapest check that can really decide.
  • A redaction is a warning sign, because the secret should never have reached the model.
🔑
The one idea to remember

A guardrail that can only block is a broken product that looks safe. Most problems should not end the conversation, which is why there are four responses, not one.
