Production / Langfuse - LLM observability

1 · What you already know

You know that an LLM app takes a question, maybe searches some documents, calls a model and returns an answer. When something goes wrong, you need to see what happened inside.

Observability means being able to tell what your system did, and why, from the records it leaves behind. For an LLM app, that also means knowing whether the answer was any good.

Langfuse is a popular open-source tool for this. This page shows what it records, and what it gives you that plain log files cannot.

2 · What breaks now

Say your app already writes logs, and every log line includes a run id (a unique ID for each request). So you can find all the lines for one request. Then a user reports a bad answer, and you have four questions:

The questionWhat the logs can answer
What did this request do?Everything, if you search by the run id
Where did the 4 seconds go?You can work it out by subtracting timestamps, if you find the right lines
Was the answer any good?Nothing. There is nowhere to record that
How many other requests were like this one?Nothing. Each line stands alone

The first two questions are about organising your logs, and a run id mostly solves them. The last two need something logs do not have.

A log line records that something happened. It has no place to say whether it was correct, because you only find that out later. Maybe the user clicks thumbs-down. Maybe a rule checks whether the answer had a source. Maybe another model grades it. You learn the quality after the request has finished, and by then the log line is already written.

3 · Simple breakdown - a tracing platform vs your own logging

A Langfuse

What it is. An open-source tool that records each request as a trace. A trace is the full story of one request, broken into steps called spans (for example: search documents, then call the model). It also stores quality scores, prompts and test datasets.

Core purpose. To answer three things about any request: what it did, what it cost, and whether it was any good, without you building your own storage and viewer.

Execution model.

Architecture under the hood. Three parts. An SDK (a library you add to your code) that wraps your function calls. A server that receives the data in the background. And a database that stores traces, scores, prompts and datasets.

State handling. Traces and scores are saved permanently and you can search them. A session groups one conversation. A user id groups everything one person did.

Limitations and advanced features. The SDK collects data in memory and sends it in batches. If your program exits before sending (called flushing), that data is lost. Traces also store the full prompts and answers, so how long you keep them is a privacy decision, not just a storage one.

B Your own logging

What it is. Lines of text your code writes at different points, like "INFO: search returned 3 results".

Core purpose. To record that something happened, with no extra tool or service to run.

Execution model. Each part of your code writes a line when it runs. The lines are not linked to each other unless you add a shared field like a run id.

Architecture under the hood. A logger and somewhere to store the lines, like a file. Nothing more.

State handling. Only what each line says. There is no single record for a whole request, and no score.

Limitations and advanced features. To rebuild one request, you search and guess. You work out timings by hand, and there is nowhere to add a quality score.

The core differences

LangfuseYour own logging
Shows one full requestYes, as a tree of stepsOnly if every line has the same run id
Stores a quality scoreYes, that is the main pointNo
Effort to runA service to host, or a paid hosted planAlmost none

In short - which one to choose

  • Use a tracing tool once you need to know why a request was slow, expensive or wrong. That is usually when real users arrive.
  • Use your own logging before that, but put a run id on every line, so you can connect it to traces later.
  • The tool matters less than the idea. Treat each request as one record, and attach a quality score to it.

4 · Without the technology

You can build a simple version yourself: a small decorator that times each function and saves the result to a database. That gives you timings for each step. Here is what it does not give you:

  • A viewer. A trace is a tree of steps, and looking at trees in a database table is painful. A good viewer is most of what the tool gives you.
  • Scores added later. A thumbs-down might arrive minutes after the request, and it has to find the right trace.
  • Summaries. A question like "how many answers scored below 0.5 this week?" is now a query you have to write and maintain.
  • Background sending. That db.insert runs while the user waits, so recording the request makes it slower.

The last one causes trouble first. If you save traces the simple way, every request gets slower just so you can measure how slow it was.

5 · Runtime mechanics

Here is what happens for one traced request, step by step:

  1. A trace starts when the request arrives. It records who the user is and which conversation (session) this is.
  2. Each step opens a span. A model call opens a special span called a generation, which also records the model name, the number of tokens and the cost.
  3. Each span closes when its step finishes. The data is kept in memory for now, not saved straight away.
  4. In the background, the SDK sends the data to the server in a batch, so the user does not wait for it.
  5. Scores are added to the trace afterwards, from the user, from a rule, or from a judge model grading some of the answers.

Step 5 is what makes this different from logging. You can still add a score after the request is over, which is exactly when you find out whether the answer was good.

6 · The components, one at a time

The five objects

ObjectWhat it is
TraceOne whole request, from start to finish. Everything else sits inside it
SpanOne step inside the request, with a start and end time. Spans can contain other spans
GenerationA span for a model call. It also records the model, tokens and cost
ScoreA number that says how good something was, attached to a trace or a generation
Session and userGroups: one conversation, and everything one person did

Learn these five and you understand most of the tool.

Three sources of scores

A score can come from three places. A judge here means another LLM asked to grade the answer, and faithfulness means the answer sticks to the documents it was given.

Save each kind under its own name. If the judge says an answer is great but users keep clicking thumbs-down, you want to see that disagreement, not hide it in an average.

Sessions and users

Without these, each trace stands alone. With them, you can ask things like "show me every request in conversations that ended with the user asking for a human", in one search.

Prompt management

Langfuse can store your prompts with version numbers and labels like "production". Each trace then records which prompt version produced it, so when quality drops you can tell whether a prompt change caused it. The risk: if people edit prompts in the tool instead of in your code, the change is never reviewed.

Datasets and offline runs

A golden set is a fixed list of test questions with known good answers. You can store it in Langfuse next to your traces. Then, when you try a new prompt version, you can compare its results directly with how production behaves today.

The flush

The SDK sends data in the background, in batches. A short script or a serverless function that exits without calling flush() loses its last traces, and those are often the ones you wanted to see.

7 · State and data flow

"State" means the data the system keeps while it works. For tracing:

  1. What data is kept? The open trace and its spans, plus any spans waiting in memory to be sent.
  2. Who writes it? The SDK, as each step starts and ends. Your code adds scores and extra details.
  3. Who reads it? You, afterwards. The request itself never reads its own trace.
  4. Is it replaced or added to? Added to. New spans are added, and a score is a new record, not an edit.
  5. How do the pieces fit together? Each span stores the ID of its parent step, so the tree is built when you view it.
  6. Is it only in memory? Only until the flush. That is why the flush matters.
  7. Is it saved partway? Each batch that is sent is saved. If the program crashes, anything still waiting in memory is lost.
  8. Is it in a database? Yes, and that includes the full prompts and answers.
  9. How long is it kept? As long as your retention setting says. This is a privacy decision.
  10. How do you find it again? By trace id, session id or user id.

Rows 6 and 8 cause the most surprises in production. Data that is never flushed is lost, and data that is kept may contain personal information. Both are controlled by default settings until someone changes them.

9 · Break it

Now add tracing to a batch job in the obvious way, and run it.

Thirteen traces are missing, and they are the last thirteen. The SDK was sending data in batches in the background. The program exited before the last batch was sent, and no error appeared.

Then someone else finds a second problem.

The trace store now holds parts of card numbers and dates of birth. By default, Langfuse saves inputs and outputs exactly as they are, and nobody changed that setting.

10 · Fix it

1 · Flush before the program exits. One line fixes the first bug.

The same goes for serverless functions (like AWS Lambda), which can be paused the moment they return.

2 · Hide personal data before it is saved, not when it is shown. If you only hide it in the viewer, it is still stored in the database.

3 · Save a summary instead of the full content when you do not need the content.

Hiding personal data is the same idea a guardrail uses on an answer - see the output check, and RAG production concerns for what a search trace contains.

4 · Choose how long to keep traces on purpose. Traces contain real conversations, so someone should decide this, not leave it to a default.

5 · Score a sample, but keep all the important traces. Run the judge model on a sample of requests to save money, but keep every error and every expensive request in full.

13 · Interview preparation

Beginner What are the core objects in Langfuse? ›

There are five. A trace is one whole request from start to finish. A span is one step inside it, like searching documents. A generation is a span for a model call, and it also records the model, tokens and cost. A score is a number that says how good the answer was. Sessions and users group traces by conversation and by person. For example, one chat question becomes a trace with a search span, a generation, and a thumbs-up score.

Beginner What does a score give you that a log line does not? ›

A place to record whether the answer was good. You usually find that out after the request is over, for example when the user clicks thumbs-down a minute later, or a judge model grades the answer. By then the log line is already written. A score can be added to the trace afterwards, so the quality sits right next to what happened.

Intermediate Where do scores come from? ›

Three places. User feedback, like thumbs up or down, which matters most. Rules in code, which are cheap and give the same result every time, like "does the answer cite a source?" or "is it valid JSON?". And a judge model, which is another LLM grading the answer. It scales without people, but it can be wrong. I save each kind under its own name, so if the judge and the users disagree, I can see it.

Intermediate Why does instrumentation have to be asynchronous? ›

Instrumentation means the code that records traces. If it saves each step while the user waits, every request gets slower just so you can measure it. So the SDK keeps the data in memory and sends it in the background, in batches. The catch is that if the program exits before the last batch is sent, that data is lost. So you must call flush before exiting.

Senior A batch job produced 500 results but only 487 traces. What happened? ›

The program exited before the last batch of traces was sent. The SDK sends data in the background, and when the program ends, anything still in memory is thrown away with no error. The fix is to call flush() before the program ends. The same applies to serverless functions, which can be paused the moment they return.

Senior What is the data-protection risk in a tracing platform? ›

By default, traces save the user's input and the model's output exactly as they are. So if a customer types their card number or date of birth, it ends up in the trace store. I hide personal data before it is saved, not just in the viewer, because hiding it in the viewer still leaves it in the database. Then I set a clear retention period instead of keeping the default.

Staff · design How would you use tracing and scoring together to improve a RAG application? ›

First, I score every request automatically on things a rule can check: did it cite a source, did it refuse, is the output valid. I add user feedback when it arrives, and I run a judge model on a sample to check faithfulness. Then I look for disagreements. If the judge scores high but users click thumbs-down, the judge is checking the wrong thing. If few answers cite sources but users are happy, my citation rule may be too strict. Finally, every real failure I confirm goes into the golden test set, so my offline tests cover each kind of failure seen in production.

14 · In short, and what comes next

Remember these six:

  • Five objects: trace, span, generation, score, session. The rest is detail.
  • A score records something a log line cannot, because you learn the quality after the request.
  • Save user, rule and judge scores separately, so disagreements stay visible.
  • Call flush before a short program exits, or you lose the last batch.
  • Hide personal data before it is saved. Traces hold real conversations, so decide how long to keep them.
  • Load prompts by label, so every trace records which prompt version produced it.
🔑
The one idea to remember

Tracing tells you what happened. A score tells you whether it was any good. The score always arrives later, which is why a trace is a record you can keep adding to, not a line you write once.
