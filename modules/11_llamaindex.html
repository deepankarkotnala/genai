LlamaIndex

Module 10 gave you components you wire together yourself. LlamaIndex takes the same retrieval pipeline and makes it the default: load documents, index them, ask a question, get an answer with sources. This page is about what that default buys you and what it costs.

⏱ Study + practice · 8–12 h Difficulty · Intermediate Prereq · Modules 04–06, 10

1 · What you already know

From module 10 you can build a retrieval chain: run a retriever and a passthrough in parallel, fill a prompt, call the model, parse the reply. You chose every part and you wrote the wiring.

From module 06 you know the stages underneath it - load, split, embed, store, search.

LlamaIndex packages those five stages behind three lines. This page is about when that is the right trade and when it hides something you needed to see.

2 · What breaks now

Your module 10 chain answers questions over one folder of clean text. Now the real requirements arrive:

RequirementWhat it costs you in a hand-wired chain
Ingest PDFs, Word files, Slack, Notion and a databaseA loader per source, each with its own metadata handling
Cite which document each sentence came fromThread source metadata through every step yourself
Split by heading in Markdown but by function in codeA splitter per file type, chosen by extension
Rebuild only the documents that changedTrack hashes, diff them, delete stale vectors
Answer a question that spans four documentsQuery decomposition, then merge the sub-answers

None of these is hard. All of them are plumbing, and all of them exist in every document-heavy product. LlamaIndex is that plumbing, already written, with retrieval as the centre of the library rather than one component in it.

3 · Simple breakdown - LlamaIndex vs LangChain

A LlamaIndex

Basic level

What it is. LlamaIndex is an open-source Python framework for building retrieval applications, built from readers, node parsers, indexes, retrievers, postprocessors and query engines.

Core purpose. It reduces the code needed to get from a folder of documents to an answer with citations.

Execution model.

Intermediate level

Architecture under the hood. The unit is a Node - a chunk of text with metadata and relationships to its neighbours and parent document. A StorageContext holds three stores: the vector store, the docstore that keeps node text, and the index store that keeps the structure. A query engine composes a retriever, optional postprocessors such as a reranker, and a response synthesizer that decides how retrieved nodes become one answer.

State handling. The index is persistent state, written to disk or a vector database and reloaded on start-up. A query holds only the question, the retrieved nodes and the answer. Chat engines add a memory buffer, which you own and which is not stored by the index.

Limitations and advanced features. The defaults are strong, which makes it easy to ship a pipeline you cannot explain - chunk size, top-k and the response mode all have opinions baked in. Its agent and workflow support is younger than LangGraph's. Advanced features are ingestion pipelines with caching and document-hash upserts, sub-question query engines, recursive retrieval over summaries, metadata filters and a large set of reranker integrations.

B LangChain

Basic level

What it is. LangChain is an open-source Python framework for building LLM-based applications from reusable components such as models, prompts, retrievers, tools, and runnables.

Core purpose. It reduces the amount of application code you need to write when several LLM-related components must work together.

Execution model.

Intermediate level

Architecture under the hood. Every component implements one interface, Runnable, which defines invoke, batch, stream and their async versions. The | operator builds a RunnableSequence that runs components in order. RunnableParallel runs components at the same time and returns a dictionary. Streaming, batching and callbacks are implemented once on Runnable, so every chain gets them.

State handling. A chain is stateless. The only data that exists during a run is the value passed from one component to the next. Chat history is added with RunnableWithMessageHistory, which reads and writes a store you supply, keyed by a session id.

Limitations and advanced features. A chain is acyclic and runs forward once: no loops, no rejoining branches, no pause for approval, no recovery after a crash. Advanced features wrap any component - .with_retry(), .with_fallbacks(), .with_structured_output(), .bind_tools().

The core differences

LlamaIndexLangChain
Workflow design Retrieval is the frame. A query engine is assembled from retriever, postprocessors and synthesizer, and the ingestion pipeline is a first-class object. Composition is the frame. Retrieval is one Runnable among many, wired in by you with |.
Error recovery Ingestion caches by document hash, so a failed run resumes without re-embedding. Query failures are per query. Retry and fallback per component. Ingestion is your own code, so resuming it is your own problem.
Architectural paradigm A document index with a query layer over it. A component pipeline behind one shared interface.

In short - which one to choose

Choose LlamaIndex when:

  • Retrieval over documents is the product, not a feature of it.
  • You ingest many formats and sources and want the readers written already.
  • Citations and source attribution are a requirement.
  • Re-indexing changed documents cheaply matters.

Choose LangChain when:

  • Retrieval is one step among several in a larger flow.
  • You want explicit control of every stage, and to see all of them.
  • You are heading toward LangGraph for control flow anyway.

Choose neither when:

  • You have one folder of clean text and 50 lines would do it.
  • You have not built the five ingestion stages by hand once - module 06 first.
  • You are considering both at once. Pick one for retrieval; using two is the worst outcome.

5 · Runtime mechanics

Two paths. Indexing runs rarely; querying runs constantly.

Indexing

  1. A reader turns each source file into one or more Document objects, each with text and metadata.
  2. A node parser splits documents into Node objects, keeping metadata and recording each node's relationship to its neighbours and its parent.
  3. The index embeds every node and writes the vectors to the vector store, the node text to the docstore, and the structure to the index store.

Querying

  1. The question is embedded with the same model used at index time.
  2. The retriever returns the top-k nodes by similarity, after any metadata filter.
  3. Postprocessors run in order - typically a reranker, a similarity cut-off, or both.
  4. The response synthesizer builds one or more prompts from the surviving nodes and calls the model.
  5. The answer is returned with source_nodes attached, so every claim can be traced to a node and its metadata.

Step 8 is the difference that matters. The sources come back by default, rather than being something you threaded through yourself.

6 · The components, one at a time

Getting data in

1 · Document

Text plus metadata. Metadata set here survives into every node and into the answer's sources, which is how citation works.

2 · Reader

Turns a source into Documents. SimpleDirectoryReader picks a parser by file extension; hundreds more exist for Slack, Notion, S3, SQL and web pages.

3 · Node

A chunk, with metadata and relationships. The relationships are what let a retriever find a small precise chunk and then hand the model its larger parent.

4 · Node parser

The splitter. Sentence-aware by default; structure-aware versions exist for Markdown, code and HTML.

Storing and finding

5 · Index

VectorStoreIndex is the one you will use. Others exist: SummaryIndex reads everything, DocumentSummaryIndex retrieves by summary then drills down, PropertyGraphIndex builds entity relationships.

6 · StorageContext

Three stores, and they are separable: the vector store for embeddings, the docstore for node text, the index store for structure. Point the vector store at a real database when you outgrow local files.

7 · Retriever

Question in, nodes out, with a score. similarity_top_k is the single most consequential number on this page.

8 · Metadata filter

Restrict the search space before similarity runs. This is where per-user authorisation belongs - filter before retrieval, never after.

Turning nodes into an answer

9 · Postprocessor

Runs between retrieval and the model. A reranker re-scores the retrieved nodes with a cross-encoder; a cut-off drops anything below a similarity threshold.

10 · Response synthesizer

Decides how nodes become one answer, and it is the setting people never look at.

ModeWhat it doesModel calls
compactPacks nodes into as few prompts as fit. The defaultUsually 1
refineAnswers with node 1, then revises with each further nodeOne per node
tree_summarizeSummarises in pairs up a treeSeveral

refine with top-k of 10 is ten model calls for one question. That is the most common surprise cost in a LlamaIndex application.

11 · Query engine

The assembled object: retriever, postprocessors, synthesizer.

12 · Chat engine

A query engine plus conversation memory, so follow-up questions resolve pronouns against earlier turns.

13 · Ingestion pipeline

Named transformations with a cache keyed by document hash. Re-running only processes what changed.

14 · Sub-question query engine

Splits a comparison question into parts, answers each against the index, then combines them.

7 · State and data flow

1 · What data is state?The index: vectors, node text, and structure. Per query, only the question, the retrieved nodes and the answer.
2 · Who writes each field?Ingestion writes the index. Nothing at query time writes to it.
3 · Who reads it?The retriever reads vectors; the synthesizer reads node text.
4 · Replaced, appended or merged?Nodes are inserted or deleted by id. An ingestion pipeline upserts by document hash.
5 · What controls merging?The document id and hash. Re-ingesting an unchanged document is a no-op.
6 · Only in memory?Only until you persist(). The default index is in memory and dies with the process.
7 · Checkpointed?The ingestion cache is the closest thing, and it is per transformation.
8 · In a database?Yes, once the vector store is Qdrant, Chroma, pgvector or similar.
9 · How long does it survive?As long as the store. Deleting stale nodes is your job.
10 · What key retrieves it again?The persist directory, or the collection name in the vector store.

8 · Trace

Rows 1–3 run once. Rows 4–7 run per question. Switch row 7 to refine and it becomes one model call per node, which is the same answer at five times the cost.

9 · Break it

Set a cut-off high enough that nothing survives it.

No exception. The retriever found nodes, the postprocessor removed all of them, and the synthesizer returned a string. A caller that does str(response) and shows it to a user has just displayed Empty Response as an answer.

The second failure is worse because the output looks correct. Change the embedding model after building the index.

Query vectors from one model are compared against node vectors from another. The scores are arithmetic nonsense, the top-5 are effectively random, and nothing anywhere raises an error.

10 · Fix it

Both failures are invisible by default, so make them loud. Check the sources, not the string.

And record which embedding model built the index, so a mismatch fails at load rather than at answer time.

Nine lines that turn a silent wrong answer into a start-up crash. That trade is almost always correct.

13 · Interview preparation

Beginner  What is LlamaIndex and how is it different from LangChain? ›

LlamaIndex is a data framework specialized for connecting data to LLMs - loading, chunking into Nodes, indexing, retrieving, and synthesizing answers (RAG). LangChain is a general composition framework for any LLM pipeline. LlamaIndex is the data/RAG specialist with stronger ingestion and advanced-retrieval abstractions; they're often combined.

Beginner  What's the difference between a Document and a Node? ›

A Document is a whole source (a file, page, or record). A Node is a chunk of a Document - the actual retrievable unit - carrying text, metadata, an embedding, and relationships to neighboring nodes (prev/next/parent). Node parsers turn Documents into Nodes.

Intermediate  What exactly is a Query Engine made of? ›

A retriever (fetches relevant Nodes from an index), optional node postprocessors (rerank, filter, window-replace), and a response synthesizer (composes Nodes + query into a grounded answer, with a synthesis mode like compact/refine/tree_summarize). It's the end-to-end "ask → answer with sources" object.

Intermediate  Explain sentence-window / auto-merging retrieval. ›

Both solve the small-vs-large chunk dilemma (Module 06's parent-document). Sentence-window embeds single sentences for precise matching but returns each matched sentence with a window of surrounding sentences for context (via a metadata-replacement postprocessor). Auto-merging uses a hierarchy of chunk sizes and merges small matched chunks into their parent when enough siblings hit - giving precision plus coherent context.

Senior  How do you take a LlamaIndex prototype to production? ›

Swap the in-memory store for a real vector DB (Qdrant/pgvector) and persist the index so you don't re-embed on boot. Move ingestion into a scheduled, idempotent IngestionPipeline that handles updates/deletes and tags model_version (Module 04). Tune chunking and add reranking, validated by an eval set (Module 06). Set local/hosted models and temperature via Settings; add metadata-based access control; expose the query engine behind a service boundary (FastAPI). Add tracing/observability and cost controls (Module 14). Treat it as the data layer, with orchestration/agents handled by LangGraph if needed.

Senior  When would you combine LlamaIndex and LangGraph? ›

When the app needs both strong retrieval and multi-step/agentic control. Use LlamaIndex to build a high-quality query engine (advanced retrieval, synthesis), then expose it as a tool to a LangGraph agent that decides when to retrieve, can retrieve iteratively (Agentic RAG, Module 06), branch, and keep state. LlamaIndex handles "how to retrieve well"; LangGraph handles "how to orchestrate the reasoning loop."

Staff · design  Design a multi-source enterprise knowledge engine with LlamaIndex. ›

Ingestion: LlamaHub readers per source (wiki, tickets, docs, DB) → IngestionPipeline (parse to Nodes with rich metadata: source, ACL, freshness, model_version) → embed → persist to a sharded vector store (Module 05). Retrieval: per-source indexes with a router query engine (DocumentSummaryIndex) to pick relevant sources, sentence-window/auto-merging for context, reranking for precision, and metadata pre-filtering for access control (never post-filter security). Synthesis: compact for Q&A, tree_summarize for overviews, always returning source_nodes for citations. Operations: scheduled re-ingestion to meet freshness SLAs, eval gates (recall/faithfulness, Module 06) in CI, observability + cost tracking (Module 14). Expose the engine as a tool to a LangGraph agent for multi-step questions. The deliverable is a governed, fresh, citable retrieval layer reusable across the org.

14 · In short, and what comes next

Remember these five:

  • The unit is a Node - a chunk with metadata and relationships, which is what makes citation work.
  • Settings is global. If you do not set the embedding model, something else does.
  • The embedding model at query time must match the one that built the index.
  • response_mode="refine" is one model call per node.
  • An empty result is returned as the string Empty Response, not as an error.
🔑
The one idea to remember

LlamaIndex makes retrieval the frame instead of a component. That is worth it when documents are the product, and it is a layer of defaults you must open when they are not.
