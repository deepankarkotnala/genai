Local LLMs and Ollama

Module 02 explained where the memory goes. This page turns that into a number you can check against your own machine, then runs a model on it. Install Ollama here - the lab in phase 4 depends on it.

⏱ Study + practice · 8–12 h Difficulty · Intermediate Prereq · Modules 01, 02

1 · What you already know

From module 01: parameters are numbers, and "7B" means seven billion of them. From module 02: the KV cache grows with every token and is often what runs out first.

So far every model you have used ran on somebody else's hardware. This page is about running one on yours, and about knowing before you start whether it will fit.

2 · What breaks now

Four ordinary situations where a hosted API is the wrong answer:

SituationWhy the API fails you
The data cannot leave the buildingHealth records, legal documents, unreleased code. A contract term, not a preference
You are running 50 million classificationsAt small per-call prices this is still six figures. A 3B model on one GPU is not
You need the same answer next yearHosted model versions are retired. Weights on your disk are not
You are developing offline, or on a planeNo network, no model

And the question that stops people immediately: will a 7B model even run on my laptop? That is arithmetic, and you can do it before downloading anything.

3 · Simple breakdown - local serving vs hosted API

A Local serving

Basic level

What it is. Local serving runs the model weights on hardware you control, behind a small HTTP server such as Ollama, vLLM or llama.cpp, which your application calls over localhost.

Core purpose. It keeps the data and the weights on your own machine, and removes per-token pricing in exchange for the cost of the hardware.

Execution model.

Intermediate level

Architecture under the hood. Ollama wraps llama.cpp. Weights are stored in GGUF files, already quantised, and memory-mapped at load time. Layers are placed on the GPU up to the memory you have; the rest stay on the CPU, which is why a model can run "partially offloaded" and be very slow. vLLM is the other common choice: it keeps weights in GPU memory, adds paged attention and continuous batching, and is built for many concurrent users rather than one.

State handling. The weights are loaded once and stay resident until the model is evicted, which Ollama does after about five idle minutes. Per request there is only the KV cache from module 02. Conversation history is not stored by the server - your application re-sends it.

Limitations and advanced features. Open-weight models of a size that fits one machine are behind the largest hosted models on hard reasoning. Throughput is one machine's worth. Quantisation below 4-bit degrades quality noticeably. Advanced use includes serving several models by swapping, custom Modelfile definitions, and moving to vLLM once more than a handful of concurrent users appear.

B Hosted API

Basic level

What it is. A hosted API is a provider's HTTPS endpoint that accepts your messages, runs the model on their hardware, and returns the result, billed per token.

Core purpose. It gives immediate access to models far larger than your hardware could hold, with no capacity planning.

Execution model.

Intermediate level

Architecture under the hood. A load balancer, a queue, and a fleet running continuous batching. Your request is interleaved with other customers', which is why latency varies with their load rather than yours. Rate limits are applied per key, usually as requests and tokens per minute.

State handling. None that you own. Each request carries its whole context. Some providers cache identical prompt prefixes for a few minutes and charge less for the cached part.

Limitations and advanced features. The data leaves your network. Model versions are retired on the provider's schedule, so "latest" can change your outputs without a deploy on your side. Costs scale linearly with usage forever. Advanced features include batch endpoints at lower prices, prompt caching, and provisioned capacity.

The core differences

Local servingHosted API
Workflow design You size the hardware, pick the quantisation and manage load. Capacity is fixed and known. You send a request. Capacity is elastic but shared, and you cannot see the queue.
Error recovery Failures are yours: out of memory, model not pulled, GPU driver. All reproducible and fixable on the machine. Failures are rate limits, timeouts and outages. You cannot fix them, only retry and fall back.
Architectural paradigm A fixed local resource with a hard memory ceiling. A metered shared service with a soft rate ceiling.

In short - which one to choose

Run locally when:

  • The data is not permitted to leave your network.
  • Volume is high and the task is simple enough for a small model.
  • You need reproducible output over months or years.
  • You are developing, testing, or running this course's labs.

Use a hosted API when:

  • The task needs the strongest available reasoning.
  • Traffic is spiky and you do not want idle hardware.
  • You are proving a product idea and hardware would be premature.

Do not run locally when:

  • You have not done the memory arithmetic in section 5.
  • You need many concurrent users and have one GPU.
  • Nobody on the team will own driver and dependency upgrades.

4 · Without the technology

Loading a model without a serving layer is possible, and shows what the server is doing for you.

On a 16 GB card this fails. 7 billion parameters at 2 bytes each is 14 GB before any KV cache, and PyTorch needs working space on top.

You also now own: quantising the weights, deciding which layers go to CPU, holding the model in memory between requests, batching, and streaming. Ollama is those six jobs plus an HTTP endpoint.

5 · Runtime mechanics

The arithmetic first, because it decides everything else. Memory has three parts.

PrecisionBytes per parameterA 7B modelQuality
fp16 / bf16214 GBReference
int8 / Q817 GBAlmost identical
Q4_K_M~0.55~4 GBSmall, usually acceptable loss
Q2~0.32.5 GBNoticeably worse; rarely worth it

So a 7B model at Q4_K_M is about 4 GB of weights, plus roughly 0.5 GB of KV cache at 4k context, plus 1 GB of overhead. About 5.5 GB - which fits an 8 GB card, and does not fit a 6 GB one once your desktop is also using it.

6 · The components, one at a time

1 · The model file

A single GGUF file holding the quantised weights, the tokenizer and the metadata. Portable - copy it to another machine and it runs.

2 · Tags and sizes

The part after the colon selects size and quantisation. No tag means the default, which is usually Q4_K_M.

3 · Base versus instruct

A base model continues text. An instruct model has been fine-tuned to follow instructions - module 01's section 3. Pulling a base model and wondering why it does not answer questions is the most common first mistake here.

4 · The server

Ollama runs as a background service on port 11434. It loads a model on first use and evicts it after roughly five idle minutes, so the first request after a pause is slow.

5 · Context length

Set per request with num_ctx. It is capped by the model, and raising it raises KV cache memory in direct proportion.

6 · Sampling options

The same controls as module 01, under options.

temperature: 0 plus a fixed seed is how you get repeatable output for a test suite.

7 · Streaming

Leave stream true and the endpoint returns newline-delimited JSON, one object per token.

8 · The OpenAI-compatible endpoint

Ollama also serves the OpenAI chat schema, so LangChain and most other libraries work unchanged against a local model.

This one line is why the rest of this course never needs an API key.

9 · Modelfile

A small text file that pins a system prompt and sampling defaults into a named model, so callers cannot forget them.

10 · Embedding models

Smaller models that return a vector instead of text. Needed from module 04 onward, and they run comfortably on a CPU.

7 · State and data flow

1 · What data is state?The loaded weights, and the KV cache for each in-flight request.
2 · Who writes it?The server, on load and during generation.
3 · Who reads it?The forward pass, for that request only.
4 · Replaced, appended or merged?Weights are read-only. The KV cache is appended per token.
5 · What controls merging?Nothing. There is no shared state between requests.
6 · Only in memory?Weights come from disk and are memory-mapped. The cache is memory only.
7 · Cached?The model stays resident for about five idle minutes, then is evicted.
8 · In a database?No. Conversation history is your application's job.
9 · How long does it survive?KV cache: one request. Weights: until eviction or restart.
10 · What key retrieves it again?The model tag. There is no session id at this layer.

The server is stateless between requests. If a local chatbot appears to remember, it is because your code re-sent the messages - exactly as with a hosted API.

8 · Trace

What happens on a first request after a restart, versus the second one.

StepFirst requestSecond request
Server receives the call1 ms1 ms
Model resident?No - read GGUF from disk, map into memoryYes
Load time2–20 s, depending on size and disk0 s
Prefill (read the prompt)~120 ms for 300 tokens~120 ms
Decode~35 tokens/sec~35 tokens/sec
Total for a 200-token answer~11 s~6 s

The two are identical apart from the load. A "slow model" complaint is very often just cold-start after the five-minute eviction - check /api/ps before tuning anything else.

9 · Break it

Pull a model that does not fit, and it still runs. That is the problem.

On a 12 GB card there is no error. Ollama places as many layers on the GPU as fit and runs the rest on the CPU, so the model answers - at about 1.5 tokens per second instead of 40. A 200-token reply takes over two minutes.

The second silent failure is quality. Pull the same model at Q2 and it answers fast and confidently, with more of the answers wrong. Nothing in the output says which quantisation produced it.

10 · Fix it

Do the arithmetic before pulling, and check the placement after loading.

Then confirm what actually happened, rather than trusting that it fitted.

The PROCESSOR column is the single most useful diagnostic on this page. Anything other than 100% GPU explains a slow model completely.

13 · Interview preparation

Beginner  Why run an LLM locally instead of calling an API? ›

Data privacy (nothing leaves your network), no per-token cost, offline/edge capability, predictable latency, and full version control. The trade-off is that you own the hardware, ops, and scaling, and open models may lag frontier quality on the hardest tasks.

Beginner  What is quantization and what does it cost you? ›

Storing model weights at lower precision (e.g. 4-bit instead of 16-bit), shrinking memory ~3–4× and speeding inference. The cost is a small, usually acceptable accuracy loss; aggressive quants (Q3 and below) degrade quality more noticeably. Q4_K_M is the common sweet spot.

Intermediate  Estimate the VRAM to run a 13B model at Q4. ›

~4.5 bits × 13B / 8 ≈ 7.3 GB of weights, ×1.2 for KV cache + activations ≈ ~9 GB at modest context. A 12 GB GPU runs it comfortably; an 8 GB GPU would need a smaller quant, shorter context, or partial CPU offload (slower).

Intermediate  What's the difference between Ollama and vLLM? ›

Ollama optimizes for easy single-box/local use and developer experience. vLLM optimizes for high-throughput multi-user serving via continuous batching and paged KV cache. Use Ollama to prototype and for desktop/edge; graduate to vLLM/TGI for a production API serving many concurrent users.

Senior  A hospital wants private RAG over patient records. Walk through your local deployment. ›

All compute on-prem/in-VPC; nothing leaves the network. Run a local instruct model (e.g. Qwen2.5/Llama3.x, Q4–Q8 by GPU budget) via vLLM for concurrency, plus a local embedding model. Vector DB on-prem (pgvector/Qdrant). Add a gateway for auth, audit logging, and PII guardrails; pin model + prompt versions; build an eval set of clinical Q&A to gate releases. Document hardware sizing from the VRAM math and plan capacity for peak concurrency. Privacy and auditability are the design center, not latency.

Staff · design  Design a hybrid local+hosted model router to cut cost 70% without hurting quality. ›

Classify each request by difficulty (heuristics + a tiny classifier or the local model's self-assessed confidence). Route easy/high-volume tasks (formatting, extraction, simple Q&A) to a local Q4 model; escalate hard/ambiguous tasks (complex reasoning, long context) to a hosted frontier model. Add a confidence/verification gate: if the local output fails a validator (schema, faithfulness, low logprob), retry on hosted. Track per-route quality with evals and per-route cost; tune the threshold to hit the cost target while keeping quality SLO. Cache identical requests. This routing layer lives in the orchestration tier from Module 01's gateway design.

14 · In short, and what comes next

Remember these five:

  • Memory is weights plus KV cache plus about 1 GB. Do the sum before pulling.
  • Q4_K_M is the usual stopping point: a 7B model in roughly 4 GB.
  • A model that does not fit still runs, on the CPU, very slowly. Check ollama ps.
  • Base models complete text; instruct models follow instructions.
  • The OpenAI-compatible endpoint means local and hosted differ by a base URL.
🔑
The one idea to remember

Local serving trades a hard memory ceiling for no per-token cost and no data leaving the machine. Everything else on this page - quantisation, offload, context length, eviction - is a consequence of that ceiling.
