Embeddings

An embedding model turns a piece of text into a fixed-length list of numbers. Two texts that mean similar things get lists that point in similar directions, and a similarity function turns that into a score you can sort by. Every retrieval system in this course rests on that one operation.

⏱ Study + practice · 8–12 h Difficulty · Intermediate Prereq · Modules 01, 03

1 · What you already know

From module 01: token ids index an embedding table, giving each token a vector. Tokens used in similar contexts end up with similar vectors.

That was one vector per token, inside the model. This page is about one vector for a whole sentence or document, produced by a separate model you call yourself.

2 · What breaks now

You need to find the handbook paragraph that answers a user's question. The obvious approach is to search for the words.

The handbook says "Refunds are accepted within 30 days of delivery." It shares almost no words with the question, so word matching finds nothing.

QueryDocumentWord overlapSame meaning?
how long to send something backrefunds accepted within 30 daysnoneyes

Word overlap is not meaning. An embedding model is trained so that the first and third rows score high and the second scores low.

3 · Simple breakdown - dense embeddings vs BM25

A Dense embeddings

Basic level

What it is. A dense embedding is a fixed-length list of floating-point numbers produced by a neural model from a piece of text, where texts with similar meaning produce vectors pointing in similar directions.

Core purpose. It lets you find text that means the same thing as the query even when it shares none of the same words.

Execution model.

Intermediate level

Architecture under the hood. A transformer encoder, usually much smaller than a chat model - 20 to 500 million parameters. It reads all tokens at once and produces one vector per token; a pooling step then combines them into a single vector, most often by taking the mean. Models are trained with contrastive objectives on pairs known to be related, which is what makes distance mean similarity. Output is typically 384 to 3,072 dimensions.

State handling. Stateless. The same text always produces the same vector for a given model. The vectors you store are the persistent state, and they are only valid for the model that produced them.

Limitations and advanced features. Poor at exact identifiers - product codes, error numbers and names are compressed into a general direction, so SKU-90210 and SKU-90211 look nearly identical. The input has its own token limit, usually 512, and text beyond it is silently truncated. Advanced features are instruction-prefixed models that embed queries and documents differently, Matryoshka models you can truncate to fewer dimensions, and multi-vector models such as ColBERT.

B BM25 keyword search

Basic level

What it is. BM25 is a scoring function that ranks documents by the query terms they contain, weighting rare terms more heavily and discounting repeated ones.

Core purpose. It finds documents containing the words you asked for, and it is exact about which words those are.

Execution model.

Intermediate level

Architecture under the hood. An inverted index: a map from each term to the list of documents containing it, with positions and counts. Scoring combines term frequency in the document, inverse document frequency across the collection, and a length normalisation controlled by two constants, k1 and b. No neural network and no training are involved.

State handling. The index is the state, updated incrementally as documents are added or removed. Adding a document does not require touching the others.

Limitations and advanced features. A query sharing no terms with a relevant document scores zero - the failure in section 2. Synonyms, paraphrase and other languages are invisible to it. Advanced features are stemming and lemmatisation, stopword lists, field boosting, phrase and proximity matching, and learned sparse models such as SPLADE that keep the inverted index but let a model decide the term weights.

The core differences

Dense embeddingsBM25
Workflow design Embed everything once, embed the query, compare vectors. Adding documents means running the model again. Build an inverted index, look up query terms, score candidates. Adding a document is a cheap index update.
Error recovery A miss returns confident but unrelated neighbours, because something is always nearest. Failure looks identical to success. A miss returns an empty list or a zero score, which is a signal you can branch on.
Architectural paradigm Approximate nearest-neighbour search in a learned continuous space. Exact term lookup with a statistical ranking function.

In short - which one to choose

Use dense embeddings when:

  • Users ask in their own words and the documents use different ones.
  • Paraphrase, synonyms or multiple languages matter.
  • The corpus is prose rather than identifiers.

Use BM25 when:

  • Queries contain exact identifiers, codes, names or error strings.
  • You need to explain why a document matched.
  • The corpus changes constantly and re-embedding is expensive.

Use both - hybrid - when:

  • Real users do both, which is almost always. This is the honest default.
  • You have measured each separately and know which one each query type needs.

4 · Without the technology

The pre-neural way to turn text into a vector was to count words.

The vector has one dimension per vocabulary word, and it is almost entirely zeros - a sparse vector. Two texts are similar only if they literally share words.

A dense embedding has a few hundred dimensions, all non-zero, and none of them corresponds to a specific word. Meaning is spread across all of them, which is exactly why paraphrase works.

5 · Runtime mechanics

What happens on one embed("...") call. Six steps.

  1. The text is tokenized by the embedding model's own tokenizer, which is usually not the same one your chat model uses.
  2. Anything past the model's input limit - commonly 512 tokens - is silently truncated.
  3. The tokens pass through the encoder, producing one vector per token.
  4. Pooling combines them into one vector. Mean pooling averages across tokens; CLS pooling takes the first token's vector.
  5. The vector is usually normalised to length 1, which makes cosine similarity equal to a dot product.
  6. You store it, or compare it against stored vectors and sort by score.

Step 2 is the one that bites. A 3,000-token document embedded by a 512-token model produces a vector describing only its first sixth, with no warning.

6 · The components, one at a time

1 · The vector

A fixed-length list of floats. The length is set by the model and never changes. Individual dimensions have no human meaning.

2 · Dimensions

More dimensions can carry more distinction, at a cost in storage and search time.

3 · Cosine similarity

The cosine of the angle between two vectors: 1 identical direction, 0 unrelated, −1 opposite. It ignores length, which is why it is the default for text.

4 · Dot product and Euclidean distance

On normalised vectors, the dot product equals cosine and is faster. Euclidean distance also ranks the same way once vectors are normalised. Normalise at write time and the choice stops mattering.

5 · Pooling

How token vectors become one vector. Mean pooling is the common default; the model card states which the model was trained with, and using a different one degrades quality quietly.

6 · Normalisation

Scaling a vector to length 1. Do it once, at write time, and store normalised.

8 · Asymmetric search and prefixes

Some models are trained to embed a short question and a long passage differently, and expect a prefix to say which is which. Omitting it costs real accuracy.

9 · Chunking, briefly

One vector per chunk, not per document. A 40-page PDF as one vector is a vector of nothing in particular. Chunking is module 06; here the point is that chunk size decides what a vector actually represents.

10 · Bi-encoder and cross-encoder

Everything above is a bi-encoder: query and document embedded separately, so documents can be embedded in advance. A cross-encoder reads the pair together and scores it - much more accurate, and impossible to precompute, which is why it is used to rerank a shortlist rather than to search.

11 · Quantisation

Storing vectors as int8 or binary instead of fp32 cuts memory four to thirty-two times, with a small recall loss. Worth it above roughly a million vectors.

7 · State and data flow

1 · What data is state?The stored vectors, plus the text and metadata beside them.
2 · Who writes each field?The ingestion job. Query time writes nothing.
3 · Who reads it?The similarity search, on every query.
4 · Replaced, appended or merged?Appended by id. Changing a document means deleting and re-inserting its vectors.
5 · What controls merging?The id you assign. No id means silent duplicates.
6 · Only in memory?Only in a toy. Real systems persist to a vector database - module 05.
7 · Cached?Embeddings are deterministic, so caching by text hash is free and cuts re-ingestion cost.
8 · In a database?Yes, with the text and metadata alongside.
9 · How long does it survive?Until the model changes. Then every vector is invalid.
10 · What key retrieves it again?The chunk id, and the model name that produced it.

Row 9 is the operational fact of this page. The embedding model is not a swappable component - changing it invalidates the entire index.

9 · Break it

Ask about something the corpus does not cover.

Four chunks came back, as they always will. Similarity search returns the nearest vectors; it has no concept of "nothing here is relevant". The scores are lower, but nothing compares them to a threshold, and the model downstream will happily answer from them.

The second failure is exact identifiers.

To the embedding model these strings differ by one token in a general "product code" direction. BM25 would have matched the exact string and scored the others zero.

10 · Fix it

Compare the top score against a threshold you calibrated, not one you guessed.

Calibrate floor from data, because the number differs per model and per corpus.

For identifiers, stop asking embeddings to do it.

Reciprocal rank fusion combines positions rather than scores, which matters because a cosine of 0.7 and a BM25 score of 14 are not on the same scale and never will be.

13 · Interview preparation

Beginner  What is a text embedding? ›

A fixed-length numeric vector representing the meaning of a piece of text, produced by a model trained so that semantically similar texts get nearby vectors. It lets you measure relevance with geometric distance instead of keyword overlap.

Beginner  Why cosine similarity instead of Euclidean distance for text? ›

Cosine measures the angle between vectors, ignoring magnitude - and for text, direction (which concepts are present) matters more than length. With normalized vectors, cosine, dot product, and Euclidean give the same ranking, so people normalize and use the fast dot product.

Intermediate  Dense vs sparse embeddings - when do you need each? ›

Dense (semantic) embeddings match meaning and paraphrase but miss exact terms. Sparse/lexical (BM25, SPLADE) match exact keywords, codes, and rare proper nouns but miss synonyms. Use dense for conceptual queries, sparse for precise terms, and hybrid (combine both, then rerank) when you need both - covered in Module 06.

Intermediate  How does embedding dimensionality affect a system? ›

Higher dimensions can capture more nuance but cost more storage (linear in dims × number of vectors) and slightly slower similarity computation and index build. 384-d is fast/light; 768–1024 is a common quality balance; 1536+ for top quality. Choose based on recall needs vs. storage/latency budget; some models (Matryoshka) let you truncate dims gracefully.

Senior  Your retrieval quality dropped overnight. Embeddings are a suspect - how do you investigate? ›

Check for a silent model/version change (different model → incompatible space) or a normalization/prefix regression (someone dropped the query: prefix). Verify index and query use the same model + same preprocessing. Inspect a few queries' nearest neighbors manually. Run your retrieval eval set (recall@k, MRR) against a known-good baseline. If a model upgrade happened, you likely need a full re-embed; partial re-index leaves mixed spaces.

Staff · design  Design an embedding platform serving 50 teams over billions of documents. ›

Centralize a versioned embedding service (one or few approved models) so vectors are comparable and re-index jobs are coordinated. Components: a batched GPU embedding API with autoscaling; a feature/registry that records model id + version + normalization alongside every vector; an idempotent, resumable re-embedding pipeline (model upgrades = backfill jobs); a cache layer for hot query vectors and semantic caching; cost/latency dashboards per team. Governance: deprecation policy for models, eval gates before any model swap (recall@k regression check), and PII handling for inputs. Treat the embedding model like a database schema - versioned, migrated deliberately, never silently changed.

14 · In short, and what comes next

Remember these five:

  • An embedding is one fixed-length vector per chunk, and only valid for the model that made it.
  • Normalise once at write time, and cosine becomes a dot product.
  • Similarity search always returns something. Enforce a calibrated score floor.
  • Embeddings are poor at exact identifiers. That is what BM25 is for.
  • Text beyond the model's input limit is truncated silently.
🔑
The one idea to remember

Nearest is not the same as relevant. An embedding index answers "what is closest", and turning that into "what is useful" needs a threshold, a hybrid partner, or a reranker - usually all three.
