Embeddings

An embedding turns a piece of text into one list of numbers, so that texts with similar meaning get similar lists. That one trick lets a computer see that "how long to send something back" and "refunds are accepted within 30 days" mean nearly the same thing. This page is built in three levels: read Level 1 first, and stop there if you like.

Everything on this page comes back to five ideas. Level 1 covers the first three.

  1. An embedding is one list of numbers per piece of text. Similar meaning gives lists that point in a similar direction.
  2. Cosine similarity measures how closely two embeddings point the same way. 1 means the same direction, 0 means unrelated. Store vectors at length 1 and it becomes a simple dot product.
  3. Nearest is not the same as relevant. A search always returns something, so you need a minimum score.
  4. Embeddings are weak at exact codes and names. Keyword search (BM25) is strong there, so real systems use both.
  5. Embeddings only work with the model that made them. Change the model and you must re-embed everything.
🧠
Memory hook

Meaning becomes coordinates; near means similar. Every text gets a spot on a meaning map - "refund policy" and "return an item" sit side by side. To search, drop the question on the map, look at its neighbours, and check they are close enough to be useful.

Level 1The core ideaAbout 25 minutes. No maths beyond multiplying, adding and one square root.

1 · What you already know

From 01 and 02: inside a model, every token becomes a vector - a list of numbers - and the transformer layers blend those vectors so each one carries meaning from its context.

That was one vector per token, inside the chat model. This page is about one vector for a whole sentence or paragraph, made by a separate, smaller model called an embedding model. You send it text; it sends back the list of numbers.

2 · The problem: matching words is not matching meaning

A user asks a support bot a question. The answer is somewhere in the company handbook. The obvious way to find it is to search for the user's words.

User asksHandbook saysShared wordsSame meaning?
how long to send something backrefunds accepted within 30 daysnoneyes
cancel my subscriptionterminating your plannoneyes
java performancejava coffee roasting temperatureoneno

Word search gets all three wrong. It misses the first two because they share no words, and it matches the third because one word happens to repeat. Word overlap is not meaning. An embedding model is trained so that the first two pairs score high and the third scores low.

3 · The big idea: meaning as a position on a map

Picture a map where every piece of text has a location, and texts that mean similar things sit close together. An embedding is that location, written as numbers. To find the handbook passage that answers a question, put the question on the map and look at what is nearby.

Three things to notice:

  • Different words, same neighbourhood. "send it back?" lands next to "refund policy" even though they share no words.
  • Nobody drew this map by hand. The embedding model learned where to put things by training on millions of pairs of texts known to be related.
  • Real maps have hundreds of directions, not two - often 384 to 3,072. No single direction has a human meaning like "refunds". Meaning is spread across all of them.

The map is an analogy, but a close one: an embedding really is a point in space, and search really is "find the nearest points".

4 · Measuring closeness: cosine similarity

Think of each embedding as an arrow from the centre of the map to its point. Cosine similarity asks one question: how much do two arrows point the same way?

CosineMeaningExample
1Same directionTwo texts with the same meaning
0Unrelated (at right angles)A refund question and a coffee article
-1Opposite directionRare with text embeddings; in practice most scores sit between 0 and 1

Cosine looks only at direction, not length. That matters: a one-line FAQ answer and a long policy page about the same topic point the same way, so they score the same.

5 · Worked example: search by hand

Here is a real search, small enough to check with a pencil. Real embeddings have hundreds of numbers; these have three. To make them readable, pretend the three numbers mean "about returns", "about cancelling" and "about coffee". Real dimensions have no such names.

TextEmbedding
Question: how long to send something back?[3, 1, 0]
A · Refunds are accepted within 30 days[4, 2, 0]
B · Terminating your plan[1, 3, 0]
C · Java coffee roasting[0, 0, 4]

Step 1 · Dot product: multiply number by number and add

DocumentQuestion · documentDot product
A3×4 + 1×2 + 0×014
B3×1 + 1×3 + 0×06
C3×0 + 1×0 + 0×40

Step 2 · Divide by the two lengths

The length of a vector is the square root of the sum of its squares. The question's length is √(9 + 1 + 0) = √10 ≈ 3.16. Dividing by both lengths removes the effect of length and leaves only direction.

DocumentIts lengthDot ÷ (3.16 × its length)Cosine
A√20 ≈ 4.4714 ÷ 14.140.99
B√10 ≈ 3.166 ÷ 10.000.60
C√16 = 40 ÷ 12.650.00

Step 3 · Sort by score

A (0.99) comes first, B (0.60) second, C (0.00) last. The refund passage answers the question, and it shares no words with it. That is semantic search.

🔑
The shortcut every real system uses

Scale every vector to length 1 once, when you store it. This is called normalising. Then step 2 disappears: the question becomes [0.95, 0.32, 0], A becomes [0.89, 0.45, 0], and their plain dot product is 0.99 - the same answer, with less work on every search.

Try one more by hand: a shorter document [2, 1, 0] points exactly the same way as A. Its cosine with the question is also 0.99, which is why length does not matter.

Q What is an embedding, in one sentence? ›
A fixed-length list of numbers that represents the meaning of a piece of text, made so that texts with similar meaning get lists pointing in a similar direction.
Q Why does word search miss "how long to send something back" against "refunds accepted within 30 days"? ›
They share no words. Word search matches spelling, not meaning; the embeddings of the two texts sit close together because their meanings are close.
Q What do cosine scores of 1 and 0 mean? ›
1 means the two vectors point the same way (same meaning). 0 means they are at right angles (unrelated).
Q Why does a short FAQ answer and a long page on the same topic get the same cosine? ›
Cosine divides out the lengths and looks only at direction. Same topic, same direction, same score.
Q What does normalising buy you? ›
With every vector stored at length 1, cosine similarity is just the dot product, so each search skips the length calculation.

6 · What happens when you embed a text

  1. Tokenize. The text is split into tokens by the embedding model's own tokenizer, which is usually not the one your chat model uses.
  2. Cut to the input limit. Anything past the model's limit - 512 tokens on many classic models, 8,000 or more on newer ones - is dropped without any warning.
  3. Encode. The tokens pass through a transformer, which gives one vector per token.
  4. Pool. Those token vectors are combined into one vector. Many sentence-transformer models average them (mean pooling), BGE uses the first [CLS] token, and newer LLM-based embedders use the last token. Use whatever the model was trained with.
  5. Normalise. The vector is scaled to length 1, so cosine becomes a dot product.
  6. Store or compare. At ingestion you store it next to its text. At question time you compare it with the stored vectors and sort by score.

Step 2 is the one that bites. A 3,000-token document sent to a 512-token model gets a vector that describes only its first 17% - and nothing tells you.

Bi-encoder and cross-encoder

Everything above is a bi-encoder: the question and each document are embedded separately, so documents can be embedded in advance. A cross-encoder reads the question and one document together and outputs a relevance score. It is more accurate but cannot be precomputed, so it is used to rerank a shortlist of, say, 50 results - never to search everything.

8 · What you store, and when it goes stale

An embedding system stores three things per chunk: the vector, the original text, and metadata such as the source document and date. The search runs on the vectors; the text is what you hand to the model afterwards.

Who writes itThe ingestion job, once per chunk. Answering a question writes nothing.
How a change worksA document changes: delete its old chunks by id and insert the new ones. Without a stable id you get silent duplicates.
CachingThe same text through the same model gives the same vector, so caching by a hash of model name plus text makes re-ingestion almost free.
When it goes staleWhen the embedding model changes. Vectors from two models live in different spaces and cannot be compared. Every vector must be rebuilt.

The embedding model is not a swappable part. Changing it invalidates the whole index, so record the model name with the index and refuse to search on a mismatch.

10 · Break it

Ask about something the handbook does not cover

Ask the support bot about crypto payments, which the handbook never mentions. Four chunks still come back, because something is always nearest. The scores are lower, but if nothing checks them, the chat model will happily answer from unrelated text.

Search for an exact code

Ask about product SKU-90210. To an embedding model, SKU-90210 and SKU-90211 are almost the same point on the map - both are "a product code". The manual for the wrong product can easily rank first. Keyword search would have matched the exact string.

11 · Fix it

Add a minimum score

Compare the top score against a threshold, and say "I don't know" below it. Set the threshold from data, not by guessing: score a set of questions you have labelled as answerable or not, and pick the value that separates them. The right number differs for every model and every corpus.

Add keyword search, and merge by rank

Run BM25 keyword search alongside the embedding search. This is called hybrid search. The two scores cannot be added - a cosine of 0.7 and a BM25 score of 14 are on different scales - so merge the two lists by position instead. The standard method is reciprocal rank fusion (RRF): each list gives a document 1 ÷ (60 + its rank), and you add them up.

Question: "SKU-90210 return window"Keyword rankEmbedding rankRRF score
Returns policy211/62 + 1/61 = 0.0325
SKU-90210 manual131/61 + 1/63 = 0.0323
SKU-90211 manual (wrong product)-21/62 = 0.0161

Both useful documents end up on top, and the wrong product drops to third. Hybrid search is the honest default, because real users ask in their own words and type exact codes.

Check yourself: Level 2

Q What happens to a 3,000-token document sent to a model with a 512-token limit? ›
Everything after the first 512 tokens is dropped without a warning, so the vector describes only the first 17% of the document. Chunk documents to fit the limit.
Q You switch to a better embedding model. What must you do with the existing index? ›
Re-embed everything. Vectors from different models live in different spaces and cannot be compared, so a half-migrated index gives wrong results silently.
Q Why can't you just add a cosine score and a BM25 score together? ›
They are on different scales. Reciprocal rank fusion merges by position instead: each list contributes 1 ÷ (60 + rank).
Q What is the difference between a bi-encoder and a cross-encoder? ›
A bi-encoder embeds question and document separately, so documents are embedded in advance and search is fast. A cross-encoder reads the pair together - more accurate, but too slow for anything except reranking a shortlist.
Q How do you stop a search from answering a question the documents do not cover? ›
Enforce a minimum score, calibrated on labelled questions, and answer "I don't know" below it.

13 · Dense embeddings vs BM25, side by side

A reference summary in the six-label format used across the course.

A Dense embeddings

Basic level

What it is. A fixed-length list of numbers produced by a neural model from a piece of text, where texts with similar meaning produce vectors pointing in similar directions.

Core purpose. It finds text that means the same thing as the question even when it shares none of the same words.

Execution model. Embed every chunk once, embed the question, compare by cosine, return the closest. The diagram in section 6 shows it.

Intermediate level

Architecture under the hood. A transformer encoder, usually much smaller than a chat model. It produces one vector per token, and a pooling step combines them into one. It is trained on pairs of texts known to be related, which is what makes distance mean similarity. Output is typically 384 to 3,072 dimensions.

State handling. The model itself is stateless: the same text gives the same vector for a given model. The stored vectors are the state, and they are valid only for the model that produced them.

Limitations and advanced features. Weak on exact identifiers such as product codes, error numbers and names. Text past the input limit is silently dropped. Advanced options include models that embed questions and passages differently, models whose vectors can be shortened to fewer dimensions (Matryoshka), and multi-vector models such as ColBERT.

B BM25 keyword search

Basic level

What it is. A scoring function that ranks documents by the question's words they contain, giving rare words more weight and repeated words less.

Core purpose. It finds documents containing the exact words you asked for.

Execution model.

Intermediate level

Architecture under the hood. An inverted index: a map from each word to the documents that contain it. The score combines how often the word appears in the document, how rare it is across the collection, and the document's length. No neural network and no training are involved.

State handling. The index is the state. Adding or removing a document is a cheap update that does not touch the others.

Limitations and advanced features. A question that shares no words with a relevant document scores zero - the failure in section 2. Synonyms and paraphrases are invisible to it. Advanced options include stemming, stopword lists, field boosting, phrase matching, and learned sparse models such as SPLADE that let a model choose the word weights.

The core differences

Dense embeddingsBM25
Workflow design Embed everything once, embed the question, compare vectors. Adding documents means running the model again. Build an inverted index, look up the question's words, score the matches. Adding a document is a cheap index update.
When nothing matches Still returns the nearest neighbours, with lower scores. Without a minimum score, a miss looks much like a hit. Returns an empty list or zero scores, which is a clear signal you can act on.
Architectural paradigm Nearest-neighbour search in a learned space of meaning. Exact word lookup with a statistical ranking formula.

In short - which one to choose

Use dense embeddings when:

  • Users ask in their own words and the documents use different ones.
  • Paraphrase, synonyms or multiple languages matter.
  • The documents are prose rather than identifiers.

Use BM25 when:

  • Questions contain exact codes, names or error messages.
  • You need to explain why a document matched.
  • The documents change constantly and re-embedding is expensive.

Use both - hybrid - when:

  • Real users do both, which is almost always. This is the honest default.
  • You have measured each one and know which kind of question needs which.

The standard production shape is hybrid retrieval feeding a reranker: BM25 and dense search each return about 50 results, rank fusion merges them, a cross-encoder reorders the shortlist, and the top few reach the model.

15 · Interview preparation

Beginner What is a text embedding? ›

A fixed-length numeric vector representing the meaning of a piece of text, produced by a model trained so that semantically similar texts get nearby vectors. It lets you measure relevance with geometric distance instead of keyword overlap.

Beginner Why cosine similarity instead of Euclidean distance for text? ›

Cosine measures the angle between vectors, ignoring magnitude - and for text, direction (which concepts are present) matters more than length. With normalized vectors, cosine, dot product, and Euclidean give the same ranking, so people normalize and use the fast dot product.

Intermediate Dense vs sparse embeddings - when do you need each? ›

Dense (semantic) embeddings match meaning and paraphrase but miss exact terms. Sparse/lexical (BM25, SPLADE) match exact keywords, codes, and rare proper nouns but miss synonyms. Use dense for conceptual queries, sparse for precise terms, and hybrid (combine both, then rerank) when you need both - covered in 05 RAG, End-to-End.

Intermediate How does embedding dimensionality affect a system? ›

Higher dimensions can capture more nuance but cost more storage (linear in dims × number of vectors) and slightly slower similarity computation and index build. 384-d is fast/light; 768–1024 is a common quality balance; 1536+ for top quality. Choose based on recall needs vs. storage/latency budget; some models (Matryoshka) let you truncate dims gracefully.

Senior Your retrieval quality dropped overnight. Embeddings are a suspect - how do you investigate? ›

Check for a silent model/version change (different model → incompatible space) or a normalization/prefix regression (someone dropped the query: prefix). Verify index and query use the same model + same preprocessing. Inspect a few queries' nearest neighbors manually. Run your retrieval eval set (recall@k, MRR) against a known-good baseline. If a model upgrade happened, you likely need a full re-embed; partial re-index leaves mixed spaces.

Staff · design Design an embedding platform serving 50 teams over billions of documents. ›

Centralize a versioned embedding service (one or few approved models) so vectors are comparable and re-index jobs are coordinated. Components: a batched GPU embedding API with autoscaling; a feature/registry that records model id + version + normalization alongside every vector; an idempotent, resumable re-embedding pipeline (model upgrades = backfill jobs); a cache layer for hot query vectors and semantic caching; cost/latency dashboards per team. Governance: deprecation policy for models, eval gates before any model swap (recall@k regression check), and PII handling for inputs. Treat the embedding model like a database schema - versioned, migrated deliberately, never silently changed.

🔑
The one idea to remember

Nearest is not the same as relevant. An embedding search answers "what is closest". Turning that into "what is useful" needs a minimum score, a keyword partner, or a reranker - usually all three.
