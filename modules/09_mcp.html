Model Context Protocol (MCP)

In Module 08 you wired tools into an agent by hand — schemas, execution, glue code — bespoke to one app and one framework. MCP is the open standard that makes that integration universal: write a tool server once, and any MCP-capable client (Claude Desktop, IDEs, your own agent) can use it. It's the "USB-C of AI tooling" — one protocol so models and data sources plug together without custom adapters.

⏱ Study + practice · 8–12 h Difficulty · Intermediate Prereq · Module 08, FastAPI basics
🔗
MCP is one of three agent protocols

MCP standardises the boundary between an agent and its tools and data. Two sibling standards cover the other two boundaries: A2A (Agent2Agent) for delegating work to other agents across vendors, and A2UI for agents that render real interfaces instead of walls of text. For the comparative brief — including what changed in the 2026-07-28 MCP revision — see Agent Protocols — MCP · A2A · A2UI →. For the policy layer around all three — trust boundaries, identity and middleware — see §11 Middleware, Identity and Agent Interoperability →.

1 · Executive summary

In plain words first: in Module 08 you wrote the tools and the agent, so they only ever worked with each other. MCP is an agreement about how a tool describes itself and how it is called, so a tool you write can be used by an agent you did not write, and the other way round. Same tools as last module; a standard plug instead of soldered wires.

The Model Context Protocol (MCP) is an open standard (introduced by Anthropic, now broadly adopted) that defines how applications expose context and capabilities to LLMs. An publishes three things — tools (actions the model can invoke), resources (data the model can read), and prompts (reusable templates) — over a standard JSON-RPC protocol. An MCP client (inside the host app) discovers and calls them. Build the server once; reuse it everywhere.

❓

Why it exists

Every tool integration was custom per app × per framework — an M×N explosion. MCP collapses it to M+N: tools and clients share one protocol.

🔧

Problem it solves

Standardized, discoverable, reusable tool/data access for LLMs — with a clean security boundary between the model and your systems.

🌐

Where it fits

The interoperability layer for agents (08). LangGraph/CrewAI agents consume MCP servers; your services become MCP servers.

🔑
The one idea to remember

MCP standardizes the agent–tool boundary. Tools = model can do; Resources = model can read; Prompts = reusable templates. Write a server once; every MCP client gets your capabilities for free.

2 · First-principles breakdown

What — a universal adapter for AI capabilities

Before USB, every device had its own connector. Before MCP, every AI app integrated every tool its own way: your ElasticSearch tool for LangChain didn't work in Claude Desktop or in a CrewAI agent — you rewrote it each time. MCP defines a single plug. Expose your database, file system, or API as an MCP server, and any compliant client speaks to it through the same protocol.

🔌
The M×N → M+N insight

With M AI apps and N tools, bespoke integration needs up to M×N connectors. With MCP, each app implements the client once (M) and each tool implements the server once (N) → M+N. That's the same network-effect win that USB, HTTP, and LSP delivered in their domains.

Why — separation of concerns & security boundary

MCP cleanly splits responsibilities: the host (the AI app) manages the model and the conversation; the server owns access to a specific system (your DB, files, API) and decides exactly what it exposes. The model never touches your database directly — it asks the server, which enforces what's allowed. That boundary is a feature: least-privilege by construction.

How — three primitives, one protocol

PrimitiveWhat it isWho controls invocationExample
ToolAn action the model can call (has side effects or computation)Model-controlled — the LLM decides to call itrun_es_query, create_ticket
ResourceRead-only data the model/app can load into contextApp-controlled — host decides what to attachfile://report.pdf, a DB row
PromptA reusable, parameterized prompt templateUser-controlled — surfaced as a command/summarize-incident

4 · Deep technical explanation

The protocol

MCP rides on JSON-RPC 2.0. After a capability negotiation handshake (initialize), the client can call standard methods: tools/list, tools/call, resources/list, resources/read, prompts/list, prompts/get. The server responds with structured results. Because the schema is standardized, discovery is automatic — the host learns what a server offers at runtime.

Transports

TransportHowUse when
stdioServer is a local subprocess; messages over stdin/stdoutLocal tools, desktop apps, dev — simplest & default
Streamable HTTP / SSEServer is an HTTP endpoint; supports remote + streamingRemote/shared servers, multi-user, cloud deployment

Tool registration

A tool needs a name, a clear description (the model reads this to decide when to call it — Module 08), and a typed input schema. The official Python SDK (FastMCP) derives the schema from type hints and the docstring, so a well-typed function is a tool definition.

Resource & prompt registration

  • Resources are addressed by URI (e.g. es://indices, file:///logs/today.log). The host reads them into context — they're data, not actions, so no side effects.
  • Prompts are named, parameterized templates the server offers (e.g. an "investigate incident" workflow). Clients surface them as slash-commands/menu items for the user to trigger.

Security model

The server is the trust boundary. Best practices: least privilege (expose only needed operations — read-only where possible), input validation on every tool, no secrets in tool descriptions, authn/authz for HTTP transports, and guarding against prompt injection via resource/tool content (untrusted data the model reads can carry instructions). Consequential tools should require host-side human approval (Module 08 §6).

Tradeoffs & limitations

Strengths

  • Write once, use in any MCP client
  • Automatic discovery of capabilities
  • Clean security/permission boundary
  • Decouples tools from agent frameworks

Limits

  • An extra layer (process/network) vs. direct calls
  • Young ecosystem; conventions still settling
  • Auth/remote story is evolving
  • Overkill for a single in-process tool

5 · Interactive: discover & call

Step through how a host discovers a server's capabilities and routes a model's tool call.

DEMO Host ↔ ElasticSearch MCP server
🤝 initialize → negotiate capabilities 📋 tools/list → ["list_indices", "search_index", "get_mapping"] 💭 LLM: "user wants errors in app-logs → call search_index" ⚡ tools/call search_index({index:"app-logs", query:"level:ERROR"}) 👁 server runs ES query → returns 23 hits ✅ "Found 23 errors, mostly timeout in service X."

The host never hard-coded these tools — it discovered them via tools/list. Swap in a different server and the same host gains new capabilities with zero code changes.

6 · Practical Python — build an MCP server

Minimal — a FastMCP server with one tool

server_minimal.py
# pip install "mcp[cli]"   — the official Python SDK
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("demo-server")

@mcp.tool()
def add(a: int, b: int) -> int:
    """Add two integers and return the sum."""   # docstring = tool description
    return a + b

@mcp.tool()
def greet(name: str) -> str:
    """Return a friendly greeting for the given name."""
    return f"Hello, {name}!"

if __name__ == "__main__":
    mcp.run()                # stdio transport by default — type hints become the schema

Intermediate — tools + resources + prompts together

server_full.py
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("knowledge-server")
NOTES = {"runbook": "Restart service X via systemctl..."}

@mcp.tool()                                  # ACTION (model-controlled)
def save_note(key: str, text: str) -> str:
    """Persist a note under a key."""
    NOTES[key] = text
    return f"saved {key}"

@mcp.resource("note://{key}")              # DATA (app-controlled, read-only)
def read_note(key: str) -> str:
    """Read a stored note by key."""
    return NOTES.get(key, "(not found)")

@mcp.prompt()                                # TEMPLATE (user-controlled)
def incident_review(service: str) -> str:
    """Reusable incident-review prompt."""
    return (f"Investigate the latest incident for {service}. "
            "List symptoms, likely cause, and remediation steps.")

if __name__ == "__main__":
    mcp.run()

A client that consumes the server

client.py
import asyncio
from mcp import ClientSession, StdioServerParameters
from mcp.client.stdio import stdio_client

async def main():
    params = StdioServerParameters(command="python", args=["server_full.py"])
    async with stdio_client(params) as (read, write):
        async with ClientSession(read, write) as s:
            await s.initialize()
            tools = await s.list_tools()           # discovery
            print("tools:", [t.name for t in tools.tools])
            res = await s.call_tool("save_note", {"key": "x", "text": "hi"})
            print(res.content)

asyncio.run(main())

Production — a FastAPI-backed MCP server (your existing API → MCP)

fastapi_mcp.py
# You already build FastAPI services. Two clean ways to expose them via MCP:
# (A) Wrap existing service functions as MCP tools (share business logic).
# (B) Mount MCP as an HTTP transport alongside your REST routes.
from fastapi import FastAPI
from mcp.server.fastmcp import FastMCP
import httpx

# --- shared business logic (used by both REST and MCP) ---
async def _lookup_order(order_id: str) -> dict:
    async with httpx.AsyncClient() as c:
        r = await c.get(f"http://orders-svc/orders/{order_id}")
        return r.json()

# --- REST surface (humans / existing clients) ---
api = FastAPI()
@api.get("/orders/{order_id}")
async def get_order(order_id: str):
    return await _lookup_order(order_id)

# --- MCP surface (LLM agents), HTTP transport for remote use ---
mcp = FastMCP("orders-mcp")

@mcp.tool()
async def lookup_order(order_id: str) -> dict:
    """Look up an order's status and items by its ID."""
    return await _lookup_order(order_id)   # same logic, zero duplication

# Serve MCP over Streamable HTTP (e.g. uvicorn) for remote agents.
app = mcp.streamable_http_app()        # mount alongside or separate from `api`
🧩

The senior pattern: keep business logic in plain functions and expose it through both REST (for humans/services) and MCP (for agents). One implementation, two interfaces — no drift. Your FastAPI + Docker skills transfer directly.

7 · Local MCP development & Ollama

MCP servers run locally over stdio — perfect for offline dev. Pair a local Ollama model (with tool calling, Module 08) as the host's brain and your MCP servers as its hands, for a 100% local agentic stack.

dev.sh
# Inspect/debug a server interactively with the MCP Inspector
mcp dev server_full.py        # opens a UI to list/call tools, read resources

# Register a local server with Claude Desktop (stdio)
# ~/.config/Claude/claude_desktop_config.json:
# { "mcpServers": { "knowledge": {
#     "command": "python", "args": ["/abs/path/server_full.py"] } } }
local_host.py
# Minimal "host": local Ollama model + an MCP server's tools.
import asyncio, json, ollama
from mcp import ClientSession, StdioServerParameters
from mcp.client.stdio import stdio_client

async def run(user_msg):
    p = StdioServerParameters(command="python", args=["server_full.py"])
    async with stdio_client(p) as (r, w), ClientSession(r, w) as s:
        await s.initialize()
        listed = (await s.list_tools()).tools
        # translate MCP tool schemas → Ollama tool format
        tools = [{"type": "function", "function": {
            "name": t.name, "description": t.description,
            "parameters": t.inputSchema}} for t in listed]
        out = ollama.chat(model="qwen2.5",
            messages=[{"role": "user", "content": user_msg}], tools=tools)
        for call in out["message"].get("tool_calls", []):
            res = await s.call_tool(call["function"]["name"],
                                     call["function"]["arguments"])
            print(res.content)

asyncio.run(run("Save a note 'deploy' = 'use blue-green'"))

8 · ElasticSearch MCP server (worked example)

This is exactly the kind of server you'll build at work: wrap ElasticSearch so any agent can investigate logs and indices safely. Note the read-only, least-privilege design.

es_mcp_server.py
from mcp.server.fastmcp import FastMCP
from elasticsearch import Elasticsearch

mcp = FastMCP("elasticsearch")
es = Elasticsearch("http://localhost:9200")

ALLOWED = {"app-logs", "audit", "metrics"}    # allow-list = least privilege

def _check(index: str):
    if index not in ALLOWED:
        raise ValueError(f"index '{index}' not permitted")

@mcp.tool()
def list_indices() -> list[str]:
    """List the ElasticSearch indices available for querying."""
    return sorted(ALLOWED)

@mcp.tool()
def get_mapping(index: str) -> dict:
    """Return the field mapping (schema) of an index."""
    _check(index)
    return es.indices.get_mapping(index=index).body

@mcp.tool()
def search_index(index: str, query: str, size: int = 10) -> dict:
    """Run a Lucene query_string search and return the top hits.

    index: one of the allowed indices.
    query: Lucene syntax, e.g. 'level:ERROR AND service:checkout'.
    size:  max hits to return (capped at 50)."""
    _check(index)
    size = min(size, 50)                          # bound result size (cost/latency)
    res = es.search(index=index, size=size,
        query={"query_string": {"query": query}})
    hits = res["hits"]["hits"]
    return {"total": res["hits"]["total"]["value"],
            "hits": [{"id": h["_id"], "source": h["_source"]} for h in hits]}

@mcp.resource("es://indices")
def indices_resource() -> str:
    """The list of queryable indices, as a readable resource."""
    return "\n".join(sorted(ALLOWED))

@mcp.prompt()
def investigate(symptom: str) -> str:
    """Guided log-investigation prompt."""
    return (f"Investigate '{symptom}'. First list_indices, then get_mapping "
            "for the relevant one, then search_index. Summarize root cause.")

if __name__ == "__main__":
    mcp.run()
🛡️

Notice the safety design: an index allow-list, bounded result size, read-only operations only (no delete/update tools), and rich docstrings so the model queries correctly. This server is the heart of the MCP ElasticSearch Server capstone.

9 · Industry perspective

🚀 Startups

Use existing MCP servers (filesystem, GitHub, Postgres, Slack) to give an assistant capabilities in hours, not weeks. Build one custom server for the proprietary system and you're done.

🏢 Enterprises

Wrap internal systems (data warehouse, ticketing, ES) as governed MCP servers behind auth, with audit logging and least-privilege scopes. One server is reused across every internal AI app — the integration layer of an enterprise AI platform.

Why this matters strategically

MCP turns tool integrations into reusable infrastructure. Instead of each team re-wiring ElasticSearch into LangChain, then again into Claude Desktop, then again into a CrewAI agent, you publish one ES MCP server and every team/app consumes it. That's the difference between N teams × M frameworks of glue and a single maintained capability.

Common production challenges: auth for remote/multi-tenant servers, prompt-injection through resource/tool content, versioning tool schemas without breaking clients, observability across the host↔server boundary, and stopping over-broad tools (always prefer narrow, read-only ones).

10 · Top mistakes engineers make

❌ Exposing over-broad tools

A generic "run any SQL/ES query" or "execute shell" tool is a security hole. Expose narrow, validated, read-only operations.

❌ Weak tool descriptions

The model selects and fills tools from descriptions/schemas. Vague docstrings → wrong calls. Treat them as prompts.

❌ No input validation

The model can pass anything. Validate args and bound result sizes server-side — never trust the caller.

❌ Confusing tools and resources

Actions (side effects) = tools; read-only data = resources. Mixing them muddles the security model.

❌ Ignoring prompt injection

Content the model reads (a log line, a doc) can contain instructions. Treat resource/tool output as untrusted.

❌ Duplicating business logic

Don't reimplement logic in the MCP tool. Share plain functions between REST and MCP surfaces.

11 · Middleware, Identity and Agent Interoperability

Everything so far has been about the capability boundary: how an agent reaches a tool. This section is about the policy boundaries that sit around it — who is calling, what they are allowed to do, which system is trusted with what, and how independent agent systems talk to each other. This is where most production and system-design interviews for agentic roles actually land.

11.1 · The complete architecture

A request to an agentic application does not travel through one program. It crosses a series of boundaries, and at each boundary a different kind of policy is applied. Read the flow downwards; the amber markers are the points where trust changes.

🔑
The one idea to remember

Middleware is not one product and not one physical layer. It is a pattern: apply cross-cutting policy at well-defined boundaries, where every request must pass and where the policy can be reasoned about in one place. A gateway, an ASGI middleware class, an agent hook and a tool wrapper are all the same pattern applied at different boundaries.

11.2 · API middleware versus agent middleware

Interviewers ask this because candidates who have only built web services assume middleware means "the thing that checks the JWT", and candidates who have only built agents assume it means "the thing that edits the prompt". Both are middleware; they run at different times and protect different things.

LayerExamplesRuns whenMain responsibility
Gateway middlewareTLS, WAF, coarse rate limitsBefore the applicationEdge protection and routing
HTTP middlewareJWT validation, request IDs, tenant resolutionOn each HTTP requestRequest-level security and context
Agent middlewareTool filtering, prompt enrichment, retriesAround model and tool callsControl agent behaviour
Tool middlewareArgument validation, permission checks, idempotencyBefore or after tool executionSafe and reliable actions
Observability middlewareTraces, metrics, audit logsAcross all stagesExplain and debug behaviour
🗣
The distinction to say out loud

HTTP middleware controls requests entering the application. Agent middleware controls decisions and actions inside the agent loop. Tool middleware protects the systems the agent can affect.

The reason the three cannot be collapsed: one HTTP request can produce many model calls and many tool calls. A per-request check runs once; a per-action check runs every time the agent tries to do something. Budgets, allowlists and approval gates only work at the second granularity.

11.3 · JWT, OAuth 2.0 and identity

Start with the distinction the rest of this depends on. Authentication answers "who is making this call, and can I prove it?" Authorization answers "is this caller allowed to perform this specific operation on this specific resource?" They fail differently: a broken authentication check lets a stranger in; a broken authorization check lets a legitimate user do something they should not.

JWT — a token format

  • A JWT is a compact claims-token format. It is a container for statements about a subject, encoded so it can travel in an HTTP header.
  • A JWT may be signed (JWS — integrity and origin, contents readable by anyone) and can also be encrypted (JWE — contents hidden). Signed is the common case; "the payload is base64, not secret" is worth saying out loud.
  • A JWT is not, by itself, a login system or an authorization policy. It is what a login system hands you and what a policy engine reads. Choosing JWTs decides nothing about how users authenticate or what they may do.
  • Important claims: iss (issuer), aud (audience), sub (subject), exp (expiry), nbf (not-before). Also useful in practice: iat, jti for replay tracking, and kid in the header for key selection.
  • Validation must include the expected issuer, the expected audience, an explicit list of allowed algorithms, the signature, expiry and not-before, and key selection from a trusted source. Every one of these is a real-world breach when omitted.

OAuth 2.0 — delegated authorization

  • OAuth 2.0 is an authorization framework. It describes how a client obtains permission to act on a resource, not how a person proves who they are.
  • An access token represents delegated authority — "the bearer may do these things, on this resource server, for this long". The token format is not specified by OAuth itself; it is often a JWT, sometimes opaque.
  • Scopes are not a replacement for application-level authorization. A scope such as orders:write says the client was granted a category of access. It does not say this user may refund that order in that tenant. The resource server still owes a real authorization decision.
  • Tokens should not be forwarded blindly from the user through every agent and tool. A token minted for your API is not a token your downstream tool should accept, and passing it on hands that tool the user's full authority.
  • Service-to-service identity and delegated user identity are different things and often need different tokens. "The agent is calling as itself" and "the agent is calling on behalf of Priya" are different security statements and should be different credentials.

OpenID Connect — an identity layer

  • OpenID Connect adds an identity layer over OAuth 2.0: a standard way to learn who authenticated and how.
  • An ID token identifies the authenticated user to the client. Its audience is the client application.
  • An ID token should not automatically be treated as an API access token. It was issued for a different audience and a different purpose; a resource server that accepts it is accepting a token that was never scoped for it.

The identity questions an agentic system forces you to answer

A conventional API has one caller per request. An agent has several, layered, and they can differ from one tool call to the next.

  • Which identity is acting — the end user, the application, the agent, or the tool itself?
  • Which tenant owns the request, and is that established from the token rather than from a request body the caller controls?
  • Is the agent acting on behalf of a user, or as its own service identity? Scheduled and background work usually has no user at all.
  • Which scopes and permissions should reach an MCP server — all of the caller's, or the narrow subset this tool needs?
  • Should a remote A2A agent receive the original user token? Almost always no; it is a different trust domain, possibly a different vendor.
  • How is an action recorded for audit and non-repudiation, so that "the agent did it" resolves to a user, a tenant, a prompt and a policy decision?
  • What happens when a long-running task outlives its access token? Agent tasks routinely run longer than a fifteen-minute token lifetime.
⚠️
Do not do these
  • Blind token forwarding — passing the user's access token to every downstream tool, MCP server and remote agent. This is the classic confused-deputy setup.
  • Trusting unsigned or incorrectly validated tokens — including accepting an unsecured algorithm, or letting the token's own header choose the verification algorithm.
  • Accepting any issuer or audience — a valid signature from the wrong issuer, or a token minted for a different service, is not authorization for yours.
  • Reading claims without verifying the signature — decoding a JWT to get sub or tenant "just for logging" is how unverified claims end up in a policy decision.
  • Storing secrets in prompts or agent state — anything in the context window can be summarised, logged, traced, cached, or extracted by prompt injection.
  • Giving every tool the same broad credential — one shared service account defeats least privilege and makes the audit log useless.

11.4 · MCP versus A2A versus middleware

These are asked together because candidates conflate them. They solve different problems and none of them substitutes for another.

ConceptPrimary purposeTypical participantsDoes not solve
MiddlewareEnforce cross-cutting policy and behaviourComponents inside an applicationInteroperability by itself
MCPConnect AI applications to tools and contextMCP host/client and MCP serverGeneral remote-agent collaboration
A2AEnable independent agents to discover and collaborateA2A client and remote agentLocal application middleware
JWTRepresent signed or encrypted claimsToken issuer and consumerComplete authentication or authorization architecture
OAuth / OIDCDelegated authorization and identityClients, authorization servers and resource serversAgent orchestration
🔑
Say this clearly

MCP and A2A are complementary.

MCP usually connects an agentic application to tools, resources and context. A2A connects independent agent systems that may be implemented by different teams or vendors. Middleware enforces the policies around both.

A useful test: if the thing on the other side is a capability you call and get a result from, that is the MCP shape. If it is an autonomous peer that accepts a task, works on it over time and returns messages and artifacts, that is the A2A shape.

💬
Interview currency — how deep to go
  • Understand MCP architecture and security boundaries in practical detail: host, client, server, the three primitives, transports, and who authorizes what. This is expected.
  • Understand A2A concepts, use cases and trade-offs: discovery and capability declaration, task delegation, messages and artifacts, and when a remote peer beats an in-process tool.
  • Do not memorise rapidly changing wire-level fields. Both specifications are moving. An interviewer who wants a field name will accept "I would check the current specification"; one who wants the trust model will not accept a memorised field name instead of it.

Where each concern belongs

PlacementConcerns that belong here
At the gatewayTLS, WAF, coarse per-IP and per-key rate limits, request size caps, routing. Cheap, blunt, before your code runs.
In HTTP middlewareToken validation, principal and tenant resolution, correlation IDs, request schema validation, per-request quota accounting, audit metadata.
In the agent runtimeContext enrichment, model routing, tool allowlists, retries and fallbacks, budgets, guardrails, approval gates, tracing of decisions.

🛡
Defence in depth

The agent layer must not be the only place authorization is enforced. An allowlist in the agent runtime is a usability and cost control — it stops the model from choosing a tool. It is not a security control, because a prompt injection, a bug, a new code path or a second client can route around it. The tool server and the database must independently refuse an action the caller is not entitled to. If removing the agent's allowlist would let a user do something they should not, the design is one bug away from a breach.

11.6 · A request, end to end

A user asks an enterprise support agent to refund an order.

1 · Gateway applies coarse limitsTLS, WAF, per-key rate limit — before any application code
2 · HTTP middleware validates the access tokenissuer, audience, algorithm, signature, expiry, key selection
3 · Tenant and user context are attachedderived from verified claims and pinned to the request
4 · Agent middleware adds policy and allowed-tool contextrefund policy for this tenant, plus only the tools this role may use
5 · The model proposes a refund-tool calla proposal — nothing has happened yet
6 · Tool middleware validates arguments and permissionsschema, order ownership, tenant match, entitlement to refund
7 · An approval gate is triggered above a monetary thresholda human sees the order, the reason and the amount, and decides
8 · An MCP server executes the approved actionwith its own least-privilege credential and an idempotency key
9 · Audit middleware records user, agent, tool and resultimmutable, separate from application logs
10 · A response is returned with a trace IDso the run can be reconstructed later
Figure 3 · The model appears once, at step 5, and only proposes. Every step that grants authority or changes state is enforced by code the model cannot influence.

The A2A variation

Now suppose the refund needs a currency conversion and a ledger adjustment owned by a separate finance platform, run by another team, with its own agent. Steps 1–7 are unchanged. Between steps 7 and 8, the support agent delegates:

  • It discovers the finance agent and reads its declared capabilities — the interviewer wants to hear that you treat that declaration as a claim, not a guarantee.
  • It delegates a task with the minimum necessary information: the order reference, the amount and the reason. Not the user's access token, not the conversation, not the customer's full profile.
  • It authenticates as its own service identity to the finance platform, and carries the acting user as an explicit, verifiable assertion rather than by handing over the user's credential.
  • The finance agent works over time and returns messages and artifacts — a ledger entry reference, a status. The support agent validates those against its own schema before using them.
  • The finance platform runs its own authentication, authorization, budgets and audit. It does not assume the caller validated anything.
  • Both sides record the delegation, so the audit trail crosses the boundary and the refund resolves to a user even though two systems executed it.

Example A — HTTP middleware

Runnable after installing and configuring dependencies. Needs pip install fastapi uvicorn and a real implementation of verify_access_token. Written against Starlette's BaseHTTPMiddleware, which FastAPI re-exports.

http_middleware.py
import uuid
from dataclasses import dataclass

from fastapi import FastAPI, Request
from fastapi.responses import JSONResponse
from starlette.middleware.base import BaseHTTPMiddleware


@dataclass(frozen=True)
class Principal:
    """Who is acting. Every field comes from VERIFIED token claims."""
    subject: str
    tenant_id: str
    scopes: frozenset


class AuthError(Exception):
    pass


def verify_access_token(token: str) -> dict:
    """Verify and return the token claims. Supply this from a maintained
    library (for example PyJWT with a JWKS client) -- never hand-rolled
    crypto. It MUST enforce, and raise AuthError on failure:

      * signature, against a key selected by `kid` from the trusted JWKS
      * `alg` restricted to an explicit allowlist -- never taken from the
        token header, and never "none"
      * `iss` equal to the expected issuer
      * `aud` equal to THIS service's audience
      * `exp` and `nbf` against the current clock, with small leeway

    Returning unverified claims from here defeats every check below.
    """
    raise NotImplementedError("wire this to your identity provider")


class CorrelationIdMiddleware(BaseHTTPMiddleware):
    """One ID per request, echoed back and carried into every downstream call."""

    async def dispatch(self, request: Request, call_next):
        request_id = request.headers.get("x-request-id") or str(uuid.uuid4())
        request.state.request_id = request_id
        response = await call_next(request)
        response.headers["x-request-id"] = request_id
        return response


class AuthenticationMiddleware(BaseHTTPMiddleware):
    """Attach a verified Principal, or reject. Tenant comes from the token."""

    PUBLIC_PATHS = {"/healthz", "/openapi.json"}

    async def dispatch(self, request: Request, call_next):
        if request.url.path in self.PUBLIC_PATHS:
            return await call_next(request)

        header = request.headers.get("authorization", "")
        scheme, _, token = header.partition(" ")
        if scheme.lower() != "bearer" or not token:
            return self._deny(request, "missing bearer token")

        try:
            claims = verify_access_token(token)
        except AuthError:
            # Deliberately vague to the caller; the detail goes to the log.
            return self._deny(request, "invalid token")

        # Tenant is read from verified claims, never from a body or query
        # parameter the caller controls. This one line is the whole
        # multi-tenant isolation story at this layer.
        tenant_id = claims.get("tenant")
        if not tenant_id:
            return self._deny(request, "token carries no tenant")

        request.state.principal = Principal(
            subject=claims["sub"],
            tenant_id=tenant_id,
            scopes=frozenset(claims.get("scope", "").split()),
        )
        return await call_next(request)

    def _deny(self, request: Request, reason: str) -> JSONResponse:
        request_id = getattr(request.state, "request_id", "-")
        # Log `reason` with request_id here. Do NOT return it: token
        # diagnostics tell an attacker which check they still have to pass.
        return JSONResponse(
            status_code=401,
            content={"error": "unauthenticated", "request_id": request_id},
            headers={"www-authenticate": "Bearer"},
        )


app = FastAPI()
# Starlette runs the LAST-added middleware OUTERMOST, so adding
# correlation second means every auth denial already has a request ID.
app.add_middleware(AuthenticationMiddleware)
app.add_middleware(CorrelationIdMiddleware)


@app.get("/whoami")
async def whoami(request: Request) -> dict:
    principal = request.state.principal
    return {
        "subject": principal.subject,
        "tenant": principal.tenant_id,
        "request_id": request.state.request_id,
    }

Example B — agent middleware

Runnable after installing and configuring dependencies. Needs pip install langchain langgraph and a configured model provider. This uses the LangChain agent-middleware API — create_agent with a middleware list, the @wrap_model_call and @wrap_tool_call hooks, and the built-in human-in-the-loop and model-fallback middleware. Middleware APIs in this ecosystem move; check the current documentation linked in the References before relying on exact signatures.

agent_middleware.py
import logging

from langchain.agents import create_agent
from langchain.agents.middleware import (
    HumanInTheLoopMiddleware,
    ModelFallbackMiddleware,
    wrap_model_call,
    wrap_tool_call,
)

log = logging.getLogger("agent")

# Role -> the tools that role may even SEE. This is a usability and cost
# control, not the security boundary: the tool server re-checks (Example C).
TOOLS_BY_ROLE = {
    "support_read_only": {"lookup_order", "search_policy"},
    "support_agent": {"lookup_order", "search_policy", "issue_refund"},
}


@wrap_model_call
def allowlist_tools(request, handler):
    """Show the model only the tools this user's role permits."""
    role = (request.runtime.context or {}).get("role", "support_read_only")
    permitted = TOOLS_BY_ROLE.get(role, set())
    allowed = [t for t in request.tools if t.name in permitted]
    return handler(request.override(tools=allowed))


@wrap_model_call
def log_model_calls(request, handler):
    """Record shape and outcome, not content -- traces are a data store too."""
    log.info("model call: %d message(s), %d tool(s) offered",
             len(request.messages), len(request.tools))
    response = handler(request)
    log.info("model returned %d tool call(s)",
             len(getattr(response.result[0], "tool_calls", []) or []))
    return response


@wrap_tool_call
def retry_transient_tool_errors(request, handler, *, max_attempts: int = 3):
    """Retry ONLY transient failures. A rejected permission is not transient,
    and a write without an idempotency key must never be retried here."""
    for attempt in range(max_attempts):
        try:
            return handler(request)
        except (TimeoutError, ConnectionError):
            if attempt == max_attempts - 1:
                raise
            log.warning("transient tool failure, retrying (%d)", attempt + 1)


agent = create_agent(
    model="anthropic:claude-sonnet-5",
    tools=[],                       # your @tool functions go here
    middleware=[
        log_model_calls,
        allowlist_tools,
        retry_transient_tool_errors,
        # Human approval is a CONDITION on a tool, not a prompt instruction:
        # the run pauses and waits for a decision before the tool executes.
        HumanInTheLoopMiddleware(
            interrupt_on={"issue_refund": {"allowed_decisions": ["approve", "edit", "reject"]}}
        ),
        ModelFallbackMiddleware("anthropic:claude-haiku-4-5-20251001"),
    ],
)

Example C — the tool boundary

Concept excerpt. It is valid Python and shows the complete check order, but OrderStore, AuditLog and IdempotencyStore are illustrative interfaces rather than a library you can install. This is the layer that must hold even if the agent layer is bypassed entirely.

tool_boundary.py
from dataclasses import dataclass
from decimal import Decimal

from pydantic import BaseModel, Field, ValidationError


class RefundInput(BaseModel):
    """The schema is the contract. Anything outside it is rejected before
    any business logic runs -- the model can propose anything at all."""
    order_id: str = Field(min_length=6, max_length=32, pattern=r"^ord_[A-Za-z0-9]+$")
    amount: Decimal = Field(gt=0, le=Decimal("10000.00"))
    reason: str = Field(min_length=3, max_length=400)


@dataclass(frozen=True)
class ToolCallContext:
    tenant_id: str
    subject: str
    permissions: frozenset
    request_id: str
    idempotency_key: str


class ToolDenied(Exception):
    pass


def issue_refund(raw_args: dict, ctx: ToolCallContext, *,
                 orders, idempotency, audit) -> dict:
    """Refund an order. Every guard below runs BEFORE any state changes."""

    # 1. Permission. Checked here as well as in the agent runtime, because
    #    the runtime allowlist is not a security boundary.
    if "orders:refund" not in ctx.permissions:
        raise ToolDenied("caller may not issue refunds")

    # 2. Input schema. Reject malformed proposals with a message the agent
    #    can act on, without leaking internals.
    try:
        args = RefundInput.model_validate(raw_args)
    except ValidationError as err:
        raise ToolDenied(f"invalid arguments: {err.error_count()} problem(s)")

    # 3. Tenant. The order is loaded WITH the tenant, so a valid order id
    #    belonging to another customer simply does not resolve.
    order = orders.get(tenant_id=ctx.tenant_id, order_id=args.order_id)
    if order is None:
        raise ToolDenied("order not found for this tenant")
    if args.amount > order.refundable_amount:
        raise ToolDenied("amount exceeds the refundable balance")

    # 4. Idempotency. A retry -- by the agent, the framework or a human --
    #    returns the FIRST result instead of paying twice.
    cached = idempotency.lookup(ctx.tenant_id, ctx.idempotency_key)
    if cached is not None:
        return cached

    result = orders.refund(
        tenant_id=ctx.tenant_id,
        order_id=args.order_id,
        amount=args.amount,
        idempotency_key=ctx.idempotency_key,
    )
    idempotency.store(ctx.tenant_id, ctx.idempotency_key, result)

    # 5. Audit metadata. Immutable, and enough to answer "who caused this?"
    #    long after the conversation has been deleted.
    audit.record(
        action="issue_refund",
        tenant_id=ctx.tenant_id,
        subject=ctx.subject,
        request_id=ctx.request_id,
        idempotency_key=ctx.idempotency_key,
        outcome=result["status"],
        # The reason is free text proposed by a model. Store it as evidence,
        # never as an authorization input.
        stated_reason=args.reason,
    )
    return result

12 · Interview preparation

Beginner  What is MCP and what problem does it solve? ›

An open standard for how applications expose context and capabilities (tools, resources, prompts) to LLMs over a common JSON-RPC protocol. It replaces bespoke, per-app-per-tool integrations (M×N) with write-once servers any compliant client can use (M+N) — the "USB-C of AI tooling."

Beginner  Name MCP's three primitives. ›

Tools — actions the model can invoke (model-controlled). Resources — read-only data loaded into context (app-controlled). Prompts — reusable parameterized templates surfaced to the user (user-controlled).

Intermediate  Walk through host, client, and server roles. ›

The host is the AI app (Claude Desktop, IDE, your agent) — it runs the LLM and conversation. It spawns one client per server. Each server wraps a specific system (DB, files, ES) and exposes tools/resources/prompts. Flow: client initializes (capability negotiation) → lists tools → LLM picks one → client calls tools/call → server executes against the real system → result returns. The server is the security boundary.

Intermediate  Tool vs resource — when to use which? ›

Use a tool for actions/computation that the model decides to invoke (side effects: write a record, run a query). Use a resource for read-only data the host attaches to context (a file, a config, a row), addressed by URI with no side effects. The split keeps "what the model can do" separate from "what it can read," which clarifies permissions.

Senior  How do you secure an MCP server exposing ElasticSearch? ›

Least privilege: read-only tools only (no delete/update), an index allow-list, and bounded result sizes. Validate every argument server-side; never expose a raw "run any query" tool — offer constrained operations (search, get_mapping). For HTTP transport, add authn/authz and per-caller scopes. Treat returned log content as untrusted (prompt-injection defense). Log all calls for audit. Require host-side human approval for any consequential action. Keep secrets out of descriptions and out of the model's view.

Senior  Why prefer MCP over hard-coding tools in your agent framework? ›

Decoupling and reuse. Hard-coded tools are tied to one framework and app; an MCP server is consumed by any compliant client (Claude Desktop, IDEs, LangGraph, CrewAI), so one team maintains a capability once and every app benefits. It also enforces a clean security boundary and enables runtime discovery. The cost is an extra layer — justified when a tool is shared across apps; overkill for a single in-process helper.

Staff · design  Design an enterprise MCP gateway exposing 30 internal systems to AI apps. ›

A governed catalog of MCP servers, one per system, behind a central gateway providing: auth (SSO/OAuth, per-app and per-user identity propagated to servers), authorization (least-privilege scopes; the model only sees tools the caller may use), safety (input validation, output redaction/PII, prompt-injection defenses on returned content, human-in-the-loop for consequential tools), observability (trace every host↔server call, per-tool cost/latency, full audit log), schema governance (versioned tool schemas, deprecation policy, contract tests so client upgrades don't break), and reliability (rate limits, timeouts, circuit breakers per backend). Share business logic with existing REST services to avoid drift. The deliverable is reusable, auditable capability infrastructure — the integration spine of the Enterprise GenAI Platform (Module 15).

13 · Knowledge check

1 · What is the core value proposition of MCP?
MCP standardizes the agent–tool boundary. Write a server once and any compliant client can use it, collapsing bespoke per-app-per-tool integrations into a reusable layer.
2 · Which primitive should expose "delete a record"?
Actions with side effects are tools (model-controlled). Resources are read-only data. A destructive tool should additionally require host-side human approval.
3 · How does an MCP client know what a server offers?
After capability negotiation, the client calls standardized list methods to discover tools/resources/prompts at runtime — no hard-coding, so swapping servers needs no client changes.
4 · Best practice for an ElasticSearch MCP tool?
Least privilege: constrained read-only operations, an allow-list of indices, validated args, and capped result sizes. A generic "run anything" tool is a security and cost hazard.

In one breath

Client and server, in MCP terms

Deliberately borrowed words, worth pinning down because the roles feel backwards at first.

The server is the small program you write that owns some capability — your database, your files, your internal API — and offers it in a standard shape. It contains no model.

The client is the application that has the model in it: a desktop assistant, an IDE, or your own agent. It connects to servers, discovers what they offer, and calls them on the model behalf.

"Server" here does not imply a machine in a data centre. Most MCP servers are a script running on your own laptop, talking over its input and output streams.
