Model Context Protocol

MCP is a protocol for describing tools and calling them across a process boundary. Module 08's tools were Python functions in your own file. MCP moves them behind a server with a discovery step, which buys reuse and costs you a trust boundary you now have to defend.

⏱ Study + practice · 8–12 h Difficulty · Advanced Prereq · Module 08

1 · What you already know

From module 08: a tool is a Python function, a JSON schema describing it, and a registry mapping the name back to the function. Your dispatch layer checks that the tool exists, that the arguments validate, and that the caller is allowed to run it.

All three lived in one process, in code you wrote. This page is what changes when the tool lives somewhere else and you did not write it.

2 · What breaks now

Four teams each build an agent. Each needs to read from the ticketing system.

Three implementations of one integration, three schemas, three sets of credentials, three places to fix a bug. Add a fourth agent and the integration is written again.

Then the other direction: your agent needs Slack, GitHub, Postgres and a file system. That is four integrations you write and maintain, each with its own auth and its own schema style.

Without a protocolCost
N agents × M systemsN × M integrations to write
Every team invents its own schema shapeNothing is reusable across teams
Tool changes ship inside the agentUpdating a tool means redeploying every agent
Credentials live in each agentEvery agent is a place a secret can leak

MCP turns N × M into N + M by putting one agreed interface between the two sides. That is the entire value proposition, and it is a familiar one - it is what a protocol always buys.

3 · Simple breakdown - MCP vs a hand-written tool layer

A MCP

Basic level

What it is. MCP is an open protocol, built on JSON-RPC, in which a host application connects a client to one or more servers that expose tools, resources and prompts through a fixed set of discovery and invocation methods.

Core purpose. It lets any compliant agent use any compliant tool server without either side being written for the other.

Execution model.

Intermediate level

Architecture under the hood. Three roles. The host is your application and owns the model and the policy. A client is created per server and speaks JSON-RPC 2.0 over a transport - stdio for a local subprocess, streamable HTTP for a remote one. A server exposes three primitive kinds: tools (model-invoked actions), resources (application-read data addressed by URI), and prompts (user-selected templates). Connections open with an initialize handshake that negotiates protocol version and capabilities.

State handling. The connection is stateful - the handshake, the negotiated capabilities and the discovered tool list persist for its life. Any data state belongs to the server. The host keeps the message list, exactly as in module 08. Servers may notify clients that their tool list changed, so discovery is not necessarily a one-off.

Limitations and advanced features. Every call crosses a process boundary, so latency is higher than a local function. The tool descriptions come from the server and go into your prompt, which is a text injection path you do not control. A server you did not write runs with whatever permissions you gave it. Advanced features are sampling (a server asking the host to run a model call), roots (the host telling a server which paths it may touch), and elicitation.

B A hand-written tool layer

Basic level

What it is. A hand-written tool layer is the module 08 arrangement - functions in your own codebase, schemas you author, and a registry you dispatch through.

Core purpose. It gives the model capabilities with no protocol, no extra process and no third-party code in the path.

Execution model.

Intermediate level

Architecture under the hood. A dictionary, a Pydantic model per tool, and a dispatch function. No serialisation, no transport, no handshake. The call is a Python function call.

State handling. Whatever your process holds. There is no connection to keep alive and nothing to reconnect.

Limitations and advanced features. Nothing is reusable outside this codebase. Every agent that needs the same integration writes it again, and a change to a tool means redeploying every agent that embeds it. Credentials sit in each agent process.

The core differences

MCPHand-written layer
Workflow design Discover tools at run time from a server, convert to schemas, call over a transport. The tool list can change without redeploying the agent. Tools are known at compile time and shipped inside the agent. Changing one means changing the agent.
Error recovery Two failure classes: protocol and transport failures (server dead, handshake mismatch, timeout) and tool errors returned as content. Retries must be safe across a boundary you do not control. One failure class: a Python exception you catch. Everything is in one stack trace.
Architectural paradigm A client–server protocol with run-time capability discovery. Direct in-process function dispatch.

In short - which one to choose

Use MCP when:

  • The same integration is needed by more than one agent or team.
  • You want to use existing servers for GitHub, Postgres, Slack or a file system rather than writing them.
  • Tools should be updatable without redeploying every agent that uses them.
  • You want tool credentials in one server rather than in every agent.

Keep tools in-process when:

  • One agent uses them and nothing else will.
  • The tool is a few lines of your own code.
  • Latency is tight enough that a boundary crossing per call matters.

Do not adopt MCP when:

  • You have one agent and three tools. It is a protocol for a problem you do not have.
  • You would be installing third-party servers you have not read, with credentials attached - see section 9.

4 · Without the technology

The module 08 tool layer, which is the thing MCP replaces.

Correct, simple, and entirely private to this file. The schema is hand-maintained alongside the function, and drift between them is a real bug - a parameter renamed in the function but not the schema fails at call time with a confusing message.

MCP replaces the hand-written schema with one the server generates from the function signature, and replaces the registry with a discovery call. The dispatch layer, and every check in it, stays exactly where it was.

5 · Runtime mechanics

One MCP-backed agent turn, in nine steps.

  1. The host starts the server - a subprocess for stdio, or an HTTP connection for remote.
  2. The client sends initialize, naming its protocol version and capabilities; the server replies with its own.
  3. The client sends tools/list. The server returns each tool's name, description and JSON Schema.
  4. The host converts those into the format its model expects and puts them in the request.
  5. The model returns a tool request, as in module 08.
  6. The host validates it - this step is yours, and MCP does not do it for you.
  7. The client sends tools/call with the name and arguments.
  8. The server executes against the real system and returns content blocks, or an error flag.
  9. The host appends the result and the loop continues.

Steps 3 and 4 are the new ones. Everything the server sent in step 3 - including the descriptions - is now text inside your prompt, which is the root of section 9.

6 · The components, one at a time

The three roles

1 · Host

Your application. It owns the model, the conversation, the policy and the decision to honour a tool call. MCP does not move any of that responsibility to the server.

2 · Client

One per server, created by the host. It manages the connection, the handshake and the JSON-RPC message exchange. Four servers means four clients.

3 · Server

Exposes capabilities. It may be a local subprocess you wrote, or a remote service someone else runs.

The three primitives

4 · Tools

Actions the model chooses to invoke. This is the primitive that matters most, and the one that carries risk.

5 · Resources

Data the application reads, addressed by URI. Not model-invoked - the host decides what to fetch, which is why resources carry less risk than tools.

6 · Prompts

Templates the user selects - the slash-command style menu in a host application.

Who invokes each primitive is the whole design. Model, application, user - three different trust levels, and MCP names them deliberately.

Connection

7 · Transports

TransportShapeUse it when
stdioLocal subprocess, pipesLocal tools, desktop hosts, development
Streamable HTTPRemote serviceShared servers, multi-user, anything across a network

stdio has no network exposure but runs the server with your user's permissions. HTTP is authenticated and auditable but must be secured like any other service.

8 · The handshake

initialize exchanges protocol version and capabilities. Version mismatch fails here rather than mid-run, which is the right place for it.

9 · Discovery

tools/list is the run-time equivalent of module 08's hard-coded TOOLS array. A server can notify the client that the list changed, so the available tools are not fixed at start-up.

10 · Invocation

tools/call returns content blocks plus an isError flag. A tool error is returned as content so the model can react - the same design as module 08, section 7.

Control

11 · Roots

The host tells the server which filesystem paths or URIs it may operate within. It is a declared boundary, and worth understanding as such: a cooperative server honours it, and a malicious one is not stopped by it.

12 · Sampling

A server asks the host to run a model call on its behalf. The host stays in control of which model, what it costs and whether to allow it at all - but note the direction of the request, because it is the reverse of everything else here.

13 · Approval

The host decides whether a tool call proceeds. This is module 08's dispatch layer, unchanged and still mandatory. MCP standardises how the tool is described and reached; it does not decide whether calling it is a good idea.

7 · State and data flow

1 · What data is state?Per connection: the handshake result, negotiated capabilities and discovered tool list. Per run: the message list, in the host.
2 · Who writes each field?The handshake writes capabilities; discovery writes the tool list; the host appends messages.
3 · Who reads it?The host reads the tool list to build every model request.
4 · Replaced, appended or merged?The tool list is replaced on a change notification. Messages are appended.
5 · What controls merging?Nothing automatic. Two servers exposing the same tool name is your collision to resolve.
6 · Only in memory?Yes on both sides, unless the server persists its own data.
7 · Checkpointed?No. A dropped connection loses the session and requires a fresh handshake.
8 · In a database?Only inside whatever the server talks to.
9 · How long does it survive?The life of the connection.
10 · What key retrieves it again?Nothing - reconnecting starts over from initialize.

Row 5 is a real operational problem. Connect a GitHub server and a GitLab server and both may expose create_issue; the model sees two identical names and picks arbitrarily. Namespace them on the host side.

9 · Break it

Install a third-party server and connect it. Its tool descriptions arrive in step 3 and go straight into your prompt.

The model reads that as an instruction, because it is text in the prompt and the model cannot tell where in the prompt it came from. If a filesystem server is also connected, the call is well-formed and the arguments are valid.

Every check from module 08 passes. The tool exists, the schema validates, the types are right. The attack is in the description, which is data you accepted from a third party and inserted into your own instructions.

Two related failures worth naming. A server can change its descriptions after you approved it - rug-pull - because discovery happens at run time. And two servers can expose the same tool name, so the model picks one arbitrarily and you cannot tell which from the transcript.

10 · Fix it

1 · Allowlist the tools you will expose, by namespaced name. A server advertising a new tool then gets ignored rather than adopted.

2 · Pin what you approved, so a changed description is a failure and not a surprise.

3 · Namespace every tool so collisions are impossible and the transcript says which server ran.

4 · Keep the write gate. It is the layer that survives when a description defeats the other three, exactly as in module 08.

5 · Give each server only what it needs. A notes server does not need filesystem access; run it with credentials scoped to notes. The strongest control here is not in the protocol - it is that the file tool was never available to be called.

Middleware, Identity and Agent Interoperability

Last reviewed: August 2026

Everything above this point treats the agent as one process calling tools. Production puts a layer around it. That layer answers three questions the protocol does not: where policy is enforced, who is acting, and how two independent agent systems talk.

API middleware and agent middleware

API middleware runs per request. It authenticates the caller, checks a scope, logs the call and returns. The unit of work is one request, and the decision is stateless.

Agent middleware runs per run, and a run is many model calls and many tool calls. That changes what it has to do:

API middlewareAgent middleware
UnitOne requestOne run, N tool calls
Decides onCaller and routeCaller, tool, arguments, and the run so far
BudgetRate limitTokens, cost and step count
Untrusted inputRequest bodyRequest body and every tool result
TerminationResponse sentMust cap steps, or the loop does not end

The budget row is the one people miss. A rate limit on requests does not bound an agent, because one request can spend 40 model calls.

Authentication and authorization

Authentication establishes who is calling. Authorization decides what that caller may do. They fail differently, and conflating them is the most common design error here.

  • JWT - a signed, self-describing token. It carries claims and it is verifiable without a database lookup.
  • OAuth 2.0 - a delegation protocol. It obtains a scoped access token for a resource, on behalf of a user.
  • OpenID Connect - an identity layer on top of OAuth 2.0. It adds an ID token saying who the user is.

A JWT alone is not an authentication system. It is one message in one. It does not issue, rotate, revoke or scope itself, and a token that cannot be revoked is a valid token until it expires.

Validating one, in full - skipping any line makes the check decorative.

Six checks: signature, algorithm, issuer, audience, expiry, subject. Pinning the algorithm is not optional - accepting the token's own alg lets a caller present alg: none, or hand you an HMAC token signed with your public key.

The confused deputy

Your agent holds credentials broader than any single user's. A user asks it to read a file; the agent reads it with its permissions, not theirs. The agent has become a deputy that is confused about whose authority it is using.

Two rules prevent it:

  1. Propagate identity, never replace it. Exchange the user's token for a downstream token scoped to that user, and let the backend enforce access.
  2. Never forward a token to a party it was not issued for. The audience claim exists for this. An MCP server that receives your platform token can replay it against anything that accepts it.

MCP and A2A

They solve adjacent problems and are not alternatives:

MCPA2A
ConnectsAn agent to a toolAn agent to another agent
The other end isA capability you invokeA peer that plans and may refuse
Discoverytools/listAgent card
ResultA return valueA negotiated task, possibly long-running
TrustYou trust the server's textBoth sides authenticate; neither is in charge

The distinction is whether the far side has its own goals. A tool does not. Another agent does, which is why A2A needs task state and mutual authentication where MCP needs neither.

Multi-tenant isolation

One platform, many customers, and no cross-tenant leak. State the tenant at every layer rather than assuming it:

  • Credentials - per tenant, never one shared service account.
  • Vector store - a namespace or collection per tenant, and the tenant filter applied in the query, not after it.
  • Checkpointer - the tenant id is part of the thread key, so a resumed run cannot attach to another tenant's state.
  • Cache - tenant in the cache key. A shared prompt cache is a cross-tenant read.
  • Budget - metered per tenant, so one tenant cannot spend another's capacity.

Observability without leaking

You need traces to debug a run, and traces are exactly where sensitive data collects. Log the shape of a call and the identifiers, not the payload: tool name, argument keys, result size, latency, token count, decision, and the run's correlation id. Redact at the point of capture rather than in the viewer - a redaction applied downstream still means the raw value was written somewhere.

🔑
The one idea to remember

The protocol authenticates the connection; it never authorizes the action. Identity, scope, tenancy and budget are yours to enforce, on every tool call, for the whole run.

13 · Interview preparation

Beginner  What is MCP and what problem does it solve? ›

An open standard for how applications expose context and capabilities (tools, resources, prompts) to LLMs over a common JSON-RPC protocol. It replaces bespoke, per-app-per-tool integrations (M×N) with write-once servers any compliant client can use (M+N) - the "USB-C of AI tooling."

Beginner  Name MCP's three primitives. ›

Tools - actions the model can invoke (model-controlled). Resources - read-only data loaded into context (app-controlled). Prompts - reusable parameterized templates surfaced to the user (user-controlled).

Intermediate  Walk through host, client, and server roles. ›

The host is the AI app (Claude Desktop, IDE, your agent) - it runs the LLM and conversation. It spawns one client per server. Each server wraps a specific system (DB, files, ES) and exposes tools/resources/prompts. Flow: client initializes (capability negotiation) → lists tools → LLM picks one → client calls tools/call → server executes against the real system → result returns. The server is the security boundary.

Intermediate  Tool vs resource - when to use which? ›

Use a tool for actions/computation that the model decides to invoke (side effects: write a record, run a query). Use a resource for read-only data the host attaches to context (a file, a config, a row), addressed by URI with no side effects. The split keeps "what the model can do" separate from "what it can read," which clarifies permissions.

Senior  How do you secure an MCP server exposing ElasticSearch? ›

Least privilege: read-only tools only (no delete/update), an index allow-list, and bounded result sizes. Validate every argument server-side; never expose a raw "run any query" tool - offer constrained operations (search, get_mapping). For HTTP transport, add authn/authz and per-caller scopes. Treat returned log content as untrusted (prompt-injection defense). Log all calls for audit. Require host-side human approval for any consequential action. Keep secrets out of descriptions and out of the model's view.

Senior  Why prefer MCP over hard-coding tools in your agent framework? ›

Decoupling and reuse. Hard-coded tools are tied to one framework and app; an MCP server is consumed by any compliant client (Claude Desktop, IDEs, LangGraph, CrewAI), so one team maintains a capability once and every app benefits. It also enforces a clean security boundary and enables runtime discovery. The cost is an extra layer - justified when a tool is shared across apps; overkill for a single in-process helper.

Staff · design  Design an enterprise MCP gateway exposing 30 internal systems to AI apps. ›

A governed catalog of MCP servers, one per system, behind a central gateway providing: auth (SSO/OAuth, per-app and per-user identity propagated to servers), authorization (least-privilege scopes; the model only sees tools the caller may use), safety (input validation, output redaction/PII, prompt-injection defenses on returned content, human-in-the-loop for consequential tools), observability (trace every host↔server call, per-tool cost/latency, full audit log), schema governance (versioned tool schemas, deprecation policy, contract tests so client upgrades don't break), and reliability (rate limits, timeouts, circuit breakers per backend). Share business logic with existing REST services to avoid drift. The deliverable is reusable, auditable capability infrastructure - the integration spine of the Enterprise GenAI Platform (Module 15).

14 · In short, and what comes next

Remember these six:

  • Three roles: host, client, server. Three primitives: tools, resources, prompts.
  • Who invokes each primitive - model, application, user - is the trust design.
  • MCP turns N × M integrations into N + M. That is the only reason to adopt it.
  • Tool descriptions come from the server and land in your prompt. Treat them as untrusted input.
  • Allowlist, namespace and fingerprint the tools you accept.
  • The host still owns validation and approval. The protocol moves none of that.
🔑
The one idea to remember

MCP standardises how a tool is described and reached, not whether calling it is safe. Every check from module 08 still applies, and one new one appears: the tool's own description is now text you did not write, sitting inside your prompt.
