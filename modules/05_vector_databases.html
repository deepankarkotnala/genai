Module 05 · Retrieval track

Vector databases

Module 04 ended with a NumPy scan over every vector. That is correct, and it stops being fast at about a million rows. A vector database replaces the scan with an index that checks a few thousand candidates instead of all of them - and accepts being occasionally wrong in exchange.

⏱ Study + practice · 9–14 h Difficulty · Intermediate Prereq · Module 04

1 · What you already know

From module 04: chunks become normalised vectors, and a query vector is compared against all of them with one matrix multiply. You measured it - about 8 ms for ten thousand vectors.

You also know that something is always nearest, so a score floor is compulsory.

This page is about what happens to that matrix multiply when there are ten million vectors instead of ten thousand.

2 · What breaks now

The scan is linear in the number of vectors, so the cost scales exactly with the corpus:

VectorsMemory (768 dims, fp32)One scanAt 50 queries/sec
10,00030 MB8 msFine
1,000,0003 GB~800 msAlready impossible
10,000,00030 GB~8 sNot on one machine

And three requirements arrive at the same time as the scale:

  • Filter first. "Only documents this user's team can see" must restrict the search, not the results.
  • Update in place. A document changes; its old vectors must go without rebuilding everything.
  • Survive a restart. A 30 GB in-memory array rebuilt on every deploy is not a system.

All four problems are solved by the same thing: an index that does not look at every vector, inside a database that persists and filters.

3 · Simple breakdown - vector database vs relational database

A Vector database

Basic level

What it is. A vector database stores high-dimensional vectors with their metadata and returns the approximate nearest neighbours of a query vector, using an index such as HNSW or IVF.

Core purpose. It makes similarity search stay fast as the collection grows, by checking a small fraction of the vectors instead of all of them.

Execution model.

Intermediate level

Architecture under the hood. The default index is HNSW, a layered graph. The top layer holds few nodes with long links; each layer below is denser. A search enters at the top, greedily walks toward the query, drops a layer and repeats, so it reaches the neighbourhood in a few hops instead of a full scan. Two parameters govern it: M, links per node, fixed at build time; and ef_search, how many candidates to keep during the walk, tunable per query. IVF is the alternative - cluster the vectors, search only the nearest clusters.

State handling. Vectors, metadata and the graph are persisted to disk and memory-mapped on start-up. Inserts update the graph incrementally. Deletes are usually soft - the node is marked as removed but stays in the graph until a compaction pass, so deleted vectors still cost memory and search time.

Limitations and advanced features. Results are approximate: the walk can miss a true neighbour, and how often is your recall. Building an HNSW index is slow and memory-hungry. Heavy filtering interacts badly with the graph, because a walk can dead-end in a region where nothing passes the filter. Advanced features are scalar and binary quantisation, hybrid search with BM25, multi-tenancy by partition, and replication.

B Relational database

Basic level

What it is. A relational database stores rows in typed tables and answers queries with exact predicates, using B-tree and hash indexes to avoid scanning every row.

Core purpose. It returns exactly the rows that match a condition, with transactional guarantees about what is stored.

Execution model.

Intermediate level

Architecture under the hood. A B-tree keeps keys sorted, so a lookup descends a shallow tree and a range scan walks the leaves. This works because one dimension has a total order. In 768 dimensions there is no such order - the tree degenerates and a B-tree over vectors is no better than a scan. That single fact is why a different index exists.

State handling. Rows persist with ACID guarantees. A committed write is durable and visible to the next reader, and a transaction either applies completely or not at all.

Limitations and advanced features. No native notion of "similar" for high-dimensional data. pgvector closes most of the gap by adding vector columns and HNSW or IVFFlat indexes to Postgres, which lets one database hold rows, metadata and vectors together - usually the right first choice.

The core differences

Vector databaseRelational database
Workflow design Ask for the k nearest vectors and get a ranked, approximate list. Tuning trades recall against latency. Ask for rows matching a predicate and get all of them, exactly. There is nothing to trade.
Error recovery A missed neighbour raises nothing - it is silently absent from the results. Only measuring recall against exact search reveals it. A wrong result is a bug in the query, and the same query always returns the same rows, so it is reproducible.
Architectural paradigm Approximate nearest-neighbour search over a graph or clustering. Exact set retrieval over an ordered index.

In short - which one to choose

Use a dedicated vector database when:

  • You are past roughly ten million vectors, or need very high query throughput.
  • Vector search is the product and you need its tuning knobs exposed.
  • You need built-in hybrid search and reranking.

Use pgvector in your existing Postgres when:

  • You are below a few million vectors, which is most systems.
  • The vectors belong next to rows you already store, and you want one backup story.
  • You would rather not operate another database. This is the right default.

Use neither when:

  • You have fewer than 50,000 vectors. NumPy in memory is exact, faster to reason about, and has no recall to worry about.
  • You have not yet measured whether retrieval is your bottleneck.

4 · Without the technology

The module 04 search, with the two things a database adds bolted on by hand.

This is correct - it is exact search with a filter. It also, at ten million vectors, allocates a copy of the allowed subset and scans it, so a query is seconds and memory doubles.

Add persistence, incremental updates and concurrent access and you have written a database. The interesting part is not the storage; it is that the scan itself has to go.

5 · Runtime mechanics

How an HNSW search avoids the scan. Seven steps.

  1. At build time each vector becomes a node, linked to roughly M near neighbours.
  2. Nodes are assigned to layers at random with exponentially decreasing probability, so the top layer holds a handful of nodes and the bottom holds all of them.
  3. A search starts at a fixed entry point in the top layer.
  4. It moves greedily to whichever neighbour is closer to the query, until no neighbour improves.
  5. It drops to the next layer down and repeats from that node.
  6. At the bottom layer it keeps a candidate list of size ef_search, exploring neighbours until the list stops improving.
  7. The best k candidates are scored exactly and returned.

The walk touches on the order of ef_search × M nodes - a few thousand - whatever the collection size. That is the whole trick, and step 4 is where it can go wrong: a greedy walk can settle in the wrong region and never find the true nearest neighbour.

6 · The components, one at a time

Storing

1 · Collection

A named set of vectors that all share one dimension and one distance metric. Both are fixed at creation - changing either means a new collection.

2 · Point

One id, one vector, one payload. The payload is where the text and the metadata live - without it a search returns ids you cannot use.

3 · Distance metric

Cosine for normalised text embeddings; dot product is equivalent and faster on normalised vectors; Euclidean is rarely right for text. It must match what the embedding model was trained for.

4 · Upsert and delete

Upsert by id replaces. Deleting by a payload filter is how you remove a whole document's chunks.

Searching

5 · HNSW parameters

ParameterWhen it appliesRaising it
mBuildBetter recall, more memory, slower build

6 · Recall

The fraction of true nearest neighbours the approximate search actually returned. It is the number this whole page trades against latency, and nothing reports it unless you measure it.

7 · Metadata filter

Restricts which points are eligible during the search. This is the authorisation boundary - filtering after retrieval means you already searched data the user may not see.

8 · Payload index

Without one, a filter is evaluated by checking points as the walk visits them, which is slow and makes dead-ends likely. Index every field you filter on.

9 · Quantisation

Store vectors as int8 or binary, search on those, then rescore the shortlist with the full-precision vectors. Four to thirty-two times less memory for a small recall cost.

10 · Hybrid search

Most vector databases now store a sparse vector alongside the dense one and fuse the two result lists by rank - the reciprocal rank fusion from module 04, run inside the database.

11 · IVF, the alternative index

Cluster the vectors into nlist groups, then search only the nprobe nearest clusters. Faster to build and smaller than HNSW, generally lower recall at the same speed. It is what pgvector's ivfflat uses.

7 · State and data flow

1 · What data is state?Vectors, payloads, and the HNSW graph linking them.
2 · Who writes each field?Upserts write vectors and payloads and update the graph incrementally.
3 · Who reads it?Every query reads the graph; only the returned points' payloads are read.
4 · Replaced, appended or merged?Replaced by id. No id means a duplicate, not an update.
5 · What controls merging?The point id. Deriving it from a document id and chunk index makes re-ingestion idempotent.
6 · Only in memory?No - persisted and memory-mapped, though the graph is usually resident.
7 · Checkpointed?Snapshots, and a write-ahead log for durability between them.
8 · In a database?This is the database.
9 · How long does it survive?Until deleted - and a delete is soft, so it still costs memory until compaction.
10 · What key retrieves it again?Collection name plus point id.

Recall improves quickly and then barely at all, while latency keeps climbing. ef_search is the one knob to tune, and the curve flattens far earlier than people expect.

9 · Break it

Filter hard on a field with no payload index.

The graph walk moves toward the query, then discards almost every node it reaches because the filter rejects it. It runs out of candidates before finding the twelve that qualify. The results are wrong and nothing says so - this is the failure mode people misdiagnose as "the embeddings are bad".

The second failure is quieter still. Ingest the same document twice with generated ids.

Now every chunk exists twice. Retrieval returns four results that are two documents repeated, the model sees the same passage twice, and the collection has doubled in size. Nothing raises.

10 · Fix it

Index every filtered field, and let the database switch strategy when a filter is very selective.

With the index present, Qdrant estimates how many points pass the filter and falls back to an exact scan of that subset when it is small - which is both correct and fast, because the subset is tiny.

Then measure recall rather than assuming it. Exact search is the ground truth.

And make ids deterministic so re-ingestion cannot duplicate - derive each id from the document id and chunk number. Together these three turn every silent failure on this page into either a measured number or an impossible state.

13 · Interview preparation

Beginner  What is a vector database for? ›

To store embeddings and answer "which stored vectors are nearest to this query vector?" at scale and low latency, using approximate nearest-neighbor indexes - plus metadata filtering. It's the storage + retrieval engine of RAG.

Beginner  What does "approximate" mean in ANN? ›

The index may not return the exact true nearest neighbors every time - it returns very-close ones much faster than brute force. The miss rate (1 − recall) is small and tunable; you trade a little accuracy for big speed gains.

Intermediate  Explain HNSW and its key parameters. ›

A hierarchical navigable small-world graph: multiple layers, sparse on top for long hops, dense at the bottom holding all vectors. Search starts at the top and greedily descends toward the query - roughly O(log N). Params: M (edges/node → recall & memory), ef_construction (build-time quality), and ef_search (query-time candidates → the live recall/latency dial).

Intermediate  Pre-filtering vs post-filtering - when does it matter? ›

Post-filtering runs ANN then discards non-matches - fine for permissive filters, but selective filters can leave you with too few or zero results because the top-k were all filtered out. Pre-filtering restricts the search space to matching vectors first, giving correct top-k for selective filters. Use pre-filtering for tenant/permission/date constraints.

Senior  Recall is fine in tests but bad in prod. Diagnose. ›

Suspects: (1) production data distribution differs from test; (2) ef_search lowered for latency; (3) selective metadata filters + post-filtering starving results; (4) index not rebuilt after a bulk load, or stale after deletes; (5) embedding model/version drift between index and query (Module 04). Reproduce with a flat-index ground truth on prod queries, compare recall@k, and isolate the variable. Fix the specific cause - often raise ef_search or switch to pre-filtering.

Staff · design  Design vector search for 1B vectors, multi-tenant, <50ms p99. ›

1B × 768 floats won't fit one node in RAM as raw HNSW - use IVF+PQ or quantized HNSW to compress, and shard by tenant or hash with replicas for HA. Pre-filter by tenant (route to the tenant's shard for isolation + smaller search space). Tune ef_search per route to hit p99 under the recall SLO; add a small re-rank stage (Module 06) on the top candidates to recover precision lost to quantization. Operate: background re-index jobs for model upgrades (versioned vectors), warm caches, monitor recall@k continuously with a sampled ground-truth job, and capacity-plan RAM. Consider a tiered design: quantized index for breadth, exact rescoring on finalists.

14 · In short, and what comes next

Remember these five:

  • An approximate index checks a few thousand candidates whatever the collection size.
  • ef_search is the query-time knob. Recall flattens early; latency does not.
  • Recall is invisible unless you measure it against exact search.
  • Filter fields must be payload-indexed, or a selective filter silently returns too few.
  • Point ids must be derived, not random, or re-ingestion duplicates everything.
🔑
The one idea to remember

A vector database trades exactness for speed, and the trade is invisible by default. Everything operational on this page - recall measurement, payload indexes, deterministic ids - exists to make that trade something you chose rather than something that happened to you.
