Module 08 · Agents track

Agentic AI

An agent is a loop. The model chooses an action, your code runs it, the result goes back into the conversation, and the model chooses again - until something stops it. This page is that loop, written by hand, broken deliberately, and then given the guards it needs to be trusted.

⏱ Study + practice · 12–18 h Difficulty · Advanced Prereq · Modules 01, 04–06

1 · What you already know

From module 01: a model takes messages and returns a probability distribution over next tokens. From module 06: you can put retrieved text in the prompt before it answers.

Every one of those was one call. You decided what went in, the model produced text, and the interaction ended.

This page is about the model deciding what happens next, more than once.

2 · What breaks now

A support ticket arrives: "My order A-91 never arrived and I want my money back."

Answering it needs three things a single call cannot do:

StepWhy one call fails
Look up order A-91The model has no access to your database
Check the refund policy for undelivered goodsWhich policy applies depends on what the lookup returned
Decide whether to refund, and how muchDepends on both previous results

You could write this as a fixed sequence - look up, then fetch policy, then decide. That works until the ticket mentions two orders, or none, or asks something else entirely.

The number of steps and their order depend on what earlier steps returned. That is the condition under which a loop with the model inside it beats a fixed pipeline - and the condition under which it becomes much harder to operate.

3 · Simple breakdown - agent vs workflow

A Agent

Basic level

What it is. An agent is a program in which a model repeatedly chooses the next action from a set of tools, the application executes that action and appends the result, and the loop continues until a termination condition is met.

Core purpose. It handles tasks where the number of steps and their order are not known before the run starts.

Execution model.

Intermediate level

Architecture under the hood. Six parts: the message list, the tool registry mapping names to functions, the JSON schemas describing those tools to the model, a validation layer between the model's request and execution, the loop itself, and the termination conditions. The model never executes anything - it returns a name and arguments, and your code decides whether to honour them.

State handling. The message list is the whole state, and it grows by two entries per tool call. It lives in a variable for the length of one run. Nothing is checkpointed, so a crash loses everything - which is what module 12 adds.

Limitations and advanced features. Cost and latency are unbounded without a budget, because the loop length is decided at run time. Errors compound: at 90% reliability per step, a five-step run succeeds 59% of the time. Context grows every iteration. Advanced patterns are ReAct, plan-then-execute, reflection, and routing between specialised agents.

B Workflow

Basic level

What it is. A workflow is a program in which you write the sequence of steps in advance, and a model may be called inside one or more of those steps.

Core purpose. It produces the same path on every run, so behaviour, cost and latency are known before the run starts.

Execution model.

Intermediate level

Architecture under the hood. Ordinary code - function calls, conditionals, a chain, or a graph with fixed edges. Any model call is one step among several, and its output is data flowing to the next step rather than a decision about which step comes next.

State handling. Local variables, or the state object if you are using a graph. The path is fixed, so what exists at each point is known when you write it.

Limitations and advanced features. It cannot handle inputs you did not anticipate - an unexpected case falls through to a default or an error. Adding cases grows a branching tree that becomes hard to read. Advanced features are conditional routing, parallel branches and retries per step, all of which stay deterministic.

The core differences

AgentWorkflowFixed code, no model
Workflow design The model picks the next action at run time. Two runs on the same input can take different paths. You pick the steps in advance. The path is identical every run; only the data differs. No model in the decision at all. Fully deterministic.
Error recovery Failures compound across steps and the loop can wander or repeat. Recovery means budgets, repeat detection and fallbacks you add yourself. Each step is retried or falls back independently, and a failure is attributable to a named step. Ordinary exception handling.
Architectural paradigm Run-time decision loop over a tool set. Predetermined pipeline with model calls inside steps. A program.

In short - which one to choose

Build an agent when:

  • The next step genuinely depends on what the last step returned.
  • The number of steps varies by input and you cannot enumerate the cases.
  • The task is open-ended exploration rather than a known procedure.

Build a workflow when:

  • The steps are the same every time, even if a model runs inside one of them.
  • You need predictable cost, latency and behaviour.
  • Anything irreversible happens - money, customer-visible actions, deletions.

Build neither when:

  • One prompt and one answer would do it.
  • You cannot yet name the tools. If the tool list is unclear, the design is unclear.
  • You are choosing an agent because it sounds more capable. Risk always pulls back toward a guarded workflow.

4 · Without the technology

The workflow version of the ticket task. Explicit, readable, and correct for the case it was written for.

Three steps, always in that order, one model call. Cost and latency are known. It is testable.

Now: the ticket mentions two orders. Or none, but names a product. Or asks about a refund and a delivery date. Each case is another branch, and the branches interact.

An agent replaces the branching with a loop and lets the model pick from a tool list. That is the trade - you stop enumerating cases and start managing a non-deterministic loop.

5 · Runtime mechanics

One agent run, in nine steps.

  1. The message list starts with a system prompt and the user's request.
  2. Your code serialises each tool into a JSON schema - name, description, typed parameters.
  3. Messages and schemas go to the model in one request.
  4. The model returns either normal text, or a structured request naming a tool and its arguments.
  5. If there is no tool request, that text is the final answer and the loop ends.
  6. Otherwise your code validates: is this a tool that exists, are the arguments the right shape, is the caller allowed to run it.
  7. The tool executes. Its return value - or its error - is appended as a tool message.
  8. The step counter increments and the budget is checked.
  9. Back to step 3, with a longer message list.

Step 6 is the one beginners omit and the one interviewers ask about. The model's output is a request, not a command, and the gap between those two words is where every safety property of an agent lives.

6 · The components, one at a time

The pieces

1 · The message list

The entire state. Four roles: system for standing instructions, user, assistant for the model's turns including tool requests, and tool for results.

2 · Tool

An ordinary function. Nothing about it is special until you describe it.

3 · Tool schema

The JSON Schema the model reads. The description is a prompt - it is the only thing the model uses to decide whether this tool applies. Say when to use it and when not to.

4 · Tool registry

Name to function. Look up by name and check membership - a model will eventually invent a tool name, and indexing straight into the dictionary turns that into a KeyError in production.

5 · Argument validation

The model can return valid JSON with wrong types or missing fields. Validate against the schema with Pydantic before executing - the Pydantic page covers this.

Running the loop

6 · The loop

Call, check for tool requests, execute, append, repeat. Ten lines, and every production concern below is a guard bolted onto it.

7 · Termination conditions

Four, and you need all four:

ConditionFires when
Natural stopThe model returns no tool call. The normal exit
Step budgetA fixed maximum number of iterations
Token or cost budgetCumulative spend crosses a threshold
Repeat detectionThe same tool with the same arguments twice in a row

Only the first is the model's decision, which is exactly why the other three exist.

8 · Repeat detection

Feeding the loop back an error is better than raising: the model often recovers, where a crash cannot.

9 · Error handling inside tools

A tool that raises kills the run. A tool that returns an error message gives the model a chance to try something else.

Patterns and boundaries

10 · ReAct

The default shape: the model reasons briefly, acts, observes the result, and repeats. The loop above is ReAct - the reasoning is whatever the model says alongside its tool call.

11 · Plan-then-execute

Ask for the whole plan first, then run the steps. Cheaper and more predictable, and worse when a step returns something the plan did not anticipate. Some implementations re-plan after each step, which costs the savings back.

12 · Reflection

A second model call that criticises the first answer and can send it back for revision. Doubles the cost; useful when a wrong answer is expensive.

13 · Read tools and write tools

The most useful split on this page. Read tools are safe to retry and safe to let the loop call freely. Write tools spend money or change customer records, and belong behind explicit approval.

14 · Recommend versus execute

The safest agent design is one that proposes an action and returns it for a human to confirm. An agent that recommends is a different risk class from one that acts, and saying so in an interview is worth more than naming three frameworks.

7 · State and data flow

1 · What data is state?The message list, plus the counters you keep - steps taken, tokens spent, calls seen.
2 · Who writes each field?The model appends assistant turns; your code appends tool results.
3 · Who reads it?The model reads the whole list on every iteration.
4 · Replaced, appended or merged?Appended only. Two messages per tool call.
5 · What controls merging?Nothing - it is a list that grows.
6 · Only in memory?Yes, in one Python variable.
7 · Checkpointed?No. This is the gap module 12 fills.
8 · In a database?Only if you put it there.
9 · How long does it survive?Until the function returns. A crash at step 7 loses all seven steps.
10 · What key retrieves it again?None. There is no run id at this layer.

9 · Break it

Give the agent a question its tools cannot answer, with the guards removed.

Six model calls, six database hits, no answer. The model had one tool, so it kept using it. Without repeat detection this burns the entire budget on the same failing action.

The second failure is worse, and it is what section 6's dispatch layer exists for.

The model treated text inside the ticket as an instruction. The tool call is well-formed, the arguments are valid, and the schema is satisfied - validation alone does not stop this. Only the read/write split and the approval gate do, and module 09 covers the general problem.

10 · Fix it

1 · Repeat detection, and feed the error back to the model rather than raising. The model usually changes approach after one refusal.

2 · Tell the model what it cannot do, so "I don't know" is an available move.

3 · Mark untrusted content as data, not instructions.

4 · Gate every write behind approval - the dispatch function. This is the only one of the four that holds when the other three fail.

The layers matter in that order of reliability. The prompt is guidance and can be overridden by clever text; the dispatch check is code and cannot.

11 · Production version

ConcernWhat you do
TerminationAll four conditions. A step budget alone still allows six identical failing calls
Untrusted contentDelimit it and say it is data. Assume the delimiter can be defeated and gate writes anyway
Write toolsSeparate registry, explicit approval, idempotency key per action so a retry cannot double-refund
Argument validationPydantic per tool, with real constraints. amount_paise needs an upper bound
AuthorisationCheck inside the tool against the caller's identity, not in the prompt. The model must not be the access control
CostSum tokens across iterations. A ten-step run costs far more than ten times one call, because context grows
LatencyBudget in wall-clock seconds as well as steps. A slow tool can hold a run open indefinitely
TracingOne correlation id per run; log every step, tool, arguments, result and duration. A trace is the only way to debug a path that differs every run
EvaluationScore the trajectory - which tools ran, in what order - not only the final answer. A right answer by the wrong route will break later
DurabilityNothing here survives a crash. That is module 12

13 · Interview preparation

Beginner  What is an LLM agent? ›

An LLM run in a control loop where it can call tools and act on their results. Instead of one-shot text output, it reasons about the next step, calls a tool, observes the result, and repeats until the goal is met - letting it perform multi-step, tool-using, dynamic tasks.

Beginner  What is ReAct? ›

Reason + Act: a pattern where the agent interleaves Thought (reason about the next step), Action (call a tool), and Observation (the tool's result), looping until it can give a final answer. The interleaving lets it adapt each step to what tools return.

Intermediate  How does tool/function calling actually work? ›

You pass the model tool schemas (name, description, JSON parameter spec). The model, trained for this, returns a structured request naming a tool and its arguments instead of plain text. Your runtime executes the tool and returns the result as a new message. The model never runs anything itself - it requests; your code executes. Description/schema quality drives correct tool selection.

Intermediate  Explain the three layers of agent memory. ›

Working memory: the current context window - the live scratchpad for this task. Short-term memory: the conversation/episode history, summarized as it grows to fit the window. Long-term memory: persistent facts stored in a vector DB and retrieved when relevant - essentially RAG over the agent's own past, enabling cross-session recall.

Senior  An agent keeps looping on the same failed action. How do you diagnose and fix it? ›

Inspect the trace: it's usually a tool returning an error the model can't act on, a missing capability, or an ambiguous goal. Fixes: enforce a max-step budget with graceful stop; add loop detection (repeated identical actions → break/re-plan); feed tool errors back clearly so the model can self-correct; improve the failing tool's description or add the missing tool; add a reflection/re-plan step; escalate to a human after N failures. Long-term, add this case to the agent eval set.

Senior  How do you evaluate an agent given non-determinism? ›

Don't assert exact outputs. Measure: task success (final-state/golden-outcome check), trajectory quality (sensible tool choices, no wasted steps - often LLM-as-judge over the trace), tool-call correctness (right tool, valid args), efficiency (steps/tokens/cost/latency), and safety (no unsafe actions). Run a suite of representative tasks repeatedly to capture variance, gate deploys on success rate, and sample production failures back into the suite.

Staff · design  Design a safe agent platform for internal employees to automate workflows. ›

Core: a guarded agent runtime (step/token budgets, arg validation, full trace logging). Tools as a governed registry with least-privilege scopes, schemas, and per-tool risk classification; consequential actions (write/delete/send/pay) require human-in-the-loop approval and dry-run. Safety: input/output guardrails, prompt-injection defenses on tool results, allow-lists, sandboxed code execution. Observability: every trace logged for audit + replay; cost/latency per run; alerting on loops and budget breaches. Evaluation: a task suite gating any new tool/agent in CI; staged rollout. Memory: per-user long-term memory with access controls and PII handling. Start agents on the low-autonomy end of the spectrum and increase autonomy only as eval evidence accrues. Governance and traceability are the product, not the model.

14 · In short, and what comes next

Remember these six:

  • An agent is a loop; the model chooses actions, your code executes them.
  • The model returns a request, never a command. The gap is where safety lives.
  • Four termination conditions: natural stop, step budget, cost budget, repeat detection.
  • Return tool errors into the loop instead of raising - the model often recovers.
  • Split read tools from write tools. Gate writes in code, not in the prompt.
  • At 90% per step, a five-step run succeeds 59% of the time.
🔑
The one idea to remember

Build a workflow unless the next step genuinely depends on what the last step returned. An agent buys you flexibility and charges you predictability, cost control and debuggability - and risk always pulls you back toward the guarded version.
