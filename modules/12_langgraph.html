LangGraph

In module 09 you met chains. A chain runs forward once and then it is finished. This page is about the four things it cannot do - loop, choose its next step while running, wait for a person, and survive a crash - and the framework that adds them.

Everything on this page comes back to five ideas. Level 1 covers the first two.

  1. A chain does not know where it is. Give the run a state, save it after every step, and looping, branching, pausing and resuming all become possible.
  2. A graph is nodes and edges over one shared state. A node returns only the fields it changed; an edge, or a router reading the state, picks the next node.
  3. Reducers decide how updates merge. Overwrite by default; add_messages appends. Forget it and the conversation silently resets.
  4. The checkpointer is the memory. State is saved after every superstep under a thread_id; interrupt() pauses the run and Command(resume=...) continues it.
  5. Every loop needs three stops. The normal exit, a step budget in the state, and the recursion_limit as the last line of defence.
🧠
Memory hook

A board game with save slots. The state is the board, each node is a move, the checkpointer is one save slot per thread_id, and an interrupt is a pause for the referee. A reducer is a whiteboard or a ledger: the default wipes the whiteboard and writes the new value; add_messages adds a line to the ledger.

1 · What you already know

In module 09 you met chains: prompt | model | parser. Every component has the same four methods, the | runs them in order, and the value moves from one to the next until the last one returns.

In module 06 you saw the agent loop as plain steps: send messages, read the reply, run the tool it asked for, append the result, send again.

You cannot write that loop as a chain. This page is about why, and what to use instead.

2 · What breaks now

Take the agent loop from module 06 and try to express it with |: model, then tools, then model, then tools, and so on.

You cannot finish that line, because you do not know how many times to repeat it. The number of tool calls depends on what the model asks for, which you only learn while the run is happening.

What you needWhy a chain cannot do it
Go back to an earlier stepThe order is fixed before the run starts
Pick the next step from the last resultThere is nowhere to put the decision
Stop and wait for a person to approveinvoke either returns or raises; it cannot pause
Continue after a crashNothing was written down, so there is nothing to continue from

All four are the same missing thing. A chain does not know where it is. Give the run a piece of data that says where it is, save that data after every step, and all four problems disappear at once. That data is called the state.

3 · Simple breakdown - LangGraph vs LangChain

A LangGraph

Basic level

What it is. LangGraph is an open-source Python framework from the LangChain team (it depends only on langchain-core, not on LangChain itself), for writing LLM applications as a graph of nodes that read and update one shared state object.

Core purpose. It runs workflows that loop, choose the next step at run time, pause for human approval, or continue after a crash.

Execution model.

Intermediate level

Architecture under the hood. A StateGraph holds the state schema, the nodes and the edges. Compiling it produces a Pregel runtime that executes in supersteps: every node scheduled for a step runs, then their updates are merged. A reducer declared per state field decides how the merge works - overwrite by default, or add_messages to append. A checkpointer (InMemorySaver, SqliteSaver, PostgresSaver) writes the state after every superstep.

State handling. One shared state object exists for the whole run. Each node returns a partial update, which the runtime merges through the reducers. With a checkpointer, every version is stored under a thread_id, which is what allows resume, replay and history.

Limitations and advanced features. More setup than a chain: a schema, node functions, edges and a compile step before anything runs. A cycle with no exit condition is easy to write, so the runtime enforces a recursion_limit. Advanced features are interrupt() for human approval (resumed with Command(resume=...); the static interrupt_before and interrupt_after are mainly for debugging), Command to route and update state in one return, subgraphs, per-node streaming, and time travel from any checkpoint.

B LangChain

Basic level

What it is. LangChain is an open-source Python framework for building LLM-based applications from reusable components such as models, prompts, retrievers, tools, and runnables.

Core purpose. It reduces the amount of application code you need to write when several LLM-related components must work together.

Execution model.

Intermediate level

Architecture under the hood. Every component implements one interface, Runnable, which defines invoke, batch, stream and their async versions. The | operator builds a RunnableSequence that runs components in order. RunnableParallel runs components at the same time and returns a dictionary. Streaming, batching and callbacks are implemented once on Runnable, so every chain gets them.

State handling. A chain is stateless. The only data that exists during a run is the value passed from one component to the next. Chat history used to be added with RunnableWithMessageHistory, keyed by a session id; that is now legacy, and the LangChain docs point to LangGraph checkpointers for conversation memory instead.

Limitations and advanced features. A chain is acyclic and runs forward once: it can fan out and join again (RunnableParallel), but it cannot loop back, pause for approval or recover after a crash. Advanced features wrap any component - .with_retry(), .with_fallbacks(), .with_structured_output(), .bind_tools().

The core differences

LangGraphLangChain
Workflow design Named nodes with edges evaluated while running. A conditional edge reads the state and picks the next node, so loops and branches are normal. A fixed forward sequence built with |. The order is decided before the run starts and does not change during it.
Error recovery The checkpointer saves state after every node, so a failed run resumes from the last completed node instead of starting over. .with_retry() re-runs one component from its own beginning. .with_fallbacks() swaps in a different component. Nothing is saved, so a crash loses the run.
Architectural paradigm A state machine with a persistent shared state object. A directed acyclic graph of components behind one shared interface.

In short - which one to choose

Choose LangGraph when:

  • The workflow loops - call the model, run a tool, call the model again.
  • The next step depends on what the previous step returned.
  • The run must pause for a person to approve something, then continue.
  • The run must survive a crash and continue from where it stopped.

Choose LangChain when:

  • The steps always run in the same fixed order.
  • You want retrieval, prompting and parsing wired together with less code.
  • You expect to swap the model, the retriever or the vector store later.

Choose neither when:

  • The whole task is one prompt and one answer. Call the model directly.
  • You do not yet understand the plain agent loop. Module 06 first.
  • The workflow is fixed and you are reaching for a graph out of habit.

4 · Without the technology

The agent loop from module 06, written by hand, is a for loop around a list called messages. Each pass calls the model with the list, appends its reply, runs any tool it asked for and appends the result. The loop stops when the model asks for no more tools.

This works. It loops, and it stops. What it cannot do:

  • Pause. To wait for approval you would have to return from the function, store messages yourself, and rebuild the loop on the next request.
  • Resume. If the process dies at step 7, messages dies with it.
  • Branch cleanly. Add a second decision and the for body grows an if tree nobody can read.
  • Be inspected. There is no record of which step ran, or what the data looked like between steps.

LangGraph is this loop, with messages promoted to a named object the framework saves after every step.

5 · Runtime mechanics

What happens when you call graph.invoke(...). Eight steps.

  1. The runtime takes your input dictionary as the starting state.
  2. START names the first node.
  3. That node function is called with the whole current state.
  4. It returns a partial update - a dictionary with only the keys it changed.
  5. The runtime merges that update into the state, one field at a time, using the reducer declared for each field.
  6. The edges leaving that node are evaluated. A normal edge names the next node. A conditional edge calls your router function, which reads the state and returns a name.
  7. Steps 3 to 6 repeat for the next node.
  8. When a node routes to END, the run stops and the final state is returned.

Steps 3 to 6 are one superstep. With a checkpointer attached, the state is written to storage at the end of every superstep - which is the entire mechanism behind resume, pause and time travel.

6 · The components, one at a time

Learn each one on its own. The order below is the order you write them in.

The graph

1 · State

A schema listing every field the run can hold. A TypedDict is enough; a Pydantic model adds validation at each step.

2 · Node

A plain function. It receives the whole state and returns a dictionary containing only the fields it changed. It never edits the state it was given.

3 · Edge

Says which node runs next. A normal edge is unconditional: after A, always B.

4 · START and END

Two reserved names. START marks the entry point, END stops the run. They are not nodes and they do not run code.

5 · StateGraph and compile

StateGraph collects the schema, nodes and edges. compile() checks the graph is valid and returns a runnable object. Errors such as an unreachable node surface here, not at run time.

6 · Invoke

The compiled graph is a Runnable, so it has the same four methods as everything in module 09.

Controlling the flow

7 · Reducer

Decides how a node's update merges into a field. The default is overwrite. Annotate a field to change it - add_messages appends instead of replacing, which is what a conversation needs.

Without a reducer, the second node to write messages deletes what the first one wrote. This is the single most common LangGraph bug.

8 · Conditional edge

A function that reads the state and returns the name of the next node. This is where a graph stops being a chain.

9 · Parallel branches

Two edges out of one node, with no edge between them, means both nodes run in the same superstep. Their updates are merged afterwards - which is exactly when you need a reducer. Without one, two writes to the same key in one superstep do not silently overwrite: the run stops with InvalidUpdateError ("can receive only one value per step"). Plain overwrite only happens when the writes land in different steps.

Durability

10 · Checkpointer

Saves the state after every superstep. InMemorySaver (older name: MemorySaver) keeps it in the process. SqliteSaver and PostgresSaver write to a database and survive a restart.

11 · Thread

A thread_id names one run's history. Reuse it and the graph loads the previous state and continues; use a new one and it starts fresh.

This is what "memory" means here. The model remembers nothing. The graph reloads the saved messages and sends them again.

12 · Interrupt

A node calls interrupt(payload) - for example the proposed refund - and the run stops there with the state checkpointed. The graph is paused, not cancelled. The static interrupt_before / interrupt_after options also exist, but the LangGraph docs recommend them for debugging, not for human approval.

13 · Resume

Invoke the graph again on the same thread with Command(resume=value). The value - "approved", an edited argument, a rejection message - becomes the return value of interrupt() inside the node.

One trap: on resume the interrupted node runs again from its first line, not from the interrupt() call. Anything the node did before the pause runs twice, so keep side effects after the interrupt, make them idempotent, or move them to an earlier node. Nodes that finished before the pause do not run again.

14 · Command

Lets a node return a state update and a routing decision together, instead of needing a separate conditional edge.

15 · Subgraph

A compiled graph used as a node inside another graph. Use it when one flat graph grows past the point where you can read it.

7 · State and data flow

Four questions about the state, and the answers that matter.

What is state?One object matching the schema you declared, shared by every node for the whole run. Every node and every router reads it.
How is an update merged?By the field's reducer, declared in the Annotated[...] type. Overwrite by default; add_messages appends.
Where is it saved?After every superstep, when a checkpointer is attached: in the process with InMemorySaver, in a database with SqliteSaver or PostgresSaver. Deleting old rows is your job.
What key retrieves it again?thread_id, from the config dictionary.

8 · Trace

What actually ran for "Where is order A-91?".

SuperstepNodeReturnsRouter says
1agentAIMessage with one tool call"tools"
2toolsToolMessage("shipped 12 Aug")fixed edge back to agent
3agentAIMessage("Order A-91 shipped on 12 August.")END

The agent node ran twice. Its code did not change between the two runs - only the state did, because superstep 2 appended the tool result. That is the loop: the same node, a longer message list, a different decision.

9 · Break it

Now remove the exit condition. Route to tools unconditionally.

The graph keeps looping until the recursion_limit - 25 steps by default in most versions; check yours, and always set it explicitly - stops it with an error. Every model call on the way was paid for. Nothing in the graph noticed the run was pointless - the router said "tools" every time and the runtime obeyed.

There is a second failure with no error at all. Drop the add_messages reducer from the messages field.

Now superstep 2 replaces the message list instead of appending to it. The model loses the question it was answering, and the conversation silently resets on every turn. Nothing raises. The graph just gets stupider.

10 · Fix it

The loop needs a condition that can become false, and a budget that stops it even if the condition never does. The router sends the run to END when the model asks for no tools. A step counter in the state sends it to END after a fixed number of steps. And the recursion_limit stays as the last line of defence.

Three separate stops now: the model stops asking for tools, the step budget runs out, or the recursion limit fires. The first is the normal exit. The other two exist because the first one cannot be trusted.

The silent reducer bug is fixed by putting the add_messages annotation back. While you are learning, also check that the message list only ever grows, because the failure is invisible otherwise.

Q What is a superstep, and what happens at the end of one? ›
One round of running the scheduled nodes, merging their updates through the reducers and evaluating the edges. With a checkpointer attached, the state is written to storage at the end of every superstep.

It makes updates to messages append instead of overwrite. Without it each update replaces the list, the model loses the question, and the conversation silently resets.

The run stops with InvalidUpdateError. Two values in one superstep need a reducer to combine them.
Q On resume after interrupt(), where does the node start? ›
From its first line, not from the interrupt() call. Anything it did before the pause runs again, so keep side effects after the interrupt or make them idempotent.
Q Name the three stops every loop needs. ›
The router sending the run to END when the model asks for no tools, a step budget in the state, and the recursion_limit as the last line of defence.

The most expensive mistake on this page is a graph that loops in production without a step budget. The recursion limit will stop it, but only after every step up to that limit - 25 by default in most versions, more if someone raised it - has been paid for, on every request.

13 · Interview preparation

Beginner  What is LangGraph and why not just use LCEL? ›

LangGraph models LLM apps as stateful graphs (state + nodes + edges) that support cycles, branching, parallelism, durability, and human-in-the-loop. LCEL composes acyclic pipelines and can't express loops or pause/resume. Agents inherently loop and branch, so they need a graph, not a DAG.

Beginner  What are nodes and edges? ›

A node is a function that takes the current state and returns a partial update (the unit of work - an LLM call, a tool, a retrieval). An edge connects nodes: a normal edge always goes A→B; a conditional edge runs a router function that returns the next node's name based on state. START and END are sentinels.

Intermediate  What is a reducer and why does it matter? ›

A reducer defines how a node's returned value merges into existing state. By default keys are overwritten; for accumulating fields (like a message list) you use a reducer such as add_messages to append. Reducers are also essential for merging the outputs of parallel branches: if two nodes in the same superstep write a key that has no reducer, LangGraph raises InvalidUpdateError ("can receive only one value per step"). Silent overwrite only happens when writes land in different supersteps.

Intermediate  How does checkpointing enable memory and human-in-the-loop? ›

A checkpointer persists state after each step, keyed by thread_id. Memory: reuse a thread to continue a conversation with full prior state. Human-in-the-loop: a node calls interrupt(payload), which pauses the graph and checkpoints state; your app shows the payload to a human; invoking again on the same thread with Command(resume=decision) continues, and the decision becomes interrupt()'s return value. Note the interrupted node re-runs from its start on resume, so side effects before the interrupt must be idempotent. (Static interrupt_before exists but is recommended for debugging.) Same mechanism enables crash-resume and time-travel debugging.

Senior  Design an agent that must get human approval before any write action. ›

Separate read tools from write tools into different nodes (or route by tool risk). Compile with a durable checkpointer; the write node calls interrupt({"proposed_call": ...}) before executing anything. Flow: agent proposes → conditional edge routes a write to the write node → graph pauses and checkpoints → your UI surfaces the proposed call (with diff/dry-run) → human approves/edits/rejects → resume with Command(resume={"action": "approve" | "edit" | "reject", ...}) to execute, or return a rejection message and loop back to the agent. Because the node re-runs from its start on resume, keep everything before interrupt() side-effect free. Bound the loop with recursion_limit, log every state transition for audit, and store checkpoints in Postgres so approvals can happen asynchronously (minutes/hours later) and survive restarts.

Senior  How do you run retrieval from three sources concurrently and merge? ›

From a single "split" node, add edges to three retrieval nodes (web/docs/db); LangGraph runs nodes with no dependency between them concurrently. Each writes to a state field with an appropriate reducer (e.g. a list that accumulates results) so their outputs merge deterministically at a downstream "merge" node, which all three edge into. Wall-clock becomes the slowest branch, not the sum. Guard each branch with its own error handling so one failure doesn't sink the merge.

Staff · design  Design a durable, multi-step research agent platform on LangGraph. ›

Model each workflow as an explicit graph: planner node → parallel retrieval/tool nodes (fan-out with reducers) → synthesis node → reflection node (conditional edge loops back if quality is low). Compile with a Postgres checkpointer for durability, resume, and audit; key runs by thread_id for memory and multi-session continuation. Add interrupt() inside consequential nodes for human approval; bound cycles with recursion_limit and step/token budgets (Module 06). Wrap external tools as MCP servers (Module 07) and retrievers as RAG components (Module 05). Add tracing/observability (Module 15) over the event stream, an eval suite over graph trajectories gating deploys, and per-tenant state isolation. Stream state/events to the UI for transparency. The graph is the auditable spec; durability + HITL + explicit routing are what make it production-grade.

14 · In short, and what comes next

The five ideas from the top of the page. Try to say each one before you read it.

  1. A chain does not know where it is. Give the run a state, save it after every step, and looping, branching, pausing and resuming all become possible.
  2. A graph is nodes and edges over one shared state. A node returns only the fields it changed; an edge, or a router reading the state, picks the next node.
  3. Reducers decide how updates merge. Overwrite by default; add_messages appends. Forget it and the conversation silently resets.
  4. The checkpointer is the memory. State is saved after every superstep under a thread_id; interrupt() pauses the run and Command(resume=...) continues it.
  5. Every loop needs three stops. The normal exit, a step budget in the state, and the recursion_limit as the last line of defence.

Use LangGraph when:

  • The workflow loops, or the next step depends on the last result.
  • A person must approve a step before it runs.
  • The run must survive a restart and continue where it stopped.
  • You need to see which steps ran, in what order, after the fact.

Do not use it when:

  • The steps are fixed and always run in the same order. Use a chain.
  • One prompt, one answer. Call the model directly.
  • You do not yet understand the plain agent loop. Module 06 first.

The one idea to remember

The state is the whole point. Nodes are functions and edges are rules, but the reason a graph can loop, branch, pause and recover is that one object holds where the run has got to, and the checkpointer writes it down after every step.
