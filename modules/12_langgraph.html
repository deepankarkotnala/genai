LangGraph

In module 10 you built chains. A chain runs forward once and then it is finished. This page is about the four things it cannot do - loop, choose its next step while running, wait for a person, and survive a crash - and the framework that adds them.

⏱ Study + labs · 16–24 h Difficulty · Advanced Prereq · Modules 08, 10

1 · What you already know

In module 10 you built chains: prompt | model | parser. Every component has the same four methods, the | runs them in order, and the value moves from one to the next until the last one returns.

In module 08 you wrote an agent loop by hand: send messages, read the reply, run the tool it asked for, append the result, send again.

You cannot write that loop as a chain. This page is about why, and what to use instead.

2 · What breaks now

Take the agent loop from module 08 and try to express it with |.

You cannot finish that line, because you do not know how many times to repeat it. The number of tool calls depends on what the model asks for, which you only learn while the run is happening.

What you needWhy a chain cannot do it
Go back to an earlier stepThe order is fixed before the run starts
Pick the next step from the last resultThere is nowhere to put the decision
Stop and wait for a person to approveinvoke either returns or raises; it cannot pause
Continue after a crashNothing was written down, so there is nothing to continue from

All four are the same missing thing. A chain does not know where it is. Give the run a piece of data that says where it is, save that data after every step, and all four problems disappear at once. That data is called the state.

3 · Simple breakdown - LangGraph vs LangChain

A LangGraph

Basic level

What it is. LangGraph is an open-source Python framework, built on LangChain, for writing LLM applications as a graph of nodes that read and update one shared state object.

Core purpose. It runs workflows that loop, choose the next step at run time, pause for human approval, or continue after a crash.

Execution model.

Intermediate level

Architecture under the hood. A StateGraph holds the state schema, the nodes and the edges. Compiling it produces a Pregel runtime that executes in supersteps: every node scheduled for a step runs, then their updates are merged. A reducer declared per state field decides how the merge works - overwrite by default, or add_messages to append. A checkpointer (MemorySaver, SqliteSaver, PostgresSaver) writes the state after every superstep.

State handling. One shared state object exists for the whole run. Each node returns a partial update, which the runtime merges through the reducers. With a checkpointer, every version is stored under a thread_id, which is what allows resume, replay and history.

Limitations and advanced features. More setup than a chain: a schema, node functions, edges and a compile step before anything runs. A cycle with no exit condition is easy to write, so the runtime enforces a recursion_limit. Advanced features are interrupt_before and interrupt_after for human approval, Command to route and update state in one return, subgraphs, per-node streaming, and time travel from any checkpoint.

B LangChain

Basic level

What it is. LangChain is an open-source Python framework for building LLM-based applications from reusable components such as models, prompts, retrievers, tools, and runnables.

Core purpose. It reduces the amount of application code you need to write when several LLM-related components must work together.

Execution model.

Intermediate level

Architecture under the hood. Every component implements one interface, Runnable, which defines invoke, batch, stream and their async versions. The | operator builds a RunnableSequence that runs components in order. RunnableParallel runs components at the same time and returns a dictionary. Streaming, batching and callbacks are implemented once on Runnable, so every chain gets them.

State handling. A chain is stateless. The only data that exists during a run is the value passed from one component to the next. Chat history is added with RunnableWithMessageHistory, which reads and writes a store you supply, keyed by a session id.

Limitations and advanced features. A chain is acyclic and runs forward once: no loops, no rejoining branches, no pause for approval, no recovery after a crash. Advanced features wrap any component - .with_retry(), .with_fallbacks(), .with_structured_output(), .bind_tools().

The core differences

LangGraphLangChain
Workflow design Named nodes with edges evaluated while running. A conditional edge reads the state and picks the next node, so loops and branches are normal. A fixed forward sequence built with |. The order is decided before the run starts and does not change during it.
Error recovery The checkpointer saves state after every node, so a failed run resumes from the last completed node instead of starting over. .with_retry() re-runs one component from its own beginning. .with_fallbacks() swaps in a different component. Nothing is saved, so a crash loses the run.
Architectural paradigm A state machine with a persistent shared state object. A directed acyclic graph of components behind one shared interface.

In short - which one to choose

Choose LangGraph when:

  • The workflow loops - call the model, run a tool, call the model again.
  • The next step depends on what the previous step returned.
  • The run must pause for a person to approve something, then continue.
  • The run must survive a crash and continue from where it stopped.

Choose LangChain when:

  • The steps always run in the same fixed order.
  • You want retrieval, prompting and parsing wired together with less code.
  • You expect to swap the model, the retriever or the vector store later.

Choose neither when:

  • The whole task is one prompt and one answer. Call the model directly.
  • You have not yet written the loop by hand once. Module 08 first.
  • The workflow is fixed and you are reaching for a graph out of habit.

4 · Without the technology

The agent loop from module 08, written by hand.

This works. It loops, and it stops. What it cannot do:

  • Pause. To wait for approval you would have to return from the function, store messages yourself, and rebuild the loop on the next request.
  • Resume. If the process dies at step 7, messages dies with it.
  • Branch cleanly. Add a second decision and the for body grows an if tree nobody can read.
  • Be inspected. There is no record of which step ran, or what the data looked like between steps.

LangGraph is this loop, with messages promoted to a named object the framework saves after every step.

5 · Runtime mechanics

What happens when you call graph.invoke(...). Eight steps.

  1. The runtime takes your input dictionary as the starting state.
  2. START names the first node.
  3. That node function is called with the whole current state.
  4. It returns a partial update - a dictionary with only the keys it changed.
  5. The runtime merges that update into the state, one field at a time, using the reducer declared for each field.
  6. The edges leaving that node are evaluated. A normal edge names the next node. A conditional edge calls your router function, which reads the state and returns a name.
  7. Steps 3 to 6 repeat for the next node.
  8. When a node routes to END, the run stops and the final state is returned.

Steps 3 to 6 are one superstep. With a checkpointer attached, the state is written to storage at the end of every superstep - which is the entire mechanism behind resume, pause and time travel.

6 · The components, one at a time

Learn each one on its own. The order below is the order you write them in.

The graph

1 · State

A schema listing every field the run can hold. A TypedDict is enough; a Pydantic model adds validation at each step.

2 · Node

A plain function. It receives the whole state and returns a dictionary containing only the fields it changed. It never edits the state it was given.

3 · Edge

Says which node runs next. A normal edge is unconditional: after A, always B.

4 · START and END

Two reserved names. START marks the entry point, END stops the run. They are not nodes and they do not run code.

5 · StateGraph and compile

StateGraph collects the schema, nodes and edges. compile() checks the graph is valid and returns a runnable object. Errors such as an unreachable node surface here, not at run time.

6 · Invoke

The compiled graph is a Runnable, so it has the same four methods as everything in module 10.

Controlling the flow

7 · Reducer

Decides how a node's update merges into a field. The default is overwrite. Annotate a field to change it - add_messages appends instead of replacing, which is what a conversation needs.

Without a reducer, the second node to write messages deletes what the first one wrote. This is the single most common LangGraph bug.

8 · Conditional edge

A function that reads the state and returns the name of the next node. This is where a graph stops being a chain.

9 · Parallel branches

Two edges out of one node, with no edge between them, means both nodes run in the same superstep. Their updates are merged afterwards - which is exactly when you need a reducer.

Durability

10 · Checkpointer

Saves the state after every superstep. MemorySaver keeps it in the process. SqliteSaver and PostgresSaver write to a database and survive a restart.

11 · Thread

A thread_id names one run's history. Reuse it and the graph loads the previous state and continues; use a new one and it starts fresh.

This is what "memory" means here. The model remembers nothing. The graph reloads the saved messages and sends them again.

12 · Interrupt

Stops the run before or after a named node and checkpoints the state. The graph is paused, not cancelled.

13 · Resume

Calling invoke with None on the same thread continues from the checkpoint. Nothing before the pause runs again.

To change the state before continuing - an edited argument, a rejection message - write to it first.

14 · Command

Lets a node return a state update and a routing decision together, instead of needing a separate conditional edge.

15 · Subgraph

A compiled graph used as a node inside another graph. Use it when one flat graph grows past the point where you can read it.

7 · State and data flow

The same ten questions asked on every stateful page in this portal.

1 · What data is state?One object matching the schema you declared, shared by every node for the whole run.
2 · Who writes each field?Any node that returns that key. Several nodes may write the same field.
3 · Who reads it?Every node receives the whole state, and the router functions read it too.
4 · Replaced, appended or merged?Whatever the field's reducer says. Overwrite by default.
5 · What reducer controls merging?The one in the Annotated[...] type. add_messages appends; a plain type overwrites.
6 · Only in process memory?Only with no checkpointer, or with MemorySaver.
7 · Checkpointed?Yes, after every superstep, when a checkpointer is attached.
8 · In a database?With SqliteSaver or PostgresSaver.
9 · How long does it survive?As long as the checkpoint rows exist. Deleting them is your job.
10 · What key retrieves it again?thread_id, from the config dictionary.

The agent node ran twice. Its code did not change between the two runs - only the state did, because superstep 2 appended the tool result. That is the loop: the same node, a longer message list, a different decision.

9 · Break it

Now remove the exit condition. Route to tools unconditionally.

Twenty-five model calls happened before it stopped. They were all paid for. Nothing in the graph noticed the run was pointless - the router said "tools" every time and the runtime obeyed.

There is a second failure with no error at all. Drop the reducer.

Now superstep 2 replaces the message list instead of appending to it. The model loses the question it was answering, and the conversation silently resets on every turn. Nothing raises. The graph just gets stupider.

10 · Fix it

The loop needs a condition that can become false, and a budget that stops it even if the condition never does.

Three separate stops now: the model stops asking for tools, the step budget runs out, or the recursion limit fires. The first is the normal exit. The other two exist because the first one cannot be trusted.

The silent reducer bug is fixed by the annotation alone - and it is worth adding one assertion while you are learning, because the failure is invisible otherwise.

Durable statePostgresSaver, not MemorySaver. A checkpoint that dies with the process is a demo

AuthorisationCheck permission inside the node, before the side effect. An edge is routing, not a security boundary

RollbackVersion the graph. A checkpoint written by an old shape may not load into a new one

The most expensive mistake on this page is a graph that loops in production without a step budget. The recursion limit will stop it, but only after twenty-five model calls per request.

13 · Interview preparation

Beginner  What is LangGraph and why not just use LCEL? ›

LangGraph models LLM apps as stateful graphs (state + nodes + edges) that support cycles, branching, parallelism, durability, and human-in-the-loop. LCEL composes acyclic pipelines and can't express loops or pause/resume. Agents inherently loop and branch, so they need a graph, not a DAG.

Beginner  What are nodes and edges? ›

A node is a function that takes the current state and returns a partial update (the unit of work - an LLM call, a tool, a retrieval). An edge connects nodes: a normal edge always goes A→B; a conditional edge runs a router function that returns the next node's name based on state. START and END are sentinels.

Intermediate  What is a reducer and why does it matter? ›

A reducer defines how a node's returned value merges into existing state. By default keys are overwritten; for accumulating fields (like a message list) you use a reducer such as add_messages to append. Reducers are also essential for deterministically merging the outputs of parallel branches - without the right reducer, concurrent updates clobber each other.

Intermediate  How does checkpointing enable memory and human-in-the-loop? ›

A checkpointer persists state after each step, keyed by thread_id. Memory: reuse a thread to continue a conversation with full prior state. Human-in-the-loop: interrupt_before a node pauses the graph and checkpoints state; your app shows the proposed action to a human; calling invoke with None on the same thread resumes from that exact checkpoint. Same mechanism enables crash-resume and time-travel debugging.

Senior  Design an agent that must get human approval before any write action. ›

Separate read tools from write tools into different nodes (or route by tool risk). Compile with a durable checkpointer and interrupt_before=["write_tools"]. Flow: agent proposes → conditional edge routes a write to the write node → graph pauses and checkpoints → your UI surfaces the proposed call (with diff/dry-run) → human approves/edits/rejects → resume from checkpoint to execute, or inject a rejection message and loop back to the agent. Bound the loop with recursion_limit, log every state transition for audit, and store checkpoints in Postgres so approvals can happen asynchronously (minutes/hours later) and survive restarts.

Senior  How do you run retrieval from three sources concurrently and merge? ›

From a single "split" node, add edges to three retrieval nodes (web/docs/db); LangGraph runs nodes with no dependency between them concurrently. Each writes to a state field with an appropriate reducer (e.g. a list that accumulates results) so their outputs merge deterministically at a downstream "merge" node, which all three edge into. Wall-clock becomes the slowest branch, not the sum. Guard each branch with its own error handling so one failure doesn't sink the merge.

Staff · design  Design a durable, multi-step research agent platform on LangGraph. ›

Model each workflow as an explicit graph: planner node → parallel retrieval/tool nodes (fan-out with reducers) → synthesis node → reflection node (conditional edge loops back if quality is low). Compile with a Postgres checkpointer for durability, resume, and audit; key runs by thread_id for memory and multi-session continuation. Add interrupt_before on consequential nodes for human approval; bound cycles with recursion_limit and step/token budgets (Module 08). Wrap external tools as MCP servers (Module 09) and retrievers as LlamaIndex query engines (Module 11). Add tracing/observability (Module 14) over the event stream, an eval suite over graph trajectories gating deploys, and per-tenant state isolation. Stream state/events to the UI for transparency. The graph is the auditable spec; durability + HITL + explicit routing are what make it production-grade.

14 · In short, and what comes next

Use LangGraph when:

  • The workflow loops, or the next step depends on the last result.
  • A person must approve a step before it runs.
  • The run must survive a restart and continue where it stopped.
  • You need to see which steps ran, in what order, after the fact.

Do not use it when:

  • The steps are fixed and always run in the same order. Use a chain.
  • One prompt, one answer. Call the model directly.
  • You have not written the loop by hand yet. Module 08 first.
🔑
The one idea to remember

The state is the whole point. Nodes are functions and edges are rules, but the reason a graph can loop, branch, pause and recover is that one object holds where the run has got to, and the checkpointer writes it down after every step.
