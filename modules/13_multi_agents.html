Agents / 13 · Multi-Agent Systems

1 · What you already know

From module 08 you have one agent: a loop, a tool registry, a step limit. From module 12 you can express that loop as a graph with explicit edges and shared state.

This page is about splitting one agent into several, and about the fact that doing so is usually the wrong answer.

2 · What breaks now

One agent has grown to cover research, drafting, SQL and incident triage. Its prompt is 1,400 tokens and it declares 22 tools.

Three things degrade at once, and none of them is a bug you can fix in the loop:

SymptomCause
The wrong tool is chosen22 candidates, most irrelevant to any single request
Instructions conflictSQL rules and incident rules share one prompt, and both apply always
Every request pays for every toolSchemas are sent whether or not the request could use them
One credential set for everythingThe process holds the union of every permission any path needs

The first three are solved by routing: one cheap classification call, then a smaller prompt. The fourth is the one that needs real separation, and it is the honest reason to build a supervisor.

3 · Simple breakdown - a supervisor vs one agent with every tool

A A supervisor topology

What it is. A supervisor is an agent whose tools are other agents. It reads a request, routes it to a worker, collects the result, and decides what happens next.

Core purpose. It keeps each worker's prompt and tool list small, and lets workers hold different credentials or run on different models.

Execution model.

Architecture under the hood. A supervisor node, one worker per specialism with its own tools, and a shared state object or a message contract for what a worker returns.

State handling. In LangGraph, one state object that the supervisor and workers read and write. Each worker may also keep its own subgraph state.

Limitations and advanced features. Every routing decision and every handoff is another model call, so cost and latency grow with the number of hops. Handoff loops and diffuse responsibility are failure modes a single agent does not have.

B One agent with every tool

What it is. A single loop with every tool declared to it, and one system prompt covering every case it may encounter.

Core purpose. It answers any request the tool set can reach, with no routing and no coordination.

Execution model. One agent loop. The model picks from the whole tool list on every step.

Architecture under the hood. One prompt, one registry, one loop. Nothing coordinates because there is nothing to coordinate.

State handling. One message list for the whole run.

Limitations and advanced features. Tool choice degrades as the list grows, and every request pays for every schema. It cannot give two request types different credentials.

The core differences

A supervisor topologyOne agent with every tool
Model calls per requestOne per step, plus one per routing decisionOne per step
Prompt sizeSmall, per workerGrows with every tool and rule added
Different credentials per pathYesNo, one identity for the run

In short - which one to choose

  • Use one agent until it is measurably struggling. This is the honest default, and it is where most production systems should stop.
  • Use a supervisor when workers need genuinely different tools, different credentials, or different models.
  • Use a pipeline when the order is fixed and known, because then no model needs to decide the routing at all.

4 · Without the technology

Before reaching for multiple agents, narrow the one you have.

Measured over 40 requests in the course project.

Routing cut cost by 49% at equal accuracy. The supervisor cost three times as much and answered no better.

What routing cannot do: give the billing path a credential the docs path does not have, run two paths at once, or let a worker use a different model. Those are what a supervisor buys.

5 · Runtime mechanics

One supervised request, in order:

  1. The supervisor reads the request and the results collected so far.
  2. It decides which worker should act next, or that the request is finished.
  3. That worker runs its own loop, with its own tools, prompt and step limit.
  4. It returns a result and a status - answered, refused, or stopped at its limit.
  5. The supervisor merges that into shared state and returns to step 1.

Steps 1 and 2 are a model call every time round. A supervisor with three workers and two hops each is seven model calls before any work happens, which is where the cost in section 4 came from.

6 · The components, one at a time

The supervisor

Decides who acts next and when the request is finished. Give it no domain tools. Its step budget bounds the number of hops.

The worker

An ordinary agent with a narrow tool set, its own prompt, and its own step limit. A worker that loops must not be able to exhaust the supervisor's budget.

The handoff

What crosses between agents. This is the expensive decision.

Every handoff is tokens one agent produced and another must read. Summarise before handing off.

The status contract

A worker that returns only text cannot be distinguished from one that failed politely. The supervisor must be able to branch on the status.

7 · State and data flow

  1. What data is state? The shared message list, the collected results, and the next routing decision.
  2. Who writes each field? The supervisor writes next; each worker appends its own result.
  3. Who reads each field? Every node sees the whole state. A worker's internal loop state is private to it.
  4. Replaced, appended or merged? Messages append via add_messages; next is replaced every hop.
  5. What reducer controls merging? add_messages for the transcript, and operator.add for accumulating findings from parallel workers.
  6. Is it only in process memory? Without a checkpointer, yes.
  7. Is it checkpointed? With one, after every superstep - which is what lets a long-running worker resume.
  8. Is it in a database? The checkpoint store, and the trace.
  9. How long does it survive? The request, plus whatever the checkpointer retains.
  10. What thread, user or key retrieves it again? The thread_id, which every worker must inherit - and the run id, which every trace span must share.

Row 10 has a practical consequence. A worker that generates its own run id produces a trace showing unrelated runs, and you cannot then answer what one request did.

8 · Trace

Count the supervisor rows: three of the six model calls did no work. They decided who should work. That is the coordination overhead, and it is the number to quote when someone proposes a fourth agent.

Compare the routed single agent on the same request: 3.8 model calls, 2.9 seconds, $0.0021.

9 · Break it

Remove the hop bound and give the workers overlapping responsibilities.

Thirty-eight hops, 76 model calls, no answer. Neither agent is broken: each is doing exactly what its prompt says, and the supervisor is routing correctly according to what it was told.

This is a handoff loop, and it is a failure mode a single agent cannot have. Note also that a repeat check on the tool calls would not catch it: every hop makes different calls.

10 · Fix it

1 · Bound the hops, at the supervisor. This is the one that must exist.

2 · Give exactly one agent the authority to finish. Workers propose; only the supervisor ends the request. Two agents that can each send work back to the other have no termination condition.

3 · Detect the oscillation, not just the repeat. The signature is the worker sequence, not the tool calls.

4 · Name a finalizer. One agent owns the final answer, so quality does not become nobody's responsibility. Diffuse ownership is the quieter version of this bug: the request completes, and the output is worse than any single agent would have produced.

13 · Interview preparation

Beginner  What is a multi-agent system and why use one? ›

Several specialized agents, each with its own role, prompt, and tools, coordinated to solve a complex task. Benefits: specialization (focused agents make better decisions than one bloated agent), modularity (test/iterate per agent), and parallelism. Costs: coordination overhead, latency, more LLM calls, and new failure modes - so use it only when one agent genuinely can't cope.

Beginner  What is the supervisor pattern? ›

A manager agent that receives the task, delegates subtasks to specialized worker agents, collects their results, and decides the next step until done. It's the dominant production topology because control is centralized and easy to reason about - a star shape rather than a chaotic mesh.

Intermediate  Supervisor vs network (handoff) - tradeoffs? ›

Supervisor centralizes routing: predictable, auditable, easy to bound, but the supervisor is a bottleneck and single point of decision. Network lets any agent hand off to any peer: flexible for fluid workflows, but harder to reason about, easier to loop, and trickier to bound and debug. Most production systems pick supervisor for control; use network when the workflow genuinely needs peer-to-peer transfers.

Intermediate  What's the hard part of a handoff? ›

Deciding what context to transfer. Too little and the receiving agent lacks the information to act; too much and you pollute its prompt and pay for excess tokens. The right approach passes a concise structured brief (the subtask + the few relevant facts/pointers to shared state), not the entire conversation transcript.

Senior  How do you decide between one agent and a multi-agent system? ›

Default to one well-scoped agent. Split into multiple agents when: roles are genuinely distinct (different tools/expertise), the single agent is measurably failing (wrong tool choices, context bloat, lost thread on evals), you need true parallelism, or you need different models/permissions per role. Always validate with an eval that the multi-agent version beats the single-agent baseline on success rate and justifies the extra cost/latency. Complexity must earn its place.

Senior  How do you prevent and detect handoff loops? ›

Prevent: prefer a supervisor topology (bounded paths) over a mesh; give the supervisor sole authority to terminate; set a hard cap on total hops (recursion_limit). Detect: track the handoff sequence and flag repeats (A→B→A→B); monitor messages-per-task and alert on outliers; in the trace, watch for no net progress in shared state across hops. On detection, force termination/escalation and feed the case into the eval suite.

Staff · design  Design a multi-agent customer-support system with safety and observability. ›

Topology: a supervisor/triage agent routes to specialists (billing, technical, account) - bounded star, not a mesh. Build on LangGraph for explicit routing, durable checkpoints, and per-agent attribution. Each specialist gets least-privilege tools via MCP (Module 09) and RAG over its domain docs (07/11). Handoffs carry a structured brief + shared-state pointers, capped by recursion_limit with the supervisor able to escalate to a human. Safety: human-in-the-loop (Module 12) before refunds/account changes; guardrails on inputs/outputs (Module 14). Observability: trace every transition, attribute success/failure per agent, track handoff correctness and tokens/task. Eval: golden conversations gating deploys; compare against a single-agent baseline to justify the architecture. A designated finalizer owns the user-facing response. The deliverables that matter: bounded coordination, least privilege, human gates on consequential actions, and per-agent traceability.

14 · In short, and what comes next

Remember these six:

  • Start with one agent. Split only when it is measurably struggling.
  • Routing gives most of the benefit for one cheap call and no coordination.
  • A supervisor earns its cost on different tools, credentials or models - not on tidiness.
  • Every hop is a model call that does no work. Count them before adding an agent.
  • Bound the hops, and let exactly one agent finish the request.
  • A handoff carries a brief and pointers, never the whole transcript.
🔑
The one idea to remember

Multi-agent buys specialisation and pays in coordination. The measurement in section 4 is the argument: routing cut cost by half at equal accuracy, and the supervisor tripled it for nothing. Only pay when a worker needs authority the others must not have.
