Foundations of LLMs

A language model does one thing: given some text, it produces a probability for every possible next token. Everything else - chat, summarising, tool calling, agents - is that one operation, run in a loop, with the output fed back in.

⏱ Study + practice · 8–12 h Difficulty · Beginner Prereq · basic Python

1 · What you already know

You have used a chat model. You typed a question and got an answer back, one word at a time.

That is the whole surface. This page is about what happened underneath it, at the level you need in order to debug it later.

2 · What breaks now

Without knowing the mechanics, five ordinary things stay confusing:

What you seeWhat you cannot explain yet
The same prompt gives a different answer each timeWhere the randomness comes from, and how to switch it off
A long document is rejectedWhat the limit counts, and why it is not characters
The bill is higher than expectedWhat you are actually charged for
The model states a false fact confidentlyWhy it has no way to know it is wrong
It answers in the wrong language or formatWhich part of the input it is really conditioned on

All five have the same answer, and it is mechanical. The model computes a probability distribution over the next token, and something picks one token from it. That sentence explains every row in the table.

3 · Simple breakdown - pre-training vs fine-tuning

A Pre-training

Basic level

What it is. Pre-training is the process that creates a base language model by adjusting billions of numerical parameters so the model predicts the next token in a very large collection of text.

Core purpose. It produces a model that has learned the statistical structure of language and a large amount of world knowledge, without being aimed at any particular task.

Execution model.

Intermediate level

Architecture under the hood. A tokenizer, an embedding table, a stack of transformer layers, and an output layer that produces one logit per token in the vocabulary. Training runs on thousands of GPUs for weeks, using an optimizer such as AdamW, and costs millions of dollars. Module 02 opens the transformer layer itself.

State handling. The learned state is the parameters - the weights. They are written once during training and then frozen. During use the model holds no state at all between requests.

Limitations and advanced features. The knowledge is fixed at the training cut-off and cannot be updated without retraining. The base model completes text rather than following instructions, so it is rarely used directly. It has no notion of truth, only of which token is statistically likely.

B Fine-tuning

Basic level

What it is. Fine-tuning continues training an already pre-trained model on a much smaller, task-specific dataset, changing the weights so the model behaves differently.

Core purpose. It changes behaviour, format or tone - not knowledge. It is how a base model becomes an instruction-following chat model.

Execution model.

Intermediate level

Architecture under the hood. The same network, the same loop. Full fine-tuning updates every parameter and needs memory for the weights, the gradients and the optimizer state. LoRA instead freezes the original weights and trains a small pair of low-rank matrices per layer, which is why a 7B model can be fine-tuned on one consumer GPU.

State handling. The output is a new set of weights, or with LoRA a small adapter file of a few hundred megabytes that is loaded on top of the frozen base.

Limitations and advanced features. It is a poor way to add facts: the model may repeat the new data's style while still getting details wrong, and every update needs another training run. Too many steps on a narrow dataset cause catastrophic forgetting, where general ability degrades. Variants include instruction tuning, preference tuning such as DPO, and RLHF.

The core differences

Pre-trainingFine-tuning
Workflow design One very long run over a general corpus, from random starting weights. Weeks, thousands of GPUs. A short run over a curated dataset, starting from finished weights. Hours to days, often one GPU.
Error recovery Checkpoints every few hours; a failed run resumes from the last one. A bad data mix is only visible after the fact. Cheap enough to discard and re-run. The real risk is silent quality loss on tasks outside the training set, caught only by evaluation.
Architectural paradigm Builds the capability. Produces a base model that completes text. Redirects an existing capability. Produces a model that behaves a particular way.

In short - which one applies to you

Pre-training is relevant when:

  • You are choosing a base model and need to know what its cut-off and training mix imply.
  • You are explaining in an interview why a model cannot know about last week.
  • Almost never as something you will run yourself.

Fine-tune when:

  • You need a consistent output format or tone that prompting cannot hold.
  • You have hundreds to thousands of good examples of the behaviour you want.
  • A smaller fine-tuned model would be cheaper than a large prompted one at your volume.

Do neither when:

  • You want the model to know your documents. That is retrieval - module 06.
  • You have not tried a better prompt and a few examples first.
  • Your data changes weekly. Retraining cannot keep up; retrieval can.

4 · Without the technology

Before neural language models, next-word prediction was done by counting. An n-gram model counts how often each word follows the two before it.

This is a real language model. It also fails immediately: a word pair it never saw returns nothing, and it cannot tell that "the cat sat" and "a cat sat" are nearly the same context. A neural model replaces the lookup table with a function that maps similar contexts to similar predictions. That is the whole upgrade.

5 · Runtime mechanics

What happens when you send a prompt. Nine steps.

  1. The tokenizer splits your text into tokens - short word pieces.
  2. Each token is looked up in the vocabulary and becomes an integer token id.
  3. Each id indexes an embedding table, producing a vector of a few thousand numbers.
  4. Position information is added, so the model can tell word order.
  5. The vectors pass through the stack of transformer layers.
  6. The final layer produces one logit per vocabulary entry - a raw score, roughly 50,000 to 200,000 of them.
  7. Softmax turns those scores into probabilities that sum to 1.
  8. A sampling rule picks one token from that distribution.
  9. The chosen token is appended to the input and steps 3 to 8 run again.

Step 8 is the only place randomness enters. Steps 1 to 7 are deterministic: the same input produces the same probabilities every time.

6 · The components, one at a time

1 · Token

The unit the model reads. Roughly ¾ of a word in English. Common words are one token; rare words and most non-English text split into several.

2 · Tokenizer and vocabulary

A fixed table built before training, usually by byte-pair encoding: start from characters, repeatedly merge the most frequent adjacent pair, stop at a set size. The model can only ever read tokens in that table.

3 · Embedding

A lookup table with one vector per vocabulary entry. Token id 5341 fetches row 5341. The vectors are learned during training, so tokens used in similar contexts end up with similar vectors.

4 · Parameter and layer

A parameter is one number the model learned. A layer is one block of the network. "7B" means seven billion parameters, which at 16-bit precision is about 14 GB just to hold the weights.

5 · Logit

The raw score the final layer gives each vocabulary entry. Unbounded, can be negative, and only meaningful relative to the other logits in the same step.

6 · Probability and softmax

Softmax exponentiates the logits and divides by their sum, turning them into positive numbers that add to 1.

7 · Temperature

Logits are divided by the temperature before softmax. Below 1 sharpens the distribution; above 1 flattens it. temperature=0 means "always take the highest", which is the only setting that makes output repeatable.

8 · Sampling: greedy, top-k, top-p

The rule that picks one token from the distribution.

RuleWhat it doesUse when
GreedyAlways the highest probabilityExtraction, classification, anything you will parse
Top-kKeep the k most likely, sample among themSimple control over variety
Top-p (nucleus)Keep the smallest set whose probabilities sum to pThe usual default for open-ended text

9 · Context window

The maximum number of tokens the model can attend to at once - prompt plus generated output together. It is a hard architectural limit, not a setting.

10 · Inference versus training

Training changes the weights. Inference does not. Every request you send starts from the same frozen weights and the model remembers nothing from the last one. Anything resembling memory is text your application re-sent.

7 · State and data flow

1 · What data is state?The token sequence so far. Nothing else survives between steps.
2 · Who writes it?You write the prompt; the sampler appends one token per step.
3 · Who reads it?Every layer, on every step, reads the whole sequence.
4 · Replaced, appended or merged?Appended. Tokens are never edited or removed once generated.
5 · What controls merging?Nothing - it is a list that only grows.
6 · Only in memory?Yes, in the serving process, for the length of one request.
7 · Cached?The KV cache stores each layer's intermediate values so earlier tokens are not recomputed. It is an optimisation, not memory.
8 · In a database?Never, unless your application puts it there.
9 · How long does it survive?Until the response finishes.
10 · What key retrieves it again?None. The next request starts empty.

9 · Break it

Feed the model more tokens than it can hold.

That one raises. The dangerous version does not - a serving layer that silently drops the oldest tokens to make the request fit.

Now the request succeeds and the answer is confidently wrong, because the instructions were at the start of the prompt and have just been deleted.

10 · Fix it

Count before you send, and never let the trim decide what matters.

The system prompt and the question are never candidates for removal. History is dropped oldest-first, and running out raises instead of silently truncating. Deciding what to drop is your job, and it is the subject of module 06.

13 · Interview preparation

Beginner  What is an LLM, in one sentence? ›

A neural network (transformer) trained to predict the next token in a sequence; by sampling tokens repeatedly it generates coherent text. It models the statistical structure of language, not a database of facts.

Beginner  What is a token and why use tokens instead of words? ›

A token is a subword unit produced by a tokenizer (e.g., BPE). Subwords give a fixed-size vocabulary that handles any word - common words are one token, rare/novel words split into pieces - avoiding both a huge word vocabulary and a too-granular character model.

Intermediate  Explain temperature, top-k, and top-p. ›

Temperature scales logits before softmax - lower sharpens toward the top token, higher flattens for diversity. Top-k restricts sampling to the k highest-probability tokens. Top-p (nucleus) restricts to the smallest set whose cumulative probability ≥ p, adapting to model confidence. Use temperature 0 for deterministic tasks; top-p ≈ 0.9 with moderate temperature for natural generation.

Intermediate  Why is generating long outputs slow and expensive? ›

Generation is autoregressive. After a full-prompt prefill, ordinary KV-cached decoding performs roughly one model step per output token, passing the newly sampled token ID directly to the model while reusing cached attention keys and values from earlier positions. Output work still grows with generated length, and the KV cache consumes memory that grows with the active sequence.

Senior  A model gives confidently wrong answers about your internal docs. Diagnose and fix. ›

The model has no knowledge of private data - it's hallucinating plausible text. Fix by grounding: retrieve relevant internal documents and inject them into context (RAG, End-to-End), instruct the model to answer only from provided context and cite sources, and add an evaluation harness to measure faithfulness. Lower temperature and add a "say 'I don't know'" instruction to reduce fabrication.

Senior  How do you make LLM features testable in CI given non-determinism? ›

Pin temperature to 0; assert on properties not exact strings (schema validity, presence of required fields, no PII, factuality against references); use an LLM-as-judge or rubric eval for open-ended outputs; snapshot-test prompts and version them; run a golden-dataset eval on every prompt change to catch regressions.

Staff · design  Design a multi-tenant LLM gateway for an enterprise. ›

Single entry point that all teams call. Responsibilities: auth & tenancy (API keys per team, quotas), routing (model selection by task/cost, fallback chains), safety (PII redaction, input/output guardrails), observability (per-tenant token/cost metrics, tracing, prompt logging with retention policy), resilience (retries, circuit breakers, caching of identical/cacheable prompts), and cost control (budgets, alerts). Keep it stateless and horizontally scalable; push prompt templates to a versioned registry. This is the spine of the Enterprise GenAI Platform capstone.

14 · In short, and what comes next

Remember these five:

  • The model outputs a probability for every token in its vocabulary, every step.
  • Sampling is the only source of randomness. temperature=0 removes it.
  • The context window counts tokens, not words, and includes the answer.
  • The weights are frozen at inference. The model remembers nothing between requests.
  • Fine-tuning changes behaviour. Retrieval adds knowledge. They are not alternatives.

The one idea to remember

Next-token prediction, in a loop, with the output fed back in. Chat, summarising, tool calling and agents are all that one operation wrapped in application code.
