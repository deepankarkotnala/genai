20 questions
01What is an AI agent?agentdefinitionarchitecture＋
Strong answer

An agent is a system in which a model observes state, chooses an action—often a tool call—receives the result and repeats until a goal or stop condition is reached. The production system also includes orchestration, memory, policy, validation and telemetry. A single LLM call that returns JSON is better described as a bounded model task, not automatically an autonomous agent.

30-second version

An agent is a controlled decision loop around a model: observe, decide, act, validate and stop. The surrounding software makes it safe and reliable.

Likely follow-up: Would you call a one-shot resume screener an agent?
02When should you use an agent instead of a fixed workflow?agentworkflowtrade-off＋
Strong answer

Use an agent when the next step genuinely depends on observations and cannot be enumerated economically—for example exploratory research across several tools. Use a workflow when the sequence is known, compliance requires predictability, or the action is high consequence. Many strong systems use a deterministic graph with agentic choice only inside bounded nodes.

30-second version

Use workflows for known paths and agents for dynamic decisions. Keep the agentic surface as small as the problem allows.

Likely follow-up: Give a case where an agent is unnecessary complexity.
03Explain the ReAct pattern.reacttoolsloop＋
Strong answer

ReAct alternates reasoning about the current state with an action such as calling a search or database tool, then uses the observation to decide the next step. In production I implement the loop through structured tool calls rather than parsing free-form text, cap iterations and cost, and validate every action.

30-second version

ReAct is reason, act, observe, repeat. Production versions use structured calls, budgets and policy checks.

Likely follow-up: What are common ReAct failure modes?
04How do you design a good tool for an agent?toolssecurityapi-design＋
Strong answer

A good tool has a narrow verb, typed input, clear description, deterministic authorization and predictable errors. It returns only the data needed, is idempotent when possible, exposes timeouts and never lets model text become code or raw SQL. High-impact tools support dry-run, confirmation or human approval.

30-second version

Make tools small, typed and least-privilege. The server authorizes and executes them; the model only proposes a call.

Likely follow-up: How would you design a tool that sends an email?
05How should multiple agents communicate?multi-agentorchestrationstate＋
Strong answer

I prefer explicit typed messages or shared workflow state over unrestricted natural-language chatter. A supervisor or graph owns routing, each specialist has a narrow role and tool set, and artifacts are stored with provenance. Multi-agent designs need clear termination, conflict resolution, budgets and an explanation of why separate agents outperform simpler modules.

30-second version

Use typed handoffs and an orchestrator, not an unbounded group chat. Separate agents only when roles or permissions truly differ.

Likely follow-up: When does a multi-agent system become counterproductive?
06Why is LangGraph useful for production agents?langgraphstateworkflow＋
Strong answer

LangGraph represents execution as state, nodes and conditional edges, which makes loops, retries, checkpoints, parallel branches and human interrupts explicit. It is useful when an agent must be resumed or audited and when routing is more complex than a simple chain. The framework does not replace good state design or security policy.

30-second version

LangGraph makes agent control flow and durable state explicit, so complex loops and human checkpoints are easier to test and operate.

Likely follow-up: What belongs in graph state, and what should stay outside it?
07What is the Model Context Protocol (MCP)?mcpintegrationsecurity＋
Strong answer

MCP is a protocol for exposing tools, resources and prompt-like capabilities to model applications through a consistent client-server interface. It can reduce custom integration work and make capabilities discoverable, but it does not automatically solve authorization, tenancy or trust. The host must approve servers and tools and validate every invocation.

30-second version

MCP standardizes how AI applications discover and use external capabilities. It improves interoperability, not security by default.

Likely follow-up: How would you secure an enterprise MCP server?
08How do you design memory for an agent?memoryprivacyretrieval＋
Strong answer

I separate short-term execution state, conversation history, user profile and long-term retrieved memory. Each has a different retention, privacy and relevance policy. I summarize or retrieve selectively rather than replaying everything, store provenance, and let users inspect or delete persistent memory.

30-second version

Memory is not one chat transcript. Separate working state from durable, permissioned knowledge and retrieve only what is relevant.

Likely follow-up: How do you prevent stale or incorrect memory from compounding?
09How do you handle tool failures, retries and duplicate actions?reliabilityidempotencytools＋
Strong answer

Classify errors as transient, permanent or policy-related. Retry only transient failures with bounded exponential backoff and jitter, use timeouts and circuit breakers, and attach an idempotency key to side-effecting calls. Persist execution state so a resume does not repeat an already completed action.

30-second version

Retry only safe transient failures, make side effects idempotent, and checkpoint state before and after tools.

Likely follow-up: What if a payment tool times out after the provider accepted it?
10Where should human-in-the-loop controls appear?human-in-loopsafetyux＋
Strong answer

Use a human checkpoint for high-impact, irreversible, low-confidence or policy-sensitive actions. Present the proposed action, evidence, uncertainty and editable fields—not only an approve button. The workflow must handle delays, rejection and escalation, and the decision should be audited.

30-second version

Put humans before consequential actions and give them evidence and control. Design the pause and rejection path as first-class workflow states.

Likely follow-up: How do you avoid approval fatigue?

Middleware, Identity and Interoperability

Ten questions on the layer around the agent: where policy is enforced, who is acting, and how independent agent systems interoperate. These come up in production and system-design rounds for agentic roles far more often than protocol trivia does.

11Where does middleware belong in an agentic system?middlewarearchitectureboundaries＋
Strong answer

Middleware is not one layer; it is a pattern applied at every boundary a request crosses. At the gateway: TLS, WAF and coarse rate limits. In HTTP middleware: token validation, principal and tenant resolution, correlation IDs, request validation. In the agent runtime: context enrichment, model routing, tool allowlists, retries, budgets, guardrails and approval gates. At the tool or MCP server: argument validation, the real authorization decision, idempotency and audit. In the database: row-level tenant isolation and constraints. I place a concern at the layer where it can be enforced completely and cannot be bypassed.

Trade-off / failure mode. Concentrating everything in one layer is simpler to reason about but creates a single bypass. The common failure is putting authorization only in the agent runtime: it looks like it works, then a second client, a new code path or a prompt injection reaches the tool directly and nothing stops it.

30-second version

Middleware is cross-cutting policy applied at boundaries. Gateway, HTTP layer, agent runtime, tool server and database each own the checks they can enforce completely — and the important ones are enforced more than once.

Likely follow-up: Which of those checks would you deliberately duplicate, and why is duplication not just waste?
12What is the difference between API middleware and agent middleware?middlewareagenthttp＋
Strong answer

They run at different granularities. HTTP middleware runs once per request, before any application logic, and answers request-level questions: is this token valid, which tenant is this, what is the correlation ID, is the payload well-formed. Agent middleware runs around every model call and every tool call inside a single request, and answers decision-level questions: which tools may this role even see, what context should be injected, has this run exceeded its token budget, does this action need human approval. Tool middleware is a third layer that protects the systems the agent can affect.

Trade-off / failure mode. The two cannot be collapsed, because one HTTP request can produce dozens of model and tool calls. Enforcing budgets or approval gates at the HTTP layer means checking once at the start, when the run has spent nothing and proposed no action — so a runaway loop passes the check and then costs five figures.

30-second version

HTTP middleware controls requests entering the application. Agent middleware controls decisions and actions inside the agent loop. One request, many agent decisions — so they need different checks at different granularities.

Likely follow-up: Where would you enforce a per-tenant cost cap, and what happens when it is hit mid-run?
13What is the difference between authentication and authorization?authenticationauthorizationsecurity＋
Strong answer

Authentication establishes who is making the call and proves it — a verified token, a session, a client certificate. Authorization decides whether that established identity may perform this specific operation on this specific resource. In an agentic system the interesting part is that "who" is layered: the end user, the application, the agent's own service identity, and the tool's credential can all differ, and the authorization decision may depend on several of them at once. A common design is to authenticate the user at the edge, carry the acting user as a verifiable assertion, and let each downstream service make its own authorization decision.

Trade-off / failure mode. They fail differently, which is why conflating them is dangerous. A broken authentication check lets a stranger in and is usually noisy. A broken authorization check lets a legitimate, fully authenticated user do something they should not — and looks completely normal in the logs.

30-second version

Authentication is "who are you, and can you prove it". Authorization is "may you do this particular thing to this particular resource". Agents make the first question layered, because the user, the app, the agent and the tool are four different identities.

Likely follow-up: A scheduled agent runs at 2 a.m. with no user present. Whose authority is it using?
14Why is a JWT not a complete authentication system?jwttokenssecurity＋
Strong answer

A JWT is a token format — a compact, usually signed container for claims such as issuer, audience, subject and expiry. It is what an authentication system hands you and what an authorization layer reads. Choosing JWTs decides nothing about how users prove identity, how sessions are established, how credentials are revoked, how keys are rotated, or what anyone is permitted to do. Those are the actual authentication and authorization architecture; the token is the transport for its output.

Trade-off / failure mode. The property that makes JWTs attractive — stateless verification without a lookup — is also the one that bites. A stateless token cannot be revoked before it expires, so a compromised or de-provisioned session stays valid for its whole lifetime. That is why short expiry plus refresh, or a denylist for high-impact tokens, is part of any serious design. It is also worth saying that a signed payload is encoded, not encrypted: anyone holding the token can read the claims.

30-second version

A JWT is a claims format, not a login system and not a policy. It carries the result of authentication; it does not perform it, and it says nothing about what the holder may do.

Likely follow-up: How would you revoke access immediately when a user is de-provisioned?
15What must you check when validating a JWT?jwtvalidationsecurity＋
Strong answer

Signature, against a key selected by the header's key id from a trusted key set — not from anything the token supplies. Algorithm, restricted to an explicit server-side allowlist, never taken from the token header and never the unsecured "none". Issuer, equal to the expected authorization server. Audience, equal to this service's own identifier. Expiry and not-before, with only small clock leeway. And the key material must come from a source you trust and refresh, so rotation does not require a deploy. I use a maintained library for all of it rather than hand-rolling verification.

Trade-off / failure mode. Each omission is a real class of breach: letting the token pick its algorithm enables algorithm-confusion and "none" attacks; skipping audience lets a token minted for another service be replayed against yours; skipping issuer accepts a valid signature from the wrong authority. The subtlest one is decoding without verifying "just for logging" — the unverified sub or tenant then leaks into a policy decision later.

30-second version

Signature with a key chosen by key id from a trusted key set, an explicit algorithm allowlist, expected issuer, this service's audience, and expiry and not-before. Never trust the token to tell you how to verify it.

Likely follow-up: Key rotation starts failing signatures in production. Walk me through what you check.
16How do you avoid confused-deputy and token-forwarding problems?oauthconfused-deputydelegation＋
Strong answer

A confused deputy is a trusted component that uses its own or a caller's authority to do something the real requester was not entitled to. In agentic systems the classic setup is forwarding the user's inbound access token to every tool, MCP server and remote agent — each of which now holds the user's full authority for everything, not just the one operation. The fix is token exchange at each boundary: mint a new, short-lived, audience-restricted credential scoped to exactly the downstream operation, and carry the acting user as an explicit assertion rather than by handing over their credential. The agent authenticates as itself; the user is data, not a bearer token.

Trade-off / failure mode. Exchange costs a round trip and real infrastructure — an authorization server, per-downstream audiences, key management — which is why teams skip it and forward the token instead. The failure is quiet: nothing breaks, the audit log shows the user as the caller everywhere, and one compromised or malicious tool can act as that user against every other system.

30-second version

Never forward the inbound token. Exchange it at each boundary for a short-lived, audience-restricted credential scoped to that one downstream, and pass the acting user as a verifiable assertion instead of as a bearer credential.

Likely follow-up: A third-party MCP server needs to read one customer's orders. What exactly does it receive?
17What is the difference between MCP and A2A?mcpa2ainteroperability＋
Strong answer

They standardise different boundaries and are complementary. MCP connects an AI application to tools, resources and context: a host runs a client per server, the server owns access to a system and exposes narrow capabilities. A2A connects independent agent systems — often built by different teams or vendors — so they can discover each other, declare capabilities, delegate tasks and exchange messages and artifacts. My test: if the thing on the other side is a capability I call and get a result from, that is the MCP shape. If it is an autonomous peer that accepts a task, works on it over time and reports back, that is the A2A shape. Middleware is neither; it enforces policy around both.

Trade-off / failure mode. Reaching for A2A where a tool would do adds a network boundary, an availability dependency, a trust domain and a much harder debugging story for no benefit. The opposite mistake is modelling a genuinely autonomous, long-running, separately-owned system as a synchronous tool call — which then times out, retries and duplicates work.

30-second version

MCP standardises the agent-to-tool boundary; A2A standardises the agent-to-agent boundary. Capability you call versus peer you delegate to. They are complementary, and neither provides the security policy around them.

Likely follow-up: A remote agent declares a capability it does not really have. How does your system find out?
18How do you secure an MCP tool call?mcpsecuritytools＋
Strong answer

In order: the host approves the server and the specific tools, so capability is opt-in rather than discovered-and-trusted. The agent runtime shows the model only the tools this role and tenant may use. At the server, before anything executes: check the caller's permission for this operation, validate arguments against a schema, resolve the resource together with the tenant so another tenant's identifier simply does not exist, enforce an idempotency key on writes, bound the result size, and execute with a least-privilege credential belonging to that tool rather than a shared service account. Then record an audit event that names the user, the tenant, the tool, the arguments and the outcome. Treat everything the tool returns as untrusted content.

Trade-off / failure mode. The tempting shortcut is to treat the runtime allowlist as the security boundary — it is not, because a prompt injection, a bug or a second client routes around it. The check that must never be skipped is the server-side authorization: if removing the agent's allowlist would let a user do something they should not, the design is one bug away from a breach.

30-second version

Explicit host approval of servers and tools, narrow allowlists in the runtime, and the real decision at the server: permission, schema, tenant-scoped resolution, idempotency, least-privilege credential and audit. The agent layer is a control, not a boundary.

Likely follow-up: An MCP server ships a new tool in a minor version. What in your pipeline notices?
19How do you enforce multi-tenant isolation in an agent platform?multi-tenantisolationcaching＋
Strong answer

Tenant comes from verified token claims, never from a request body, header or query parameter the caller controls, and it is pinned to the request context at the edge. From there it must be carried into every downstream decision: retrieval filters applied at query time rather than after ranking, row-level isolation in the database, tenant in every cache key alongside user entitlements and model version, per-tenant rate limits and cost budgets, tenant-scoped tool credentials, and tenant in every trace and audit record. Isolation is not a layer in the stack — it cuts across all of them, because any one of them can leak.

Trade-off / failure mode. Full per-tenant isolation — separate indexes, separate caches, separate credentials — is the safest and the most expensive, and it scales badly past a few hundred tenants; shared infrastructure with tenant-scoped keys is cheaper and one missing key away from disclosure. The two places it usually breaks in agent systems are the semantic or prompt cache, where a key that omits tenant serves one customer's answer to another, and post-filtering of retrieval results, where the data has already been read before the filter runs.

30-second version

Tenant from verified claims, pinned at the edge, and carried into retrieval filters, database rows, cache keys, budgets, tool credentials and audit. It is a cross-cutting property, not a layer — and caches and retrieval are where it usually leaks.

Likely follow-up: Your semantic cache doubled the hit rate after a refactor. Why might that be bad news?
20How do you design observability without leaking sensitive data?observabilityprivacytracing＋
Strong answer

Start by treating the trace store as a data store with the same classification, retention and access obligations as a database — because that is what it is. Redact at the emitting layer, not in a downstream pipeline: log prompt hashes, token counts, shapes, tool names, latency, outcome and decision reasons rather than raw content, and redact tool arguments field by field. Keep a separate immutable audit stream that records who caused what — user, tenant, agent, tool, policy decision, result — which is what you actually need during an incident. Sample verbose content narrowly, with consent and short retention, when you genuinely need it for debugging or evaluation.

Trade-off / failure mode. Aggressive redaction makes real debugging harder: without the prompt you often cannot reproduce why the model chose a tool. The honest answer is to buy back that ability with structure — decision logs, tool-call traces and evaluation datasets built from consented samples — rather than by retaining everything. The failure mode when you do not is that your tracing tool quietly becomes the largest unencrypted store of customer data you own, discovered during an audit rather than a design review.

30-second version

Traces are a data store. Redact at emission, log shapes and decisions rather than content, keep a separate immutable audit trail of who caused what, and apply real retention and access control. Buy back debuggability with structured decision logs, not with raw prompts.

Likely follow-up: Production returns a wrong answer and you have no prompts stored. How do you debug it?
