Mock interview rounds

The topic pages teach one answer at a time. A real round is three questions deep on one thread, where each follow-up is chosen because of what you just said. This page is the rehearsal: five rounds, timed, in the order they are usually scheduled.

5 rounds · 11 questionsUse a timerSay answers aloud
⏱
How to run these

Set a timer for the round, answer out loud without opening anything, and only then read what the interviewer was listening for. Recording yourself is uncomfortable and worth it — almost every weak answer is too long rather than wrong. Where a round tests a topic in depth, the link takes you to the full bank for it.

📋
The five rounds

1 · RAG debugging (20 min) → 2 · Agents (20 min) → 3 · Python coding (45 min) → 4 · System design (45 min) → 5 · Behavioural (30 min). That is roughly a real loop. Do them on separate days before doing them back to back.

11 questions
01Round 1 · "Walk me through your RAG pipeline, and where it most commonly fails."round-1rag＋
Strong answer

Two halves. Offline: load, chunk, embed, index. Online: retrieve with hybrid search, rerank, put the best few chunks in the prompt with an answer-only-from-this-context instruction, generate with citations. Then name the failure you have actually seen — usually retrieval, and usually chunking: a table split down the middle, or chunks so large the relevant sentence drowns.

30-second version

Offline load-chunk-embed-index; online retrieve-rerank-ground-generate-cite. Most failures are retrieval, and most retrieval failures are chunking.

Listening for: whether you separate offline from online, and whether the failure you name is specific enough to have been lived through.
Red flag: Describing the happy path only, then having no answer when asked what goes wrong. Full bank: Embeddings, Vector Search & RAG.
02Round 1 · "Retrieval looks fine but the answers are still wrong. What now?"round-1debugging＋
Strong answer

If the right chunks were retrieved, it is a generation problem, so stop tuning the retriever. Three usual causes: the prompt does not force context-only answering, so the model falls back on training knowledge; too much context, and the middle gets ignored; or the chunks are there but contradict each other and nothing tells the model which to trust. Fix in that order, and confirm with a faithfulness measure rather than by reading a few answers.

30-second version

Right chunks retrieved means it is generation, not retrieval. Check the context-only instruction, then context length, then contradictions between chunks.

Listening for: that you split the pipeline and stop working on the half that is already fine.
Red flag: Reaching for a bigger model or a different embedding model before locating the stage.
03Round 1 · "How do you evaluate this, and gate deploys on it?"round-1evaluation＋
Strong answer

A small golden set of real questions with expected answers — fifty is enough to start. Measure retrieval and generation separately: recall@k for whether the evidence was found, faithfulness for whether the answer stuck to it. Run it in CI on every prompt, chunking or model change, and block the merge on a regression. Sample production traffic weekly to grow the set with questions that actually failed.

30-second version

Golden set, retrieval and generation scored separately, run in CI, merge blocked on regression, set grown from real failures.

Listening for: two metrics rather than one blended score, and evaluation wired into CI rather than run by hand.
Red flag: "We check the outputs look good." Full bank: Evaluation & LLMOps.
04Round 2 · "How does tool calling work, end to end?"round-2tool-calling＋
Strong answer

You describe the tools and their input schemas to the model. Instead of prose it returns a structured request to call one. Your code runs the real function and puts the result back into the conversation. The model then decides whether it has enough to answer or wants another call. The model never executes anything — that boundary is where validation and permissions live.

30-second version

Schemas in, structured call request out, your code executes and returns the result, model continues. It asks; your code decides whether to comply.

Listening for: whether you say out loud that the model does not run the tool. Getting this wrong undermines every safety answer after it.
Red flag: Describing the model as "calling the API itself". Full bank: Agents, Tool Use & MCP.
05Round 2 · "How do you make an agent reliable in production?"round-2reliability＋
Strong answer

Bound it: a maximum number of steps and a token or cost budget per run, so a confused agent fails cheaply instead of looping. Validate every tool call against its schema before executing. Make tools least-privilege and idempotent, so a retry cannot double-charge anyone. Timeouts and retries with backoff. Then trace every run, because an agent failure is only debuggable if you can see the steps it took.

30-second version

Step and cost ceilings, schema validation on every call, least-privilege idempotent tools, timeouts and retries, and a trace of every run.

Listening for: bounded loops and idempotency. Both mean you have watched an agent misbehave with real money or real emails.
Red flag: Answering only with prompt improvements.
06Round 3 · Return validated JSON from an LLM, retrying on schema failure.round-3coding＋
Strong answer

Define the schema as a Pydantic model and treat it as the source of truth. Request structured output, validate, and on a validation error feed the error text back for a bounded repair attempt — two tries, not a while True. Keep temperature low. Count and log the failure rate, because a rising rate is a signal about the prompt or the model, not noise to swallow.

class Extract(BaseModel):
    name: str
    amount: float

def extract(text: str, tries: int = 2) -> Extract:
    err = None
    for _ in range(tries + 1):
        raw = call_model(text, schema=Extract, repair=err, temperature=0)
        try:
            return Extract.model_validate_json(raw)
        except ValidationError as e:
            err = str(e)          # feed the reason back, once
    raise ValueError(f"schema failed after {tries} repairs: {err}")
30-second version

Pydantic schema, structured call, validate, bounded repair loop that feeds the validation error back, temperature 0, failure rate logged.

Listening for: a bounded loop and a raised error at the end. Unbounded retries against a paid API is the trap in this question.
Red flag: Parsing with a regex, or retrying forever with no logging.
07Round 3 · Compute recall@k for a retriever from labelled query → relevant-doc pairs.round-3metrics＋
Strong answer

For each query, the fraction of its relevant documents that appear in the top k; then average over queries. Say the edge cases before you are asked: a query with no labelled relevant docs is excluded rather than scored zero, and a retriever returning fewer than k results is fine. Mention that recall@k ignores order — that is what MRR or nDCG are for.

def recall_at_k(runs: dict[str, list[str]],
                truth: dict[str, set[str]], k: int) -> float:
    scores = []
    for q, relevant in truth.items():
        if not relevant:
            continue                      # nothing to recall: skip, do not score 0
        hits = len(set(runs.get(q, [])[:k]) & relevant)
        scores.append(hits / len(relevant))
    return sum(scores) / len(scores) if scores else 0.0
30-second version

Per query, relevant docs found in top k over total relevant; mean across queries; skip queries with no labels; recall@k is order-blind.

Listening for: the empty-truth case, and knowing what the metric does not capture.
Red flag: Dividing by k instead of by the number of relevant documents — that is precision@k.
08Round 3 · Make 100 LLM calls concurrently without exceeding a rate limit.round-3asyncio＋
Strong answer

A semaphore caps how many calls are in flight; gather collects them. Retry on 429 with exponential backoff plus jitter, so a batch that hits the limit does not retry in lockstep and hit it again. Do not let one failure lose the other 99 — collect exceptions rather than raising out of the gather. If the limit is tokens per minute rather than requests, a token-bucket is the honest answer, not a semaphore.

async def run_all(prompts, limit=8):
    sem = asyncio.Semaphore(limit)

    async def one(p):
        async with sem:
            for attempt in range(5):
                try:
                    return await call_model(p)
                except RateLimited:
                    await asyncio.sleep(2 ** attempt + random.random())
            raise

    return await asyncio.gather(*(one(p) for p in prompts),
                                return_exceptions=True)
30-second version

Semaphore for concurrency, gather with return_exceptions, jittered exponential backoff on 429, token-bucket if the limit is per-token.

Listening for: jitter, and not losing the whole batch to one failure.
Red flag: Firing all 100 at once and treating 429s as an unexpected error. Full bank: Python, Backend & Cloud.
09Round 4 · "Design an assistant over our internal docs that respects permissions."round-4system-design＋
Strong answer

Spend the first two minutes clarifying — sources, whose permissions, freshness, scale, latency, budget — then state requirements before drawing anything. Draw the layers in order: ingestion and sync, retrieval with permission filters applied at query time, orchestration, safety, evaluation, observability. Close by naming what you traded and what you would measure first.

30-second version

Clarify, state requirements, draw the six layers, close on trade-offs. Permissions filter at retrieval; freshness gets an SLA.

Listening for: the clarifying questions. Candidates who draw first almost always design for the wrong constraint.
Red flag: A whiteboard full of boxes and no stated requirement. Full bank: GenAI System Design.
10Round 5 · "Tell me about a GenAI project you owned, and its impact."round-5behavioural＋
Strong answer

Lead with the business impact and a number, then work backwards: the situation, the decisions that were yours specifically, the architecture, and the metric that moved — latency, cost, quality or adoption. Own one trade-off you would make differently now. Keep it under two minutes and stop; the follow-ups are where the round is actually won.

30-second version

Impact and a number first, then situation, your decisions, the architecture, the metric moved, and one trade-off you would revisit.

Listening for: "I" rather than "we" on the decisions, and a number you can defend.
Red flag: Five minutes of architecture with no outcome. Full bank: Project & behavioural.
11Round 5 · "Tell me about a time you were wrong, or a project failed."round-5failure＋
Strong answer

Pick a real failure with a real cost, say plainly what you got wrong, and then give the systemic fix — not "I learned to communicate better" but "we had no evaluation set, so a prompt change regressed quality silently; I added a golden set to CI, and that class of regression stopped." Reflection plus a change that outlasted you is the whole answer.

30-second version

A genuine failure, what you got wrong, and the systemic change that stopped it recurring.

Listening for: a fix to the system rather than a promise to try harder.
Red flag: A disguised humblebrag, or a failure caused entirely by other people.
