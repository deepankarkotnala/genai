Frameworks / LangGraph / AsyncIO for LangGraph

1 · What you already know

From module 12 you build a LangGraph application as nodes over one state object. Each node is a Python function, and the runtime calls them in the order the edges allow.

Every node so far has been synchronous. This page is about what changes when a node spends nearly all its time waiting, which is what a model call does.

2 · What breaks now

A node that enriches a ticket needs three lookups, and none depends on the others.

That node takes 950 ms, and for almost all of it the process does nothing but wait.

All three rows are the same problem. The process is blocked on I/O it never needed to wait for in sequence. Overlap the waiting and the third row becomes about 800 ms.

3 · Simple breakdown - asyncio vs threads

A asyncio

What it is. asyncio is a Python library that runs many I/O-bound operations on one thread, by suspending each one while it waits and resuming it when its data is ready.

Core purpose. It removes waiting time from I/O-bound work. Twenty model calls that each take 800 ms finish in about 800 ms rather than 16 seconds.

Execution model.

Architecture under the hood. An event loop that schedules work, coroutines that can suspend at an await, and tasks that wrap a coroutine so the loop can progress it.

State handling. Each coroutine keeps its own local variables across a suspension. There is no lock on shared data, because only one coroutine runs at any instant.

Limitations and advanced features. It gives no CPU parallelism, and one blocking call freezes every task on the loop. TaskGroup, Semaphore and wait_for add structure, bounds and cancellation.

B Threads

What it is. A thread is an operating-system execution context. The OS decides when each one runs, and can suspend any of them at almost any point.

Core purpose. It runs blocking code without rewriting it, and lets one blocking call proceed while other work continues.

Execution model. The OS scheduler pre-empts threads. Python's global interpreter lock still allows only one thread to execute bytecode at a time.

Architecture under the hood. A pool of OS threads, each with its own stack, all sharing the process memory.

State handling. Every thread sees the same memory, so any mutable value touched by two threads needs a lock.

Limitations and advanced features. Each thread costs about 8 MB of stack, so thousands are impractical. Pre-emption means a data race can appear between any two bytecodes.

The core differences

asyncioThreads
Concurrency for I/OThousands of tasks on one threadTens to hundreds of threads
Where a switch can happenOnly at an awaitAt almost any point
One blocking callFreezes every taskBlocks only that thread

In short - which one to choose

  • Use asyncio when the work is I/O-bound and you control the libraries: model calls, HTTP requests, database queries.
  • Use threads when a library is blocking and has no async version, or when one blocking call must not stop everything else.
  • Use processes for CPU-bound work. Neither of the other two gives CPU parallelism in Python.

4 · Without the technology

Threads are the older answer, and they work.

This takes about 400 ms rather than 950. It is correct, and for three lookups it is a perfectly good answer.

What it cannot do:

  • Scale to a thousand. Each thread costs roughly 8 MB of stack, so a thousand concurrent lookups is about 8 GB.
  • Tell you where a switch happens. The OS can suspend a thread between any two bytecodes, so every shared mutable value needs a lock.
  • Cancel cleanly. There is no safe way to stop a thread from outside it.

asyncio gives up CPU parallelism, which Python did not have here anyway, and buys cheap concurrency and explicit switch points.

5 · Runtime mechanics

One await, in order:

  1. The coroutine runs normally until it reaches an await on something that is not ready.
  2. It suspends, keeping its local variables, and returns control to the event loop.
  3. The loop picks another ready task and runs it, up to that task's next await.
  4. The operating system reports that the awaited I/O has completed.
  5. The loop resumes the first coroutine at the line after its await.

Steps 2 and 5 are the whole mechanism. A switch happens only at an await, which is why asyncio needs no lock around data one coroutine holds across a suspension.

6 · The components, one at a time

The coroutine function

Declared with async def. Calling it does not run it.

A missing await is the most common asyncio bug, and Python reports it only when the object is garbage collected.

The event loop

The scheduler. It resumes ready tasks and asks the operating system about I/O readiness. asyncio.run() creates one, runs your coroutine, and closes it.

The task

A coroutine wrapped so the loop can progress it independently of the caller.

gather and TaskGroup

Prefer TaskGroup. With gather, one failure leaves the other tasks running unless you pass return_exceptions=True and handle them yourself.

Semaphore

Without a bound, a thousand tasks send a thousand requests at once and the provider answers with 429s.

7 · State and data flow

  1. What data is state? Each coroutine's local variables, plus the loop's set of ready tasks.
  2. Who writes each field? The coroutine itself. Nothing else can reach its locals.
  3. Who reads each field? Only that coroutine.
  4. Replaced, appended or merged? Ordinary Python assignment. There is no merge step.
  5. What reducer controls merging? None. That is why a coroutine's own data needs no lock.
  6. Is it only in process memory? Yes.
  7. Is it checkpointed? No. A suspended coroutine exists only in memory.
  8. Is it in a database? No.
  9. How long does it survive? Until the coroutine returns or is cancelled.
  10. What thread, user or key retrieves it again? Nothing. A lost task reference is a lost task.

Row 5 is the property people underrate. Shared mutable data still needs care, but only across an await: between two awaits, no other coroutine can run.

9 · Break it

Put one ordinary blocking call inside an async node.

No error and no warning. The node returns the right answer, and throughput collapses.

One synchronous call froze the event loop for 900 ms. Every other task on that loop, including the nineteen other requests, made no progress, because there is one thread and it was inside legacy_model.score.

10 · Fix it

1 · Move the blocking call off the loop. One line.

The call still takes 900 ms, but it takes it on a worker thread while the loop keeps serving every other task.

2 · Find the blocking calls you did not know about. Debug mode logs any callback that holds the loop too long.

3 · Bound the concurrency, or fixing the block just moves the failure to the provider.

4 · Never use time.sleep in async code. One blocks the loop; the other suspends one task.

13 · Interview preparation

Q What happens when an async function is called? ›
It returns a coroutine object. The body runs only when the coroutine is awaited or scheduled as a task by an event loop.
Q Does AsyncIO use multiple threads? ›
The normal event-loop model is one thread executing one Python task at a time, switching at await points. Threads can be introduced deliberately, for example with asyncio.to_thread.
Q Why can a single blocking call be disastrous? ›
Because the event loop cannot schedule any other task while the loop thread is blocked, so the latency of unrelated requests rises too.
Q TaskGroup vs gather? ›
Both run awaitables concurrently. TaskGroup gives structured lifecycle and cancels sibling tasks when one fails, making it the safer default for related child work. Gather is useful when its ordering and exception behaviour are exactly what you need.
Q Where should concurrency limits live in a LangGraph system? ›
At every scarce boundary: graph/service admission, per-provider/API semaphore or rate limiter, database pool, and worker queue. The smallest local semaphore alone is not a complete capacity strategy.
Q How would you make an async tool call reliable? ›
Use a total deadline, bounded retries for transient errors, idempotency where side effects exist, cancellation propagation, concurrency/rate limits, structured logs/traces, and explicit error mapping into graph state.

14 · In short, and what comes next

Remember these six:

  • asyncio overlaps waiting, never computing. It gives no CPU parallelism.
  • A switch happens only at an await, which is why locks are rarely needed.
  • Calling an async def function returns a coroutine and runs nothing.
  • One blocking call freezes every task on the loop. Send it to a thread.
  • Bound concurrency with a Semaphore, or you move the failure to the provider.
  • Prefer TaskGroup: with gather, one failure leaves siblings running.
🔑
The one idea to remember

asyncio is concurrency without parallelism. It makes twenty model calls take about as long as the slowest one, and it does nothing at all for work that is actually computing.
