Lesson 4 · Making it competent

Reasoning patterns, measured rather than argued

⏱ ~3 h total 25 min read · 75 min build · 45 min break/debug · 30 min interview Prereq · Lesson 3 Next · Lesson 5
🎯
By the end of this lesson you will be able to
  • Explain ReAct, plan-and-execute, reflection and routing by name, and implement each.
  • Say what each one costs, in model calls, not adjectives.
  • Name the specific failure each pattern is prone to — and show it happening.
  • Explain why a reasoning pattern is control flow, not a framework feature.
  • Add a tool whose name deliberately limits what the model thinks it may do.

1 · The thing to understand before the four names

Every pattern in this lesson calls the same brain.decide() and the same execute(). Nothing new is imported. What changes is only:

  1. what you put in the messages, and
  2. what your code does with the answer.
🔑
A reasoning pattern is control flow

"ReAct" and "plan-and-execute" are about twenty lines of Python each. Frameworks give them class names, which makes them look like features you must adopt. Knowing they are control flow is what lets you say in an interview: "I'd implement routing directly — it's one classification call and a filtered tool list."

2 · ReAct — reason and act, interleaved

You already built this. It is Lesson 2's loop: decide one action, run it, feed the result back, repeat.

Strength: it adapts. Step 2 can use what step 1 returned — the only reason to prefer an agent over a workflow at all.

Weakness: one model call per step, so cost and latency scale with trajectory length, and there is no global view. It never committed to a route, so it can wander.

3 · Plan-and-execute — decide everything up front

Ask for the whole plan in one call, then run it without re-planning, then synthesise.

Strength: two model calls, regardless of plan length. And you can show the plan to a human before anything runs — which is why regulated workflows like this shape.

Weakness: the plan is made in ignorance. §7 shows exactly what that costs.

4 · Reflection — critique once, then revise

Produce an answer, ask for a critique, revise. Once.

⚠️
Two things to say about reflection that most candidates miss

It does not converge. Critique-revise loops oscillate or drift into agreeable rewording while the token bill grows. One pass. If one pass is not enough, the fix is a better first prompt or a real evaluator, not more passes.

A model critiquing itself shares its own blind spots. Reflection cannot find an error the model cannot see. It catches omissions well and wrong beliefs badly. It is not a substitute for evaluation (Lesson 10) or a human.

5 · Routing — classify first, then narrow

One cheap call decides the kind of ticket; the agent then runs with a smaller tool set.

This is the pattern production systems actually use and candidates mention least. It pays twice: fewer tools means better selection accuracy (Lesson 3), and a router can send the easy majority down a deterministic path so the agent only sees the remainder — the answer to Lesson 2's 10,000-tickets-a-day question.

ROUTES = {
    "billing":   ["read_ticket", "lookup_order", "search_kb", "draft_reply"],
    "technical": ["read_ticket", "search_kb", "draft_reply"],
    "general":   ["read_ticket", "search_kb", "draft_reply"],
}

Note the billing route is the only one with lookup_order. A technical ticket about a failed checkout has no order to look up — no order was created. Removing the tool removes the temptation.

6 · Build: patterns.py and draft_reply

Open project/agent/patterns.py. Four functions, one shared loop.

The new tool is draft_reply, and its declaration carries a deliberate decision:

"description": (
    "Compose a draft reply to the customer. Returns the draft for a "
    "human to review -- it does not send anything. Cite the knowledge "
    "base article ids you relied on so the reviewer can check them."
),
🔑
The tool is called draft_reply, not send_reply

The name and description together set the model's belief about how far its authority reaches. A tool called send_reply invites the model to act as though the customer has already been contacted — and to tell the customer so. Naming is part of the safety design, not cosmetics.

It also does two semantic checks the schema cannot:

known = {a["id"] for a in _load_kb()}
unknown = [c for c in citations if c not in known]
if unknown:
    return {"error": "unknown_citation", "message": ...}

A schema-valid citation list can contain refund-policy-v2 — plausible, authoritative-sounding, nonexistent. Fabricated citations are worse than none, because they survive a skim. Try it:

>>> execute("draft_reply", {"ticket_id": "TCK-1001", "summary": "Duplicate charge confirmed.",
...                        "next_step": "Agent will review.", "citations": ["refund-policy-v2"]})
{'error': 'unknown_citation',
 'message': "These article ids do not exist: refund-policy-v2. ..."}

7 · Run all four and read the numbers

cd teach-agents/project
python steps/l05_retrieval.py

  pattern        model calls  tools   trajectory
  --------------------------------------------------------------------------
  react                    5      4   read_ticket -> lookup_order -> search_kb -> draft_reply
  plan_execute             2      4   read_ticket -> lookup_order -> search_kb -> draft_reply
  reflect                  7      4   read_ticket -> lookup_order -> search_kb -> draft_reply
  route                    6      4   read_ticket -> lookup_order -> search_kb -> draft_reply

Same work, four prices. plan_execute is flat at 2 calls however long the plan; react grows with steps; reflect is react plus 2; route is react plus 1, buying a smaller tool set.

On this ticket every pattern reaches the same place, which is the honest result: on an easy ticket the pattern does not matter, so pick the cheap one. Patterns earn their keep on hard tickets.

8 · Break it — the planning blind spot

Now a ticket that mentions no order. TCK-1005 is an account question.

python steps/l05_retrieval.py TCK-1005

  react                    4      3   read_ticket -> search_kb -> draft_reply
  plan_execute             2      4   read_ticket -> lookup_order -> search_kb -> draft_reply

ReAct reads the ticket, sees no order id, and skips lookup_order. Plan-and-execute committed to it before reading anything, so it calls it anyway:

  1. read_ticket({'ticket_id': 'TCK-1005'})
  2. lookup_order({'order_id': 'ORD-0000'})  -> ERROR not_found
  3. search_kb({'query': 'account', 'limit': 2})
  4. draft_reply({'ticket_id': 'TCK-1005', 'citations': ['refunds']})
🐛
Where ORD-0000 came from, and why it matters

The plan said lookup_order(from ticket body). There was no order in the body, so the executor substituted a placeholder and called the tool with fiction. That is plan-and-execute's structural weakness in one line: a plan written before anything ran cannot reference a value that only exists after step 1.

Real plan-executors fix this with typed slots — lookup_order(order_id=$1.order_id) — and with "re-plan if a step fails". Both are re-planning wearing a disguise, and they are most of why plan-and-execute stops being the simple option.

🔬
Exercise · make one failure become three

In _arguments_for(), delete the _is_placeholder(arg) guard so the planner's literal text is passed straight through as a query. Run TCK-1005 again. You will see a cascade: a nonsense query 'from ticket category' → the wrong article retrieved → that wrong article cited in a customer reply. One unresolved placeholder, three failures, and only the third is visible to the customer.

This is the shape of most agent incidents: not a dramatic error, but a small unvalidated value flowing downhill until it reaches something a person reads.

Two more experiments worth running:

Reflection on a thin answer. python steps/l05_retrieval.py --pattern reflect TCK-1005 — the critique is specific: "Gaps: it does not state whether the order is refund eligible; it does not say who acts next." Now run it on TCK-1001 and watch the critique shrink, because there was less missing.

Routing on a technical ticket. --pattern route TCK-1003 (a checkout 502). Route becomes technical and lookup_order is not even offered.

9 · The production concern

Pattern choice is a cost and latency decision, so it belongs in the same conversation as budgets. Three things follow:

Mix them. Real systems route first, then run ReAct on what survives, and reflect only on outputs a customer will see. "Which pattern do you use?" is often the wrong question.

Reflection is the first thing to cut. It roughly doubles cost for a quality gain you should measure before paying for. Lesson 10 gives you the means.

Where autonomy sits is a spectrum, not a switch: fixed code → workflow → workflow with local autonomy → fully autonomous. All four patterns here sit at "workflow with local autonomy" — the model decides within a step, while your code owns the shape. Lesson 13 pushes further right and measures what it costs.

🧰
You already know this

Routing is a load balancer with a classifier. Plan-and-execute is a query planner: build the plan, then run it, and the reason databases separate the two is exactly the reason agents do. Reflection is code review — valuable, and weakest when the reviewer wrote the code.

10 · Interview practice

Two-minute answer — "Explain ReAct, and when you'd use something else."

🎤

"ReAct interleaves reasoning and acting: the model picks one action, my code runs it, the result goes back into the conversation, and it decides again. It's adaptive, which is the only reason to use an agent rather than a workflow — step two can depend on what step one returned.

The cost is one model call per step. So when the steps are knowable up front I'd use plan-and-execute instead: two calls regardless of plan length, and I can show the plan to a human before anything runs. Its weakness is that the plan is made in ignorance — in our triage agent, a plan that includes 'look up the order' will call it even on a ticket with no order, because the order id only exists inside the ticket body.

In practice I'd combine them: route first with one cheap classification call to narrow the tool set, ReAct for the genuinely open cases, and reflection only on output a customer will read, because it roughly doubles cost. And I'd measure that before paying for it."

Q System design · Your agent averages 8 steps and costs too much. Reduce it without losing quality. ›

Get the trajectory distribution first — you cannot cut what you have not measured. Then, in order of payoff:

Route. One cheap call to classify, then a narrowed tool set. Often the easy majority does not need the agent at all.

Collapse tool calls. Eight steps often means several separate lookups that could be one coarser tool. Each round trip is a model call; merging two tools removes one.

Model routing. Cheap model for gathering, strong model for the final judgement (Lesson 11).

Cache. Repeated prefixes across runs are what prompt caching is for.

Drop reflection unless evaluation shows it earning its keep.

Then the discipline: set a cost ceiling per run and alert on breaches, so this does not recur silently.

Q Debugging · An agent using plan-and-execute keeps calling a tool with obviously wrong arguments. Why? ›

Almost certainly unresolved plan placeholders. The plan was written before any tool ran, so it refers to values that did not exist yet — "the order from the ticket" — and the executor substituted something to make the call go through.

Check whether the executor resolves references from earlier results, or whether it passes the plan's prose through as an argument. Then look for the cascade: a bad argument produces a bad result, which is used to build the next call. The visible symptom is usually two or three steps downstream of the cause.

Fixes, cheapest first: validate arguments and reject placeholder-looking values; have the planner emit typed slots referencing step outputs; re-plan when a step fails; or switch to ReAct for this task, since a plan that cannot be written in advance is a signal the task is not plannable.

Q Coding · Implement routing, from scratch, in 10 minutes. ›

One classification call with a constrained output ("reply with exactly one word from this list"), validate the answer against your route map and fall back to a default if it is not in it, then run the normal loop with the tool list filtered to that route.

Say while writing: "I validate the route rather than trusting the string" and "the fallback is a real route, not an exception". A router that crashes on an unexpected word has moved the failure rather than handled it.

Q Senior follow-up · How do you decide whether reflection is worth its cost? ›

Make it an A/B on a golden set, not a judgement call. Run with and without reflection, score both on the outcome metrics that matter, and compare against the cost and latency delta. Reflection typically helps most where the failure mode is "incomplete" and least where it is "confidently wrong", because a model cannot critique what it cannot see.

If it wins on only some ticket types, apply it selectively — reflect on refund recommendations, skip it on password resets. Selective application is usually where the real win is.

Q Senior follow-up · A colleague wants to add a fifth pattern for every new problem. What do you say? ›

That patterns are control flow, so each one is cheap to write and expensive to own: another path to test, trace, evaluate and explain at 3 a.m. The question is not "does this pattern help sometimes" but "does it help enough to justify a permanent branch".

I'd want a measured win on the golden set, a named owner, and an answer to what it does when its assumption breaks — the way plan-and-execute breaks on unplannable tasks. Absent those, prefer tuning the tool descriptions and the router, which usually moves the number more than a new pattern does.

11 · Recap

  • A reasoning pattern is control flow plus prompting. Same decide(), same tools.
  • ReAct: adaptive, one call per step. Plan-and-execute: 2 calls, blind to what it has not yet seen. Reflection: +2 calls, catches omissions not errors, exactly one pass. Routing: +1 call, buys a smaller tool set.
  • On easy tickets all four agree — so pick the cheap one. Patterns matter on hard tickets.
  • Plan-and-execute called lookup_order(ORD-0000) on a ticket with no order. That is the pattern's structural weakness, not a bug.
  • One unresolved placeholder became three failures, and only the last was customer-visible.
  • draft_reply, not send_reply — naming limits what the model believes it may do. Fabricated citations are rejected because they survive a skim.
