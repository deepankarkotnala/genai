Lesson 1 · Foundations

The model mechanics you must be able to explain

⏱ ~2.5 h total 25 min read · 60 min build · 30 min break/debug · 25 min interview Prereq · Python Next · Lesson 2
🎯
By the end of this lesson you will be able to
  • Say what a language model does, in one sentence, without the word "AI".
  • Explain messages and roles, and why the model has no memory between calls.
  • Explain the context window as a budget, and what gets evicted first.
  • Explain why the same prompt can give different answers, and what temperature actually controls.
  • Explain structured output and why schema-valid is not the same as correct.
  • Explain what really happens when a model "calls a tool" — it doesn't call anything.
  • Have built brain.py: one interface, three interchangeable backends, no API key.

1 · What a language model does

Strip away the branding and a language model is a fixed pile of numbers that, given some text, scores which chunk of text plausibly comes next. It does this once, returns the result, and forgets everything.

🔑
The one-sentence version

A language model is a function from text to text. It has no memory, no clock, no file system and no network. Everything it appears to know about your situation was in the text you sent it.

Three consequences follow, and every one of them shows up in interviews:

  • It cannot act. It produces text. It cannot read your database or refund a customer. Anything an agent achieves, it achieves through code you wrote.
  • It cannot remember. Each call is independent. A chat that "remembers" your name is re-sending your name every single time.
  • It cannot look anything up. Facts it wasn't sent are either baked into its weights from training or unavailable. This is the entire reason retrieval exists (Lesson 5).
🧰
You already know this

A model call is a stateless HTTP request against an expensive, slightly unreliable service that returns unstructured text. You have built systems against those before. Almost everything in this course is that instinct applied carefully.

2 · Messages and roles

You don't send a model a string. You send it a list of messages, each with a role. Four roles matter:

RoleWho wrote itWhat it's for
systemyou, the engineerstanding instructions: who the agent is, what it may and may not do
userthe person or calling codethe goal for this run
assistantthe model, previouslywhat it said or decided earlier in this run
toolyour codethe result of an action the model requested

That last row is the whole trick of agents. Your code runs something, and the result is appended to the conversation as a tool message. On the next call the model sees it and can reason about it. Nothing magical — a growing list of messages.

⚠️
The mistake that causes real incidents

Roles look like a security boundary. They are not one. A system message is not privileged in the way a kernel is privileged — it is text in the same stream as everything else, and text arriving from a customer can contradict it. Lesson 9 attacks this directly. For now: roles organise a conversation; they do not enforce anything.

3 · The context window is a budget

Context window — the maximum number of tokens the model can consider in one call, counting your input and its output.

A token is roughly ¾ of an English word. The number that matters is that the window is finite and shared. System prompt, tool declarations, conversation history, tool results and the answer all compete for the same space.

This is why agents degrade over long runs rather than failing cleanly. Each step appends a tool result. Twenty steps in, the original goal is a small fraction of what the model is looking at, and the useful signal is diluted. Lesson 6 is about managing this deliberately.

✅
In plain English

Think of one fixed-size whiteboard. Instructions, the question, everything discovered so far, and room to write the answer all share it. Fill it with tool output and there's no room left to think.

4 · Deterministic vs probabilistic

The model produces a probability distribution over possible next tokens. Something then has to pick one. That picking step is where variability comes from.

temperature controls how sharply that distribution is sampled. At 0 you take the highest-probability token every time; higher values give lower-probability tokens a real chance.

⚠️
temperature=0 is not determinism

It is the closest you can get, and it is not a guarantee. Floating-point non-associativity across batched requests, GPU kernel scheduling, load-dependent batching and silent model updates all mean identical input can produce different output. Interviewers like this question because "set temperature to 0" is the shallow answer.

The engineering conclusion: never rely on an exact-match assertion against a live model. Assert on structure, on constraints, and on whether the trajectory was acceptable — which is exactly what Lesson 10 builds.

5 · Structured output

An agent needs decisions it can act on — {"tool": "read_ticket", "ticket_id": "TCK-1001"}, not "I'll take a look at that ticket for you!". Three mechanisms, in increasing reliability:

  1. Ask nicely. "Reply with JSON only." Works most of the time, which is another way of saying it fails in production.
  2. JSON mode. The provider guarantees syntactically valid JSON. It does not guarantee your shape.
  3. Schema-constrained decoding. You supply a JSON Schema and the decoder can only emit tokens consistent with it. This is what native tool calling uses.
🛡️
Schema-valid is not semantically valid — say this in the interview

Constrained decoding guarantees the shape. It cannot guarantee the content. {"ticket_id": "TCK-9999"} is perfectly schema-valid and names a ticket that does not exist. Schema validation and semantic validation are separate layers and you need both. Lesson 3 builds the second one.

So every structured call needs a validate-and-repair path: parse, validate, and on failure send the error back once and let the model correct itself. Once — not in a loop. A retry loop against a model that cannot satisfy the schema burns money until something else stops it.

6 · What "tool calling" actually is

The name is misleading, and clearing it up is worth easy interview points.

The model never calls anything. You send a list of tool declarations — name, description, parameter schema — alongside the conversation. The model emits a structured message that names a tool and supplies arguments. Your code decides whether to honour it, runs the function, and appends the result as a tool message.

🔑
The two facts that follow

1. A tool declaration is a prompt. The model never sees your Python — only the name, description and schema. When a tool gets picked at the wrong moment, fix the description before blaming the model.

2. Every tool call passes through your code. That is the enforcement point. Not the system prompt — the dispatch function.

7 · Build: brain.py

Here is the design decision that makes everything afterwards possible: the loop never imports a vendor SDK. It depends on one small interface.

Why it matters: weld the loop to a vendor and you cannot test without a network call, cannot swap models, and cannot reproduce a bug. Put one interface in between and all three become easy.

Open project/brain.py. The contract is four lines:

class Brain(Protocol):
    """The whole contract. If it has this method, the loop can drive it."""
    name: str

    def decide(self, messages: list[Message], tools: list[dict]) -> BrainResult:
        """Look at the conversation so far and choose the single next action."""

And the return type carries the decision plus the numbers you'll be asked about later:

@dataclass(frozen=True)
class BrainResult:
    tool_call: ToolCall | None
    final_text: str | None
    backend: str
    model: str
    latency_ms: int
    prompt_tokens: int | None = None
    completion_tokens: int | None = None
    truncated: bool = False

    def __post_init__(self) -> None:
        if (self.tool_call is None) == (self.final_text is None):
            raise MalformedDecision(...)

Two things to notice. The telemetry fields aren't decoration — "what did this run cost and where did the time go" is a question about any agent you claim to have built, and you cannot answer it if the numbers were never captured. And __post_init__ enforces the invariant that a decision is either an action or an answer. Making illegal states unrepresentable is cheaper than checking for them at every call site.

Errors are split by layer, because they need opposite responses:

class BrainError(Exception): ...            # the call itself
class BrainUnavailable(BrainError): ...     # cannot reach the backend
class BrainTimeout(BrainError): ...         # reached it, no answer in time
class ModelNotInstalled(BrainError): ...    # backend up, model absent
class MalformedDecision(BrainError): ...    # answered, but unusable
🧰
You already know this

Retrying a connection-refused is pointless; retrying a malformed response might work. Same distinction you already make between 5xx and 4xx. Agents that collapse both into "retry the call" waste money on failures that can never succeed.

The deterministic backend

StubBrain is the default, so this course needs no API key. It is not a mock returning a canned string. It is a small rule engine that reads the same conversation a real model reads, and decides from what it has learned rather than which turn it is on:

if ticket is None and "read_ticket" not in attempted and "read_ticket" in available:
    ticket_id = _extract(goal, prefix="TCK-")
    if ticket_id:
        return ToolCall("read_ticket", {"ticket_id": ticket_id})

Because the rules read state, the trajectory reacts: remove a tool and the path changes; edit a fixture and the path changes. A mock keyed on step number cannot do that, so it never tests the interesting part of a loop — what happens when a result arrives that you didn't expect.

8 · Break it

Three deliberate breakages. Do them in a REPL from teach-agents/project.

1 · Violate the decision invariant.

from brain import BrainResult, ToolCall
BrainResult(tool_call=ToolCall("read_ticket", {}), final_text="also an answer",
            backend="x", model="y", latency_ms=0)

You get MalformedDecision. Now ask yourself what the loop would have done if this were allowed — acted and returned, in the same step. Every downstream trace and cost figure would be wrong.

2 · Ask for a backend that isn't there.

from brain import get_brain
get_brain("gpt-9")

Read the error. It names the valid options. An error that doesn't tell you what is allowed makes you go read the source.

3 · Ask for Ollama without Ollama. Set AGENT_BRAIN=ollama and run python steps/l02_loop.py. You get BrainUnavailable telling you to run ollama serve — not a silent downgrade to the stub. This is deliberate: a fallback that hides a misconfiguration lets you believe you tested a real model when you tested a rule engine.

9 · The production concern

The interface in this lesson is the seam where real systems get their flexibility. With it you can route cheap models for easy steps and strong models for hard ones (Lesson 11), swap providers when pricing changes, run the identical loop in tests and production, and pin a model version so a silent provider update doesn't change your behaviour overnight.

Without it, every one of those becomes a refactor.

⚠️
Don't over-abstract

One method, three implementations. If your abstraction needs a config system and a plugin registry before it runs, you have built a framework instead of an agent. Interviewers notice the difference.

10 · Interview practice

Two-minute answer — "What is an LLM and what are its limits?"

🎤

"A language model is a function from text to text — it scores which text plausibly continues what you sent it. It's stateless, so each call is independent: anything it seems to remember was re-sent. It can't take actions, so any real capability comes from code around it.

Practically that means three constraints. Everything it knows about the situation has to fit in a finite context window, which is a budget you manage rather than a limit you hit. Output is probabilistic — temperature=0 gets you close to reproducible but doesn't guarantee it, so I never assert exact matches against a live model. And when it 'calls a tool' it isn't calling anything: it emits a structured request my code chooses whether to honour. That last point is where all the safety lives, because the dispatch function is the enforcement point, not the prompt."

Q System design · Your team wants one agent that can use models from three providers. How do you structure it? ›

One interface with a single decide-style method returning a normalised decision type; one adapter per provider translating to and from that type. The loop depends only on the interface. Provider-specific concerns — auth, retry, token accounting, tool-call encoding — live in the adapter.

Then say what you'd watch out for: providers disagree on tool-calling formats and on how they signal truncation, so the adapter must normalise both, and a "lowest common denominator" interface can quietly cost you provider-specific features like prompt caching. Also pin model versions per adapter — an unpinned model is an un-versioned dependency.

Q Debugging · An agent worked in staging and misbehaves in production with the same code and prompts. Where do you look? ›

Start from what differs, not from the prompt. Model version or alias drift between environments. Temperature or sampling config differing. Context length — production conversations are longer, so history that fit in staging is now being truncated. Tool declarations differing because a feature flag exposes a different tool set. Real data hitting edge cases the fixtures didn't have.

Then the answer they actually want: you cannot diagnose this without per-run traces recording model, version, sampling params, token counts and the tool sequence. If those weren't captured, the first fix is capturing them.

Q Coding · Write the model-boundary interface for an agent, from scratch, no framework. ›

What a strong answer includes: a message type with a role; a decision type that is either a tool call or a final answer, with that invariant enforced in the constructor; telemetry fields; an error hierarchy separating transport failures from content failures; and a deterministic implementation for tests that reacts to inputs rather than replaying a script.

What weak answers miss: returning a bare string (loses tool calls), allowing both fields to be set (makes illegal states representable), and one generic LLMError (destroys the retry policy).

Q Senior follow-up · How would you test an agent's model layer? ›

Three tiers. Unit: a deterministic backend, no network, asserting on trajectory and structure. Contract: for each real adapter, one marked integration test proving it translates tool calls and telemetry correctly — run on demand, not in the main suite. Behavioural: a golden set scored on outcome and trajectory, tolerating different-but-acceptable paths (Lesson 10).

The trap to name yourself: a mock that always returns the same call gives high coverage and tests nothing interesting, because it never exercises what the loop does with an unexpected result.

Q Senior follow-up · A provider deprecates the model you pinned, in 30 days. What's your plan? ›

Treat it as a dependency upgrade with a behavioural contract. Run the golden set against the new model and diff outcome and trajectory — same answers via different tool sequences may still be a cost regression. Compare tokens, latency and cost per run. Shadow it on real traffic without serving its output. Roll out behind a flag by percentage, with the old model still reachable. Expect prompt adjustments: prompts are tuned to a model, so "same prompt, new model" is not a null change.

Then the honest part: without a golden set you cannot do any of this, which is why Lesson 10 exists.

11 · Recap

  • A model is a stateless function from text to text. No memory, no actions, no lookups.
  • Messages have roles. Roles organise; they do not enforce.
  • The context window is a shared budget, and long agent runs are what exhausts it.
  • temperature=0 is near-reproducible, not deterministic. Never assert exact matches on a live model.
  • Schema-valid ≠ semantically valid. You need both layers.
  • The model doesn't call tools. It requests them; your dispatch code decides. That's the enforcement point.
  • One interface, three backends, no API key — and a deterministic backend that reacts to state, not to turn count.
