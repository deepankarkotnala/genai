Lesson 11 · Proving it works

Tracing, latency and cost

⏱ ~3 h total 25 min read · 75 min build · 50 min break/debug · 30 min interview Prereq · Lesson 10 Next · Lesson 12
🎯
By the end of this lesson you will be able to
  • Explain what a trace gives you that logs cannot.
  • Debug a broken run from its span tree alone.
  • State your agent's cost per run, and explain why it is quadratic in steps.
  • Answer "your agent costs $0.40 a ticket — get it under $0.10."
  • Explain prompt caching and model routing, and when each pays.
  • Say why traces need redaction before they are written.

1 · What a trace gives you that logs do not

Four questions logs answer badly and a trace answers directly: what happened (the ordered sequence), how long (per span, so you see where time actually went), what it cost (tokens priced per model), and why it broke (an error class attached to the span that failed, not to the run).

One correlation id ties a run together. That is the difference between "an agent misbehaved yesterday" and "run r_9c577a spent 179ms in search_kb, got unavailable, and escalated".

2 · The shape

@dataclass
class Span:
    span_id: str
    run_id: str          # the correlation id, on every span
    name: str
    kind: str            # "model" | "tool" | "control"
    parent_id: str | None
    duration_ms: int
    ok: bool
    error_class: str | None
    model: str | None
    prompt_tokens: int
    completion_tokens: int
    cost_usd: float

Spans nest, but the store is flat with a parent_id — easier to write, easier to query, and what every real tracing backend does. Tracing is opt-in: pass a Trace and the same loop produces a tree; omit it and Lessons 2–9 stay readable.

3 · Read a healthy run

cd teach-agents/project
python steps/l10_evaluated.py --trace

run r_3518de4651  Triage ticket TCK-1001
  model   decide:1                   0ms  100+2tok
  tool    tool:read_ticket           4ms
  model   decide:2                   0ms  142+2tok
  tool    tool:lookup_order          0ms
  model   decide:3                   0ms  165+4tok
  tool    tool:search_kb             3ms
  model   decide:4                   0ms  267+24tok
  tool    tool:draft_reply           2ms
  model   decide:5                   0ms  326+48tok
  total: 9 spans, 1080 tokens, $0.00000, 9ms, 0 error(s)
📈
Look at the prompt tokens: 100 → 142 → 165 → 267 → 326

Every step re-sends the entire transcript. So the cost of a run is quadratic in the number of steps, not linear — step 5 costs three times step 1 for the same model.

This is the real argument for fewer, coarser tools, and for routing. Halving the steps does much better than halving the price per token. There is a test pinning this growth, so it cannot silently stop being true.

4 · Debug a broken run from the trace alone

python steps/l10_evaluated.py --debug

  model   decide:1                   0ms  100+2tok
  tool    tool:read_ticket           0ms
  model   decide:2                   0ms  142+2tok
  tool    tool:lookup_order        154ms
  model   decide:3                   0ms  165+4tok
  tool    tool:search_kb           179ms  !! unavailable
  model   decide:4                   0ms  181+11tok
  tool    tool:escalate              0ms
  total: 8 spans, 607 tokens, 333ms, 1 error(s)

  slowest spans: [('tool:search_kb', '179ms'), ('tool:lookup_order', '154ms')]
  failed spans : [('tool:search_kb', 'unavailable')]

Read it in this order, and practise saying it out loud:

Which span failed? search_kb, error class unavailable.

What did it cost in time? 179ms — and that includes the retries, which is why a failing tool can be slower than a working one.

What did the agent do next? One more model call, then escalate. Correct behaviour, visible in the trace rather than inferred.

What is the second-order signal? lookup_order took 154ms when it normally takes 0. Two slow tools in one run is a dependency problem, not an agent problem.

A log line saying ERROR: search_kb failed answers the first question and none of the others.

5 · Cost, stated as a number

python steps/l10_evaluated.py --cost

  This run: 5 model calls, 1000 in + 80 out

  model          $/run     $/10k tickets
  ----------------------------------------
  small        0.00019              1.98
  large        0.00420             42.00

  large is 22x the price of small.
🔑
"What does your agent cost?" is a fair question and most people cannot answer it

You can only answer it if the numbers were captured. That is why BrainResult has carried prompt_tokens, completion_tokens and latency_ms since Lesson 1 — not decoration, groundwork.

Unknown models cost 0.0 and say so, rather than guessing. A cost figure you cannot source is worse than none.

6 · The four levers

LeverMechanismTypical win
Fewer stepscoarser tools, routinglargest — cost is quadratic in steps
Model routingcheap model gathers, strong model judgeslarge, if one step needs the judgement
Prompt cachingreuse the stable prefix across callslarge for long system prompts
Smaller resultsLesson 6's capscompounds, because every step re-sends them

Prompt caching works because the front of your prompt barely changes: system prompt, tool declarations, the goal. Providers can cache that prefix and charge less for it — but only if it is genuinely stable, which means put the volatile parts last. A timestamp near the top of your system prompt silently disables caching for the whole run.

Model routing exploits the 22× gap above. Gather facts with the cheap model; spend the expensive one on the step where judgement matters. Lesson 4's router is the mechanism.

7 · Traces are a data-retention surface

def _clean(attributes):
    for key, value in attributes.items():
        if isinstance(value, str):
            cleaned, found = redact_secrets(value)
            out[key] = cleaned
            if found: out[f"{key}_redacted"] = found
⚠️
Redact on the way in, not on the way out

A trace holding a card number is a retention problem wearing a debugging hat. Traces get copied into dashboards, tickets, screenshots and third-party tools that production data is not supposed to reach — and unlike a database, nobody thinks of them as a data store subject to deletion requests.

Note it also records that something was redacted. Silent redaction makes a future engineer think the field was always empty.

8 · Break it

1 · Find the quadratic. Run --trace, note prompt tokens per step, then raise max_steps and add a fault so the run takes longer. Plot them. The curve is the argument for coarser tools, and you will remember it better for having drawn it.

2 · Break caching. Add f"Current time: {time.time()}" to the top of SYSTEM_PROMPT. Nothing fails, no test goes red — and in production you have just disabled prefix caching for every run. This is a cost regression invisible to every check you have. What would catch it?

3 · Remove redaction from _clean(), then trace a run whose attributes contain an approval token. Look at the saved JSON in traces/. That file is now a credential.

4 · Attribute the time. Inject slow={"search_kb": 2.0} and confirm the span tree points at the right culprit. Then inject slowness into two tools and check you can still tell which dominated.

9 · The production concern

Sample, do not trace everything. Full-fidelity traces at 10,000 runs a day is a storage bill. Common practice: sample healthy runs at a few percent, keep 100% of failures, and always keep runs that touched money.

Alert on ratios, not counts. Escalation rate, retry rate, cost per resolved ticket. Absolute error counts move with traffic; ratios move with health.

Latency is p99, not mean. An agent with a 3s mean and a 40s p99 feels broken, because the slow runs are the complicated ones — the tickets that mattered most.

Use a real backend when you outgrow this. Our tracer is ~150 lines to make the shape legible. Langfuse and OpenTelemetry give you retention, search, dashboards and sampling. The concepts transfer exactly; span, parent, attributes and correlation id are the same everywhere.

🧰
You already know this

Distributed tracing, correlation ids, span attributes, sampling, p99 versus mean, PII in logs. This is APM pointed at a new kind of span. Two things are genuinely different: a span has a token cost, so tracing doubles as billing; and the prompt-token growth means agent cost scales super-linearly with steps in a way ordinary services do not.

10 · Interview practice

Two-minute answer — "Your agent costs $0.40 a ticket. Get it under $0.10."

🎤

"First I'd get the breakdown per run — tokens in and out per model call — because the fix depends entirely on where the money goes. Assume it's mostly input tokens, which it usually is.

The biggest lever is fewer steps, because cost is quadratic in steps: every step re-sends the whole transcript. In our trace the prompt grew 100 → 326 tokens across five calls. So I'd route first — one cheap classification call, then a narrowed tool set — and merge fine-grained tools into coarser ones. Going from six steps to three is roughly a quarter of the cost, not half.

Then model routing: gather facts with the cheap model and spend the expensive one only where judgement matters. In our price table that's a 22× gap, so it matters more than most micro-optimisations.

Then prompt caching on the stable prefix — system prompt and tool declarations — which means keeping volatile content out of the front of the prompt. A timestamp near the top silently disables caching for the whole run.

Then smaller tool results, which compounds because every step re-sends them.

And I'd set a cost ceiling per run with alerting, so this doesn't drift back. The thing I'd say last is that I'd measure quality alongside cost on the golden set — a cheaper agent that escalates twice as often hasn't saved anything, it's moved the cost to the support team."

Q System design · Design observability for an agent platform running several agents. ›

One trace per run, correlation id propagated to every downstream call so an agent's tool call can be joined to the service that served it. Spans typed — model, tool, retrieval, control — because you want to slice latency by kind, and "where does the time go" is usually answered by span kind before span name.

Attributes: agent name and version, prompt version, model and model version, tenant, ticket category. Version fields are what let you answer "did the change I shipped on Tuesday do this".

Sampling: a few percent of successes, 100% of failures, 100% of anything touching money. Retention: shorter for successes than failures, with redaction at write time.

Then the dashboards that matter, which are ratios: resolution rate, escalation rate, retry rate, cost per resolved ticket, p99 latency — sliced by agent, model version and tenant, because aggregates hide the broken segment.

And a cost budget per agent with alerting, since the failure mode of a multi-agent platform is one agent quietly looping and spending.

Q Debugging · p99 latency is 40s, mean is 3s. Where does the time go? ›

The mean tells you nothing here — the distribution is bimodal, so I'd look only at the slow tail and compare it against a fast run.

Most likely: step count, since the slow runs are the complicated tickets that take eight steps instead of three, and each step is a round trip. Check whether p99 runs correlate with step count before anything else.

Then: a slow dependency visible as one dominant span; retries, which multiply a step's latency invisibly unless the trace records the attempt count; large prompts, since time-to-first-token grows with input length, so the same quadratic that drives cost also drives latency; and queueing if the tool pool is saturated, which shows as slow spans with fast underlying services.

Fixes in order: cap steps harder for the slow segment, parallelise independent tool calls, stream partial output so the user sees progress, and set a total wall-clock budget that escalates rather than continues.

Q Coding · Add tracing to an existing agent loop. ›

A context manager per span that records start, duration, ok/error and attributes, with a stack for parent ids. A trace object holding a run id and a flat list of spans. Wrap each model call and each tool call. Record token usage and price it from a table.

Details that signal experience: make it opt-in so the loop stays readable without it; flat storage with parent_id rather than nesting; redact attributes on write; capture the error class on the span rather than a stringified exception; and make sure the span still closes when the body raises.

Q Senior follow-up · What would you alert on? ›

Ratios and budgets, not error counts. Escalation rate rising is the earliest quality signal and it is free. Human override rate on drafted replies — if reviewers rewrite 60% of drafts, the agent is not helping. Cost per resolved ticket, which catches loops and prompt bloat that no error surfaces. p99 latency. Retry rate per tool, which finds a degrading dependency before it fails outright. And refund volume, because that is the blast radius.

What I would not alert on: raw error counts, which track traffic; and individual run failures, which are normal and will train people to ignore the channel.

Q Senior follow-up · A cost regression shipped and no test caught it. What now? ›

Expected — correctness tests do not measure cost. The fix is to make cost a first-class assertion: record tokens and cost per case in the golden set and fail the build when a case exceeds its budget by more than a threshold. That is how a timestamp added to a system prompt, which breaks prefix caching without changing a single answer, becomes visible.

Then two operational additions: a cost dashboard per prompt version so a regression is attributable to a change, and a canary that runs the golden set nightly against production configuration, since cost can regress from a provider-side change you did not make.

The general principle: anything you care about and do not assert will regress. Cost, latency and escalation rate all deserve budgets in the eval suite, not just correctness.

11 · Recap

  • A trace answers what happened, how long, what it cost and why it broke. Logs answer the first, badly.
  • One correlation id per run, on every span. Flat storage with parent_id.
  • Cost is quadratic in steps — every step re-sends the transcript. Fewer steps beats cheaper tokens.
  • Levers in order: fewer steps, model routing, prompt caching, smaller tool results.
  • Keep volatile content out of the prompt prefix or you disable caching silently.
  • Redact on write. A trace is a data store nobody remembers to include in a deletion request.
  • Sample successes, keep all failures, keep everything that touched money.
  • Alert on ratios and budgets, not error counts.
