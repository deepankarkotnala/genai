Lesson 14 · Shipping it

Frameworks, deployment and operations

⏱ ~3.5 h total 30 min read · 85 min build · 50 min break/debug · 30 min interview Prereq · Lesson 13 Next · Lesson 15

By the end of this lesson you will be able to
  • Compare the agent frameworks and say what each actually buys — from experience, not marketing.
  • Explain stateless service, stateful run, and why that is one design not two.
  • Explain why resume restores rather than replays.
  • Explain why the approval gate only becomes real over HTTP.
  • Ship a prompt change safely — and say why a tool description edit is one too.

Now you can judge a framework

You have built the loop, the tool layer, retrieval, memory, reliability controls, an approval gate, guardrails, evals, tracing, MCP and a supervisor — all without one. That is the only position from which a framework comparison is worth anything: you know what it would be replacing.

🔑
The honest framing

A framework earns its place on durable state, resumability and human-in-the-loop interrupts — the things that are genuinely fiddly and that you are about to build by hand in this lesson. It does not earn its place by naming control flow. "ReAct" is twenty lines; you wrote it in Lesson 2.

And note what no framework gives you: your policy, your approval gate, your evals, your threat model. Those are the parts that make an agent safe, and they are yours regardless.

The answer that lands in an interview: "I built it without a framework so I'd understand the loop. For production I'd evaluate LangGraph specifically for checkpointing and durable interrupts, because that's the part I hand-rolled and the part I'd rather not own."

2 · Four things a service forces

Everything so far ran in one process, in memory. service/api.py forces four decisions the in-process loop let you avoid.

1 · Stateless service, stateful run

run_id = "run_" + uuid.uuid4().hex[:10]
STORE.save(RunRecord(run_id=run_id, goal=goal, status="running"))   # BEFORE any work

The service holds nothing. Run state lives in the store, so any process can serve any request. That is why horizontal scaling and crash recovery are the same mechanism — a scaled-out replica and a restarted process face the identical problem, and the store solves both.

Note the save happens before the work. A crash during step 1 must still leave a record that a run began; otherwise you have work in flight that nothing knows about.

2 · Resume restores; it does not replay

⚠️
Replaying would re-execute side effects

Re-running completed steps is not merely wasteful. Any step with a side effect runs twice — the double-payment problem from Lesson 8, arriving through the recovery path this time.

So resume reloads the established facts and continues. And if it cannot restore safely, it escalates with the facts it has rather than starting again. Same instinct as Lesson 7: refuse to continue in a state you cannot reason about.

3 · The approval gate becomes real

POST /runs/{id}/refund           -> 202 awaiting_approval  + idempotency_key
POST /runs/{id}/refund/approve   -> a human, a different request, hours later

In-process, "approval" was a function argument. Over HTTP it is a genuine human step in a different request, possibly on a different process, possibly the next morning. The token is minted in the service, by an authenticated human — never by the agent.

And `202`-shaped rather than 200 or 400: the work is accepted and pending a human, which is a third thing distinct from succeeded and failed.

4 · Long runs do not fit a request

Four steps take seconds; a degraded run takes a minute. So the API is submit-and-poll. A blocking endpoint that sometimes takes 60s will be killed by a load balancer, and the run will be lost with it.

3 · Versioning, and the refusal it enables

PROMPT_VERSION  = "2026-08-02.1"
TOOLSET_VERSION = "2026-08-02.1"

Every response carries them, so an answer can be attributed to a configuration after the fact. And they enable something better than attribution:

python steps/l15_capstone.py --versions

  run started under prompt 2026-01-01.0
  current prompt version    2026-08-02.1

  can_resume -> False
  reason: prompt version changed (2026-01-01.0 -> 2026-08-02.1);
          resuming would mix two behaviours in one run

  -> abandoned: Cannot resume safely; handed to a human with the facts so far.
🔑
A run half-executed under two prompts is unexplainable

No trace will account for the discontinuity, and six weeks later someone will spend a day on it. Refusing costs one abandoned run, handed to a human with its facts intact.

And say this explicitly in an interview: editing a tool description is a prompt change. The schema is identical, nothing fails, and selection behaviour moves. Descriptions belong under the same review and the same eval gate as prompts.

4 · Shipping a prompt change

1 · Run the golden set and diff outcome and trajectory. Same answers via a different tool sequence can still be a cost regression.

2 · Compare tokens, latency and cost per case. Lesson 11's point: anything you care about and do not assert will regress.

3 · Shadow on real traffic without serving the output.

4 · Roll out by percentage behind a flag, with the old version still reachable.

5 · Bump the version, so in-flight runs abandon rather than mixing behaviours.

6 · Break it

1 · Traverse the path. Call STORE.load("../../../etc/passwd"). Rejected — the run id arrives from an HTTP path parameter, so it is untrusted input like any other. Remove the guard and see what the store will happily open.

2 · Break atomicity. Replace the temp-file-then-rename with a direct write, then kill the process mid-save. You now have a half-written state file that parses as corrupt or, worse, as plausible. A test asserts no .tmp files survive a save.

3 · Make resume replay. Change resume_run to re-run from step 0 on a run that had already prepared a refund. Watch the audit log. This is the double-payment problem arriving through the recovery path.

4 · Remove the version check. Resume a run started under an old prompt. Nothing fails; the run finishes; the answer is a blend of two behaviours and the trace says nothing about it. This is the bug you cannot debug later.

5 · Corrupt a state file and list the runs. The listing skips it rather than raising — one bad file must not break recovery for every other run.

7 · Operations

Concurrency. Two requests for the same run id will race on the store. Ours does not lock; a real system needs optimistic concurrency (a version column) or a per-run lock. Say this rather than hoping nobody asks.

Streaming. Submit-and-poll is honest but feels slow. Streaming partial output — "reading the ticket… checking the order…" — changes the perceived latency without changing the real one, and is worth more to users than most real optimisations.

Secrets and config. Environment, never the request body. And note our authorisation context is server-side for exactly the reason from Lesson 9: an identity supplied by the caller is an invitation.

SLOs and a runbook. Pick two or three: resolution rate, p99 latency, cost per resolved ticket. Then write down what to do when each breaches — the runbook is what makes an SLO more than a dashboard.

⚠️
The hardest part of operating an agent

The failures are quiet. A service that is down pages you. An agent that has got 8% worse looks identical from outside — same latency, same 200s, same shape of output — and you find out from complaints weeks later.

Everything else follows: a golden set with a non-zero exit, override and escalation rates as first-class metrics, readable traces, and budgets on cost and latency as well as correctness. The instrumentation is not overhead; it is the only way you find out.

🧰
You already know this

Stateless services with external state, atomic writes, idempotent recovery, schema migrations, feature flags, percentage rollouts, SLOs and runbooks. This is ordinary operations engineering — which is exactly why it is the strongest part of your background to lead with.

8 · Interview practice

Two-minute answer — "How would you deploy this agent?"

🎤

"Stateless service, stateful run. Run state lives in a store rather than in memory, so any process can serve any request — which makes horizontal scaling and crash recovery the same mechanism. State is written before the work starts and after every step.

The API is submit-and-poll, because a degraded run can take a minute and a blocking endpoint would be killed by the load balancer with the run lost. Resume restores state rather than replaying — replaying would re-execute anything with a side effect, which is the double-payment problem arriving through the recovery path. If it can't restore safely, it escalates with the facts it has.

The approval gate becomes real here: preparing a refund returns 202 with an idempotency key, and a human approves via a separate request, possibly hours later. The token is minted in the service by an authenticated human, never by the agent.

Every response carries the prompt and toolset version, so an answer is attributable to a configuration — and a run started under one prompt refuses to resume under another, because that blend is a behaviour no trace explains.

What I'd flag as not done: the store is a directory of files rather than a database sharing a transaction boundary with the payment, and there's no concurrency control on a single run."

Q System design · Take this agent to 10,000 tickets a day across three regions. ›

Stateless workers behind a queue rather than synchronous HTTP — submit puts a job on the queue, workers pull, state goes to a shared store. That gives back-pressure, retries and horizontal scale for free, and it matches the fact that runs are already asynchronous.

Regional: state and data residency per region, since ticket bodies are customer data; a model endpoint per region for latency and compliance. Version prompts globally but roll out per region so a bad change is contained.

Capacity: at 10k/day with 15% reaching the agent, that's ~1,500 runs — small. The real constraint is provider rate limits and burst, so a queue with concurrency limits per model matters more than instance count.

Recovery: a worker dies mid-run, the job returns to the queue, and the next worker resumes from stored state rather than restarting — which requires idempotency on every side effect, not just refunds.

Then the operational floor: SLOs on resolution rate and p99, alerting on escalation and override rates, cost budget per run, and a runbook for each. And I'd name the piece I'd fix first: the ledger and the payment need one transaction boundary.

Q Debugging · A worker crashed mid-run. What happens next? ›

Depends entirely on what was persisted and whether a side effect was in flight — those two questions come before anything else.

If state was written after each step, the next worker loads it and continues from the established facts. If a refund had been prepared, no money moved and the approval is still pending, so resume is safe. If a refund had been executed and the crash happened before the ledger write, the idempotency key makes the retry safe — that gap is my known exposure and I'd name it.

What must not happen is replay from zero, because that re-executes side effects. And a run that cannot be resumed safely — version drift, corrupt state — should be abandoned to a human with its facts rather than restarted.

Then the systemic answer: reconciliation against the payment provider, so a crash-window discrepancy is found by a job rather than by a customer.

Q Coding · Add durable state to an agent loop. ›

A record with run id, goal, step, established facts, attempted tools, status and version fields. Write before starting and after every step. Atomic write — temp file then rename — so a crash cannot leave a half-written document. Load-and-continue on resume, never replay. Validate the run id before it touches the filesystem.

Say while writing: "written before the work, so a crash still leaves a record a run began"; "atomic, because a half-written state file is worse than none"; "restore not replay, because side effects"; and "version fields so a resume across a prompt change can be refused".

Q Senior follow-up · When would you adopt a framework? ›

When it owns something genuinely fiddly that I would otherwise maintain. For me that is durable state, resumability and human-in-the-loop interrupts — LangGraph's checkpointer territory, and precisely the part I hand-rolled in this lesson.

What would not convince me is naming control flow. ReAct is twenty lines; routing is a classification call and a filtered tool list. A framework that gives those class names has added a dependency and a migration path, not capability.

And I would keep certain things regardless of framework: policy in code, the approval gate, the eval suite, the threat model. No framework provides those, and they are what make the agent safe rather than merely working.

Q Senior follow-up · What are your SLOs, and what happens when one breaches? ›

Three: resolution rate without human intervention, p99 end-to-end latency, and cost per resolved ticket. Deliberately not "uptime" — the service being up tells you nothing about whether the agent is working.

Runbook per breach. Resolution rate drops: check escalation reasons first, since a dependency failing shows up here before it shows up as an error; then diff against the last prompt or toolset version. p99 rises: check step-count distribution and retry rate before blaming the model. Cost rises: check prompt-token growth per step, which catches prompt bloat and broken prefix caching.

And the meta-point: each of these is a ratio, so it moves with health rather than with traffic. Error counts move with traffic and will train people to ignore the channel.

9 · Recap

  • A framework earns its place on durable state, resumability and interrupts — not on naming control flow.
  • No framework gives you policy, approval, evals or a threat model. Those are yours.
  • Stateless service, stateful run. Scaling and crash recovery become one mechanism.
  • Persist before the work starts, and after every step. Atomic writes only.
  • Resume restores, never replays — replay re-executes side effects.
  • The approval gate only becomes real over HTTP: a separate request, by an authenticated human.
  • Version prompts and toolsets. Refuse to resume across a change; a blended run is unexplainable.
  • Editing a tool description is a prompt change.
  • Agent failures are quiet. Instrumentation is the only way you find out.
