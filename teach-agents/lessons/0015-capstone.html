2 · The deliverables pack

Five documents. Two exist; write the other three now, because writing them is how you find out what you cannot explain.

1 · README (exists) — what it is, how to run it, what the stub backend cannot show you. That last section is the credibility one.

2 · docs/decisions.md (exists) — 19 decisions with trade-offs and an "open exposures" section. Re-read this before any interview: each entry is a question you may be asked, and the trade-off column is what separates a good answer from a recited one.

3 · Architecture diagram — one page. The loop, the six tools, the approval gate, the store, the MCP boundary. Draw it by hand; if you cannot, you do not know it well enough to whiteboard it.

4 · Threat model — one page from Lesson 9's corpus: assets (money, customer data, the reply channel), attackers (customer, poisoned document, compromised MCP server), controls in priority order, and what remains exposed.

5 · Evaluation report — run --eval, paste the output, add two paragraphs: what the suite protects, and the coverage hole the regression drill found.

🔑
Also collect: two traces and a cost line

Save one healthy trace and one broken one from --trace and --debug. Being able to show a real span tree, point at the failed span and say what the agent did next is worth more than any diagram.

And one number: "about 1,080 tokens per run; at small-model prices that's under two dollars per ten thousand tickets." Most candidates cannot cost their own system.

3 · Drill 1 · The coding round (15 min, no notes)

Implement a tool-calling loop from scratch. Set a timer. Ship in this order:

1  message list with roles
2  a BOUNDED for loop — not while True
3  call the model; branch on tool-call vs final answer
4  dispatch through a DICTIONARY — never getattr or eval on model output
5  catch tool errors and feed them back as observations
6  append the decision and the result
7  return an object carrying WHY it stopped

Say these while typing. The commentary is half the score:

  • "The step limit is the actual bound — if termination depends on the model choosing to stop, it isn't bounded."
  • "Dictionary dispatch means a hallucinated tool name is a clean error."
  • "The tool error goes back to the model, not up the stack — a missing record is information it can act on."
  • "I return why it stopped, so the caller can tell a finished run from a truncated one."

Failing patterns: while True; eval dispatch; letting a tool exception escape; returning only a string.

Self-check: run it against a ticket that does not exist. Does it terminate cleanly and say so?

4 · Drill 2 · The whiteboard (2 min, spoken)

Prompt: "Design an agent that handles customer support tickets." Do not start drawing boxes.

Scope (15s). "What's the volume, and what can it do without a human? Those two change the design more than anything else."

Shape (30s). "Most volume is a workflow, so route first with one cheap call and send only ambiguous or multi-step tickets to the agent. At 10k/day, if the agent takes 15% that's 1,500 runs — a budget I can state."

The loop (30s). "Read the ticket, look up the order if referenced, search the KB for policy, draft a reply. Step budget of six, because measured runs finish in three or four."

The hard part (30s). "Refunds are irreversible: policy in code, dry-run default, derived idempotency key, approval token bound to the exact amount that the agent cannot mint, append-only audit."

Proof (15s). "A golden set that's mostly refusals and attacks, trajectory checks as well as outcome, traces with cost per run."

Then stop and ask what they want to go deeper on. Filling two minutes with architecture is worse than leaving room for their real question.

5 · Drill 3 · System design (20 min)

Pick one. Cover scope, shape, tools and permissions, failure handling, irreversible actions, security, evaluation, observability, cost — and what you would not build.

  1. Support triage at 10,000 tickets/day, three teams, four permission tiers.
  2. An agent with email, calendar and CRM access for 10,000 employees.
  3. Internal tools exposed to several AI applications across the company.
  4. A refund agent for a marketplace where sellers, not you, hold the funds.
  5. Retrieval over 50,000 documents, three languages, four permission tiers.

Score yourself: did you push back on any part of the premise? Name a cost or latency number? Say what you would leave out? Volunteer a failure mode unprompted? Four yeses is a strong answer.

6 · Drill 4 · Production incident (10 min, verbal)

For each: what do I look at first, candidate causes, immediate mitigation, systemic fix.

  1. "The agent has been looping for forty steps and timing out."
  2. "A customer was refunded twice."
  3. "Cost per ticket tripled overnight and no code shipped."
  4. "The agent cited a policy document that says the opposite."
  5. "Escalation rate went from 12% to 40% this morning."
  6. "A ticket contained instructions and the agent followed them."
  7. "p99 latency is 40s; mean is 3s."
  8. "Eval scores went up but complaints went up too."
🔑
The first question is always the same

Do I have a trace? If the honest answer is no, that is the finding — and saying so is a better response than speculating.

7 · Telling the story honestly

⚖️
Do not imply this shipped to customers

You are an experienced IT and ML engineer who has recently built a substantial, production-shaped agent system. That is the truth and it is a strong position. Claiming years of GenAI production experience is unnecessary and does not survive follow-ups — a well-built project you can defend in depth does.

The sentence that does the work:

🎤

"I've got nine years in software and four to five in ML. GenAI is newer for me, so rather than read about agents I built one properly — a support-triage agent with an approval gate on refunds, an eval suite, tracing and an adversarial test corpus. Most of what made it work turned out to be ordinary engineering: idempotency, retry budgets, least privilege, audit trails."

That last clause reframes your background from a gap into the reason you are credible. Then map it explicitly when relevant — idempotency keys are payment APIs, retry budgets are circuit breakers, trajectory eval is an integration test asserting a call sequence, argument-level authorisation is row-level security, prompt versioning is schema migration plus a feature flag.

And name the two things that are genuinely different, so you do not sound like you are flattening the domain: the caller is probabilistic and may sincerely believe it has not already asked; and there is no parameterised query for natural language, which is why injection defence has to be architectural.

The failure question, which is the one to want

Four real ones, better material than any success:

  • Infinite retry. Failed tool results were filtered out of observed state, so "I have no ticket" stayed true however many times reading it failed.
  • Partial data reached a customer-facing summary. refund_eligible=None formatted into prose and reported as a successful run. Needed two layers: the controller detects, the policy refuses.
  • A self-congratulating critique. The reflection pass scanned the whole history, so the system prompt's own words satisfied its checks and it always came back clean.
  • An eval hole in fully-covered code. Deleting a safety default passed 12/12 until a case was added to pin it.

For "what would you do differently": measure the multi-agent split before building it, and write the eval suite earlier — several of those bugs would have been caught by it rather than by me.

For "what are you weakest on": production operation at scale. Built the mechanisms, have not run them under real traffic for a year. Then say what you would want in month one — real traces, the escalation rate, and a golden set built from actual tickets.

8 · Readiness checklist

  • I can write the loop from memory in 15 minutes and narrate the four decisions.
  • I can give the 2-minute whiteboard answer without notes, and I stop early to ask.
  • I can state the cost of a run and why it is quadratic in steps.
  • I can explain the refund path end to end, including the ambiguous timeout.
  • I lead security answers with capability restriction, not prompt wording.
  • I can name three of my own open exposures without being prompted.
  • I can describe a bug I caused, how I found it, and what it changed.
  • I can say when not to use an agent, a framework, multi-agent, MCP and RAG.
  • I can show a trace and read it aloud.
