Lesson 8 · Making it reliable

Irreversible actions and human approval

⏱ ~4 h total · plan a weekend block 30 min read · 100 min build · 60 min break/debug · 30 min interview Prereq · Lesson 7 Next · Lesson 9
🎯
By the end of this lesson you will be able to
  • Answer "how would you safely let an AI agent spend or refund money?" completely.
  • Explain why business policy belongs in code, not in a prompt.
  • Derive an idempotency key — and explain why a UUID per attempt destroys the mechanism.
  • Bind an approval token to an exact order and amount, and say why "approved" alone is an open cheque.
  • Explain why the audit log is append-only and includes refusals.
  • Handle the case where a payment call times out and you genuinely do not know.
💰
Everything changes with one tool

Every tool so far has been reversible. A wasted lookup_order costs a few tokens. Lesson 7's retries were free.

issue_refund moves money. Now a retry might pay twice, a hallucinated argument might pay the wrong person, and a persuasive ticket might pay someone who is not entitled to anything. Every control in this lesson exists because one of those has happened to somebody.

1 · Recommend versus execute

The first and cheapest decision: make the safe thing the default.

def issue_refund(order_id, amount, reason, approval_token=None, dry_run=True):

dry_run=True. An agent that wants to move money has to say so explicitly. The reasoning is not stylistic — the unsafe path will eventually be reached by an argument nobody validated, so the unsafe path must be the one requiring effort.

And the tool's description does safety work too:

"By default this only CHECKS policy and returns a recommendation -- it does not
 move money. Executing a refund requires dry_run=false AND an approval_token
 issued by a human. Eligibility is decided by policy, not by you: if policy
 refuses, explain the reason to the customer or escalate."

That last clause matters. It tells the model that arguing about eligibility is not part of its job, which removes a whole class of attempted negotiation.

2 · Policy lives in code

🔑
The interview question underneath this

"Where does your business logic live?" If the answer is "in the system prompt", the follow-up will be unpleasant — because a policy in a prompt is a suggestion. A persuasive ticket can argue with it. policy.py cannot be argued with, because the model never gets a vote.

Note the split: the knowledge base describes the refund policy in prose so the agent can quote it to a customer. policy.py enforces it. Those are different jobs and they need different homes.

Two details worth copying:

# Every failed condition is collected, not short-circuited on the first.
if order["already_refunded"]:      reasons.append(...)
if not order["refund_eligible"]:   reasons.append(...)
if order["days_since_purchase"] > MAX_REFUND_DAYS: reasons.append(...)

A customer told "your order is too old" who is also over the amount limit comes back twice, and the agent looks evasive both times. Same instinct as collecting validation faults in Lesson 3.

# A missing field is a refusal, not a default.
missing = [f for f in required if f not in order]
if missing:
    return PolicyDecision(allowed=False, reasons=[f"order data incomplete ..."])

This is Lesson 7's partial-failure problem applied to money. If eligibility could not be read, the answer is no — never "probably fine".

3 · Idempotency

def idempotency_key(order_id, amount, reason):
    material = f"{order_id.upper()}|{amount:.2f}|{reason.strip().lower()}"
    return "idem_" + hashlib.sha256(material.encode()).hexdigest()[:16]
⚠️
Derived from the request. Not random, not time-based.

A UUID per attempt gives every retry a fresh key, so the second attempt looks like a new refund — you have implemented the mechanism and disabled it in the same line. This is the most common way idempotency is got wrong, and it is a good thing to be able to explain crisply.

Deriving from the request means the same request always produces the same key, whoever sends it and however many times. reason is included so two legitimately different refunds on one order — a duplicate charge, and later a returned item — stay distinct.

And when a duplicate is detected, the response is success, not an error:

{"status": "already_refunded", "duplicate": True, "refunded": True,
 "message": "This exact refund was already processed. No second payment was made."}

The caller asked for a state — "this refund exists" — and that state holds. Returning an error invites a workaround, and workarounds around idempotency are how double payments happen.

4 · Approval tokens

Bound to an exact (order, amount) pair:

if record["order_id"] != order_id.upper():   return False, "issued for a different order"
if abs(record["amount"] - amount) > 0.001:   return False, "authorises a different amount"
if record["used"]:                           return False, "already been used"

A token authorising "a refund on ORD-5581" rather than "120.00 on ORD-5581" is an open cheque, and an agent that misread the amount would spend it. Three checks because each has been a real incident somewhere: forged or hallucinated token, token reused for a different refund, replay.

🛡️
The agent cannot mint its own approval

grant_approval() is not in the tool registry. There is a test asserting no tool name contains "approval" or "grant".

A gate the caller can open itself is not a gate — and this is the most common way the control is implemented wrongly. An "approval step" the agent performs is theatre.

5 · The order of the checks is the design

1 does the order exist — semantic validation

2 does policy permit it — policy.py, not the prompt

3 has this exact refund already run — idempotency

4 dry run? stop here and report — recommend vs execute

5 is there a valid human approval — the gate

6 execute, record, audit — durable, append-only

Steps 2 and 3 run before the approval gate deliberately. There is no point asking a human to approve something policy forbids or that already happened — and an approval request for an impossible action trains reviewers to click through. Approval fatigue is a security failure, and it is caused by asking too often.

6 · Append-only audit

  outcome            order            amount  detail
  --------------------------------------------------------------------------
  policy_denied      ORD-5555          49.00  Refund not permitted: the order is 90 days…
  dry_run            ORD-5581         120.00  policy passed; awaiting human approval
  approval_required  ORD-5581         120.00  Executing a refund requires an approval token
  executed           ORD-5581         120.00  duplicate charge

Three rows for one refund: prepared, blocked, executed. A status column you overwrite could not tell that story. The question an audit answers is "what happened, in what order, and who decided" — and an overwritten row cannot answer it.

Every attempt is logged, refusals included. A log containing only successes cannot tell you that an agent tried forty times.

✅
Those last two lines are the whole lesson

Two calls, one payment. The audit log contains exactly one executed row. That is the property you are being asked about when someone says "how do you let an agent spend money".

8 · Break it

1 · Make the key random. Change idempotency_key to return "idem_" + uuid4().hex[:16]. Run the last two lines again. Two payments. The audit log has two executed rows. This is the single most instructive minute in the lesson.

2 · Reuse a token. Approve 480.00 on ORD-5590, then try to spend that token on ORD-5602, then on ORD-5590 for 100.00. Both refused, with different messages. Now delete the amount check and try again — the token becomes an open cheque.

3 · Flip the default. Set dry_run=False as the default. Now every policy-passing refund attempt tries to execute, and only the missing token stops it. One default, one layer of defence removed.

4 · Reorder the checks. Move the approval gate before the policy check. Now a human is asked to approve a refund on a 90-day-old order. Do that a hundred times and your reviewers stop reading.

5 · The ambiguous timeout.

set_faults(FaultPlan(slow={"issue_refund": 3.0}))
guarded_execute("issue_refund", {...}, timeout_s=0.5)
# {'error': 'timeout', 'message': '... Whether it took effect is unknown.'}

You do not know whether the money moved. Retrying might double-pay; not retrying might strand a customer. The only safe design is to have decided in advance — which is exactly what the idempotency key bought you: the follow-up call is safe either way. Without it you are choosing between two bad options with a customer waiting.

9 · The production concern

The ledger must be as durable as the payment. Ours is a JSONL file, which is honest for a course and wrong for production: if the ledger write fails after the payment succeeds, the next retry pays twice. Real systems make the payment and the idempotency record one transaction, or use the payment provider's own idempotency support.

Approval needs a real UI, expiry and signing. Our tokens are in-memory and never expire. A token that lives forever is a credential.

Reconciliation. Whatever you do, some records will disagree with the payment provider. You need a job that compares them and a runbook for the differences, because ambiguous timeouts guarantee drift.

Blast radius. Per-caller caps (Lesson 9), daily totals, and an anomaly alert on refund volume. If the agent starts refunding everything, the question is how long before anyone notices.

🧰
You already know this

Idempotency keys, approval workflows, append-only audit, transaction boundaries, reconciliation, exactly-once versus at-least-once. This is payments engineering, and none of it is AI-specific. The only new part is that the caller is a probabilistic system which may sincerely believe it has not already asked. That is a genuinely strong thing to say in an interview: it reframes the problem as one you already know how to solve.

10 · Interview practice

Two-minute answer — "How would you safely let an AI agent spend or refund money?"

🎤

"I'd start by not letting it. The tool's default is a dry run: it checks policy and returns a recommendation, and moving money needs an explicit flag plus a token. The safe path has to be the default, because the unsafe path eventually gets reached by an argument nobody validated.

Then five layers. Policy in code, not the prompt — a prompt policy is a suggestion a persuasive ticket can argue with. An idempotency key derived from the request, so a retry can't pay twice; derived, not a UUID per attempt, because a fresh key per attempt disables the mechanism you just built. An approval token bound to the exact order and amount, minted by a function the agent cannot call — a gate the caller can open itself isn't a gate. An append-only audit log including refusals, because a log of successes can't tell you the agent tried forty times. And caps on per-caller and daily amounts to bound the blast radius.

The order matters: policy and idempotency are checked before a human is asked, because asking someone to approve an impossible action trains them to click through — approval fatigue is a security failure.

The case I'd want to talk about is the timeout. If the payment call times out you don't know whether it happened. Retrying might double-pay, not retrying might strand the customer — and the idempotency key is what makes that decision safe in advance rather than at incident time. Almost none of this is AI-specific; it's payments engineering, and the only new part is a caller that may sincerely believe it hasn't already asked."

Q System design · Design an approval workflow for an agent taking customer-visible actions. ›

Tier by consequence, not uniformly — approving everything produces fatigue and fatigue produces rubber-stamping. Reversible and small: auto-execute with audit. Irreversible but bounded: single approver, token bound to the exact action. Above a threshold, or unusual: second approver.

Mechanics: the agent prepares a request containing the action, the amount, the policy verdict and the evidence it relied on — the reviewer needs to check the reasoning, not just click yes. Tokens are signed, scoped to one action, single-use, and expiring. The agent cannot mint them.

Then the parts that decide whether it works in practice: measure approval latency, because a gate that adds two days will be routed around; measure the approval rate, because 99% approvals means the gate is theatre and the threshold is wrong; and give reviewers a reject reason that feeds back into policy, so refusals improve the system instead of just stopping it.

Q Debugging · A customer was refunded twice. Walk me through the investigation. ›

Start at the audit log and count executed rows for that order. Two rows means two distinct requests reached execution; one row plus two provider payments means the provider was called twice for one request.

If two rows: compare the idempotency keys. Different keys means the requests genuinely differed — most likely the reason or the amount varied slightly, so a retry looked new. That is a key-derivation bug: too much variable material in the key. Same key with two rows means the duplicate check didn't run or the ledger write failed between them.

If one row and two payments: the failure is between us and the provider — a timeout followed by a retry at their end, which is what provider-side idempotency support exists for.

Then the systemic fix, which is the answer they want: make the payment and the ledger record one transaction, and add reconciliation against the provider so this is detected by a job rather than by a customer.

Q Coding · Implement idempotent refunds. ›

Derive a key by hashing the normalised request — uppercase the id, fix the amount to two decimals, lowercase and strip the reason. Check a durable store for that key before acting. If present, return the original outcome as a success with a duplicate flag. If absent, act, then record the key and the outcome — ideally in the same transaction as the action.

Say out loud: "derived, not random, or every retry looks new"; "the duplicate response is success, not an error, or callers build workarounds"; and "the record and the action need to be atomic, otherwise a crash between them re-opens the hole".

Q Senior follow-up · Where is your remaining exposure? ›

Name it before you are asked. The ledger is not transactional with the payment — a crash between them allows a double payment on retry. Tokens are in-memory and never expire, so a leaked token is a standing credential. No reconciliation, so a provider-side discrepancy is invisible until a customer complains. No aggregate caps, so nothing stops a hundred individually-valid refunds. And the audit log is append-only by convention, not enforcement — a file anyone can edit is not an audit trail.

Being able to enumerate your own gaps is a stronger signal than a clean-sounding design, because every real system has them and the question is whether you know where they are.

Q Senior follow-up · Would you ever let the agent refund without a human? ›

Yes, under conditions I'd state up front: a low amount cap, a category with an unambiguous policy (a confirmed duplicate charge is arithmetic, not judgement), full audit, aggregate daily limits, an anomaly alert, and a measured false-positive rate from evaluation before it ships.

The framing I'd use: the question isn't "human or not", it's "what is the cost of being wrong, times how often, versus the cost of the review". Approving thousands of £5 duplicate refunds by hand has its own failure mode — reviewers stop reading, and the gate becomes decorative while remaining expensive.

What I would not automate is anything requiring judgement about intent, anything above a threshold where a single error is material, or anything where the policy has ambiguity a model would have to resolve.

11 · Recap

  • dry_run=True is the default. The unsafe path must be the one requiring effort.
  • Policy in code, not the prompt. A prompt policy is a suggestion.
  • A missing eligibility field is a refusal, never "probably fine".
  • Idempotency keys are derived from the request. A UUID per attempt disables the mechanism.
  • A duplicate is a success response, not an error — errors invite workarounds.
  • Approval tokens bind to an exact order and amount, are single-use, and the agent cannot mint them.
  • Check policy and idempotency before asking a human. Approval fatigue is a security failure.
  • Append-only audit, refusals included. Three rows for one refund tells a story a status column cannot.
  • A timeout on a payment means unknown. The idempotency key is what makes the follow-up safe.
