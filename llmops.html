Deep Dives / LLMOps - operating LLM apps

1 · What you already know

You can evaluate an application, trace a run, and guard what goes in and out. Each of those is one practice.

This page is what they add up to, and what genuinely changes when the thing you operate is non-deterministic and you did not train it.

2 · What breaks now

The application works. Then four ordinary operational questions arrive, and none of them has an answer:

The questionWhy it cannot be answered
Why is quality worse than last month?Nobody recorded which prompt version served which request
What does a request cost?Token counts were available on every call and were not captured
Which change caused this?Prompts were edited in place, so there is no history to bisect
Is the new model better?There is no fixed set of cases to run both against

Every one of these is answerable in ordinary software, and the reason they are not answerable here is the same: the prompt was treated as configuration rather than as code.

A prompt decides behaviour. It is code with a different file extension, and an edit to it is a deploy.

3 · Simple breakdown - LLMOps vs MLOps

A LLMOps

What it is. LLMOps is the practice of running an application built on a model you did not train, where the artefacts you version are prompts, configuration and retrieval corpora.

Core purpose. It keeps a non-deterministic application improvable and defensible: you can say what changed, what it cost, and whether quality moved.

Execution model.

Architecture under the hood. A prompt registry, an evaluation suite, tracing with token accounting, guardrails, and a feedback path from production failures back into the suite.

State handling. Versions of prompts and configuration, evaluation results per version, and traces per run. The model weights are someone else's and do not change.

Limitations and advanced features. Quality is multi-dimensional and partly subjective, so no single metric gates a release. Cost is per request rather than per training run, and a provider can change the model under you.

B MLOps

What it is. MLOps is the practice of running an application around a model you trained, where the central artefacts are datasets, training runs and model weights.

Core purpose. It makes training reproducible and deployment safe for a model whose behaviour is fixed once it ships.

Execution model. Data is prepared, a training run produces weights, those weights are evaluated against a held-out set and promoted to serving.

Architecture under the hood. A feature store, a training pipeline, a model registry, and a serving layer with monitoring for drift.

State handling. Datasets, experiments and weights, all versioned. A deployed model is a fixed artefact until you replace it.

Limitations and advanced features. Retraining is slow and expensive, so change is infrequent. Drift is about the input distribution moving away from the training data.

In short - which one to choose

  • Use LLMOps when you call a model you did not train, and your leverage is in prompts, retrieval and orchestration.
  • Use MLOps when you own the training. Fine-tuning a model puts you back in this world, with its dataset and registry problems.
  • Most production systems need both, because a fine-tuned model inside an LLM application has an MLOps problem wrapped in an LLMOps one.

4 · Without the technology

Without LLMOps, the workflow is a person editing a string and watching.

This is genuinely fast, and for a prototype it is right. Three things break at the point users depend on it:

  • No attribution. Quality moved, and three prompt edits and a model upgrade all happened that week.
  • No rollback. Reverting means finding the previous string in a diff and hoping nothing else changed with it.
  • No comparison. "It seems better" is not a claim you can defend, and it is not a claim you can disprove either.

The fix is not a platform. It is treating four things as versioned artefacts - the prompt, the model and its parameters, the retrieval corpus, and the evaluation set - and recording which combination produced each result.

5 · Runtime mechanics

One change moves through five stages.

  1. Version. The prompt, model, parameters and corpus revision are pinned as one configuration with an identifier.
  2. Evaluate. The golden set runs against that configuration, producing per-metric numbers.
  3. Compare. Those numbers sit next to the current configuration's numbers, and a gate decides whether the change may ship.
  4. Deploy. The configuration is served, and every response reports which version produced it.
  5. Observe and feed back. Traces record cost, latency and quality signals, and every real failure becomes a new case in the golden set.

Stage 5 is what makes it a loop. An application whose production failures never reach its evaluation set stops improving, however good the first four stages are.

6 · The components, one at a time

The prompt registry

Prompts live in files, versioned in the repository, and are referenced by version rather than pasted.

A hosted prompt manager adds editing without a deploy. That convenience is also its risk: a prompt changed outside version control is a change nobody reviewed.

Experiment tracking

One row per configuration, so a comparison is a lookup rather than a memory.

Read the third row. Two points of quality for twenty times the cost is a decision someone should make deliberately, and it is invisible without this table.

Evaluation in the loop

The suite from the evaluation page, wired as a gate rather than a report. It runs on every configuration change and fails the build when a metric drops.

Observability

Traces with a run id, token counts and cost per span. This is what turns "it was slow yesterday" into a specific span.

Guardrails in operations

The input and output stages, with their decisions recorded so a firing rate can be tracked over time. A guardrail whose firing rate you do not watch is a check you cannot tune.

The feedback path

This is the part most teams never build, and it is the one that compounds.

7 · State and data flow

  1. What data is state? The configuration registry, evaluation results per configuration, and traces per run.
  2. Who writes each field? A deploy writes the configuration; the suite writes results; the runtime writes traces.
  3. Who reads each field? The comparison step, the gate, and whoever is investigating a regression.
  4. Replaced, appended or merged? All three append. A configuration is never edited in place, or attribution is lost.
  5. What reducer controls merging? None. The configuration id is the key that joins them.
  6. Is it only in process memory? No. None of it is useful unless it outlives the process.
  7. Is it checkpointed? Each evaluation run is a record; each trace is a record.
  8. Is it in a database? Yes, or committed files. Either works if versioned.
  9. How long does it survive? Configurations and results indefinitely; traces per your retention policy, because they hold customer data.
  10. What thread, user or key retrieves it again? The configuration id and the run id. Those two joined are the whole of LLMOps.

Row 4 is the discipline everything else rests on. An edited-in-place prompt destroys the join, and with it every question in section 2.

9 · Break it

Deploy a prompt change without running the suite. It is a two-word edit and it plainly cannot break anything.

Nothing fails. No alert fires. Quality metrics are not watched in production, because the suite is the quality signal and the suite was not run.

The bug is findable in ten seconds and the attribution is impossible. The failure is not the prompt edit; it is that a change shipped with no measurement and no version stamped on its output.

10 · Fix it

1 · Make the gate unavoidable. If shipping requires a green suite, a prompt edit cannot skip it.

2 · Stamp every response with the configuration and run id, so attribution is a lookup rather than an investigation.

3 · Watch a small number of production metrics, not just offline scores.

These are the ones that move when a prompt regresses, and they move before anyone complains.

4 · Keep the previous configuration deployable, and test that path. A rollback you have never exercised is a plan rather than a capability.

5 · Add the failure as a case. The invented policy becomes a golden-set case the same day it is found.

13 · Interview preparation

Q. What is LLMOps and how is it different from MLOps?

LLMOps is MLOps for apps built on foundation models. You usually don't train the model, so the focus moves from training pipelines and retraining-on-drift to prompts/config versioning, retrieval, evaluation, observability, guardrails, and token cost/latency of the app around a hosted model.

Q. Walk me through the LLMOps lifecycle.

Experiment with prompts/models/config → evaluate on a golden set → deploy with guardrails → observe via traces (cost, latency, quality) → feed real failures back into the next experiment. It's a continuous loop.

Q. Why version prompts and pin models?

The prompt is the behavior-defining code, so changes need history and rollback. Models change under you - a silent provider update can shift outputs - so you pin the version and re-run evals before adopting a new one.

Q. How do you reduce LLM cost without wrecking quality?

Baseline first, then apply one lever at a time: trim/compress context, cap output length, right-size the model per task, cache, and cut unnecessary agent steps - stopping at the threshold where quality starts to degrade.

Q. What's the difference between offline and online evaluation?

Offline runs on a curated golden set before deploy and gates releases (CI for prompts). Online runs on live traffic - trace scores and user feedback - to catch quality drift and surface new failure cases in production.

Q. What does a trace contain and why does it matter?

One request end-to-end: each step, tool call, prompt, response, tokens and latency. It's the foundation for debugging, cost/latency metrics, and attaching quality scores - you can't operate or improve what you can't see.

14 · In short, and what comes next

Remember these six:

  • A prompt is code. Version it, review it, and treat an edit as a deploy.
  • Pin the model version. "Latest" is a behaviour change nobody deployed.
  • Stamp every response with a configuration id and a run id, or attribution is impossible.
  • The evaluation suite is the gate, and it belongs in the pipeline rather than in a habit.
  • Capture tokens from day one. Cost cannot be reconstructed after the fact.
  • Production failures become golden-set cases. That feedback path is what compounds.
🔑
The one idea to remember

LLMOps is ordinary release engineering applied to an artefact people do not think of as code. Almost every failure in this page comes from editing a prompt in a way nobody would accept for a function.
