LLMOps & Observability

LLMOps is how you run an LLM application after launch: version everything that changes behaviour, test every change, watch production, and feed failures back. Observability is the part that shows what each request actually did. Interviewers ask because most LLM failures are silent - the app keeps answering, just worse.

⏱ 15–30 min Difficulty · Interview essentials Prereq · 14 LLM Evals

Everything on this page comes back to five ideas.

  1. A prompt is code: version it, review it, and treat an edit as a deploy.
  2. Pin exact model versions, and stamp a configuration id on every response.
  3. Gate every change with the golden set in CI.
  4. Trace every request: spans, tokens, cost, latency, and quality scores that can arrive later.
  5. Mask personal data before it is stored, and turn every real failure into a test case.

1 · The idea in one minute

In classic MLOps you train the model, so most of the work is datasets, training runs and retraining. With LLM apps you usually call a model someone else trained. What changes the app's behaviour is the prompt, the model version, its parameters (temperature, max tokens) and the retrieval data.

Think of a restaurant chain. A new recipe is tasted against a fixed tasting menu before it reaches the restaurants. Every order ticket records which recipe version was used. And every complaint is traced to its ticket, then added to the tasting menu. In an LLM app:

  • The recipe is the configuration: prompt + model + parameters + data, versioned together.
  • The tasting menu is the golden set, run as a gate before release (see 14 · LLM Evals).
  • The order ticket is a trace: a record of one request, step by step, with tokens, cost and time.
  • The complaint loop is feedback: real failures become new test cases.

A prompt is code. An edit to it is a deploy.

The lifecycle, in five steps

  1. Version the prompt, model, parameters and data revision together, under one configuration id.
  2. Evaluate that configuration on the golden set.
  3. Gate: compare with the current version, and ship only if it is not worse.
  4. Deploy, stamping the configuration id on every response.
  5. Observe traces, cost, latency and quality scores, and turn real failures into new test cases.

2 · The parts you must know

PartWhat it doesWhat goes wrong without it
Prompt versioningPrompts live in version control, or in a prompt manager with labels such as "production", and are loaded by versionNobody can say which edit caused a drop, and there is nothing to roll back to
Model pinningUses an exact model version, not an alias such as "latest"The provider updates the model and behaviour changes with no deploy of yours
Configuration idOne id for prompt + model + parameters + data revision, stamped on every responseFinding the cause of a regression is an investigation instead of a lookup
Evaluation gateThe golden set runs in the deploy pipeline and can fail itUntested prompt edits reach users
TracingRecords each request end to end: every step, prompt, answer, tool call, tokens and time"It was slow (or wrong) yesterday" cannot be diagnosed
Cost and latency trackingTokens and cost per request, per feature and per customer; p95 latency per stepSurprise bills, and no idea which step is slow
Quality scoresScores attached to traces from users (thumbs), rules (cited a source?) and a judge model on a sampleYou know what happened but not whether it was any good
Feedback loop and rollbackReal failures become golden-set cases; the previous configuration stays deployableThe system stops improving, and a bad change stays live while you scramble

The five objects of a tracing tool

ObjectWhat it is
TraceOne whole request, from start to finish. Everything else sits inside it
SpanOne step inside the request, such as retrieval or a tool call, with a start and end time. Spans can contain spans
GenerationA span for a model call. It also records the model, the prompt, tokens and cost
ScoreA quality number attached to a trace, often long after the request ended
Session and userGroups traces into one conversation, or into one person's activity

These are Langfuse's names. LangSmith calls each step a "run", and tools built on OpenTelemetry, such as Arize Phoenix, call them spans. The ideas are the same. Tools you can mention:

  • Langfuse - open source and self-hostable: tracing, prompt management with labels, datasets and scores.
  • LangSmith - from the LangChain team: tracing, datasets, evaluations and prompt management.
  • Arize Phoenix - open source, built on OpenTelemetry: tracing and evaluations.

A general application-monitoring tool tracks speed and errors. LLM tools add what matters most here: token cost, prompt versions, and a place to record that an answer was wrong.

What to watch in production

Refusal rate, citation rate, thumbs-down rate, escalations to a human, guardrail firing rate, cost per answered request, and p95 latency. These move when a prompt regresses, usually before anyone complains.

Q In the restaurant chain, what are the recipe, the tasting menu, the order ticket and the complaint loop? ›
The recipe is the configuration (prompt, model, parameters and data, versioned together), the tasting menu is the golden set, the order ticket is a trace, and the complaint loop turns real failures into new test cases.
Q You did not train the model. What changes your app's behaviour? ›
The prompt, the model version, its parameters such as temperature and max tokens, and the retrieval data.
Q Name the five objects of a tracing tool. ›
Trace (one whole request), span (one step inside it), generation (a span for a model call, with tokens and cost), score (a quality number, often added later), and session and user (which group traces together).
Q A batch job wrote 500 results but only 487 traces. What happened? ›
Tracing SDKs send data in background batches, and the program exited before the last batch was sent. Call flush before the program exits.
Q Which production metrics usually move before anyone complains about a prompt regression? ›
Refusal rate, citation rate, thumbs-down rate, escalations to a human, guardrail firing rate, cost per answered request, and p95 latency.

5 · Interview questions

Answer each one out loud before you open it.

Q What is LLMOps, and how is it different from MLOps? ›
LLMOps is MLOps for apps built on foundation models. You usually don't train the model, so the focus moves from training and retraining to versioning prompts and configuration, retrieval data, evaluation, observability, guardrails, and token cost and latency.
Q Walk me through the LLMOps lifecycle. ›
Version the configuration, evaluate it on the golden set, gate the release against the current version, deploy with the configuration id stamped on responses, then observe traces, cost and quality - and feed real failures back as new test cases. It is a loop.
Q Why version prompts and pin model versions? ›
The prompt defines behaviour, so it needs history, review and rollback like code. Models can change under an alias, and providers retire old versions, so you pin an exact version and re-run evals before moving to a new one.
Q What does a trace contain, and why do you need one? ›
One request end to end: each step as a span, every model call with its prompt, answer, tokens, cost and latency, tool calls, and the user and session ids. It is how you debug a bad answer, find the slow step, and attach quality scores to what actually happened.
Q Where do quality scores come from? ›
Three places: users (thumbs up or down), rules in code (cited a source, valid JSON), and a judge model grading a sample. Store each under its own name, so you can see when the judge and the users disagree.
Q Why is tracing sent asynchronously, and what is the catch? ›
So that recording a request does not slow it down: the SDK buffers data and sends it in background batches. The catch is that a short script or serverless function that exits without calling flush loses its last batch, with no error.
Q How do you reduce LLM cost without hurting quality? ›
Measure a baseline first, then change one thing at a time and re-run evals: trim the context, cap output length, route easy requests to a smaller model, cache repeated prompts and answers, and cut unnecessary agent steps. Stop when quality starts to drop.
Q A bigger model scores 2 points higher but costs about 19 times more. What do you do? ›
Make it a deliberate decision with both numbers on the same golden set. Often the answer is routing: the cheaper model by default, the bigger one only for the hard cases where it actually wins.
Q What is the data-protection risk of a tracing platform? ›
Traces store full prompts and answers by default, so anything a user types - card numbers, health details - lands in the trace store. Mask personal data before it is sent, restrict who can view traces, and set a deliberate retention period.
