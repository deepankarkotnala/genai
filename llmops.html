LLMOps

LLMOps is the set of practices and tooling for taking an LLM application from a notebook demo to a reliable production system — and keeping it good. It covers how you version prompts and models, track experiments, deploy, observe, evaluate, control cost and latency, and improve from real usage. This page is the interview-focused map.

⏱ Deep study · 5–8 h Interview-focused Lifecycle + tooling
🎯
The one-line answer interviewers want

LLMOps is MLOps adapted to applications built on foundation models. The model is usually a third-party API you don't train, so the operational focus shifts from training pipelines to prompts, retrieval, evaluation, observability, guardrails, and cost/latency of the app around the model.

1 · What LLMOps is — and how it differs from MLOps

Classic MLOps is built around training your own model: data pipelines, feature stores, training runs, model registries, retraining on drift. In most GenAI apps you don't train the model — you call a foundation model (Claude, GPT, an open model) and build value around it. That changes what "ops" means.

ConcernClassic MLOpsLLMOps
Core artifactA trained model + its weightsA prompt + config + retrieval + tools around a hosted model
"Training"Model training / fine-tuningPrompt engineering, RAG design, occasional fine-tuning
OutputDeterministic-ish numeric predictionsProbabilistic free text → needs multi-dimensional evals
Main runtime risksData/concept driftHallucination, prompt injection, cost blow-ups, latency
Cost driverGPU training + servingTokens per request × volume (API cost)

2 · The LLMOps lifecycle

A continuous loop, not a one-way pipeline. Each stage below is a common interview probe.

Prompt / model / config
Experiment & track compare configs
Evaluate golden set + metrics
Deploy with guardrails
Observe traces · cost · latency
Feedback → improve
The operating loop: experiment → evaluate → deploy → observe → feed real failures back into the next experiment.

3 · Prompt, model & config management

In LLMOps the prompt is the code. Treat it that way:

  • Version prompts and system instructions — every change is traceable and rollback-able, like git for prompts.
  • Pin the model & parameters — model name/version, temperature, max tokens, tool descriptions. A provider silently updating a model can change behavior; pin and re-evaluate on upgrade.
  • Separate config from code — so non-engineers can iterate on prompts without redeploying, and so you can A/B them.

4 · Experiment tracking

Replace informal trial-and-error with reproducible comparisons. Every result should trace back to the exact prompt, model, parameters, tool descriptions, dataset and agent instructions that produced it.

🧪
Concrete example

Test 3 prompt versions × 2 models = 6 configurations over the same test set; record inputs, outputs, quality score, latency, tokens and cost; build a comparison matrix; pick the best on agreed criteria — and prove it by re-running the chosen config and getting the same result.

⚠️
Interview trap

The highest quality score is not automatically the best choice — weigh it against latency and cost, and against the business need. Combinations also explode fast, so control the grid.

5 · Evaluation in the loop

Evaluation isn't a one-off — it's a gate. Run your eval suite on every prompt/model change (CI for prompts), and monitor quality after deploy.

🔗
Full treatment

Methods, golden datasets, LLM-as-judge, and RAG/agent/safety metrics are covered in LLM Evals →. In LLMOps terms: offline evals (pre-deploy, on a golden set) gate releases; online evals (post-deploy, on live traces + user feedback) catch drift.

6 · Deployment & serving concerns

Model routing & fallback

Route simple tasks to a cheaper/smaller model; fall back to another provider if one is down or rate-limited.

Caching

Cache identical/similar requests and reuse prompt prefixes (prompt caching) to cut cost and latency.

Rate limits & retries

Handle provider 429s with backoff; make retries idempotent so you don't double-charge or double-act.

Streaming

Stream tokens so time-to-first-token is low and the UX feels fast even when total latency is high.

7 · Observability & tracing

You cannot operate what you cannot see. The core unit is a trace: one request captured end-to-end, including every agent step, tool call, prompt, response, token count and latency.

  • Debugging — replay a failed request and see exactly which step went wrong.
  • Metrics — success/failure rate, latency per step, tokens and cost per agent/tool, retries and loops.
  • Quality scores & user feedback attached to traces for online evaluation.

8 · Cost, token & latency optimization

A direct, measurable part of the job — and a frequent interview topic. The levers:

LeverEffect
Prompt compression / trimming contextFewer input tokens → lower cost & latency
Right-size the model (small model for simple tasks)Large cost savings on low-risk work
Cap & control output lengthOutput tokens are often the bigger cost
Caching / prompt cachingAvoid paying for repeated work
Remove unnecessary agent/tool stepsFewer LLM calls per request
StreamingBetter perceived latency (TTFT)
⚠️
The key trade-off to state out loud

Every optimization has a point where it starts to hurt quality. The right method is: measure a baseline (quality, tokens, latency, cost), apply one change at a time, and find the threshold where quality degradation becomes unacceptable. Optimize to that line, not past it.

9 · Guardrails & safety in operations

Runtime protection is an ops responsibility: input/output guardrails, PII redaction, prompt-injection defense, scope enforcement — plus logging every guardrail trip so you can measure false-positive rate and tune it.

10 · Feedback loops & continuous improvement

What closes the loop: capture real failures (thumbs-down, escalations, low-scoring traces), fold them into the golden dataset, and re-run experiments. Production usage becomes the source of your next eval cases — this is how an LLM app gets better over time without retraining a model.

11 · Tooling landscape

  • Observability / tracing: Langfuse, LangSmith, Arize Phoenix.
  • Evaluation: RAGAS, DeepEval, promptfoo, OpenAI Evals (see LLM Evals).
  • Orchestration: LangChain, LlamaIndex, LangGraph (see LangGraph →).
  • Experiment/registry: MLflow, Weights & Biases, LangSmith datasets.
  • Serving/gateway: vLLM, LiteLLM, provider gateways (routing, caching, rate limiting).

12 · Interview cheat-sheet

Q. What is LLMOps and how is it different from MLOps?

LLMOps is MLOps for apps built on foundation models. You usually don't train the model, so the focus moves from training pipelines and retraining-on-drift to prompts/config versioning, retrieval, evaluation, observability, guardrails, and token cost/latency of the app around a hosted model.

Q. Walk me through the LLMOps lifecycle.

Experiment with prompts/models/config → evaluate on a golden set → deploy with guardrails → observe via traces (cost, latency, quality) → feed real failures back into the next experiment. It's a continuous loop.

Q. Why version prompts and pin models?

The prompt is the behavior-defining code, so changes need history and rollback. Models change under you — a silent provider update can shift outputs — so you pin the version and re-run evals before adopting a new one.

Q. How do you reduce LLM cost without wrecking quality?

Baseline first, then apply one lever at a time: trim/compress context, cap output length, right-size the model per task, cache, and cut unnecessary agent steps — stopping at the threshold where quality starts to degrade.

Q. What's the difference between offline and online evaluation?

Offline runs on a curated golden set before deploy and gates releases (CI for prompts). Online runs on live traffic — trace scores and user feedback — to catch quality drift and surface new failure cases in production.

Q. What does a trace contain and why does it matter?

One request end-to-end: each step, tool call, prompt, response, tokens and latency. It's the foundation for debugging, cost/latency metrics, and attaching quality scores — you can't operate or improve what you can't see.
