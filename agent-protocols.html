Agent Protocols — MCP · A2A · A2UI

An agent has exactly three outward boundaries: it reaches down to tools and data, sideways to other agents, and up to the human looking at a screen. Each boundary now has an open protocol — MCP (Model Context Protocol), A2A (Agent2Agent) and A2UI (Agent-to-UI). This page is the brief on all three: what each one actually is, the wire format in enough detail to be credible, how they compose in one system, and how to answer the interview question "how do these differ?" without hand-waving.

1 · Why protocols at all — the M×N problem

Before standards, every integration was bespoke. If you had M agent applications and N things to connect them to — databases, SaaS APIs, other teams' agents, front-end frameworks — you wrote M×N adapters. Each one had its own auth, its own error shape, its own idea of what "a task" meant. Change either side and adapters broke.

A protocol collapses that to M+N: every client speaks the protocol, every provider speaks the protocol, and the middle is a contract instead of glue code. That is the entire economic argument, and it's the same argument three times over.

🔌

Down — MCP

Agent ↔ tools, data, and capabilities. "What can I do, and what can I read?"

🤝

Sideways — A2A

Agent ↔ agent, across vendors and frameworks. "Who else can help, and can I delegate to them?"

🖼️

Up — A2UI

Agent ↔ human interface. "Instead of a wall of text, render the right widget."

🔑
The one-line distinction to memorise

MCP gives an agent capabilities. A2A gives an agent colleagues. A2UI gives an agent a face. They are complementary layers, not competitors — a serious system can use all three at once, and each is governed independently.

2 · The stack, in one picture

One agent, three boundaries. A2UI faces the user, A2A faces peer agents, MCP faces tools and data.

3 · MCP — Model Context Protocol (the tool boundary)

MCP is an open standard, introduced by Anthropic in November 2024 and now with broad multi-vendor adoption, for connecting a model to tools and data. It is the "USB-C of AI tooling": write a capability server once, and any MCP-capable host — Claude apps, IDEs, your own agent — can use it without custom integration code.

3.1 The shape of it

ConceptWhat it isWho controls it
ToolAn action the model can invoke, with a JSON Schema for its argumentsModel-controlled (the LLM decides to call it)
ResourceRead-only data addressed by URI (a file, a record, a query result)Application-controlled
PromptA reusable, parameterised prompt template the server offersUser-controlled (usually surfaced as a slash command)

Messages are JSON-RPC 2.0. Transports are stdio (local subprocess) and Streamable HTTP (remote). Discovery happens at runtime via tools/list, resources/list and prompts/list — nothing is hard-coded in the client, which is exactly why swapping a server needs no client change.

🗓️
Know the 2026-07-28 revision — it is the biggest change since launch

The 2026-07-28 spec revision makes MCP stateless at the protocol layer: the initialize/initialized handshake and the Mcp-Session-Id header are gone, with client metadata travelling in _meta on every request. Practically, that removes the sticky-routing and shared-session-store requirement that made horizontal scaling painful — any server instance can serve any request. It also adds a formally governed Extensions framework (reverse-DNS identifiers, independent versioning), ships MCP Apps (server-rendered HTML in sandboxed iframes) and Tasks (long-running work via task handles from tools/call) as official extensions, hardens authorization, and introduces a deprecation policy with a minimum 12-month window. Under that policy, Roots, Sampling and Logging are deprecated — replaced by tool parameters/resource URIs/config, direct LLM provider APIs, and stderr/OpenTelemetry respectively. Tools, resources and prompts are unchanged. If you learned MCP from a 2025 tutorial, the handshake and session header are the two things to unlearn.

4 · A2A — Agent2Agent (the peer boundary)

A2A is an open protocol for agents to discover each other and delegate work across organisational, vendor and framework boundaries. Google introduced it in April 2025 and transferred the spec and SDKs to the Linux Foundation in June 2025 for vendor-neutral governance; it reached v1.0 in 2026, with production SDKs in Python, JavaScript, Java, Go and .NET.

The problem it solves is different from MCP's. MCP asks "how does a model call a function?" — a mostly synchronous, request/response question. A2A asks "how does agent A hand a whole job to agent B, when B is opaque, might take twenty minutes, might need to come back and ask a clarifying question, and belongs to another company?" That demands a first-class notion of a long-running task, not a function call.

4.1 Discovery — the Agent Card

An A2A server publishes a JSON Agent Card at a well-known path, following RFC 8615:

https://{agent-domain}/.well-known/agent-card.json
{
  "protocolVersion": "1.0",
  "name": "DocumentProcessor",
  "description": "Processes and analyzes documents",
  "url": "https://agent.example.com/a2a",
  "version": "1.0.0",
  "capabilities": {
    "streaming": true,
    "pushNotifications": true,
    "extendedAgentCard": false
  },
  "defaultInputModes":  ["text/plain", "application/pdf"],
  "defaultOutputModes": ["text/plain", "application/json"],
  "skills": [
    { "name": "analyze-document", "description": "Analyzes document content" }
  ],
  "securitySchemes": [
    { "type": "apiKey", "name": "api_key", "in": "header" }
  ]
}

The card is the whole discovery story: identity, endpoint, declared skills, negotiated capabilities, and the auth schemes required. Cards can be cryptographically signed (canonicalised JSON with ECDSA/RSA) so a client can verify who it is about to trust, and an authenticated Extended Agent Card can reveal additional skills only to callers who have logged in.

🎭
Opacity is the point

A2A deliberately treats a remote agent as a black box. You learn its skills, not its tools, prompts, model or internal state. That is what makes cross-company collaboration commercially possible — the other team is not obliged to expose their implementation, and you are not coupled to it.

4.2 The data model

ObjectRole
AgentCardPublished metadata: identity, endpoint, skills, capabilities, security schemes
AgentSkillOne declared capability, so callers can select an agent before sending work
TaskThe unit of work: stable ID, lifecycle state, message history, produced artifacts
MessageA turn of communication, with a role (user / agent) and one or more Parts
PartSmallest content unit — text, raw bytes, a URL, or structured JSON
ArtifactA task output (document, image, structured data) — deliverables, as distinct from conversation
ExtensionOptional negotiated add-on capability, declared in the card

The Message/Artifact split is worth pausing on: messages are how the two agents talk, artifacts are what the work produced. Conflating them is the most common modelling mistake when people first implement A2A.

4.3 Task lifecycle

A task moves SUBMITTED → WORKING, then reaches a terminal state — COMPLETED, FAILED, CANCELED or REJECTED. Crucially it can also enter interrupted states mid-flight: INPUT_REQUIRED when the remote agent needs a clarification from the caller, and AUTH_REQUIRED when it needs credentials to proceed. Those two states are why A2A is a protocol and not just a webhook convention — they make "the other agent needs to ask you something" a modelled, resumable event rather than a failure.

4.4 Operations and bindings

The abstract operations are SendMessage, SendStreamingMessage, GetTask, ListTasks, CancelTask, SubscribeToTask, push-notification configuration (create / get / list / delete), and Agent Card retrieval. Those map onto three normative bindings: JSON-RPC 2.0 over HTTPS (primary), gRPC with protobuf, and HTTP+JSON/REST.

JSON-RPC 2.0 · SendMessage
// → request
{
  "jsonrpc": "2.0",
  "id": "request-1",
  "method": "SendMessage",
  "params": {
    "message": {
      "messageId": "msg-123",
      "role": "ROLE_USER",
      "parts": [ { "text": "Summarize this document" } ]
    },
    "configuration": { "returnImmediately": false }
  }
}

// ← response: a Task, not just a string
{
  "jsonrpc": "2.0",
  "id": "request-1",
  "result": {
    "task": {
      "id": "task-456",
      "contextId": "ctx-789",
      "status": { "state": "TASK_STATE_COMPLETED",
                  "timestamp": "2026-07-28T10:00:00Z" },
      "artifacts": [
        { "id": "art-001",
          "parts": [ { "text": "Summary: The document discusses..." } ] }
      ]
    }
  }
}

For work that outlives a request: streaming (declared via capabilities.streaming) pushes TaskStatusUpdateEvent and TaskArtifactUpdateEvent over a persistent connection, while push notifications (capabilities.pushNotifications) POST to a webhook the client registered — the right choice when a task runs for hours and holding a connection open is unreasonable. Plain GetTask polling is always available as the floor.

4.5 Security

TLS is required. The card declares which schemes it accepts: API key, HTTP Basic/Bearer, OAuth 2.0 (authorization code, client credentials, device code), OpenID Connect, or mutual TLS. Because A2A is explicitly cross-organisational, treat every remote agent's output as untrusted input — the Guardrails rules and the indirect prompt-injection threat model apply with full force to artifacts that come back from an agent you do not control.

💳
Adjacent standard: AP2

The same ecosystem has produced the Agent Payments Protocol (AP2) for agent-initiated payments — worth knowing by name, since "how would an agent actually transact?" is an increasingly common system-design follow-up. A2A is also GA in Microsoft Copilot Studio, Azure AI Foundry and Amazon Bedrock AgentCore, so it is no longer a single-vendor bet.

5 · A2UI — Agent-to-UI (the human boundary)

A2UI is an open, Apache-2.0 project from Google — released 15 December 2025 — that lets an agent render a real interface instead of a wall of text. The current stable line is v0.9.x, with v1.0 in release candidate. Its design slogan is the clearest summary of what it is: "safe like data, but expressive like code."

5.1 The problem

Two bad options preceded it. Option one: keep everything conversational, and make the user type out a date, a seat preference and a currency in prose — slow and error-prone. Option two: let the model generate executable front-end code and drop it into an iframe — which means shipping model output as code (an injection and exfiltration surface), and a UI that looks nothing like the rest of your app.

A2UI takes a third path. The agent emits declarative JSON describing a component tree and its data. The client holds a catalog of pre-approved components and renders them with its own native widgets. The agent can only ask for components that already exist and are already trusted — so there is no arbitrary code execution, and the result inherits the host app's styling automatically.

5.2 The wire format

Four server-to-client message types, each a top-level key, every message carrying a version:

MessagePurpose
createSurfaceOpen a new UI surface; names the component catalogId and optional theme
updateComponentsAdd or replace component definitions on that surface
updateDataModelSet a value at a JSON Pointer path in the surface's data model
deleteSurfaceTear the surface down
A2UI · agent → client
{ "version": "v0.9.1",
  "createSurface": {
    "surfaceId": "user_profile_card",
    "catalogId": "https://a2ui.org/specification/v0_9_1/catalogs/basic/catalog.json",
    "theme": { "primaryColor": "#00BFFF" }
  } }

{ "version": "v0.9.1",
  "updateComponents": {
    "surfaceId": "user_profile_card",
    "components": [
      { "id": "root",       "component": "Column",
        "children": ["user_name", "user_title"] },
      { "id": "user_name",  "component": "Text",
        "text": { "path": "/user/name" } },
      { "id": "user_title", "component": "Text", "text": "Software Engineer" }
    ]
  } }

{ "version": "v0.9.1",
  "updateDataModel": {
    "surfaceId": "user_profile_card",
    "path": "/user/name",
    "value": "Jane Doe"
  } }

Three design decisions in there are worth naming, because they explain why the format looks the way it does:

  • A flat adjacency list, not a nested tree. Components are a flat array; parents reference children by id, and exactly one component has "id": "root". The client assembles the tree. This is deliberately LLM-friendly — a model can stream components one at a time and revise a single node without regenerating the whole document.
  • Structure and data are separate. A property is either a literal ("text": "Software Engineer") or a binding to a JSON Pointer ("text": {"path": "/user/name"}). So refreshing a value is one small updateDataModel, not a re-render. Relative paths resolve inside a collection scope, which is how list templates work: a List whose children is {"path": "/employees", "componentId": "employee_card_template"} instantiates the template per item.
  • Incremental by default. Each message is processed independently, so the UI builds progressively as the agent thinks — the same reason streaming text feels better than waiting.

5.3 Coming back the other way

Interactivity is declared, too. A component's action is either an event (send it to the agent) or a functionCall (handle it locally, e.g. openUrl). Inputs write straight into the local data model as the user types; only a triggered action goes over the wire:

A2UI · declared action, then client → agent
// declared on the button
{ "component": "Button", "text": "Submit",
  "action": { "event": { "name": "submit_form",
                         "context": { "email": { "path": "/formData/email" } } } } }

// what the client sends when it is pressed
{ "action": {
    "name": "submit_form",
    "surfaceId": "contact_form_1",
    "sourceComponentId": "submit_button",
    "timestamp": "2026-07-28T15:17:00Z",
    "context": { "formId": "contact_form_1", "isNewsletterSubscribed": true }
  } }

Client-side checks (required, email, …) with their own messages mean basic validation happens before the agent is ever bothered — cheaper and faster than a round trip to an LLM to be told an email address is malformed.

5.4 Renderers and transport

Client renderers exist for Lit / Web Components, Flutter (via the GenUI SDK) and Angular, with React, Jetpack Compose and SwiftUI on the roadmap. Collaborators include AG-UI / CopilotKit, Opal and Gemini Enterprise.

A2UI is transport-agnostic — it needs only reliable ordered delivery and a place for metadata, so it rides on top of A2A, MCP, SSE or WebSocket. That is the key architectural fact: A2UI does not compete with the other two, it travels inside them.

⚖️
A2UI vs MCP Apps — a real interview question

Both put UI in front of an agent, differently. MCP Apps (an official MCP extension) serves server-rendered HTML in a sandboxed iframe — maximum expressive freedom, isolated, but visually foreign to the host and opaque to the orchestrating model. A2UI sends component blueprints that render with the host's own widgets, so they inherit styling and stay legible as structured data — which also means an orchestrator agent can understand what a sub-agent put on screen. Sandbox-and-isolate versus declare-and-render-natively; pick per how much you need visual consistency and model-readable UI.

🚫
"Is A2A a replacement for MCP?" — no, and saying yes is the trap

They sit at different boundaries and are routinely used together. The clean framing: MCP is how an agent uses a thing; A2A is how an agent talks to someone. A tool has a known signature and returns a value. A peer agent has goals, may take a long time, may need to ask you a question, and reasons on its own. Modelling a peer agent as an MCP tool loses the task lifecycle, the interrupted states and the streaming/webhook story; modelling a database as an A2A agent adds pointless ceremony.

7 · All three in one request

Concretely — a travel assistant booking a trip:

StepProtocolWhat happens
1—User: "Book me something in Pune for the sales offsite next month."
2MCPThe agent reads the offsite dates and the travel policy from internal systems via MCP tools/resources.
3A2ADetails are ambiguous, so it fetches the hotel partner's Agent Card, checks the search-availability skill, and SendMessages a task. That agent belongs to another company — it is a black box.
4A2AThe task streams TaskStatusUpdateEvents, then returns three options as artifacts.
5A2UIRather than describing three hotels in prose, the agent sends createSurface + updateComponents — a card list with a real date picker and a Book button, rendered in the app's own components.
6A2UIThe user picks one. The client sends an action with the selection in context.
7A2AThe agent confirms the booking as a new task; the partner agent transitions to AUTH_REQUIRED, the agent supplies OAuth credentials, and the task completes.
8MCPThe confirmation is written back to the internal expense system through an MCP tool.
🧩
Note what did not happen

No custom adapter for the hotel partner. No bespoke UI endpoint. No generated front-end code. Each boundary was crossed with a standard, which is the whole return on learning them: the integration cost of the next partner, tool and surface is near zero.

8 · Choosing — and when to skip all of this

✅

Reach for MCP when…

The same tool or data source must serve several agents or hosts, or you want a governed, audited capability layer instead of tools re-implemented per app.

✅

Reach for A2A when…

You must cross a boundary you do not control — another vendor, another team's framework, another company — or work is long-running and needs a real task lifecycle.

✅

Reach for A2UI when…

The interaction genuinely needs a widget (dates, choices, forms, comparisons), and you want it rendered in your own components rather than as model-generated code.

🛑

Skip them when…

One app, a handful of in-process tools, a chat surface, one team. Direct function calling is simpler and faster. Protocols pay off at a boundary — if you have no boundary, they are pure overhead.

🧭
The honest engineering answer

Adopt in the order the pain arrives: MCP almost always first (the tool boundary is the one you hit fastest), A2A when a second organisation or a genuinely long-running delegation appears, A2UI when text-only interaction is measurably costing you completion rate. Adopting all three up front for a single-team chatbot is resume-driven architecture.

9 · Top mistakes engineers make

  • Treating A2A as "MCP for agents." The task lifecycle — especially INPUT_REQUIRED and AUTH_REQUIRED — is the substance of A2A. A tool call has no equivalent.
  • Wrapping a peer agent as an MCP tool to avoid learning A2A. It works for a demo, then you discover you have nowhere to put "the other agent is 40% done" or "it needs a clarification."
  • Trusting A2A artifacts. Output from an agent you do not control is untrusted input. Indirect prompt injection arrives this way. Apply guardrails to inbound artifacts, not just to user messages.
  • Skipping Agent Card verification. Cards can be signed; if you delegate real work or spend real money, verify the signature and pin the counterparty.
  • Quoting the old MCP handshake. As of the 2026-07-28 revision there is no initialize handshake and no Mcp-Session-Id — describing them as current is a dated-knowledge signal in an interview.
  • Re-sending whole A2UI surfaces on every change. That is what updateDataModel and the path bindings are for; full re-renders throw away the format's main advantage.
  • Letting an agent invent A2UI components. The catalog is the security boundary. A component that is not in it must not render — silently ignoring unknown components is correct, quietly falling back to raw HTML is not.
  • Holding a connection open for hours. If a task is genuinely long, use A2A push notifications (webhooks) rather than streaming, and make the webhook handler idempotent.
  • Assuming these replace orchestration. They are transport and contract. Planning, retries, state machines and human-in-the-loop still live in your LangGraph-style orchestration layer.

10 · Interview preparation

🎤
Q · "What's the difference between MCP and A2A?"

"Different boundaries. MCP standardises how an agent uses capabilities — tools, resources, prompts — over JSON-RPC, where the counterparty is transparent and I can see the schemas. A2A standardises how an agent delegates to another agent, which is a black box, possibly at another company. The tell is the unit of work: MCP's is a tool call, A2A's is a Task with a lifecycle, artifacts, and interrupted states for when the remote agent needs input or auth. They compose — an A2A remote agent typically uses MCP internally."

🎤
Q · "Why not just have the model generate the UI as code?"

"Two reasons, security and consistency. Generated code is executable model output — an injection and exfiltration surface, and if you sandbox it in an iframe it looks nothing like the rest of the product. A2UI keeps the payload declarative: the agent names components from a catalog the client already trusts, and the client renders them with its own widgets. Safe like data, expressive like code. It also stays machine-readable, so an orchestrating agent can tell what's on screen — which generated HTML in an iframe cannot."

🎤
Q · "How would you handle an agent task that takes two hours?"

"A2A models it directly. SendMessage returns a Task rather than a value, so I'd register a push-notification config — a webhook — instead of holding a streaming connection open, and make the handler idempotent because webhooks retry. The client can also GetTask to poll, and CancelTask if the user backs out. If the remote agent needs something mid-flight it moves the task to INPUT_REQUIRED and I resume it, rather than the whole thing failing."

🎤
Q · "What changed in MCP recently?"

"The 2026-07-28 revision made it stateless at the protocol layer — the initialize handshake and Mcp-Session-Id header are gone, with client metadata in _meta per request. That's an operations win: no sticky routing or shared session store, so any instance serves any request. It also formalised Extensions with reverse-DNS IDs, shipped MCP Apps and Tasks as official extensions, hardened authorization, and deprecated Roots, Sampling and Logging under a 12-month policy. Tools, resources and prompts didn't change."

🎤
Q · "Would you adopt all three?"

"Only where there's a boundary to justify it. MCP first — the tool boundary shows up in every project and a governed capability layer pays for itself. A2A once a second organisation or a long-running delegation appears; before that its ceremony buys nothing. A2UI when I can show text-only interaction is costing completion rate. For a single-team chatbot with five in-process tools, direct function calling is the right answer and I'd say so."

11 · Knowledge check

1 · Which boundary does A2A standardise?
A2A is the peer boundary. MCP handles tools and data; A2UI handles the user interface. A2A's counterparty is deliberately opaque — you see declared skills, not the other agent's implementation.
2 · An A2A task needs a clarification from the caller half-way through. What happens?
INPUT_REQUIRED and AUTH_REQUIRED are modelled interrupted states. Making "I need to ask you something" a first-class, resumable event — rather than a failure — is a core reason A2A is a protocol and not just a webhook convention.
3 · Why is A2UI declarative JSON rather than generated front-end code?
"Safe like data, but expressive like code." The catalog is the security boundary: the agent can only request components the client already trusts, which removes the code-execution surface and keeps the UI visually consistent. It also stays machine-readable for an orchestrating agent.
4 · In A2UI, a displayed value changes. What do you send?
Structure and data are separate. Because the component bound its property with {"path": "/…"}, a single small updateDataModel refreshes it — no re-render. Re-sending whole surfaces discards the format's main efficiency.
5 · Where does an A2A client find out what a remote agent can do?
tools/list is MCP. A2A discovery is the Agent Card at a well-known path per RFC 8615. It can be cryptographically signed, and an authenticated Extended Agent Card can reveal extra skills to logged-in callers.
6 · Which statement about the MCP 2026-07-28 revision is correct?
Statelessness is the headline change, and it is an operational one: no sticky routing or shared session store for horizontal deployments. Client metadata moved into _meta per request. Tools, resources and prompts are unchanged; Roots, Sampling and Logging are deprecated under a new 12-month policy.
